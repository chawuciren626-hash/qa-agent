# 测试点设计 Skill

路径基准：`docs/`、`schemas/`、`scripts/`、`config/` 按工程动作目录返回的 `runtime_context.engine_root` 解析。正式产物在本次 run 的 `design/` 下。

## 输入

| 来源 | 用途 | 必需 |
|---|---|---|
| `analysis/requirement-ledger.json` | 规则台账：编号、分类、范围、状态 | 是 |
| `analysis/requirement_analysis.md` | 规则正文与原文引用 | 是 |
| `analysis/api_contract.json` | 接口清单与接口规则（接口轨） | 有接口轨时 |
| 派发单 | 本次 run、范围、条数上限、是否限定功能或接口链路 | 是 |
| 系统地图 / 既有接口契约 | 锚点核对依据 | 挂锚点时 |

台账读不到或损坏，直接报缺口交回队长，不凭分析正文猜规则编号。

**性能/安全测试不在当前范围**：不设计压测、并发、漏洞、渗透类测试点；
原文有这类要求就在范围说明里标"当前能力范围外"，不占正式测试点，也不阻塞其余设计。

## 输出

| 文件 | 性质 | 说明 |
|---|---|---|
| `design/test_points.json` | 必交，事实源 | 下游用例与脑图都从它生成 |
| `design/test_points.xmind` | 必交 | 从 JSON 导出，不手画不手改 |
| `design/test_points.md` | 可选 | 阅读版；不作为交接前置，不为补它重派 |
| `design/test_points-task.json` | 单点任务必交 | 全流程模式不要交 |

## 任务形态（按派发单选，不按自己习惯）

| | 全流程（lifecycle） | 单点任务（task） |
|---|---|---|
| 依据 | 台账 + 分析正文，接口轨加接口契约 | 派发单给的材料 |
| `rule_ids` | 必填，必须在台账里存在 | 可选；没有台账就不编 |
| 覆盖判定 | 按五分类，`missing` 必须清零 | 不适用；按派发范围自我检查 |
| 自检诊断 | 必做 | 不做 |
| 额外产物 | 无 | `design/test_points-task.json` |

单点任务的结果文件三个字段必填：`outcome` 取 `completed` 或 `partial`（没做完就写 partial）、`summary` 一句话说清交付了什么、`source_paths` 列出实际用到的材料路径（不能空，也不能填没用过的文件）。

## 条数上限

派发单或用户给了用例/测试点条数上限时：

1. 测试点总数不得超过上限。
2. 测试点与用例至少一一对应，所以超限说明设计粒度太细，先合并同一规则、同一场景下的字段变体。
3. 不留超限条目让用例角色删减，也不用一对多关联或复制用例来规避。

## 产物格式（强制）

### 顶层结构

两种写法都接受，任选一种，不要同时出现两个候选数组：

```json
[ { "id": "TP-001", "...": "..." } ]
```

```json
{ "run_id": "run-xxx", "title": "登录", "points": [ { "id": "TP-001" } ] }
```

用封装对象时 `run_id` 必须与本次 run 一致；数组键只认 `points` 或 `test_points`。

### 单条字段

| 字段 | 必填 | 取值 | 说明 |
|---|---|---|---|
| `id` | 是 | 唯一，`TP-001` 起顺序编号 | 不复用、不跳号补位 |
| `module` | 是 | 业务模块名 | 脑图第一层，按业务分，不按测试类型分 |
| `feature` | 是 | 业务场景名 | 脑图第二层；同模块同场景合并成一组 |
| `description` | 是 | 一句话：验什么 + 预期是什么 | 不写操作步骤，不写编号 |
| `risk` | 是 | `高` / `中` / `低` | 只接受这三个值 |
| `coverage_type` | 是 | 字符串数组 | 取值见下 |
| `source` | 是 | 本 run 内相对路径 | 如 `analysis/requirement_analysis.md`；不写 `R1`、不写 URL |
| `rule_ids` | 是 | 非空、去重的规则编号数组 | 必须在台账里真实存在 |
| `end` | 否 | `web` / `web_admin` / `app` / `miniprogram` / `desktop` / `api` / `""` | 空串=未指定 |
| `execution_layer` | 否 | `ui` / `api` | 功能点=ui，接口点=api；不写 both |
| `operation_id` | 否 | 接口契约里的 operation | 接口锚点专用 |

`coverage_type` 用这套词，可多选：`主流程`、`正常场景`、`异常场景`、`负面验证`、`边界场景`、`权限`、`兼容性`、`依赖`。

### 硬约束

1. 必填字段缺一个、`risk` 越界、`rule_ids` 为空或重复，整份被拒。
2. `source` 必须是本 run 内真实存在的文件；指向其他 run 或工作区根会被拒绝。
3. 不自造字段记录设计方法、锚点类型、缺口原因——方法写进 `design/` 附加说明或 md，缺口写进描述前缀。
4. 暂不可测的条目在 `description` 开头写 `【暂不可测】`，后接缺哪种锚点；条目保留，不删除。
5. 未确认规则的测试点保留在清单里并标注，同时说明它不计入必测覆盖。

### 示例

```json
{
  "id": "TP-004",
  "module": "登录",
  "feature": "登录失败-空凭据",
  "description": "账号或密码为空直接提交，按无效凭据处理，登录失败且不进入系统；原文未规定提示文案，不将措辞作为验收依据。",
  "risk": "中",
  "coverage_type": ["边界场景"],
  "source": "analysis/requirement_analysis.md",
  "rule_ids": ["RULE-2"],
  "end": "web",
  "execution_layer": "ui"
}
```

### 脑图结构

- 中心主题：被测功能或产品名，如「登录功能」
- 第一层：业务模块（`module`）
- 第二层：业务场景（`feature`）
- 第三层及以后：测试点（`description`）
- 叶子节点不显示 `TP-` 编号；风险、覆盖类型、来源不进节点，留在 JSON 和 md
- 导出后不手改；校验会逐项比对 `module` / `feature` / `description`，对不上就改 JSON 重新导出

### 阅读版表头

固定八列：编号 | 模块 | 场景 | 描述 | 风险等级 | 覆盖类型 | 来源 | 规则编号。一个测试点一行，内容与 JSON 完全一致。

## 覆盖判定

诊断把台账规则分五类，按类决定要不要出测试点：

| 类别 | 含义 | 怎么处理 |
|---|---|---|
| required | 范围内未驳回的需求 + 已确认假设，排除背景与环境前提 | 必须每条都有一个以上测试点，缺一条就是没做完 |
| supporting | `category=context`（背景/架构说明）或 `environment`（运行准备前提） | 只作背景，不作预期依据，不硬凑业务测试点 |
| optional | 尚未确认的假设 | 可出草稿，写明未确认；不算进必测覆盖 |
| excluded | 实现观察、范围外、已驳回 | 不能作为预期依据 |
| missing | required 里还没被覆盖的子集 | 必须清零才能交付，否则补测点或交回队长 |

补充三条：

- 范围内兼容性、运行环境的功能验收约束属于 `functional` / `constraint`，不能拿背景分类豁免。
- 性能、安全类已在分析阶段标 `out_of_scope` 的，不生成测试点，保留引用即可。
- 分类混合或自相矛盾时交回需求角色，不自己改台账、不改原材料来消掉报错。

## 设计方法

按需求形态选方法，不要求每条需求套全部方法：

| 需求形态 | 方法 | 应得到的测试点 |
|---|---|---|
| 输入范围、格式 | 等价类 + 边界值 | 有效/无效分区，空值、上下边界、单位与金额最小单位 |
| 多条件组合 | 决策表 | 每个可行组合一条；不能把 AND 改成 OR，也不能漏掉全不满足的分支 |
| 状态或历史影响结果 | 状态迁移 | 合法迁移、禁止迁移、失败后状态保持 |
| 完整用户流程 | 场景 + 异常分支 | 关键检查点，不只看最后跳转 |
| 表单、列表、弹窗、开关 | 控件场景 | 必填、格式、长度、禁用态、默认值、空数据态 |
| 业务权限 | 角色矩阵 | 无权限时不可见、不可操作、不可越权调用 |
| 接口契约 | 契约驱动 | 正向、负向（错误码/错误体）、边界、认证与越权、依赖与幂等 |
| 材料不全或新界面 | 有边界的探索 | 只产出观察与疑问，不升级成业务预期 |

接口轨的测试点保留 `operation_id`、`source` 和 `execution_layer=api`；设计阶段不发真实业务请求，不依据实测改预期。

### 功能轨与接口轨分流

- 派发单指明只做功能或只做接口时，只设计那一条链路的测试点，另一条由关联子流程处理。
- 逐条标 `execution_layer`：功能 `ui`、接口 `api`。不写 `both`，也不把同一条目复制成两套。
- 标题和交接里标明「功能」或「接口」。
- 不跨关联 run 拼接资料；来源只取本 run 内的文件。

## 锚点与端标签

锚点三选一，必须真实存在：

| 类型 | 权威来源 | 落位方式 |
|---|---|---|
| 页面锚点 | 系统地图页面清单的路由/页面标识 | 写进 `source` 或描述 |
| 接口锚点 | 系统地图接口清单或接口契约的 operation | 写进 `operation_id` |
| 代码锚点 | 被测代码的文件路径 + 符号 | 写进描述 |

规则：

- 只有 verified 的命中算有效锚点；命中 candidate 记「待晋升」，未命中记「暂不可测」，两者都不能算已覆盖。
- 系统地图缺失或明显过期时，整批标 `【暂不可测】` 并注明「地图缺失/新鲜度不足」，不猜路由。
- 同一 run 完全没有系统地图时，全部标暂不可测，交接里明说「本 run 无系统地图」。
- `end` 与来源规则的适用端一致；来源未说明就留空串，不按实现细节推断。

## 工作步骤

1. 读派发单，确定 run、范围、条数上限、是否限定功能或接口链路。
2. 读台账与分析正文；接口轨读接口契约。
3. 按模块列功能点，逐条规则展开场景，补异常、边界、权限；同一规则下的字段变体合并。
4. 保存草稿：
   - 条目少（一次能写完）直接写完整 JSON。
   - 条目多按批保存：先查当前草稿指纹拿到 `sha256` 和已有条目数，再按批提交，每批 1–20 条完整条目，`request_id` 每批固定且唯一，`base_sha256` 用上次返回值（首批发 `missing`）。
   - 只提交要改的 ID，其他条目原样不动；冲突先查回待改条目再合并，禁止整份重写。
   - 已有归档设计可 seed 初始化缺失草稿，但仍按本次台账重新核对引用。
5. 自检诊断：只传 `run_id`。看 `result.status` 是否为 `passed`，不看外层 `completed`。把 `errors` 与 `coverage.missing` 一次改完再重跑。
6. 导出脑图：只传 `run_id`，由 JSON 生成 XMind，不手画、不跑底层导出脚本。
7. 阶段校验 `stage=test_points`：逐项比对脑图与 JSON，失败改 JSON 重新导出，不删校验、不伪造回执。
8. 交接：覆盖规则数、仍缺的规则、暂不可测清单、未确认项。

## 自检清单

1. 每条都有非空 `rule_ids`，且能在台账里逐条对上
2. 台账 required 里的规则全部有覆盖，`missing` 为空
3. 每条只有一个检查目标，描述里没有操作步骤
4. 每条都有 `source`，且是本 run 内真实文件
5. `module` / `feature` 按业务划分，同场景已合并
6. 挂不上锚点的都标了 `【暂不可测】` 并写了缺口

## 不要做

- 不写用例、不执行、不判缺陷。
- 不把测试步骤、操作过程写成测试点。
- 不产出没有来源依据的测试点，也不用观察或实现细节当预期。
- 不改台账、不改上游分类、不替需求角色补规则。
- 不为通过校验删范围、删条目、改预期。
- 不跑临时脚本或绕过结构化动作，不手改导出的脑图。
