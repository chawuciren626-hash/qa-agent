# 测试设计方法与示例

返回[测试设计方法](../SKILL.md)。下列是方法示例，数值与业务规则不能移植为目标系统需求。

## 等价类与边界

先按不同预期行为划分有效与无效区间，再选代表值。若需求明确整数年龄18至65岁可接受，可用17、18、19、64、65、66检查边界；小数、缺失、null、空字符串要看类型与契约分别处理。不是每个UI控件都允许输入这些变体：UI无法输入的请求畸形值应另列API测试，不编造UI操作。

长度限制必须明确码点、UTF-16、字素或UTF-8字节；空白裁剪是否发生不能自行推断。用一个无效维度配其余有效数据避免错误遮蔽，但组合缺陷需另设计有依据的场景。金额使用整数最小单位验证总和，明确舍入规则来源。

## 决策表

例：来源明确“仅已登录且有编辑权限时允许修改”。

| 已登录 | 有编辑权限 | 预期 |
|---|---|---|
| 是 | 是 | 修改成功，并回查目标变化 |
| 是 | 否 | 拒绝，目标保持不变 |
| 否 | 是 | 是否可构造取决于权限模型；不能直接认定有效组合 |
| 否 | 否 | 拒绝，目标保持不变 |

先列条件、动作和可行组合，再按来源排除不可行项并记录原因。不能只生成允许的一行；不能把两条必要条件改为任选一条。风险高的组合逐一覆盖；低风险组合可有依据地合并，不用“相似”掩盖预期不同。

## 状态迁移

例：明确草稿可提交，提交后可批准，已批准不能直接删除。测试应含：草稿→提交、提交→批准、草稿直接批准被拒、已批准删除被拒且状态/数据不变。只有来源允许时才能加入撤回、重复提交等预期。

检查单状态覆盖是否漏掉迁移；按风险选择连续迁移序列，尤其权限变化、重复事件和失败回滚。每条用例独立建立初始状态，不能依赖上一条执行成功。

## 场景与探索

主流程分解为可观察检查点：输入、动作、状态变化、用户反馈、必要副作用。UI展示预期不能只用接口200替代；API数据正确也不能证明页面已正确渲染。

探索前明确问题、范围与停止条件，记录观察证据和未覆盖部分。登录/填写/点击成功不等于业务结果通过。方法应用不授权额外支付、通知、删除或跨域操作。
