# 控件与业务状态场景

返回[测试设计方法](../SKILL.md)。用于需求评审、测试点或用例设计，按本次角色输出；分析角色只识别规则与风险，不越阶段编写用例。

## 先选适用项，再确定预期

从本次材料选择实际存在的控件和业务状态。下表是候选问题，不是目标产品的默认需求。只有当前有效需求、接口契约或页面明确约束才能确定预期；实现观察单列，不反向证明实现正确。不固定用例数量，也不要求每个控件套齐全部维度。

| 对象 | 值得检查的行为差异 | 设计时容易漏掉的条件 |
|---|---|---|
| 文本、数字输入 | 空值、边界、粘贴、修改已有值、多个字段交互 | 先确认实际输入值；输入被截断时，不能把它当作超长值已提交。校验时机、空白裁剪、精度和舍入取自来源 |
| 搜索、筛选、分页 | 无结果、清空条件、组合条件、翻页后改条件 | 用已知数据区分过滤正确与偶然空结果；页码是否重置、排序是否稳定按契约判断 |
| 弹窗、抽屉、编辑表单 | 打开、确认、取消、重复打开 | 区分草稿与已保存状态；取消是否保留内容、关闭后焦点落点仅在有要求时断言 |
| 选择、日期、上传 | 未选择、修改选择、合法边界、拒绝路径 | 依赖选项、时区、文件类型/大小的口径要有来源；UI不可构造的请求畸形值不能写成UI步骤 |
| 提交与异步反馈 | 待处理、成功、业务拒绝、结果未知 | 动作完成不等于业务完成；反馈与持久状态分别核对。未知提交不能靠再次点击来确认 |

范围内兼容性按“目标环境 × 关键行为”选代表组合，不将 Web 任务自动扩成 iOS/Android/HarmonyOS。键盘、缩放、窗口变化只在要求或授权探索范围内检查；未覆盖环境如实列出。

## 业务权限与功能开关

从来源列出主体、资源归属、操作、状态和开关条件，形成可行决策组合。分别考虑允许与拒绝路径；身份、资源和数据使用授权测试对象。

- 区分入口可见、控件可操作、实际业务操作被接受三层。隐藏入口只能证明呈现行为，不能证明服务端拒绝。
- 多个授权来源之间是并集、交集还是有拒绝优先级，必须来自当前规则；不能默认部门、白名单、个人权限或开关的优先顺序。
- 权限变更前后的旧页面、已登录会话与新页面可以形成不同观察点。生效时机、是否提示、是否撤销进行中的操作按契约判断，不默认“立即生效”。
- 多身份或多资源对照先建立可辨识数据，保留允许访问的正例；不能用不存在的对象证明权限隔离。
- 接口侧验证仅在本次目标、凭据和工具支持范围内交给执行角色，不因这张清单自动开展漏洞扫描、攻击、压测或跨用户资料探测。

## 异常后的状态

从既定业务流程选择失败点，检查可观察反馈及契约要求的状态保持、补偿或后续恢复。模拟故障、只读观察与真实后端执行分开记录。没有故障注入授权或工具能力时，保留设计或未验证说明，不执行替代操作来凑覆盖。

例：材料只说“标题为空时显示请输入标题”，可设计清空标题并验证文案；不能据此增加“按钮禁用、不得写入、停留原页”三个预期。若材料另要求“拒绝保存且原记录不变”，再加入对应状态检查。
