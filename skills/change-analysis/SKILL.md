# 变更分析 Skill

路径基准：`docs/`、`config/`、`maps/` 按 `project-action.mjs catalog` 返回的 `runtime_context.engine_root` 解析；run 内产物按派发的 run 根目录解析。

## 分析纪律（强制）

- 结论必须可追溯到 diff 块：每条变更模块、风险点和测试建议注明对应文件与变更位置；不凭印象写变更判断。
- 区分事实与推断：diff 触及的文件/函数是事实；受影响的业务规则与端是推断，注明依据。推断不写成已确认结论，也不据此直接改预期。
- 候选契约更新只是建议：列出可能失效的 operation/字段与 diff 依据，交确认门禁人工评审；不直接修改接口契约、预期或任何 verified 资产。
- 测试建议供下游测试选择与测试点设计消费，不替代选择工具的预算与门禁决策，不自行冻结执行范围。

## 变更映射方法

- 按项目结构把变更文件映射到模块与端（web/web_admin/app/miniprogram/desktop/api）；跨端共享模块标注全部受影响端，不只标发起端。
- 结合系统地图与接口契约定位受影响的页面/operation；结合历史缺陷识别高风险复发区域。
- 风险分级看变更性质：共享组件、数据结构、权限与鉴权逻辑、资金/状态机相关变更优先标高风险；不只看改动行数。
- 删除与重命名和修改同样重要：被删除的页面/接口可能使既有锚点与用例失效，逐项列入候选失效清单。

## 输入与产出

输入：代码或资料 diff（unified diff 或修订对比）；可选既有系统地图、接口契约、历史缺陷与测试资产目录。

产出：`analysis/` 下的变更情报清单（Markdown，可选同名 JSON），包含四部分：变更模块（带端标签）、风险点（带依据）、测试建议（建议回归范围与优先级）、候选契约更新（仅建议，标“待人工确认”）。

## 工作步骤

1. 解析 diff，列出变更文件与变更块，保留原文位置引用。
2. 映射模块与端，标注跨端影响与共享组件。
3. 结合系统地图/接口契约定位受影响页面与接口；无地图时注明局限，不猜测。
4. 提取风险点与测试建议，逐条注明 diff 依据与推断性质。
5. 列出候选契约更新与候选失效锚点/用例，全部标“待人工确认”。
6. 保存变更情报清单，返回总控供需求分析与测试选择消费。

## 禁止事项

- 禁止直接修改契约、预期、用例或任何 verified 资产。
- 禁止无 diff 依据编造变更影响，或把推测的受影响范围写成事实。
- 禁止发起产品请求或执行测试；本 Skill 只做静态分析。
