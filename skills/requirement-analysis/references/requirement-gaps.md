## 区分需要业务决定的问题

| 缺口 | 处理方式 |
|---|---|
| 同一范围内行为有两种不同解释 | 引用相关原文，说明两种解释如何改变预期，只询问决定当前目标的关键差异 |
| 前后版本或多份材料相互矛盾 | 核对已提供的版本和适用对象；没有明确优先依据时保留冲突，不默认最新文件名或接口实现优先 |
| “及时”“正确”“体验良好”等不可直接验证表述 | 说明缺少的观察对象或判定条件；只对影响当前验收的部分澄清，不自行补响应时间或成功率阈值 |
| 账号、定位方式、测试数据等执行准备缺口 | 与业务规则分开；可由执行角色在授权范围准备的事项，不改写成业务待确认规则 |
| 清单中有、材料中没提的可选功能 | 不自动新增需求或必答题；有价值时作为非阻塞建议，否则省略 |

原文已经明确的内容直接引用。文档解析成功只证明提取成功，抽查相关表格/正文并保留提取局限；不要求用户例行复述确认全部材料。局部不确定性不阻断其他已确定且无依赖的范围，推进方式沿用当前任务策略。

## 需求影响面

在范围内关注条件、状态、角色、数据对象和输出之间的关系。权限/开关规则存在时识别条件组合；流程规则存在时识别允许与禁止的迁移。没有出现的组织、白名单、回滚机制不能因为通用清单而变成产品要求。

优先级说明关联业务影响、使用频率的已知依据、变更范围与可恢复性。未知频率标未知，不编造概率或量化分数。风险是可能发生的问题，缺陷是有证据的偏差，二者分开。

需求修订沿用既有ID与来源管理，说明哪些规则、测试点或预期可能受影响；本角色不覆盖已交付设计或已执行证据。task不补造生命周期台账，lifecycle按主Skill记录实际关联。
