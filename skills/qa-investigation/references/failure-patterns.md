# 失败分类与区分证据

返回[失败根因调查](../SKILL.md)。下表提供调查方向，不提供自动重试规则。先查本次已有证据，补充实验交总控沿有效执行入口安排。

| 现象 | 需要区分的原因 | 有用的区分证据 |
|---|---|---|
| 等待超时 | 请求未发出、依赖故障、产品未结束、定位/采样错误 | 同次动作时间、请求回执、页面状态和等待条件；超时本身不能确定是哪一类 |
| 接口成功但页面未更新 | 业务码失败、异步未完成、展示问题或观察过早 | 响应字段、契约终态、操作前后UI及采样时刻；200不是UI通过证明 |
| 拒绝提示出现但数据变化 | 产品副作用、准备数据串扰、读到其他任务结果 | 同一对象和身份的前后状态、请求关联、测试数据归属 |
| 只在部分运行失败 | 产品竞态、共享数据、环境波动或脚本不稳定 | 已有独立尝试的版本/输入差异与先后关系，不把偶发等同于环境问题 |
| 多条用例出现相似错误 | 同一依赖影响、多处独立缺陷或同一根因 | 影响对象、触发条件、证据链与已证实原因；相似文案只能产生重复候选 |

没有足够区分证据时保留needs_review，明确“已观察事实、可能解释、缺少什么证据”。重试仍失败不证明产品缺陷，重试成功也不抹去原失败。已有尝试可报告“n次中m次出现”，没有有效独立样本则不估算复现概率。

严重程度说明业务影响和可恢复性，处理优先级还考虑当前范围和时效；不根据报错措辞自动定为最高等级。缺陷草稿应让接手者找到最短已知触发路径、预期依据、实际偏差和脱敏证据，未知根因明确写未定位。

建议采用“失败位置/现象 → 有证据的原因或待核查假设 → 下一步”的表达。下一步可以是维护侧纠正脚本、业务侧确认规则或受控复测，不把技术锁、文件哈希和状态修复交给测试用户。修复建议不代表已修复，已修复不代表复测通过或关闭。
