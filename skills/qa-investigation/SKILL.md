# 失败根因调查

先查已有证据，再提出可验证假设；目标是解释失败，不是使报告变绿。简单错误可直接给出有依据的分析，不强制创建长调查日志。

遇到超时、偶发失败、页面与接口结论不一致或疑似重复缺陷时，按需读[失败分类与区分证据](references/failure-patterns.md)，不凭现象直接指定根因。

## 调查步骤

1. 读取本次有效结果、环境/构建信息、相关用例及证据。lifecycle先遵循缺陷主Skill的证据评估；task仅分析派发提供的材料，不伪造执行批次。
2. 分开记录频率（稳定复现、间歇、未复现/未知）和原因（产品、脚本、环境、数据、待确认）。稳定失败也可能是错误定位器；间歇失败也可能是产品竞态。
3. 对主要假设列支持证据、反证与区分实验。日志时间、网络响应、DOM/截图、数据前后状态应能指向同一次操作，不能拼接不同批次证明结论。
4. 优先分析已有证据。若需要真实复现，向总控返回最小实验范围、变量、数据副作用与停止条件，由现有执行入口按有效授权开展；本Skill不赋予执行权限，不自行循环重跑。
5. 记录已证实原因或保留needs_review；提供修复建议、影响范围及预防措施。修复声明不等于关闭，关闭仍须满足现有独立复测契约。

多步骤调查使用[调查记录模板](templates/investigation.md)，存放当前run的defects/investigations/，按case_id和证据批次区分文件；无批次时写“用户提供材料”，不能编造invocation_id。只在有新证据或判断变化时更新，保留原始观察引用。

## 边界

- 保留已有截图/Trace/日志，引用真实位置；调查正文只写脱敏摘要，不复制凭据、不改封存证据。
- 无法复现不表示问题不存在；预算或授权不足时交付当前证据、假设和未验证事项。
- 不改业务预期，不削弱/删除断言，不用skip或fixme将产品缺陷描述为已修复。
- 脚本问题也要有根因证据；不确定继续needs_review。最终分类使用主缺陷Skill和现有Schema允许的字段，不新增频率枚举到正式缺陷Schema。
