# 测试报告

报告不是过程流水账。读者只关心三件事：**这轮到底验了什么、还差什么、能不能放行**。
你的活是把这三个答案说得让人没法误解，而不是把执行日志搬一遍。

## 输入

| 来源 | 用途 | 缺了会怎样 |
|---|---|---|
| `execution/test_results.json` | 功能轨结果、断言、证据路径 | 本 run 没有就写"未执行"，不虚构 |
| `execution/api/test_results.json` | 接口轨结果（另一条轨） | 只读派发选中的那条轨 |
| `execution/browser-coverage.json` | 哪些设计用例没跑完、为什么 | 没有就当覆盖未核定，不写"全覆盖" |
| `quality/evidence-assessment.json` | 每个失败的可信度 | 没有就写"未评估"，不当成已确证，也不因此改判 |
| `defects/defect-records.json` | 缺陷分类、严重度、生命周期 | 没有就只报执行事实，不判缺陷 |
| `design/test_cases.json` | 设计用例总数，用来算未测 | 没有就写"覆盖未核定"，不反推分母 |
| `execution/execution-state.json` | 这批结果属于哪一次执行 | 认不清批次就停下，不混两批数字 |

以上是只读材料。**报告阶段不产生新的执行事实**：没跑过的不能补，跑挂的不能改状态。

## 输出

| 文件 | 谁写 | 说明 |
|---|---|---|
| `report/reportable-results.json` | 你 | 可交付的结果清单，报告里所有数字的唯一来源 |
| `report/issues.json` | 你 | 问题清单，没有问题就是空数组；条数与缺陷记录一致 |
| `report/test_report.md` | 你 | 正文；导出会按事实重装正式正文（你的版本留档），见下方注意事项 |
| `report/test_report.html` | 导出动作 | 用户实际拿到的东西 |
| `report/test_cases.xlsx` | 导出动作 | 内部核查用的执行版，不作为默认交付 |
| `report/report-task.json` | 你 | 任务回执：完成范围、口径、局限 |
| `report/quality-metrics.json` | 受控动作 | 质量指标，只在完整流程里生成，不手写 |

## 产物格式（强制）

### reportable-results.json

```json
{
  "run_id": "run-2026-11-22T09-08-30-388Z",
  "status": "completed",
  "cases": [
    {
      "case_id": "TC-001",
      "title": "空密码提交被拒绝",
      "status": "passed",
      "evidence_paths": ["execution/evidence/TC-001-step3.png"]
    }
  ],
  "summary": { "total": 1, "passed": 1, "failed": 0, "blocked": 0, "skipped": 0 }
}
```

硬规则，逐条都会被核：

1. `summary` 必须有 `total` / `passed` / `failed` / `blocked` / `skipped` 五个键，一个不能少。
2. `total` 等于 `cases` 的条数；四个状态计数逐项等于实际条数。
3. `status` 只有 `passed` / `failed` / `blocked` / `skipped` 四种取值。
4. `case_id` 在本文件内唯一。
5. `passed` 与 `failed` 必须有 `evidence_paths`，且路径在本 run 真实存在。
6. **`case_id`、`status`、`evidence_paths` 必须与来源结果逐字一致**（证据路径集合也要一致）。对不上的记录会被判成"来源不明确"，只能列为局限，不能当结论用。

### issues.json

顶层是**数组**。没有问题时写 `[]`，不写 `{"issues": []}` 或 `{"bugs": []}`。

每条建议字段（缺的会被显示成空，不影响通过，但影响可读性）：

| 字段 | 说明 |
|---|---|
| `defect_id` | 与缺陷记录一致，不自造新编号 |
| `title` | 具体到模块与现象 |
| `category` | `product_defect` / `script_issue` / `environment_issue` / `test_data_issue` / `needs_review` |
| `severity` | `Blocker` / `Critical` / `Major` / `Minor` / `Trivial` / `unknown` |
| `lifecycle_status` | 用缺陷记录里的真实状态，不改写 |
| `priority` | 没有人工指派就写 `unknown`，不由严重度推导 |
| `related_cases` | 关联的用例编号 |
| `evidence_refs` | 真实存在的证据路径；除待确认外不能为空 |
| `steps_to_reproduce` / `expected_result` / `actual_result` | 复现三件套 |
| `impact` / `suggestion` | 影响面与核查建议 |
| `analysis` | 根因分析，有依据才写 |

问题条数必须与缺陷记录条数对得上；只报自己判过的那部分，不许为了凑数把同一条拆成两条。

### 正文 test_report.md

交付的正式正文由导出按事实重新装配（结论摘要、未测与风险、执行事实、覆盖清单），你写的那版留档供自查。

**所以判断类内容不要只写在正文里**——写进 `issues.json` 的 `impact` / `analysis` / `suggestion`，以及回执的 `limitations` / `questions`，这些才会进交付件。

留档正文按这个顺序写：

- 从一级标题开始，**不写 YAML 头部**。
- 结论摘要 → 范围与环境 → 问题与证据 → 测试数据与清理 → 未覆盖范围与回归建议 → 残余风险。
- 必须写出 `run_id` 原文；完整流程里还要写出质量门状态的原文取值。
- **不要重复贴断言明细表**：导出会自己生成一份，重复写就出来两份。
- 标题用真实功能 / 模块名，不用 `run_id`，也不用 `test_xxx`。功能轨与接口轨要分得开。
- 模拟、导入、合成、恢复出来的结果，各种格式都要标明来源，不能混进"真实通过"。

### report-task.json

```json
{ "run_id": "run-...", "stage": "report", "outcome": "completed",
  "summary": "完成了什么", "source_paths": ["execution/test_results.json"],
  "questions": [], "limitations": [] }
```

- `outcome` 只有 `completed` / `partial`。存在未测范围、部分完成、恢复结果、来源不明确、执行受阻时，只能是 `partial`。
- `source_paths` 只列真读过的本 run 文件。
- `questions` 只留真需要人拍板的事，不放技术检查项，也不要重复索要授权。

## 统计口径

| 口径 | 算法 | 常见错写 |
|---|---|---|
| 执行率 | 已执行 / 设计用例数 | 拿断言条数当用例数 |
| 通过率 | 通过 / 已执行 | 把未执行算进分母 |
| 未测 | 设计 − 已执行 | 用"没发现失败"代替 |
| 缺陷数 | 问题清单条数 | 拿失败条数当缺陷数 |

- 断言条数、关联用例数、设计用例数是三个独立口径，不能互相换算，也不能相加。
- 一条用例有多条断言时，全部断言通过才算这条通过；部分通过单独说明，不四舍五入成通过。
- 写比例时同时写清分子、分母和计入规则。没有有效样本写"不适用"，不写 100%。
- 缺陷的**严重程度**与**生命周期状态**是两个维度，分别统计，不能相加，也不能用"已修复"代表"已关闭"。

## 证据强度怎么读

同一个"失败"，证据不同，能说的话也不同：

| 看到什么 | 能得出 | 不能得出 |
|---|---|---|
| 同一次动作里断言不通过 | 该操作的结果不符合预期 | 一定是产品缺陷（脚本、数据、环境都可能） |
| 动作之后隔几秒的独立观察不通过 | 那一刻页面没有该状态 | 动作当时的反馈也没有——可能只是采样晚了 |
| 截图、DOM 快照 | 当时页面长什么样 | 整页可见——被脱敏遮罩的区域不算看见 |
| 模拟的故障、注入的错误 | 界面在故障下的表现 | 真实服务端也会这样 |
| 框架重试后通过 | 这次跑通了 | 原来那次失败不存在，或问题已经好了 |
| 只读复查通过 | 当前状态是对的 | 之前的失败被推翻；复查不是重新执行 |
| 接口约定通过 | 接口返回符合约定 | 页面显示对了，或数据真的落库了 |

用这些材料时写"已观察到的事实 + 可能的解释 + 还缺什么"，不直接下结论。
关键区域确实被遮住、证据链断了、时间对不上的，就写清是哪一段看不见——这比给一个干净结论诚实得多。

## 结论分级

按手里证据的强度说话，不按期望说话：

| 情况 | 结论只能这样写 |
|---|---|
| 全部执行、无待确认、无高风险未决 | 本轮检查范围内未发现失败；范围外未验证 |
| 有失败且已确认为产品缺陷 | 列缺陷、现象、影响面、当前状态 |
| 存在待确认项 | "产品缺陷结论待确认"，并列关联用例 |
| 有未执行或部分执行 | 先写未测范围，再写已测结果；不给通过结论 |
| 执行受阻 | 不给通过结论；写阻塞原因与可交付部分 |
| 质量门为 blocked（完整流程） | 只能写阻塞结论 |

无论哪种情况都不出现"无风险""可以上线""测试通过""全部正常"这类绝对句。
不确定的地方写"未验证"或"未评估"，这比写一个漂亮数字有用。

## 未测与覆盖怎么算

三种东西必须分开说，混在一起就是这一行最常见的质量事故：

1. **设计了多少**（`design/test_cases.json` 条数）
2. **执行了多少**（结果文件里的真实记录）
3. **断言了多少**（断言尝试条数，可能多于用例数，也可能少于）

- 只执行了一部分时，未测清单单独成段，写清是哪几条、为什么不测。
- 覆盖百分比只在分母和关联依据都明确时给；否则描述"已覆盖什么、未覆盖什么"。
- 关联关系存在不等于整条用例执行完毕——一条用例有 5 步，只跑了 2 步仍是部分完成。
- 未测不计入通过，也不计入失败。它自成一类。

## 回归对照

只有用户明确要求初测 / 复测对照、修复验证时才做，普通报告不需要。
方法、允许的对照范围与写法见[独立回归交付](references/regression-delivery.md)。
要点先说在这里：**修复说明是输入，不是关闭证据；一条复测通过不能关掉一个缺陷。**

## 工作步骤

1. 读派发单，确认轨道（功能 / 接口）、本 run、可用来源清单。
2. 读结果与覆盖文件，确认这批结果就是本 run 封存的那批；认不清就停下问队长。
3. 读证据评估与缺陷记录，把每个失败分成"已确认缺陷 / 待确认 / 非产品问题"。
4. 写 `reportable-results.json`：逐条转写，编号、状态、证据路径与来源一致。
5. 写 `issues.json` 与正文；数字全部回填，不凭记忆写。
6. 完整流程里，等全部草稿定稿后再让受控动作生成报告指标；此后只做导出与校验，**不再改结果或缺陷**（改了指标就对不上）。
7. 导出 HTML，校验产物，写 `report-task.json`，交回执：完成内容、产物路径、真正要人定的事。

## 自检清单

- [ ] `summary` 五个键齐全，`total` 等于 `cases` 条数
- [ ] 四个状态计数逐项等于实际条数
- [ ] 每个 `case_id` 唯一，`status` 是四种合法值之一
- [ ] 每条 passed / failed 都有真实存在的 `evidence_paths`
- [ ] 编号、状态、证据路径与来源结果逐字一致
- [ ] `issues.json` 是顶层数组，没有问题时是 `[]`
- [ ] 问题条数与缺陷记录条数对得上，没有为了凑数拆分
- [ ] 正文从标题开始、含 `run_id`，没有粘贴断言明细表
- [ ] 通过率分母只有已执行用例，未测单独成段
- [ ] 有待确认项时写的是"产品缺陷结论待确认"
- [ ] 有未测 / 部分完成 / 复测结果时 `outcome=partial`

## 不要做

- 不重新执行、不模拟、不复算断言结果：报告阶段没有执行权。
- 不改 `execution/`、`defects/`、`design/` 的任何文件；数字对不上就报差异，不改事实。
- 不把待确认写成已确认，不把未执行写成通过，不把断言条数当用例数。
- 不给绝对上线结论，不用"无风险"代替"未评估"。
- 不自造编号、编号前缀、缺陷条数或历史缺陷统计；没有台账就写"未评估"。
- 不在报告里放凭据、令牌、个人敏感信息；引用证据写路径，不贴内容。
- 不为了补全报告要求用户解锁、补技术映射或批准重复操作。
