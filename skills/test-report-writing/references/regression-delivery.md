# 独立回归对照

只有当用户明确提出"修复了，帮我回归""和上一版对比"时才用。普通报告不需要这份文件，也不需要任何历史材料。

## 一句话原则

**修复说明是输入，不是关闭证据。** 开发说"已修复"，你只能写"据修复说明；本次观察结果如下"。

## 四个范围分开写

| 范围 | 含义 | 不要写成 |
|---|---|---|
| 原始复现 | 原来失败的那条，同样的输入再走一遍 | 不要换成"差不多"的输入 |
| 合法路径 | 同一功能的其他正常入口是否还通 | 不要用原 bug 路径代替 |
| 关联影响面 | 同一模块内可能被这次改动波及的行为 | 不要扩成全站回归 |
| 邻近输入 | 与失败输入相邻的边界值 | **不是所有复测的默认类别** |

用户说了"某类没覆盖"，就不能把已有检查塞进那一类充数。

## 对照怎么算成立

一条对照只有同时满足下面几条才算数，缺一条就写"无法形成有效对照"，不硬凑：

- 同一检查点：预期一致、判据一致、验证层次一致（页面还是接口）
- 独立的两轮：本轮结果单独产生，不是同一批次的重复记录
- 时间顺序成立：基线在前，本轮在后
- 证据路径真实存在
- 证据模式是真实观察；模拟、合成、旧记录未标注的都不算

同一用例编号不等于同一件事：两轮编号相同但步骤或数据变了，不能直接配对。
编号不同但能明确对应，可以配对。**配对关系由你说明理由，不靠编号猜。**

## 结论只能说到这

| 本次观察 | 能写 | 不能写 |
|---|---|---|
| 原失败点通过 | 该检查点本次观察通过 | 缺陷已修复 / 已关闭 |
| 仍然失败 | 问题仍可复现 | 修复无效（可能只修了另一处） |
| 出现新失败 | 本轮新增失败 | 一定是这次改动引起的 |
| 未覆盖该项 | 未评估 | 已修复 |

缺陷的正式关闭走缺陷治理流程，报告只提供观察，不改变缺陷状态。

## 需要对照时怎么写

在 `report/report-task.json` 里可选加一段（没有对照就不写这个字段）：

```json
{
  "regression_comparison": {
    "version": 1,
    "comparisons": [
      {
        "id": "ISSUE-001-original",
        "layer": "original",
        "baseline": { "source_path": "inputs/baseline-results.json", "case_id": "OLD-CHECK" },
        "current": { "source_path": "execution/test_results.json", "case_id": "NEW-CHECK" }
      }
    ]
  }
}
```

- `layer` 只取 `original` / `valid_path` / `impact` / `adjacent`。
- `id` 在文件内唯一；一条对照是一个观察，不是一条缺陷，多条对照不能相加当缺陷数。
- 来源文件必须真实存在于本 run，同时写进 `source_paths`。
- 对应关系说不清时，`comparisons` 留空，在 `limitations` 里写"未评估对照"，照常交付。

## 不要做

- 不编造执行时间、指纹、证据路径来凑成可比。
- 不把导入的历史结果说成自己这轮执行的。
- 不用一条通过去覆盖原失败：原失败记录保留，通过记录并列。
- 不为做对照去要求用户补材料、补映射文件或解锁。
