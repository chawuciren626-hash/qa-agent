其他失败形态（同样处理）
  • 验证码 180 秒未答 → 超时失败，答案文件握手关闭；
  • 目标站不可达 → 失败在「拉起浏览器」步，提示先检查地址连通性；
  • 登录配置缺失且站点需登录 → 失败于登录步，提示先在环境里登记登录配置。

失败可「重新派发」，轮次号不回退：失败轮也占 round，保证「每轮覆盖」的账目可对（第 N 轮失败 ≠ 第 N 轮存在但为空）。

本原型的硬规则（落码时照此验收）
只读红线除登录表单外不提交任何业务表单；写操作按钮只登记不点击——复用 explore-authenticated.mjs 既有纪律，不新写一套。
验证码策略链图形码先走批次 1F 既有策略链：test_bypass_code → ocr（≥0.9 采纳）→ captcha_service → manual，按项目成功率排序；自动拿不下才暂停等人，180 秒超时即失败；不猜、提交最多 1+1 次（防锁号）。人工填答与脚本链走同一 answer 文件协议。
会话必建探索是 run，run 必挂会话（readTaskRuns 结构约束）；派发 = 服务端代建会话 + 下发 breadth 指令，全程可在项目视图看 Trace。
失败不冒充失败轮不写任何探索资产，四层保持上一轮状态；失败轮占 round 号；部分采到的数据随中止封存并如实标注。
知识回写只由探索产物合并服务写四层（PUT /:layer 整层覆盖），前端不写；「未探到」标注原因，不画成 0。
本地执行会话、浏览器、产物都在平台服务所在机器（安装版即本机）；部署到 VM 时链路不变、位置随服务走。

原型批次：探索派发入口（原批次 3 计划项，现为未派单缺口 1）。范围仅「环境页入口 + 确认弹窗 + 进度/验证码/完成/失败四态」；登录配置管理、假设编辑等沿用现行页面，不在本批改动。
