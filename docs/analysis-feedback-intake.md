# 用户补充需求接入

## 适用范围

本项处理需求分析待确认或已确认后，用户给出澄清答案、数值变化、范围排除等补充。仅处理第一项“补充要求进入实际需求基线”，不包含测试点批量诊断和全阶段返修预算优化。

旧缺陷：总控把补充要求写进resolve_confirmation.reason并批准旧台账，下游仍按旧规则工作。批准备注不是需求更新接口。

## 新入口

结构化动作apply_analysis_feedback，字段run_id、text。text必须与当前父会话某条用户消息逐字相同，归档不改字词、标点与换行。入口核对真实会话记录，拒绝总控捏造或重述用户确认。它不自动理解业务语义或判断用户消息是否确实包含补充，意图判断仍由总控负责。

动作持有运行锁，复用需求修订机制：保存旧分析及已存在的下游产物；新增inputs/user-feedback-*.txt并记录SHA256、原会话和消息时间；发起revision_requested、使依赖阶段旧结果失效。相同原消息重复提交幂等。已有活动阶段必须先等待实际子任务结束并登记真实结果，不能直接覆盖。

派发需求角色时，revision_context.feedback_input携带新增来源。专业角色把原文登记为user_confirmation，逐项修订有关规则、范围与待确认项；部分回答须拆分，不把其余未知一并确认。新版生成、校验、handoff之后停在用户确认节点。不执行产品测试。

## 校验边界

正式分析及测试点契约核对已登记补充的文件哈希、user_confirmation来源和至少一处规则引用，缺少时不允许交付。此检查防止补充完全遗漏，但不证明每句话均正确落实；逐项业务核对仍必要。confirmed是规则来源明确的标签，不等于整个阶段已获用户批准。

本入口不替换纯粹“同意且无修改”的approved动作，也不会通过关键词猜测确认备注自动改变用户意图。旧错误批准保留为历史，通过显式修订使旧版本失效，不删除证据。

## 归档与恢复

派发回执提供输入文件的绝对读取路径；`read_source` 使用运行内相对路径。工作台账与只读归档必须明确区分，正式分析和测试点契约核对已登记修订归档的哈希；这属于交付检测，不是文件系统写权限隔离。

工程恢复后的新派发需核对恢复事件、父会话、派发身份、归档路径与哈希，再保存受控快照。失败次数和历史归档保留，返修遵循[进展控制策略](draft-revision-budgets.md)。恢复不等于批准，新台账仍由专业角色修订、校验并交付确认。
