# 用户补充需求接入

## 适用范围

本项处理需求分析待确认或已确认后，用户给出澄清答案、数值变化、范围排除等补充。仅处理第一项“补充要求进入实际需求基线”，不包含测试点批量诊断和全阶段返修预算优化。

旧缺陷：总控把补充要求写进resolve_confirmation.reason并批准旧台账，下游仍按旧规则工作。批准备注不是需求更新接口。

## 新入口

结构化动作apply_analysis_feedback，字段run_id、text。text必须与当前父会话某条用户消息逐字相同，归档不改字词、标点与换行。入口核对真实会话记录，拒绝总控捏造或重述用户确认。它不自动理解业务语义或判断用户消息是否确实包含补充，意图判断仍由总控负责。

动作持有运行锁，复用需求修订机制：保存旧分析及已存在的下游产物；新增inputs/user-feedback-*.txt并记录SHA256、原会话和消息时间；发起revision_requested、使依赖阶段旧结果失效。相同原消息重复提交幂等。已有活动阶段必须先等待实际子任务结束并登记真实结果，不能直接覆盖。

派发需求角色时，revision_context.feedback_input携带新增来源。专业角色把原文登记为user_confirmation，逐项修订有关规则、范围与待确认项；部分回答须拆分，不把其余未知一并确认。新版生成、校验、handoff之后停在用户确认节点。不执行产品测试。

## 校验边界

正式分析及测试点契约核对已登记补充的文件哈希、user_confirmation来源和至少一处规则引用，缺少时不允许交付。此检查防止补充完全遗漏，但不证明每句话均正确落实；逐项业务核对仍必要。confirmed是规则来源明确的标签，不等于整个阶段已获用户批准。

本入口不替换纯粹“同意且无修改”的approved动作，也不会通过关键词猜测确认备注自动改变用户意图。旧错误批准保留为历史，通过显式修订使旧版本失效，不删除证据。

## 验证

新增工程测试覆盖原话匹配、CRLF原样归档、重复幂等、新派发带来源、不引用补充则校验失败、引用后通过且不自动批准。原多文档会话复验结果见下方及当前进度记录。

2026-10-12工程回归179项全部通过，临时工程副本已清理，角色同步检查为in_sync。派发回执同时提供输入文件的绝对read_file路径，避免把run下的inputs误当成会话根目录下的inputs；read_source仍使用run相对路径。

工程审查恢复后的新分析派发允许接续已归档的旧正文：核对恢复事件、父会话、新派发、归档路径及文件哈希，保存新受控快照。原派发失败次数和归档不清零；同一新派发内仍执行原有有限修改预算。台账仍需专业角色修订并重新校验，不把工程恢复视为业务批准。

真实复验发现第一份修订仍遗漏权限范围字段，并把有效期答案误写成同时解决刷新策略；其临时修复脚本错误导致交接拒绝。已保留脚本、失败输出和产物，工程侧审查后通过recover-stage恢复同一run。此记录不代表该次失败被忽略，也不代表已完成测试点或全流程验收。

后续真实返修又发现归档寻址歧义：子角色把历史台账当工作副本编辑。工程主动中止派发，单独保存误写文件，按已登记SHA256从受控生成快照恢复原归档，记录failed及恢复证据后才重新派发。未直接改写manifest或清空失败次数。派发提示已分别标明唯一工作台账绝对路径和只读归档；正式分析/测试点契约增加已登记分析修订归档哈希检查，测试覆盖归档遭修改时拒绝交付。该机制是提示与交付检测，不是文件系统写权限隔离；不能宣称已彻底阻止模型误写。

原run内审查记录：audit/feedback-repair-engineering-review.md、audit/archive-write-engineering-review.md。后者说明中断原因、误写留痕、恢复来源及哈希。修复期间一次工程调用未序列化请求，产生unbound拒绝，修正调用后登记成功；该拒绝也保留，未伪造为Agent成功。
