## 一、结论摘要

**Skill 层是健康的，问题集中在 agent 提示词层。**

skill 层体例统一（工作步骤 → 自检清单 → 不要做），frontmatter 带 `sections.criteria / knowledge / steps` 三段索引——这实际上就是"只加载本次用得到的规则"的落地，和引擎的阶段分发是同一个思路。11 个 skill 无死链、无工具名、无超长文件（最长 238 行）。

agent 层找出 11 类问题，其中 4 类会导致错误行为（P0），已全部修完。

## 二、P0：会直接导致错误行为（已修）

### 1. 命令名写进了提示词（`test_agent`）

原文：

```
- 当前状态与产物位置：`node scripts/project-action.mjs summary`
- 可用动作：`node scripts/project-action.mjs catalog`
```

两个问题叠在一起：一是违反"提示词不出现工具名"的约定；二是 `catalog` 正是之前那个 56KB 单行输出被截断、agent 转去 grep、命令被拒、整个阶段报废的源头。把最容易踩坑的命令写进提示词，等于教它去踩。

改为"当前状态、已有产物、本次能用的动作，都向引擎查"。动作怎么调由引擎在派发时告知，提示词不管。

### 2. 自相矛盾：禁止自拼 vs 强制五句模板（`test_agent`）

同一份文件里前后两段互相拆台：

- 「派活怎么派」：*不自己拼一段话、不改写、不追加业务目标*
- 「派发单（每次派活必须说清五句）」+ 一个待填模板

模型读到哪个就按哪个来。轻则把引擎给的对象重写一遍（丢掉绑定），重则自己编一份派单。

改法：**五项保留，但性质从"你要写"变成"你要核对"**。对象由引擎生成，缺项是对象不完整，报给引擎重新生成，不自己补。

### 3. 工具名密集，整篇是操作手册（`desktop_test_agent`）

今晚唯一没改的平台提示词，1286 字节里塞了 `desktop_task`、`doctor`、`snapshot`、`visual`、`anchor_ok`、`replay`、`desktop_locked`、`request_id` 八个内部名字，混在业务判断里，读起来像源码注释。

按其余平台角色（安卓/小程序/浏览器）的体例重写：只留"能定位就不靠看图""没有断言不算通过""结果未知不重放""回归要能零猜测重演"这类判断，动作名全部交还引擎。顺带补上了它原本缺的材料清单和产出表。

### 4. 数量对不上（`test_report_agent`）

任务第 5 步说"写三份"，交付清单列了四个文件。agent 会照任务写三份，然后在校验时才发现少一个回执。

## 三、P1：削弱约束力或留下缺口（已修）

### 5. 恐吓式约束，3 处

原文：*"一次被拒绝的尝试也会让本阶段无法交接"*（`test_point`、`test_case`、`automation` 各一处）

这描述的是引擎事实（被 hook 拒过的命令不豁免），但写成道德后果，效果是让 agent 遇错即停、不敢再试——反而放大问题。

改法：把后果转成动作要求——"提交前把必填项核对一遍，被拒不会自动放行，这一阶段就得重来"。同一件事，从"你别犯错"变成"你怎么做对"。

### 6. 13 份都没有"不要输出"（已补）

没有一份规定过不许输出什么。后果是模型自由发挥：写思考过程、把内部字段名念出来、结尾加一句"已完成，一切正常"。

补统一段落，三句：不写思考过程与内部字段名；不自评"已完成""一切正常"；不确定就写不确定。

### 7. 13 份都没有"做不下去怎么办"（已补）

都有"什么算合格"，但没一份说**不合格之后怎么办、能改几轮、什么时候该停**。缺这段，模型要么无限重试，要么一遇阻就交半成品。

补三条：改产物不改判定标准；同一处改两轮还不过就停下报卡点；材料缺失或上游矛盾就报缺口。

### 8. 章节命名三套并存（已统一）

`你的任务` / `任务` / `怎么干` 指的是同一件事。LLM 对结构位置敏感、对同义命名不敏感，多套命名只会让不同角色的提示词无法横向比对。

统一为：`你是 → [业务分流] → 独立任务 → 生命周期模式 → 任务 → [专题判断] → 材料在哪 → 交什么 → 什么算合格 → 边界 → 做不下去怎么办 → 不要输出`。

`test_point`、`test_case` 的章节顺序原来是"专业判断 → 怎么干"，与其余 6 份相反，已重排。

### 9. 四要素缺一条：11 份里只有 4 份写了材料清单（已补 7 份）

定的四要素是"角色、要干什么、专业能力、读哪个目录的文件"。但材料清单只有安卓、小程序、环境探查、报告四份有，其余角色靠 skill 里的输入表去找。

agent 是拿着派发单干活的，第一件事就是定位材料。补了 7 张表，每张三到四行，写明哪个文件、用来干什么、缺了怎么办。

## 四、专业判断层面的三个补齐

这三条不是格式问题，是会直接产生错误结论的测试判断缺口。

### 10. 执行方式二选一，没有判断依据（`automation_execution_agent`）

提示词说"两种执行方式，按派发单说的走，不自己选"，但没说派发单没写时怎么办。模型只能猜。

补：没写明就按逐条执行——脚本路线要求先有计划、再有预检，缺一样跑不起来。这是用"能不能跑"反推"该走哪条"，比让它自由判断可靠。

### 11. 多条用例同根因，会写成多条缺陷（`defect_analysis_agent`）

原提示词只说"一个失败用例都不能漏"，没说同根因怎么合并。按字面执行，一个接口 500 导致 8 条用例失败，就会出 8 条缺陷，缺陷计数直接失真，报告里的数字也跟着虚高。

补：同一根因记一条缺陷、关联这几条用例，不按用例条数复制。

### 12. 回归轮次没有对照要求（`test_report_agent`）

其余角色都提了回归，只有报告角色没提。回归报告的价值全在对照——上轮通过这轮挂了的、上轮挂这轮过的，这两组才是决策依据。只在材料表里加了一行提示。

## 五、未动的部分与理由

| 项 | 判断 |
|---|---|
| `default_agent` 用「一、二、三」编号式 | 保留。它是一个角色三个身份（兜底/维护/助手），不是阶段角色，套统一骨架反而别扭 |
| `test_agent` 没有 task/lifecycle 分流 | 保留。队长不分形态，它只按流程推进 |
| skill 版本号不齐（`requirement-analysis` 为 `.2`，其余 `.1`） | 未动。版本号是发布用的，等 12 份全定稿后一次性拉平更合适 |
| 骨架里「专业判断」的位置 | 未强制统一。放在"任务"后还是"形式分流"后，取决于该角色的判断密度，不影响执行 |
| 11 个 skill 的正文 | 只做了结构与引用核查，未逐字改写。它们今晚刚重写，且体例已经统一；再改一轮的收益低于风险和验证成本 |
