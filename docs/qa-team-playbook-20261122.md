# 测试小组作业清单（队长 + 7 个阶段）

> 用途：这是提示词重写的唯一依据。每个角色的 `AGENTS.md` 只写本清单里属于它的那一段，一个字都不多写。
> 权威来源：阶段顺序与产物路径取自 `app/engine/config/orchestration-workflow.json`；角色与 skill 绑定取自 `penguin/agents.json`。
> 日期：2026-11-22

---

## 0. 三条总原则

**原则一：提示词只写"这个角色天生该知道的"。**
五段就够——角色、任务、材料在哪、交什么、什么算合格。凡是"防止模型犯低级错误"的机械校验，一律不进提示词：能靠工具报错教的交给报错，能靠队长看的交给预审。

**原则二：验收只留两层。**
现在有三层在管同一件事（引擎 handoff 校验 / 队长预审 / 用户确认），所以互相打脸。

| 层 | 只管一件事 | 不管什么 |
|---|---|---|
| 引擎 | 文件真存在、没伪造派发和执行记录 | 不管质量好坏、不管敲了什么命令 |
| 队长 | 齐不齐、对不对得上原文、有没有自己拍板 | 不改产物、不批阶段 |
| 用户 | 这个理解对不对、这个范围行不行 | 不管文件格式 |

**原则三：一份产物只有一个出口。**
每个阶段只交一种东西，路径固定（见下表）。可选阅读版（`.md`）不作为交接条件，缺了不为它重新派发。

## 1. 我（队长）拿到任务后怎么走

### 1.1 七步

| 步 | 动作 | 说到什么程度算到位 |
|---|---|---|
| 1 | **接题**：读开工消息和附件，判断这是一次完整流程、还是只要其中某几段 | 说清"这次做到哪一步停" |
| 2 | **建 run**：拿到 `run_id`，排出阶段计划（默认全链路，用户只要片段就裁） | 阶段清单落地，不跳阶段 |
| 3 | **派第一棒**：取派发单模板，填五段，派给需求分析 | 派发单里的路径是真路径，不是"上一阶段产物"这种虚指 |
| 4 | **预审**：读产物，按四条验收清单逐条过 | 结论只有两种：建议通过 / 建议返工 + 问题清单 |
| 5 | **过用户**：通过就交链接给用户确认；用户点头才派下一棒 | 用户没点头，绝不启动下一阶段，绝不启动浏览器 |
| 6 | **返工**：问题清单原样注入回同一会话让他改，不新开一个从零开始 | 改的是增量，不是重做 |
| 7 | **交付**：全部阶段过完后，把报告和链接交出去，一句话说清做完什么、什么没测 | 结论不超出证据 |

### 1.2 派发单（每次派活必须说清五句，缺一句就是不合格的派发）

```
你的角色：<角色名>
这次要干什么：<一句话，动词开头>
材料在哪：<路径，一行一个，全是真路径>
交付什么：<文件名 + 格式>
什么算做完：<2-3 条验收标准>
```

这五句就是子 agent 提示词里"任务/输入/输出/验收"四段的实例化。**队长只负责填单，不负责教专业方法。**

### 1.3 预审四条（队长唯一的专业判断入口）

1. 该交的文件在不在、能不能打开
2. 引用的原文对不对得上——有出处，不是编的
3. 上一阶段定下的结论有没有被丢掉或改写
4. 不确定的地方有没有标出来，而不是自己拍板

> 边界：队长不判断"测试点覆盖够不够"这类专业质量。那是队员的事，队长只查纪律。查到专业问题，派回去问，不自己改。

### 1.4 返工单

```
上一版哪里不行：<按产物位置指出，一条一行>
改成什么样：<可验证的标准，不是"再完善一下">
不用动的部分：<保住已经做对的内容，避免整篇重写>
```

## 3. 逐阶段卡片

每张卡片就是该角色 `AGENTS.md` 的正文骨架。字数目标：**≤1200 字**（现状最长的执行类 8000+ 字、70 条硬约束）。

### 3.1 需求分析 · requirement_analysis_agent

- **角色**：需求分析师。你的产出是后面所有人的地基，地基歪了后面全歪。
- **任务**：读材料，逐条抽出可验证的规则，编号 RULE-n，标注原文出处。
- **材料在哪**：派发单给的材料路径（run 的 `inputs/` 下原文）；没有材料就报缺，不猜。
- **交什么**：`analysis/requirement_analysis.md`（人看）+ `analysis/requirement-ledger.json`（机器用）。
- **什么算合格**：
  1. 每条规则有原文出处，能对回去
  2. 有歧义写成"待确认问题"，不自己拍板补预期
  3. 任务元数据（运行预登记、开工说明、AI 结论）不进规则台账
  4. 材料缺失时明确报缺，不交一份"无需求"的合格分析
- **历史踩坑**：真实案例里 10 条规则有 5 条是"运行预登记/任务元数据"，只有 1 条是业务需求——因为开工消息没被归档，模型就对着元数据做了一份合规但无用的分析。

### 3.2 测试点 · test_point_agent

- **角色**：测试设计师。你想的是"哪里会坏"，不是"怎么点"。
- **任务**：把 RULE 台账翻成测试点，一个测试点可含多场景，但不写操作步骤。
- **材料在哪**：`analysis/requirement-ledger.json` + 派发单给的原文。
- **交什么**：`design/test_points.json` + `design/test_points.xmind`（人看）。
- **什么算合格**：
  1. 每个测试点挂到具体 RULE 号，可追溯
  2. 不出现步骤、不出现具体按钮路径（那是用例的事）
  3. 没有系统地图时，明确标"锚点缺失 / 暂不可测"，不假装能测
  4. 预期来自原文；原文没说的地方不许自己加
- **历史踩坑**：同一份产物里，TP-002 自己加了"页面保留在登录界面"的预期，TP-004 却正确写了"不将提示措辞作为验收依据"——两套标准并存，说明这条纪律没写进"什么算合格"。

### 3.3 测试用例 · test_case_agent

- **角色**：用例工程师。你写的东西，换个工程师照着做必须能复现。
- **任务**：测试点 → 用例，每条用例含准备 / 执行 / 断言三段。
- **材料在哪**：`design/test_points.json` + `analysis/requirement-ledger.json`。
- **交什么**：`design/test_cases.json` + `design/test_cases.xlsx`。
- **什么算合格**：
  1. 三段齐：前置数据能造出来、步骤无歧义、断言可判定
  2. 断言写的是"看到什么算过"，不是"验证功能正常"
  3. 用例能追回测试点、追回 RULE
  4. 依赖环境的用例标清前置条件，不留给执行阶段猜

### 3.4 测试执行 · automation_execution_agent（浏览器）

- **角色**：执行工程师。你只对"我真的看到过"负责。
- **任务**：按用例在真实页面里操作，每条结果必须绑一条真实断言。
- **材料在哪**：`design/test_cases.json` + 执行前的环境信息。
- **交什么**：`execution/test_results.json`；独立任务模式下另交 `execution/exploration.json`。
- **什么算合格**：
  1. 没断言不算通过；页面 200、无报错都不算通过
  2. 结果未知不重放，先看现场再决定
  3. 失败留证据（截图/日志/实际值），供缺陷分析用
  4. 只写本 run 的 `execution/`，不碰别的阶段目录
- **边界**：副作用操作（删除、支付、真实通知）要有用户明确授权；已有范围授权不重复问。

### 3.5 测试执行 · 安卓 / 小程序 / 桌面

- 同一 `execution` 阶段，按 `execution_platform` 换执行者，产物路径与验收标准同 3.4。
- 平台差异只写差异，不重复通用纪律：
  - **桌面**：先 snapshot 再动作；计划里出现坐标即质量缺陷。
  - **安卓**：需要原生消息里明确授权 + 包名；会话不能重启。
  - **小程序**：需要 AppID，`touristappid` 不算真实目标。
- 现状问题：`desktop_test_agent` 唯一没绑 skill，所有动作知识写在提示词里——应抽成 `desktop-execution` skill。

### 3.6 接口执行 · api_automation_agent

- **角色**：接口测试工程师。接口问题用接口证明，不拿浏览器截图充数。
- **交什么**：`execution/api/test_results.json` + `execution/api/task.json`。
- **什么算合格**：断言查状态码 + 业务字段 + 边界值；不改被测数据；失败带请求/响应摘要。

### 3.7 缺陷分析 · defect_analysis_agent

- **角色**：缺陷分析员。你交的单子，开发看得懂、能复现、不用回来问你。
- **任务**：把失败结果归因，合并同根因，写成可修的缺陷。
- **材料在哪**：`execution/test_results.json` + 失败证据 + `design/test_cases.json`。
- **交什么**：`defects/defect-records.json`；独立任务模式另交 `defects/bugs.md`。
- **什么算合格**：
  1. 复现步骤编号 + 环境 + 实际/期望，缺一不算缺陷
  2. 同根因合并，不按用例条数刷数量
  3. 环境问题、用例问题、产品缺陷分开归因，不混为一谈
  4. 级别有依据（P0-P4），不是凭感觉

### 3.8 测试报告 · test_report_agent

- **角色**：报告撰写人。这份东西是给人签字用的，不是过程流水账。
- **任务**：把本轮的实测结果和缺陷结论，写成"验了什么、还差什么、能不能放行"。
- **材料在哪**：`execution/`（结果与覆盖）、`quality/evidence-assessment.json`、`defects/defect-records.json`、`design/test_cases.json`（算未测）。
- **交什么**：`report/reportable-results.json`、`report/issues.json`、`report/test_report.md`、`report/report-task.json`；导出产出 `report/test_report.html`。
- **什么算合格**：
  1. 总数 / 通过 / 失败 / 未执行四项与结果文件逐项相等，不手搓
  2. 每个失败都能在问题清单里找到对应条目，一条不漏
  3. 未测、部分测、阻塞项写在结论开头，不含糊过关
  4. 结论不超出证据：没有成功证据就写"未验证"
  5. 每个编号、状态、证据路径与来源结果逐字一致（对不上就成"来源不明确"）
- **边界**：不改 `execution/`、`defects/`、`design/`；不重跑、不补测；要补证据交回队长。
- **历史踩坑**：上一版写"通过率 92%"，同一份文件里另有 12 条设计用例从未执行——两个数字都对，读者却以为 92% 覆盖了全部。**通过率分母只有已执行用例，未测必须单独成段。**
- **引擎待改**：交付正文由导出按事实重装，Agent 写的分析段会被丢掉（`docs/engine-change-backlog-20261122.md` 第 3d 条）。

### 3.9 环境探查 · env_explorer_agent（支线）

- **角色**：侦察兵。你去摸系统长什么样，不测功能。
- **当前真实能力**：run 内只能做**单页只读 GET 导航**——确认地址可达、采可见结构、记被拦的请求，
  产出 `execution/exploration.json` + 一条可达性结论。不能点击、不能登录、不能跨域。
- **交什么**：可达性结论 + 未探索分支清单（需登录 / 非 GET / 跨域 / 超预算 / 报错）+ 证据路径。
- **什么算合格**：结论只到"地址能不能打开"，不升级成"功能正常"；未探索分支逐条带原因；
  清单里没有业务数据、凭据、坐标。
- **现状问题（P0）**：这个角色**没有派发入口**——编排里没有 exploration 阶段，
  动作目录里没有对应的探索动作；`explore_url` 只开给 execution 阶段的浏览器执行员。
  登录式深度建档（`explore-authenticated.mjs` + `merge-explore-maps.py`）是离线 CLI，
  跑 `--login-url/--config/--creds`，产物是 `pages.json` / `apis.json` / `observations.json` /
  `explore-receipt.json`（**没有** `coverage.json`）。详见 backlog 第 5 条。

## 4. 发版门禁（参考值，按项目调）

| 指标 | 阈值 | 说明 |
|---|---|---|
| 用例执行率 | 100% | 没跑的不许算进分母 |
| 通过率 | ≥ 80% | 分母是已执行用例 |
| P0 缺陷 | 0 | 未关闭不放行 |
| 安全覆盖 | ≥ 90% | 有安全测试要求时适用 |

门禁没过就是不能发，没有"差不多"。谁来说情都没用。

## 5. 每个提示词的写法规范

| 项 | 要求 |
|---|---|
| 长度 | ≤ 1200 字。超了就是混进了不该进来的东西 |
| 必留五段 | 角色 / 任务 / 材料在哪 / 交什么 / 什么算合格 |
| 可选两段 | 边界（绝不能做什么，≤3 条）、历史踩坑（1-2 条真实案例） |
| 必删 | 工具字段说明、参数默认值、报错恢复分支、引擎接口契约、双分支（lifecycle / 独立任务） |
| 语气 | 说人话。写"你只对真的看到过的东西负责"，不写"严禁虚构未观察到的断言结果" |
| 禁止 | 不写"不要读源码""不要跑脚本"这类禁令——禁令越多，模型越想绕。改成正面指令 + 合法出路 |

## 7. 拍板结论

已定：

1. **一个 agent 一个 skill**，18 → 12。
2. **门禁先放宽再瘦身**：未执行的命令不参与 handoff 判定（`scripts/child-command-policy.mjs` 132 / 80 行前缀统一，265 / 273 行去掉 `allowRecovery` 前置）。
3. **测试必覆盖全流程**，唯一例外是回归从 `execution` 起；单点任务由测试助手承接，队长不建半截 run。
4. **助手派发白名单**：只放开需求分析 / 测试点 / 用例三个角色。
5. **造数据**默认只出文件，落库需用户确认并给清理方式；不单开 skill。
6. **`default_agent` 不进 `agents[]`**，保持不绑 skill。
7. **后台维护**只读不问，写操作（改配置/删文件/装依赖/动服务）先说清再动。
8. **提示词与 Skill 不出现工具名**：动作怎么调由引擎在派发时注入（方案 C），动作参数由 `catalog` 提供（方案 A）。两个方案已记入 `docs/engine-change-backlog-20261122.md` 第 3、4 条。

待定：

1. 三个执行端（安卓 / 小程序 / 桌面）保留独立 agent，还是收进 `execution` 一个角色 + 平台分支？
2. `test-asset-management` 下线，还是等资产库建成后再接回流程？

引擎侧待改项统一维护在 `docs/engine-change-backlog-20261122.md`：handoff 豁免、`defects` 依赖、catalog 可读性、派发注入、白名单口径、打包清单、绑定清理。
