# 需求完备性检查（L-8）

## 它修的是哪个洞

```
业务真相 ──[无度量]──> 需求项 ──[V-33 双向对账]──> 测试点 ──> 用例 ──> 执行
              ↑ 这里没有覆盖度              ↑ 这里算得很细
```

V-33 算的是「需求 → 测试点」的覆盖。平台能诚实地说「覆盖了 90% 的需求」，但这 90% 的分母只有真实业务的一部分——**缺陷逃逸主要来自没写进需求的那部分**。

这个模块按五张检查表问「这一类需求在不在」，把结构性缺口显式列出来，作为**覆盖率分母的修正项**。

## 五张检查表（零 LLM，纯程序判定）

| 检查项 | 问什么 | 判定依据 |
|---|---|---|
| 实体完整性 | 每个业务实体是否都有 CRUD 类需求 | `ledger.entities[].operations`；未声明则从「实体词 + 明确动作词」文本推断 |
| 状态流转完整性 | 有状态实体是否声明了流转、回退、非法流转 | 状态词 + 回退词（回退/撤回/作废）+ 禁止词（不允许/不得/越级） |
| 数值边界 | 金额/数量/长度/时间是否有上下界与精度 | 字段词 + 边界词（范围/上限/≥/1-40/整数…） |
| 权限矩阵 | 角色 × 操作是否有明确的允许**与禁止** | 角色词 + 禁止词。只写「谁能做」不算覆盖 |
| 异常与超时 | 每个外部依赖是否有失败路径 | 依赖词（接口/第三方/支付/回调）+ 失败词（超时/重试/降级/熔断） |

## 三个状态值，不是一个分数

| 状态 | 含义 | 进分母吗 |
|---|---|---|
| `covered` | 有证据表明这类需求存在 | 是 |
| `missing` | 有证据表明缺失（例：声明了实体但没有删除需求） | 是 |
| `unknown` | **判不了**（台账没声明、文本抽不出证据） | **否** |

`score = covered / (covered + missing)`。`unknown` 不进分母——否则「台账没写清楚」会变成分数惩罚，团队的第一反应是把台账写宽松点，等于亲手废掉这项检查。

**全部 unknown 时 `score = null`**，不是 0。0 分会让团队为一个其实不缺的需求补文档；满分会让覆盖率的谎言继续。

## 分母修正

```js
adjustCoverage({ covered: 9, total: 10 }, completeness)
// → { reported: 0.9, gaps: 3, adjusted: 0.69,
//     note: '按需求完备性检查补入 3 项结构性缺口后，分母由 10 修正为 13。修正后的数值才是对业务的有效覆盖。' }
```

不直接改 V-33 的分子分母：**两套口径各说各的会打架**。这里只给「修正后的分母」和一句可直接写进报告的话，由报告层决定怎么并列展示。

## 用法

```bash
node scripts/requirement-completeness.mjs --run-id=run-xxx
# 读 output/runs/run-xxx/analysis/requirement-ledger.json
```

## 诚实边界

| 做得到 | 做不到 |
|---|---|
| 五类结构性缺口的机械核对 | 判断「这个需求写得对不对」——那需要人 |
| 声明驱动时高置信判定 | 从自由文本里可靠抽取实体与操作（所以标 `confidence: low`） |
| 缺口清单可直接转成补文档任务 | 自动补需求（那是人的工作） |

**最重要的一条边界**：它检查的是「需求文档的结构完整性」，不是「业务真相」。真实业务里没被任何人想到的那部分，这个模块同样看不见——它只是把「文档层面能问出来的问题」问完。
