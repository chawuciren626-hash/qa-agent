# 默认独立专业任务

更新日期：2026-10-13。

## 用户体验

新任务默认独立派发，只完成用户要求的能力。只有用户明确要求全流程时，总控才选择完整生命周期；“要用例和报告”不等于要求六个阶段全部运行。不要求用户填写任务契约、工作路径、哈希或环境配置。

| 用户意图 | 默认选择 | 不再强制要求 |
| --- | --- | --- |
| 分析这段文字或Word | analysis | 结构化需求台账及逐条技术确认 |
| 梳理测试点 | test_points | 先派需求分析Agent |
| 编写测试用例 | test_cases | 先有测试点和需求台账 |
| 分析失败日志或缺陷材料 | defects | 本工程必须执行过测试 |
| 根据已有资料写报告 | report | 本工程的执行轮次、全流程度量、缺陷生命周期台账 |
| 探索这个URL | execution | 前序用例、环境JSON、完整执行计划 |
| 明确要求完整测试闭环 | lifecycle | 保留已有生命周期、证据和真实执行约束 |

多个独立任务可以按用户意图组合，互相复用当前run的已交付产物；不存在强制的前序Agent依赖。需求变动或已有产物被改动，不能把旧版本继续当成当前依据。旧run沿用保存的模式，不自动迁移历史记录。

## URL入口的实际边界

本轮实现的是单页GET导航探索：读取页面标题、表单结构、按钮、链接数量，采集截图及一条可达性检查。URL必须来自本次输入，不猜测或复用其他项目环境。阻断非GET/HEAD、跨域文档导航、WebSocket，禁用Service Worker，不点击、登录或提交。

这不是完整功能测试或登录后的业务自动化。只给URL时可先完成可用探索，业务用例可以由用例Agent依据观察生成，但预期应标明来源和不确定性，不能将观察到的实现直接当作已确认需求。网页依赖被拦截请求时可能不完整；GET也不保证服务端完全无副作用，应在用户要求的测试目标范围内使用。

以上是explore_url的边界。功能测试现新增browser_task，支持同源登录、表单交互、实际断言及保留浏览器的人工验证码接力；不自动启用全流程，不要求用户补技术配置。接力后通过resume_browser派发继续原任务，不重新开始。详见[独立交互测试](interactive-browser-tasks.md)。已有生命周期执行能力保留，但只能按用户明确要求选择。

## 工程机制

- 结构化plan_run默认workflow_mode=task、review_mode=auto，只选请求任务；显式workflow_mode=lifecycle才补齐依赖。旧命令行默认行为保留兼容，用户入口使用结构化动作。
- 每个专业Agent生成自己的任务摘要JSON：来源文件、已完成内容、局限、真正待确认问题；由系统校验和保存来源指纹。用户不需要提交或检查这些技术文件。
- 独立契约核对当前任务及实际来源、文件内容、用例与Excel/XMind一致性、报告结果与证据。不创建假的前序产物来通过校验。
- diagnose_task检查草稿；已有export_test_points、export_test_cases和export_report按保存模式选择契约；父级handoff继续验证真实子Agent返回和产物。
- explore_url只在当前独立execution派发中运行，来源参数为url和source_path。已有结果不自动重跑；超时或关闭失败保留状态，不能靠删除锁文件假装完成。
- 对话回复仅展示已完成、产物链接、确需用户决定的事项；内部诊断留在日志。任务交付完成不等于产品测试通过。
