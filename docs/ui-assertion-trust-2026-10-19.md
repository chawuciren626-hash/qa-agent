# 第3项：断言依据、输入保真与浏览器观察

日期：2026-10-19。依据合并整改计划第3项，真实Agent复验仍按用户要求暂缓。

## 已实现

1. UI断言增加readonly、editable、enabled、disabled，不通过fill尝试证明不可编辑。readonly与disabled分别判定；不支持readonly语义的控件不误记为通过。
2. hidden及count=0需要当前业务区域ready.target与ready.text。执行角色自行从页面和已有材料选取，不要求用户提交审批或就绪文件。
3. 同次负向断言前后检查区域唯一性、可见性、文字、文档和节点身份；页面跳转、区域被替换等情况使证据失效，不使用历史URL永久证明就绪。已观察到主文档HTTP错误状态时，负向断言不能记通过，即使页面上恰好有匹配的区域标题。
4. 未就绪、页面不可观察记blocked；多匹配、错误定位、不适用的控件状态记工程问题。明确要求存在的元素缺失仍可为condition_not_met，不一概归为脚本错误。failed只表示条件不匹配，不自动确认产品缺陷。
5. 回执包含verdict_reason/failure_category，观察证据保留判定与后续观察的区别。复查指纹绑定ready上下文，不能在更换业务区域后冒充同一断言复查；原失败和受阻记录保留。
6. 快照增加readonly和分项truncated标记；文本、字段、控件、按钮、链接超限会明确标注，不能把未返回的内容推断为不存在。
7. 修复大快照返回问题：browser_task结构化结果从受控命令的完整command.log解析，不再将16KB output_tail当作完整JSON。没有扩大浏览器传输上限或删除来源回执。
8. 独立执行验收接受有真实回执和受控命令证据的blocked UI断言；含此类结果的执行仍为partial，可继续交付，不新增用户技术解锁。

## 续批：原生确认框策略与部分交付

已修复此前所有原生弹框一律静默dismiss、动作回执却不说明实际处理方式的问题：

- click/press可选dialog_policy，包含type（alert/confirm/prompt）、message精确文案、action（accept/dismiss）；只有accept prompt允许prompt_text。DOM模态框仍使用普通页面操作。
- 一个策略仅处理一个匹配弹框，不使用通配规则。策略在动作真正开始前启用，前置检查未通过不会被误记为“预期弹框未出现”，也不会在准备阶段自动接受背景弹框。
- 未提供策略、类型/文案不符或额外弹框保守dismiss并留证；预期弹框未观察到、处理未确认或记录失败，不把相关UI/接口断言记通过。原条件匹配结果仍在condition_verdict中保留，最终判定单独标记。
- 不增加用户解锁、环境配置或整个worker的stopped状态。其他安全检查可继续，finish交付partial并写明未验证范围。缺陷分析仍需区分产品问题和观察限制，不能把blocked当作已确认产品缺陷。
- 每个操作的dialogs.json归档类型、策略匹配、实际动作、观察与处理完成时间；相关断言绑定此证据及哈希。会话级browser-dialogs.json记录窗口外的无归属弹框，不能把它冒充某次点击的确定结果。
- 不保存原始弹框文案、默认输入或prompt答案；prompt答案加入当前worker敏感值脱敏集合。策略需要来自已有资料或可信观察，不靠未知弹框文本猜测后重放操作。
- 原request_id继续幂等返回已存回执，不重试提交；策略不授予新的删除、支付或其他业务权限。弹框关闭仅说明处理完成，不证明保存/删除成功，仍需业务结果断言。

## 续批：预期来源、样本保真和视口快照

1. UI断言新增可选expected_basis，与设计阶段的expected/kind/source_path/quote格式一致。case_ref指向已有用例时，仅同一预期全文或精确条款可继承已有依据；不把关联了某条用例等同于其中任意业务规则都已证明。
2. 来源文件和原文引用由程序核对，记录来源哈希、origin、status及semantic_verified=false。引文可定位不证明来源权威性、语义蕴含或产品规则正确；不会产生“自动审批通过”。没有依据时保持独立探索可用，报告明确为来源未记录的条件观察。
3. 已提供但无法核实的依据只使相关断言标为expectation_basis_unverified，原条件匹配结果单独保留；不停止整个worker、不要求用户提交前置文档或技术解锁。执行角色处理引用问题；只有必要的业务歧义才询问用户。继承依据只复制明确支持的字段，避免带入设计文件中无关的自由数据。
4. fill/select、text/value断言和必要的提交前检查可用value_ref直接引用当前run的inputs用例JSON或design/test_cases.json中的test_data字符串，不与value并用。支持空串、Unicode、空格和精确边界，禁止隐式类型转换、裁剪、补齐或凭空生成。
5. 同次操作中同一来源只解析一次，记录源文件哈希、用例编号、键和四种长度单位；fill/select后额外只读观察实际值是否保留样本。输入被截短是观察结果，不自动等同产品缺陷：应按当前需求判断，不能声称已完整输入128字符，也不偷偷改成127字符继续。
6. 重读原request_id优先返回原回执，即使样本来源后来变化，也不会重新读取后填写或提交。只读复查绑定原来的依据和样本版本，原失败不被后续通过覆盖。
7. value保持精确比较；引用样本的text默认精确textContent比较。普通旧text仍采用原有空白归一规则，可显式text_mode=exact或normalized。报告显示比较方式，精确条件不因模型重新抄写字符串而变化。
8. 报告保留expectation_provenance、input_provenance、comparison；已有来源与未知来源分开说明。离线恢复只投影白名单状态和比较方式，不复制原始引文、输入样本或任意自由文本，详细依据仍在原受限回执中。
9. snapshot默认document范围；可选scope=viewport按当前视口筛选。字段、按钮、链接和控件返回visible/in_viewport，文字来自相交的文字节点，保留扫描与数量截断标记。几何相交不是遮挡检测、可点击性、业务就绪或完整无障碍树；视口外和被截断的内容不能推断为不存在。
10. 敏感样本长度不进入输入观察证明；长敏感字符串断言改为先脱敏再截断，避免仅因展示截断而漏掉已知完整敏感值。这不是第4A项的全链路安全验收，也未读取或清理真实凭据。
