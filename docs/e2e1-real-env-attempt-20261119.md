## 2. 四个环境级发现（都已复现）

### 2.1 IPv6 优先导致连接假死 40 秒

```
nslookup → 240e:974:ec00:500::3d9d:2629 (IPv6) + 61.157.38.41 (IPv4)
curl 默认           → status=000, 40.4s 超时
curl -4 强制 IPv4   → status=200, 0.21s（connect 仅 2.9ms）
```

IPv6 路由不通，但客户端优先尝试 IPv6 并一直等到超时。**curl 需要 `-4`，Chromium 靠 happy eyeballs 自动回退（实测 0.86s 打开）**。

影响：任何用 Python 标准库/requests 直连该域名的脚本都会假死 40 秒，而现象会被误判成"服务挂了"。执行层需要在 HTTP 客户端一侧强制 IPv4 或设置短 connect timeout。

### 2.2 登录环节是随机算术图片验证码——不可确定性自动化

静态解析该页面只得到 1.9KB 外壳（`<div id="app">` + 一个 bundle），**控件全部由 JS 渲染**，probe 的静态解析在此必然为空。这印证了文档中"SPA 必须走浏览器兜底"的判断。

验证码形态（连续 5 次抽样）：

| 次数 | 算式 | 答案 |
|---|---|---|
| 1 | 8 + 6 = ? | 14 |
| 2 | 6 − 0 = ? | 6 |
| 3 | 6 − 1 = ? | 5 |
| 4 | 6 × 8 = ? | 48 |
| 5 | 9 − 7 = ? | 2 |

要点：
- 是**算术题**而非字符识别，四则运算（`+ − ×` 都出现过），需要"读图 + 计算"两步；
- 每次刷新都变，`img.captcha-img` 的 src 是 `blob:`，图片由接口下发；
- **登录不可能做到零 LLM 的确定性重放**。

结论：登录必须走"**一次性建立会话 + 持久化复用**"，把验证码挡住的部分隔离在一次性的会话建立上，被测功能（生成卡密）的执行路径保持零 LLM。这一层正好是 M2b 视觉兜底的真实适用场景，但它属于**前置设施**，不进入被测功能的确定性判据。

### 2.3 密码通过 URL query 明文传输（安全问题）

实际登录请求：

```
POST /gateway-admin/v2/userlogin
    ?username=admin
    &password=Sbkj%232025        ← 仅 URL 编码，未加密
    &nonce=<用户输入的验证码>
    &captcha=<服务端下发的票据>
    &client_id=gov-gateway-backend
    &loginType=PASSWORD
```

虽然是 POST，但**凭据放在 query string 里**。后果：
- 会进入 Nginx/网关 access log、浏览器历史、代理与 CDN 日志；
- `%23` 只是 `#` 的转义，不是加密，任何能看日志的人都能还原密码；
- 与 `loginType=PASSWORD` 并存，说明系统支持多登录方式，但密码方式本身传输不安全。

这是一条独立于"生成卡密"的缺陷，建议单独立项，不要混进本轮功能测试。

### 2.4 限流提示不可行动

触发后返回：

```json
{"msg":"登录失败次数过多，请稍后尝试","code":400,"subCode":"1000005200","returnValue":null}
```

问题：
- 不区分"账号被锁"与"IP 被限流"，用户无法判断换网络是否有用；
- 不返回剩余冷却时间或解锁方式，用户只能盲试，而盲试会继续加深锁定；
- 与 §2.3 叠加后更糟：密码在日志里可见，锁定又无提示，等于把"被爆破"和"用户自己输错"变成同一种现象。

同类错误码 `1000005200` 在凭据错误时返回 `"用户名或密码错误"`，说明服务端**用同一个 code 承载多种语义**，只靠 `subMsg` 文本区分——客户端做错误分支时只能匹配中文字符串，属于脆弱设计。

## 3. 会话策略（本轮确定下来的做法）

登录带**随机算术图片验证码**（`7×2`、`6×7`、`9−7` 等，含四则运算），无法零 LLM 确定性重放。处理方式：

1. 登录**只做一次**，过程中人工/视觉过验证码；
2. 把 `storageState` 落盘（cookies + `govAdminToken` 等 localStorage）；
3. 后续所有剧本用它新建 context，**不再触碰验证码**。

这样"被测功能的执行路径"仍然是零 LLM、完全可重放的，验证码被隔离在一次性的会话建立上。为此给 `BrowserHost.new_driver` 增加了 `storage_state` 参数（接受 dict 或文件路径）。

## 4. 三个真实缺陷（都在真实系统上复现）

### 4.1 用户密码输入框明文显示

「添加系统用户」弹窗里，`用户密码` 输入框的 `type="text"`（不是 `password`），且外层 `.el-input` 没有 `show-password` 类。实测填入 `QaProbe@2026` 后，截图里**密码完整明文可见**。同屏可见即泄露，与"密码长度 8-20 位、至少三种字符"的复杂度要求形成反差：防住了弱口令，却没防住肩窥。

### 4.2 `el-select` 选中后 placeholder 被清空——基于 placeholder 的定位会瞬间失效

这是本轮踩到的最有价值的一个坑：

| 状态 | `placeholder` | `readOnly` | `input.value` | 选中文本位置 |
|---|---|---|---|---|
| 选中前 | `所属角色` | true | `""` | — |
| 选中后 | **`""`** | true | `""` | `.el-select__tags-text` |

后果有两层：① 选中前能定位到的指纹，选中后就匹配不到了；② 任何 `value_equals` 断言对 select 必然失败，因为里面那个 `input` 永远是只读搜索框。

修复（已落地）：
- `probe` 的读值改为组件感知——元素在 `.el-select` / `.ant-select` 内时，读选中标签文本；
- 剧本锚点从 `placeholder` 改为 `label`。实测 `get_by_label` 对这套 `el-form` 全部命中（`昵称`/`手机号码`/`用户名`/`用户密码`/`所属角色：` 各命中 1 个），且**选中前后都稳定**。

**这条经验的普适结论**：对组件库表单，`label` 比 `placeholder` 稳；`placeholder` 是"控件状态的一部分"，会随状态变化而消失。

### 4.3 「所属角色」下拉的选项缺少业务语义

现有选项：`普通角色 / 111 / 没有首页权限 / 客服 / test / 测试 / 开发`。其中 `111`、`test`、`测试` 明显是调试残留。一个生产管理端的权限分配，选项里混着测试数据，会让运维选错角色——而角色直接决定权限边界。
