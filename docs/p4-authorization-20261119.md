# P4 判据 3：写操作授权卡点（2026-11-19）

> 判据 3 的原文是"`confirm` 权限强制"。落到代码里就是一件事：
> **凡会改被测数据的一步，必须先有一个人批准过"这一份计划"。**
>
> 本轮把它从"对话里的一句许可"变成"一条可审计的记录 + 引擎入口上的一道闸"。

---

## 1. 为什么这件事在写库闭环之后立刻要做

上一轮在真实系统里创建了账号并注销清理（`docs/e2e1-real-env-attempt-20261119.md` §7）。
那次"允许创建"是使用方在对话里给的答复，**系统里没有任何记录**。这留下一个结构性风险：

| 现状 | 后果 |
|---|---|
| 引擎已能 click / fill / press，能对真实系统提交 | 能力已经打开 |
| 是否允许提交，取决于"操作者记得不记得先问" | 全靠自觉 |
| 一旦接上 server 派发（判据 1），写能力就变成平台自动执行 | 风险从"本地脚本"升级为"平台" |

所以顺序必须是 **判据 3 先于判据 1**。反过来做，等于先把油门接上，再装刹车。

---

## 2. 为什么它不能是 `preflight` 里的一个分支

两个闸回答不同的问题：

```
preflight      → 这个环境还值得跑吗（基线可信 → 结论可比）
authorization  → 这一步允许改数据吗（有人批准过这个副作用）
```

合成一个函数会产生一个错误推论：**基线 ok = 授权 ok**。上一轮的真实场景恰好如此——
preflight 一切正常，而"允许创建"只是一句话。

两本账也决定了两者的失败语义不同：基线 blocking 判 `invalid`（环境不可比），
未授权同样判 `invalid`（**不是 `fail`**：被测系统没坏，是这次执行不该被允许）。

---

## 3. 闸挡的四类事故

不是"防攻击"，是"防误操作"。四类恰好都是自动化最容易出的：

| # | 事故 | 机制 | 状态值 |
|---|---|---|---|
| 1 | 忘了批准就跑了 | 有写动作 + 无授权记录 → 拒绝 | `missing_approval` |
| 2 | 批的是 A，跑的是改过的 A′（多了个删除动作） | 计划指纹绑定 | `plan_mismatch` |
| 3 | 在测试环境批的，拿到预发/生产跑 | 环境 ID 绑定 | `env_mismatch` / `env_unverifiable` |
| 4 | 批的是"建一个账号"，跑成了建一百个 | 单次使用（`used_at` 落盘） | `already_used` |

另外两个出口：`expired`（有效期）、`actions_not_covered`（授权范围收窄时不覆盖）。

## 4. 三个设计取舍（都不是随手定的）

### 4.1 指纹只覆盖"副作用"，不覆盖断言

`plan_fingerprint` 递归剔除 `assert / wait / evidence / verify_gone / note`，
只留 driver、target、lineage、steps、teardown.steps。

**理由**：授权批的是"改什么"，不是"看什么"。若断言也进指纹，改一个错别字就要重新审批，
人的实际反应是**绕过授权**（写一条万能 approval），闸退化成仪式。

**代价**：删掉断言换取通过不受此闸约束。但那不改副作用，属结论质量问题，
由 `decide` 断言与 replay 一致性管。这条边界写进文档而不是藏着。

### 4.2 `teardown` 一并纳入授权范围

清理本身是写操作（点"注销"就是提交）。若要求单独批准清理，最可能的结果是：
主流程批了、清理没批 → **拒绝清理 → 残留数据留在被测系统**。

"批准创建"天然应当包含"批准把这个创建物清理掉"。

但**清理补偿是另一份计划**（`plan-bbiao-user-crud.yaml-CLEANUP`），指纹不同，
需要单独签发。这不是为难清理：若清理可以无授权执行，"删除数据"就成了绕过审批的后门。
为降低摩擦，`cleanup_residue.py --dump-plan` 能直接导出清理计划供签发。

### 4.3 缺 `env_id` 一律拒绝，不做降级

环境校验是"跨环境挪用"的唯一防线。允许"没给 env_id 就跳过校验"，
等于默认放行最危险的那条路径。宁可让调用方补一个参数。

## 5. 过程中发现并修掉的真实缺陷

### 5.1 用"写动作白名单"判断是否改数据，未知动作自动获得只读身份

初版判定是 `action in MUTATING_WEB_ACTIONS`。测试用例 `drag_and_drop` 暴露了它：
不在白名单里 → 判成只读 → **不需要授权**。

后果不是理论风险：引擎将来新增一个写动作（`upload` / `drag_and_drop`），
忘了同步那张表，这个动作就**静默绕过授权闸和清理判定**。

改为**只读白名单**：`READ_ONLY_WEB_ACTIONS = (goto, wait, extract, hover, scroll)`，
未声明即视为写。漏声明的代价只是多批一次。

`StepResult.acted`（要不要清理）也统一用同一判定——两处不一致会裂成两个洞：
引擎认为写了而授权认为没写（该清理的不清理）、或相反（写动作绕过卡点）。

### 5.2 `fill` 为什么要算写动作

看起来 `fill` 只改页面状态。但授权的粒度是**这份计划（含值）**：
如果只批 `click` 不批 `fill`，那么"填任意值 + 点提交"就改任意数据，
收窄授权范围变成自欺欺人。

所以 `fill` 计入写动作，填什么由 `plan_hash` 锁住。

### 5.3 `session` 段也纳进授权范围

登录是 `POST`。若只遍历 `steps`，"计划里全是 GET"会被判成只读——
而它实际会建会话，且"把写操作塞进 session 段"成了绕过闸的口子。

### 5.4 测试替身签名漂移

`_FakeEngine.run_plan(plan)` 不接 `authorization`，replay 改动一接触真引擎就炸。
替身签名必须跟随契约，否则测试通过不代表能跑。

## 6. 真实验证（零副作用）

用真实剧本 `plan-bbiao-user-crud.yaml` 验证，但**只验证闸的两端，不实际执行写操作**：

```
① 无授权执行：
   $ python tools_manual/run_real_plan.py tests/fixtures/real/plan-bbiao-user-crud.yaml
   AUTHORIZATION_DENIED
     · 计划含写动作 ['click', 'fill']，但未提供授权记录
     plan_hash = 685cfcaf628ff4af020bb041e0d616d6773a5db48163b3f400a6d87fdf7ccce2
     未启动浏览器，未接触被测系统。          ← 早退发生在开浏览器之前

② 人工签发：
   $ python tools_manual/issue_approval.py <plan> --env-id local.console.gov-bid.com \
       --by "human:zdxadmin" --ttl 30 --out approval-crud.json
   签发前打印：计划指纹 / 写动作 ['click','fill'] / 动作分布（step 11 写、teardown 6 写）
              / 有效期 / 单次 / 签发人
   产物：APR-20261119-135816-685cfcaf，绑定上述指纹与环境

③ 纯函数校验（不执行）：
   有授权     → approved  True
   计划被改   → plan_mismatch  False     （多一步「重置密码」）
   换环境     → env_mismatch   False     （production.gov-bid.com）
```

`issue_approval.py` 与 `run_real_plan.py` 的分工是刻意的：
**能批准的和能执行的不是同一段代码**，所以 `run_real_plan.py` 里没有 `--approve`，
只有 `--approval <文件>`。执行器只读产物，不生成。

## 7. 能力边界（必须写清，否则会产生虚假安全感）

这道闸**不校验签名**。授权记录是本地 JSON，同一用户可以伪造。

它挡的是"忘了批""批错了计划""跨环境挪用""一次批反复用"，
**挡不住有意伪造**。真正的防伪造依赖签发方身份与密钥，属服务端（P5/M1）。

执行记录里因此始终带 `trust: "asserted"`——报告层读到它，才知道这不是一条
可信的批准，只是一条"有人声明过允许"的记录。报告若把它吞掉，读者会误判。

---

## 8. 闸的位置：为什么装在引擎里而不是调用方

`authorize_plan` 在 `WebEngine.run_plan` / `ApiEngine.run_plan` 的开头调用，
**编译期校验之后、第一步之前**（`ApiEngine` 更在 `session` 之前——等登录跑完再判，
顺序已经反了）。

装在引擎而不是调用方，是因为"调用方会记得先查授权"这件事永远不成立。
闸只有装在必经之路上才算闸。

`run_real_plan.py` 里还有一次前置判定，那只为省掉"为了被拒绝而先开一个浏览器"，
不替代引擎内的闸。

## 9. 测试

新增 `tests/smoke_authorization.py`（**21 例**），覆盖：

- 分类：只读计划不卡（`not_required`）、写计划必卡、`api` 的 GET/POST 分开、
  未知动作按写处理、`session` 写动作纳入、`teardown` 写动作纳入
- 四类事故：缺授权 / 计划被改 / 换环境 / 单次复用
- 边界：过期 / 未过期 / 范围收窄 / 记录缺字段
- 语义取舍：**改断言仍 approved**（防止"改一个字就重批"导致绕过）
- 引擎入口：闸拦下时驱动零调用、IR 带 `authorization` 段与 `trust`
- 引擎放行后确实开始执行（用内存驱动验证"换个理由拒绝"不算放行）

回归：`smoke_web_engine` 37、`smoke_preflight_replay` 29、`smoke_baseline`、`smoke_probe` 全绿。
