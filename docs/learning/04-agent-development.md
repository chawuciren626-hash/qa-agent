# 4. Agent 开发工程

目标：从“会调用模型”走到“能交付可靠的软件功能”。先完成第 1-3 章。

## 4.1 Agent、工作流和多 Agent

工作流规定执行步骤，Agent 允许模型在约束范围内选择下一步。实际产品常用混合方式：授权、校验和保存是确定性流程，资料选择和章节草拟可交给模型。

多 Agent 适合职责边界清楚、输入输出明确的任务，但增加调用成本、交接错误和调试难度。先让单个受控链路可测试，再根据证据决定是否拆分；不同名字的角色不自动构成有效协作。

## 4.2 最小 Agent 循环

```text
接收任务 -> 加载授权范围与当前状态 -> 组装上下文
 -> 调用模型 -> 解析响应
 -> 若为工具请求：检查工具、参数、权限、预算，执行并保存结果
 -> 将结果反馈模型，继续下一轮
 -> 若为最终输出：校验内容、产物和完成条件，返回
```

循环必须有最大步骤、总时长、最大费用、工具重试和取消条件。工具报错后模型可能重复同一请求，需要识别相同失败，不允许无限循环。

下列是伪代码，不是可直接连接生产系统的执行器：

```python
for step in range(max_steps):
    response = model_call(build_context(state))
    if response.kind == "tool_call":
        request = validate_tool_request(response, state.permissions)
        result = execute_with_limits(request)
        state = record_result(state, request, result)
    else:
        return validate_final_output(response, state)
raise StepBudgetExceeded()
```

校验 final_output 时要确认文件存在、版本对应、内容规则通过，不得仅因模型写了“完成”就结束。

## 4.3 工具设计

工具应任务清楚、参数小而明确、输出结构稳定。例如拆分 `get_project`、`get_template`、`save_draft`、`export_document`，比提供任意 SQL 或 Shell 更容易验证。

教学工具契约：

```json
{
  "name": "save_draft",
  "input": {
    "project_id": "A",
    "template_version": "V2",
    "content_ref": "draft-content-001",
    "idempotency_key": "task-demo-001-save"
  },
  "output": {
    "status": "succeeded",
    "document_id": "doc-demo-001",
    "revision": 1
  }
}
```

身份和租户信息应来自可信会话，不能相信模型自报的 `user_id`。工具层验证项目权限、字段类型、内容大小和资源归属。输出中的业务文本依然是不可信输入，不能提升为系统规则。

MCP 是连接工具/资源的一种协议，不等于 Agent 框架，也不自动授予权限或保证工具正确。使用时要核对服务身份、工具版本、认证、传输、错误语义和调用审计。

## 4.4 状态与持久化

文档任务可使用以下状态：created、collecting、needs_input、drafting、validating、awaiting_approval、exporting、completed、failed、cancelled。

每次转换记录事件和前置条件。`completed` 要求实际产物可验证；`awaiting_approval` 不得因会话摘要丢失而自动变成 approved。

数据库保存任务状态、版本和产物引用；对象或文件存储保存文档；事件日志用于追溯。若两个操作同时修改同一任务，用版本号/乐观锁拒绝过期写入，避免后完成的旧任务覆盖新版本。

checkpoint 应在重要步骤之后保存。恢复时先核对外部操作是否已发生，不要从头重复写入。流程定义、prompt、模型、模板、知识库版本应与 checkpoint 一起记录。

## 4.5 幂等、重试与补偿

幂等表示重复执行同一逻辑请求不会额外产生副作用。文档保存可以通过 idempotency_key 去重；服务器必须绑定请求内容，同一 key 携带不同内容应拒绝或明确报冲突。

读超时可在有限预算内重试；429 可遵循 Retry-After 并退避；401/403 不应盲目重试；参数错误应先修正。指数退避加抖动可降低大量任务同时重试造成的压力。

“保存成功但响应丢失”要先查询幂等记录，再决定重试。跨系统无法整体回滚时需要补偿：例如导出失败可以保留草稿和失败状态，不应声称提交成功。

取消也不是简单关闭对话：队列任务、正在执行的工具和后续回调都需识别取消状态，避免取消后仍提交文件。

## 4.6 检索与记忆接入

检索服务负责返回有权限的版本化资料；上下文构建器负责预算与去重；记忆服务负责范围、有效性和来源。把这些职责分开，方便单独测试。

缓存 key 需要包含会影响结果的身份/权限范围、版本和请求参数。错误缓存设计可能把 A 项目的答案返回给 B。缓存命中要进入日志，性能评测区分冷缓存与热缓存。

## 4.7 服务端附带技能

| 能力 | 为什么需要 | 初学者掌握程度 |
|---|---|---|
| Python/TypeScript | 编写工具和服务 | 独立写模块、异常处理和测试 |
| Web 服务框架 | 暴露任务接口 | 请求校验、认证、中间件、错误返回 |
| 数据库 | 保存任务和版本 | 表结构、索引、事务、迁移 |
| 异步与队列 | 长任务不阻塞请求 | job_id、轮询、取消、失败队列 |
| Docker/部署 | 环境可复现 | 镜像、配置注入、持久卷、健康检查 |
| CI/CD | 变更后自动验证 | 测试、制品、发布与回滚 |
| 可观测性 | 定位时间和质量问题 | trace_id、跨度、指标、脱敏日志 |

异步不等于安全并行。读取两个独立资料可并发，同一文档的保存和导出通常有顺序依赖。数据库事务也不能覆盖任意远程模型调用。

## 4.8 观测与性能

记录每次模型/工具调用的耗时、状态、token 和版本，按 run_id 关联。无需依赖模型的隐藏思维链，观察可验证的输入输出和工具事件即可定位多数流程问题。

总耗时包含队列等待、模型生成、工具执行、重试、人工等待和导出。人机协作任务应分别报告机器活跃耗时和端到端耗时，避免把审批等待算成模型性能退化。

部署应有可回滚的 prompt/模型/工具版本；上线后按质量与性能指标监控，不能只看服务 HTTP 200 比例。

## 4.9 练习与验收

先用本地固定函数模拟模型和业务工具，实现“读取资料 -> 生成结构化草稿 -> 校验 -> 保存”的小程序。加入一次工具超时、重复请求和重启恢复，再接真实模型。

验收：相同保存请求重复两次只生成一份；缺预算停在 needs_input；无权限时工具拒绝；取消后不继续导出；日志能说明失败在哪一步。代码能解释后再选择具体 Agent 框架。
