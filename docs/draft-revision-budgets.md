# 草稿返修与进展控制

更新：2026-10-14。本页替代原“两层固定返修上限”规定。

## 当前行为

安全输入错误、只读读取错误、已确认结束的非执行草稿生成/校验错误，不再因为累计第三次失败而返回 task_paused。analysis、test_points、test_cases、defects、report 的受控返修，以及分析正文的同派发重生成，均取消固定两次上限。

- corrections 保留历史失败总数，不清零、不删除原始证据。
- correction_progress 记录同一任务的请求摘要和错误诊断；连续三次相同失败返回 stalled=true，要求改变方法或报告部分结果，不锁定会话、不要求用户解锁。
- 请求或诊断变化表示可能有进展；成功调用清除连续失败提示，但历史总数保留。这不是证明业务正确，仍需产物校验。
- revision_budget 为 {limit:null,used,remaining:null,policy:"progress_based"}；used 只作审计。
- 该策略只允许显式纠正后再次调用，不会在底层自动重放产品操作。

## 仍需遵守的边界

返修继续检查真实派发归属、子任务已结束、产物哈希、归档和当前业务决定。不得覆盖已批准/拒绝或待用户决定的内容，不得伪造子任务和执行结果。未知执行结果、超时后未确认结束、身份不匹配、凭据及范围变化不自动重试。

所有专业阶段继续接收 revision_context；原产物存入 run 内 audit/revisions。专业角色从只读归档恢复工作草稿，重新生成导出物。更换派发用于真实修订关联，不是刷新额度。新策略同时接受历史 V2 和新 V3 派发；V1 保留原始严格契约。

## 与模型限制的区别

阶段纠错次数与模型每次响应的输出长度是两回事。取消前者不会取消模型服务商的上下文和输出上限。模型只产生思考、因 length 结束时，宿主仅进行一次带简短内部提示的改变策略续接，不重放全部失败思考；再次无可用输出则明确结束并保留证据。任务级轮数、网络重连限制、取消机制仍保留，避免无限消耗。

stop hook 的重复内部提醒上限也保留，它只防止无效提醒循环，不限制正常阶段返修。用户无需提供技术解锁文档。

## 验证口径

工程测试覆盖多次纠错后成功、无进展提示、成功后连续计数清理、归档/归属边界和旧策略兼容；真实 PenguinHarness 验证单独记录，不能把合成夹具称为真实 Agent 成果。
