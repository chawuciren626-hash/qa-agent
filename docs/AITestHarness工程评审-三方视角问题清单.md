# 三方视角评审：这套 AI 测试 agent 工程还差什么

> 评审视角：agent 开发工程师 / 软件测试专家 / 当前市场下的资深 AI 测试工程师  
> 评审对象：`aitestharness-tools/`（8547 行）+ v3 方案 §1~§24  
> 评审时间：2026-11-14



---

## 判断先说

这套工程的**约束设计**在我见过的同类方案里属于少见的清醒：版本冻结、血缘、分权表、L1/L2/L3 自愈红线、"不知道要说出来"，这些是别人写在 PPT 里、这里写进代码的东西。

但它有两个结构性问题，恰好落在最难补的位置：

1. **它把"预期结果"当作输入，而预期结果恰恰是测试里最难的部分。** 全链路的校验都在验"内部是否自洽"，没有一条校验指向"外部是否真实"。
2. **它测的是下游（产品是否符合需求），没有测上游（需求是否符合业务）。** 于是它能说"我覆盖了 90% 的需求"，说不了"我的需求本身完整度是多少"——而后者才是缺陷逃逸的主因。

下面按严重度分三档，每条给证据位置和改法。

---

## 一、P0：会让系统输出"看起来正确"的错误结论

这一类比"功能没做完"危险：它不会报错，会给出一个通过的报告。

### P0-1 自洽性幻觉：预期结果全链由 LLM 生产，唯一的对账是自洽

**证据**：`case/builder.py:43` —"断言由 Advisor 从 `tp.expected` 填"；`tp.expected` 由 `test_point_agent`（LLM）产出；`plan/gates.py` 闸 4 校验的是"断言是否回指测试点"。

**问题**：链条是

```
需求文档（人写）→ LLM 抽需求项 → 程序算矩阵 → LLM 补测试点（含 expected）→ LLM 写断言
```

闸 4 保证的是「断言 ↔ 测试点」一致。但如果 LLM 在第二环就误解了业务——把「满 100 减 10」读成「满 100 打 9 折」——那么测试点、断言、用例**全部自洽，全部通过**。跑通的是一条错误预期的用例，真实缺陷被"错误的预期"掩盖了。

这是测试学的经典 **oracle problem**，但在这里更隐蔽：因为系统给它加了五道闸、贴了血缘、盖了版本戳，**通过的报告比没有报告更有说服力，也更危险**。

`requirement/testability.py` 的 T1~T4 能拦"没写预期""表述歧义"，拦不了"写错了"——后者需要外部真相，而外部真相不在系统里。

**改法（三选一，都可落地）**：

- **预期溯源到人**：`expected` 必须挂 `source: "doc:§3.2 第2段"` 或 `source: "human:张三@2026-11-14"`。无源预期标 `unverified`，用例 verdict 上限压到 `inconclusive`，不许出 pass。这条最便宜，一天能做完。
- **加"预期反向验证"抽查**：程序自动挑 5% 的 `expected`，用受控输入构造一个"故意违背预期"的变体（如把折扣金额改错），如果断言仍然通过 → 说明断言没有区分力，标 `weak_assertion`。这是**变异测试**思路，`exec` 层已有能力做。
- **双层 oracle**：把"预期"分成 `business_expectation`（人确认，卡点强制）与 `technical_expectation`（可推导，如 HTTP 200 / schema 合法）。前者不走 LLM。

> 这条不修，整套系统的"通过率"指标是不能用于发布决策的。

### P0-2 `expected` 在 agent 可写范围内：这是"改预期让用例通过"的合法通路

**证据**：`irval/ownership.py:41` `HUMAN_ONLY={"approved_by"}`；`ownership.py:58` 注释**明确写着**「`expected[].matcher` 这类属于 agent 合法字段，不做限制」。而 `EXEC_FACT` 只封了 `verdict / evidence_ref / engine_version` 等执行事实。

**问题**：通路是

```
执行 fail → agent 归因 → agent 说"预期写错了" → agent 改 expected → 重跑 → pass
```

分权表全程放行。方案的 L3 红线封的是"跳过/替换步骤"，`EXEC_FACT` 封的是"伪造环境版本"，**唯独没封 verdict 的上游**。而这条通路比伪造 `engine_version` 更自然——"预期写错了当然要改"，任何人都不会觉得可疑。

系统性后果：所有不好修的问题最终都会被归因为"预期写错"。三个月后系统通过率 95%，缺陷密度不变。

**改法**：

- `expected` 改为 **`HUMAN_ONLY` 或 `agent 可提建议但需人签`**。agent 提交 `suggest_expected_change`，进待审队列，人签了才生效。
- 若坚持 agent 可写，则必须有**改动配额与审计**：同一 `case_id` 的 `expected` 在一个版本周期内改动 ≥2 次 → 强制升级人工，并在报告里标 `expectation_drift`。
- 与 §9 资产纪律对齐：资产改动要 reason、要 diff、进历史；`expected` 改动现在**什么都不要**。这是纪律的不一致，不是设计选择。

### P0-3 粒度不匹配：`invalidate` 是阶段级，`incremental` 是用例级，两者接不上

**证据**：`plan/phases.py::invalidate(state, changed_phase, only)` 的作废单位是**阶段**（`staled` 里装的是 `"case"/"plan"/"execute"`）；`knowledge/incremental.py::incremental_plan` 的产出单位是**用例子集**（"重算 12 条、不动 1498 条"）。

**问题**：需求改了 1 条，`invalidate` 只能把整个 `case` 阶段标 stale（1500 条全失效），而 `incremental` 明确算出只有 12 条受影响。编排层此时两难：

- 按状态机走 → 1500 条全量重跑，`incremental` 白做，用户一个月内放弃；
- 按 `incremental` 走 → 手工把 `case` 阶段标回 done，绕过状态机，违反 §5.4 纪律。

两个模块单独都对，**接口语义不对**。这类缺陷比"没接线"更难发现——接线了，跑起来不报错，只是把增量优化的收益全吃掉。

**改法**：`invalidate` 增加产物子集参数：

```python
invalidate(state, "requirement", only_phases=[...],
           artifact_subset={"cases": ["c-101","c-102",...]})   # 用例级
```

状态增加第三种值 `partially_stale`（含 `stale_ids`）。报告里写"1500 条中 12 条结论基于旧版本"，而不是"全部基于旧版本"或"全部有效"。这两种极端说法都是错的。

### P0-4 单状态机不支持多模块并行，`artifacts` 会被覆盖

**证据**：`PhaseState.artifacts: dict[str, dict]` —— key 是产物 kind（`requirements`/`cases`/`plans`），**一个 kind 只存一份**。没有 project/module 维度。

**问题**：真实项目是多模块的（订单、支付、库存、会员）。模块 A 在做用例、模块 B 还在需求分析时：

- 状态机只有一个 `case` 状态位，必然串行化，B 必须等 A 走完；
- 更糟的是 `artifacts["requirements"]` 被 B **覆盖**，A 的用例血缘 `derived_from` 指向的 requirements 版本就此丢失——血缘断了，但没有任何报错。

演示单模块没问题，一上真项目就崩。而"多模块并行"不是优化项，是测试团队的基本工作方式。

**改法**：`PhaseState` 加维度

```python
PhaseState(scope="order")     # 或 artifacts 用 (module, kind) 复合键
```

外加一个 `ProjectState` 管跨模块的全局阶段（如报告汇总）。这属于**装配期改动**，越晚改越贵——现在改是加一层，等业务代码铺开再改是重构。

## 四、两个链路级的元问题（比单点缺陷更值得想）

### 元问题一：系统测的是下游，没测上游

```
业务真相（人脑里的 / 需求文档里的）──[无度量]──> 需求项 ──[有度量]──> 测试点 ──> 用例 ──> 执行
                        ↑ 这里没有覆盖度                    ↑ 这里覆盖度算得很细
```

`testpoint/coverage.py` 的 V-33 双向对账做得很扎实，但它对的是"需求 → 测试点"。**没有人对"业务真相 → 需求"这一环做对账**——`knowledge/` 里的规则条款完整度、需求文档本身的完备性（边界、异常、权限是否都写了），全靠人。

后果：系统能诚实地说"我覆盖了 90% 的需求"，但这 90% 的分母可能只有真实业务的 40%。而缺陷逃逸主要来自那 60%。

**建议**：加一个"需求完备性检查"（不需要 LLM，用启发式 + 检查表）：每个实体是否都有 CRUD 的需求？每个状态是否有流转与回退？每个金额字段是否有边界与精度？缺的那几类列出来给用户看。**这是把"未测风险"从用例级提升到需求级**——现在 `plan_regression` 能说"这 15 条用例没跑"，说不了"这类场景压根没人写需求"。

### 元问题二：AI 系统自己没有回归策略

`irval` 97 用例校验的是"IR 格式是否合法"，它验不了"LLM 生成的 40 条测试点是否真的覆盖了这个需求"。而 8 个 LLM 点的输出**天然不稳定**，这是 AI 工程的第一性问题。

现在的验收是"43 项冒烟全绿"——43 项测的是确定性模块。**LLM 参与的部分等于没有测试**。这是整个工程最大的方法论空洞，也是最容易被评审专家一句话点破的地方（"你怎么证明改了 prompt 之后没变差？"）。

**建议**：见 P1-2。补 8 个 LLM 点的 golden set，这是投产前的硬门槛，不是 nice-to-have。

## 五、如果只能修三件

按"不修会让前面所有工作贬值"排：

1. **P0-1 + P0-2 一起修**（oracle 溯源 + `expected` 收权）。这是同一件事的两面：预期从哪来、谁能改。不修，通过率不可信，五道闸、血缘、版本戳全部失去意义——它们保证的是一条可能错误的用例被正确地执行了。
2. **P0-4 多模块状态机**。现在改是加一层，业务铺开后改是重构。而且这条是"能不能上真项目"的门槛。
3. **P1-2 prompt 回归集**。这是让"AI 部分"可交付的前提。没有它，每次改提示词都是赌博，而赌博的结果不会立刻显现——会在第 5 次改动后集体爆发。

## 六、这份工程真实的价值在哪（别自己讲错）

评审的最后一件事：**它最大的价值不是"AI 自动生成测试"，是"证据链"。**

市场上号称 AI 生成测试的产品，水平其实都在同一条线上——都不太可信，而且都没法证明自己不可信在哪。这套东西能给一个别人给不了的答案：

> "这条用例为什么可信？它的预期来自文档第 3.2 节，测试点由矩阵第 47 格推导，断言回指该测试点，用到的元素在资产库有三次命中记录，执行时的引擎版本是 2.1.3 且执行期已冻结，失败归因是根因聚类第 4 组。"

**这句话是护城河。** 而现在的文档在强调"AI 覆盖七阶段""8 个 LLM 调用点"——这恰恰是最容易被复制、也最容易被质疑的部分。

建议调整叙事顺序：**先讲证据链（不可复制），再讲 AI 提效（可复制）**。这样评审专家问"AI 准不准"时，你的回答是"准不准可以查，因为我们每一条都能回溯"，而不是"我们的模型很强"。

1. 原 P0-1 暗示「错误通过率无法测量」——不准确。**种子集内可测**（缺陷是人植的，有真值），不可测的是种子集外。方案 §1.3 已改为加注「仅在种子集内可测，不得对外作 SLA 承诺」。
2. 原 P1-8 说「N=3 成本未约束」——不准确。§21 决策 34 已写入库门，**真正的问题是口径没写清适用范围**，导致两种读法都成立。已改写为「口径歧义」。

这两处修正的意义大于问题本身：**一个提意见的人如果不敢改自己的话，他的意见就只是情绪。**
