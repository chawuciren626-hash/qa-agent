# 自动推进与总控技术恢复

更新：2026-10-14。

## 用户体验

用户提供文字、文件或明确授权探索的 URL，说明所需任务即可。默认独立任务派发；只有明确要求全流程时才采用 lifecycle。总控与专业角色自行处理参数、路径和草稿技术问题。仅业务歧义、授权范围变化、需要登录/验证码等真实人工介入点向用户提问，不要求用户写审查文件或批准技术解锁。

默认 auto 按证据完成当前请求，最后简短说明完成内容、可点击产物和真正待确认问题；显式 staged 保留阶段确认。自动推进不是自动批准业务规则或扩大产品测试范围。

## 恢复分类

| 情况 | 处理 |
| --- | --- |
| 结构化 JSON、参数错误，未启动业务进程 | 保留失败回执，纠正原因后继续，无固定次数上限 |
| 只读读取错误 | 独立进展记录，不占用变更令牌、不锁住其他任务 |
| 已确认结束的非执行生成、导出、校验失败 | 原专业角色修正草稿；无固定两次上限，重复无进展应换方法 |
| 已返回的 V2/V3 子任务需要草稿返修 | preview_revision 检查归属和决定，revise_stage 归档，再派发原角色 |
| 连续三次相同请求和错误 | stalled 提示改变方法或交付部分结果；不是技术解锁门禁 |
| 产品操作结果未知、超时后未确认结束 | 先查实际状态与证据，不盲目重放 |
| 业务规则、范围、凭据确需用户决定 | 只问影响当前任务的具体问题 |

corrections 为累计审计，correction_progress 为连续无进展提示。成功清理后者、不删除前者。详见[草稿返修与进展控制](draft-revision-budgets.md)。

## 证据与权限

动作继续返回 task_key、run_id、action_receipt 和 recovery。只有被分类为可安全纠正的错误，才返回 retry_allowed=true。新派发使用 V3；历史 V2 回执仍兼容；V1 不放宽。完成登记仍须真实父子调用、返回结果、对应持久回执及未解决错误已通过后续成功动作关闭。不得以“可继续纠错”冒充“已经完成”。

分析重生成只覆盖当前派发、原字节哈希和生成快照均有效的未获批草稿；所有旧版保留在 audit/analysis-generations。阶段返修保留 audit/revisions、revision_context 和原确认约束。没有前置产物的独立任务仍按独立任务合同，不强加全流程前序节点。

历史维护 review-session 接口保留兼容用途，但普通安全输入错误不再走该入口，也不再要求用户提交哈希或审查文档。未知产品执行结果仍不能自行解锁。

## 运行时保护

父任务取消会遍历当前父会话拥有的前台、后台和嵌套子任务，包括父任务已空闲但后台子任务尚未结束的情况；取消同时拒绝待审批请求，抑制取消后的完成通知。取消传播不等于外部业务事务回滚，已执行步骤和原始证据必须保留。

模型 thinking-only length 错误使用一次紧凑、标记为 harness 的恢复提示；再次无进展结束并说明限制，不把内部提示当作用户授权，不改模型或代理，不靠无限提高输出额度重试。
