# 接口自动化测试智能体建设方案

日期：2026-10-21。状态：方案阶段，尚未新增角色、执行接口请求或更改已安装宿主。

## 1. 建设结论

新增独立角色 `api_automation_agent` 和阶段 `api_execution`，与现有 `automation_execution_agent` / `execution` 并列。保留旧执行阶段 ID 和文件路径，不迁移历史任务。总控根据用户任务选择 UI、API 或两者；默认独立任务，用户明确要求全流程时才走完整链路。

接口文档驱动的完整测试顺序明确为：**获取接口文档 → 解析接口契约与业务规则 → 设计接口测试点 → 生成接口测试用例 → 执行接口测试 → 缺陷分析 → 输出报告**。测试用例及预期必须先于执行形成；执行后补充实际结果和证据，不能根据实测响应倒推预期或事后补造用例。

本次新增的是接口执行专业角色，不是包办分析、设计和报告的第二个总控。复用现有需求分析、测试点、用例、缺陷及报告角色并扩展接口能力；总控负责自动衔接。这些是职责边界，不是要求用户逐节点审批的门槛。

模型负责理解资料、选择场景、解释结果；确定性执行器负责 HTTP 请求、断言、凭据边界、证据和状态。复用现有 Node、Playwright、Ajv、目录隔离及交付能力，不另建模型接入，也不将接口测试绑定到浏览器启动。

首要目标不是增加检查门槛，而是让用户可以提供接口资料或地址后直接开展任务。只有缺少关键业务预期、必要身份认证、超出授权的写操作等情况才询问用户。

## 4. 用户体验与流程

### 独立任务，作为默认使用方式

例如：“根据这个Swagger地址测试订单接口，生成用例和报告。”

总控识别任务的目标和已有输入，补齐达成目标所需的设计工作，而不是一律直接交给接口执行角色：

- 接口文档加完整测试要求：总控依次协调分析、测试点、用例、API执行、缺陷及报告角色，自动完成阶段衔接。
- 已有接口用例加执行要求：直接派发API执行角色，复用现有用例，不为补齐流程而重做需求分析和测试点。
- 只要测试点或用例：派发对应设计角色，所需资料解析作为该任务内部动作，不发业务测试请求。
- 直接接口URL加探索测试要求：先识别方法、范围和已有契约，形成轻量测试点与可执行用例再执行；观察事实与已确认预期分开，不将探索响应自动当作业务标准。
- 已有执行结果加缺陷分析或报告要求：直接派发相应角色，检查证据是否足够，不强制重跑接口测试。

独立任务意味着可按输入和目标直接调用专业能力，不意味着省略必要的测试设计。没有历史前置节点记录不应阻塞；已有资料足够时直接复用，不够时由总控协调补齐，仅关键业务歧义才询问用户。

提供的是接口文档URL时读取文档；提供的是完整端点时按已知方法与上下文处理；只有服务根地址且无法识别端点时，询问文档入口或目标功能，不猜测批量路径、不扫描整个站点。用户无需提前制作环境JSON。

只提供Word或文字也可先设计；缺少可执行地址或认证时交付已完成设计并说明所需信息，不把整个会话永久置为技术阻塞。

### 明确全流程时，两类执行并列

```text
需求/接口文档 -> 需求分析与契约解析 -> 测试点 -> 测试用例
                         |
              +----------+-----------+
              |                      |
       UI执行 execution       API执行 api_execution
              |                      |
              +----------+-----------+
                         |
              当前已选分支结果汇总
                         |
                    缺陷分析 -> 报告
```

“结果汇总”是内部确定性动作，不新增必须由用户确认的节点或额外Agent。

API-only的完整链路仍包括接口解析、测试点、用例、执行、缺陷和报告；UI/API并行发生在执行层，不是将接口测试点或用例设计挪到执行之后。两分支分别消费适用的用例；某分支就绪且无资源冲突时可先执行，不因另一分支的无关设计工作而等待。

- UI-only/API-only只选所需分支；未选分支不是等待条件，也不计入未执行用例。
- 两分支前置条件满足且数据无冲突时同时运行。涉及同一资源或一个分支依赖另一分支创建的数据时，只对冲突操作串行，其他工作继续。
- 用户已明确授权同环境同范围测试，不逐请求再审批。新增风险、范围或身份权限时才询问。
- 用户明确要求逐阶段确认时保留该模式；默认只询问真实业务或人工事项。
- 一条分支失败/部分完成，另一条继续；最终报告注明实际结果。不会要求失败分支先变成“成功”才能汇总。
- 登录待人工操作不是完成。保留原任务、认证上下文与已执行记录；确认后续接，不重新派发或重跑。用户不处理等待时可要求先出部分报告。
- 总控只回复完成内容、主要结论、可点击交付物，以及确实需要用户处理的事项；子任务派发和答复使用中文。

## 5. 角色、Skill及工具

| 对象 | 设计 |
| --- | --- |
| 新角色 | `api_automation_agent`，接口自动化测试工程师；消费已形成的接口用例，准备请求、执行断言、采集证据与续接，不替代设计和报告角色 |
| 新阶段 | `api_execution`，全流程与现有 `execution` 同级 |
| 已有共用Skill | `api-testing`：设计、断言与证据原则；保留UI角色所需的受限api_check指导 |
| 新Skill | `api-contract-analysis`：主要由需求分析角色使用，识别资料、解析契约、说明不确定预期、生成接口清单；独立设计任务可复用解析能力 |
| 新Skill | `api-test-execution`：认证、场景编排、关联、断言、数据隔离、运行与恢复 |
| 总控 | 选择测试渠道、派发、记录已确认范围、收集结果；不亲自编写业务结果 |
| 需求分析角色 | 解析接口文档、契约、认证和业务规则，识别范围与真正待确认问题，保留来源 |
| 测试点角色 | 基于接口规则设计正向、负向、边界、认证、业务关联等覆盖点，输出结构化测试点与XMind |
| 用例角色 | 将测试点转成接口用例，明确参数、前置条件、认证引用、依赖、预期断言与清理要求；标记UI/API适用层，保留case_id及来源；执行前输出结构化用例与Excel，不默认重复生成相同设计 |
| 缺陷/报告角色 | 接收多来源结果，区分UI、API、环境、工程及证据不足，统一交付 |

结构化工具建议为 `api_task`，内部提供 `inspect_contract`、`prepare`、`start`、`status`、`resume`、`cancel`、`collect` 等动作。名称在实施批次1锁定，不把每种HTTP动词都做成新的Agent。

模型提交受约束的请求/场景描述，执行器使用已安装的Playwright `APIRequestContext`发起HTTP请求，无需启动浏览器。先构建可重复执行的声明式场景；可读脚本导出作为后续能力，不以每次临时生成任意代码作为运行前提。工具动作不是新增人工确认节点；`inspect_contract`可供分析/设计角色复用，执行角色的`prepare`只做运行准备与用例适配，不擅自补造或改变业务预期。

## 6. 首版能力与边界

### 首版必须具备

1. 输入：文字、既有Word提取结果、直接接口URL及OpenAPI/Swagger文档；优先支持OpenAPI 2.0/3.0 JSON和YAML。使用成熟解析器，部署时安装，不在任务中下载。
2. 解析：method/path、path/query/header/body、必填/类型/枚举/边界、响应与security。按选中operation分批处理并缓存来源哈希；不将整份大文档反复送给模型。
3. `$ref`：本地引用处理、循环引用保护；远程引用不自动越域抓取；支持版本之外的Schema明确标记未支持，不静默丢弃规则。3.1方言及复杂组合的完整支持单独验收，不伪称等价JSON Schema。
4. HTTP：GET/HEAD/OPTIONS及获授权的POST/PUT/PATCH/DELETE；path/query、JSON与表单；JSON、文本、空响应/204、二进制元数据与大小限制。multipart和大文件作为后续扩展。
5. 认证：Bearer、API Key、Basic、Cookie及明确配置的登录接口；使用任务级密钥引用，不把密钥写进场景、Excel、日志或报告。不自动读取其他会话的凭据。
6. 关联：从响应提取ID/token到当前场景变量，显式步骤依赖、前后置条件、创建后查询验证；不使用eval执行表达式或导入文档中的脚本。
7. 断言：HTTP状态、业务码、字段、类型、Schema、必填、边界、错误响应、分页；业务状态校验只基于可观察证据。约定未明确时不臆造应返回400/422。
8. 调度：有界并发、速率和超时限制；依赖链串行，无依赖场景可并行。时间上限用于运行保护，不是固定模型token预算。
9. 证据：逐请求、逐断言、逐用例落盘，含耗时、脱敏请求响应、来源、关联和错误分类；中断后仍可输出部分结果，不等全部结束才写文件。
10. 设计与交付：执行前形成接口测试点JSON/XMind、接口测试用例JSON/Excel，并保留需求/契约到测试点、用例的关联；执行后补充实际结果、缺陷、证据与独立或合并报告HTML/Word/PDF。未执行内容不计通过，接口调用次数不充当用例数。

### 首版不作为默认能力

GraphQL/gRPC/WebSocket、压测、自动安全攻击、批量生产清理、任意SQL查库、通用OAuth/MFA自动化、任意JS签名脚本、完整Postman脚本执行、自愈修改业务预期。Postman/cURL导入后续只解析数据，绝不执行导入的Shell或脚本。企业签名/加密通过受审查的扩展点增加，不写死某个项目。

## 7. 真并行与故障隔离

这是本轮高风险改动，先有回归基座再接真实产品。

- 将全流程“任意阶段活跃就拒绝派发”改为依赖就绪与冲突判断，不放开同阶段重复派发。
- 更新 `plan_run`、`extend_plan`及live_product路由，不能仍自动强制选择UI `execution`。新计划保存选中执行分支和契约快照；旧计划不自动增加API分支。
- 新分支使用独立dispatch、任务句柄、回执、产物命名空间；分别绑定 `run_id/stage/dispatch_id/attempt_id/request_id`。
- 长HTTP执行交给可取消worker；总控会话锁只承担短的登记/提交，不在持有全局状态锁时等待网络。保留文件原子提交和版本冲突检测，禁止两分支覆盖manifest。
- 故障作用域细化到分支/操作：API局部故障不停止UI；未知副作用冻结该资源相关写操作，而不是无条件放行其他分支。旧无作用域故障继续保守处理，不猜测历史执行结果。
- 请求同ID重取回执不重新发送；同ID但请求内容变化拒绝。超时不代表服务端未执行，写请求结果未知不自动重试。只在协议和业务明确支持时使用幂等键。
- 取消父任务传播到两子任务和worker；取消不是清理成功。报告记录已完成、未执行和结果未知；进程存活/终止不确定时不重复启动。
- 汇总只读取当前分支当前版本。全部已选分支终结后出正式报告；任一等待/运行中时，可按用户要求出标明快照时点的部分报告。失败、取消、缺证据仍可收集为限制，不伪造完成合同。
- 用时间戳证明UI/API执行区间存在重叠，同时证明两个正常分支各派发一次、没有重复业务写入。仅看到两个子Agent名称不算并行验收。

## 8. 安全与数据隔离

- URL范围来自当前输入及明确引用的API服务，文档域与API域可以不同但需有来源，不因跨域就强制所有任务转浏览器。
- 出站请求限制到本任务目标；校验重定向每一跳，跨域不转发认证；凭据不发往文档提供的任意外站。企业内网和用户明确本机目标可用，云元数据和无关服务不能任意访问。
- GET也可能有副作用；请求方法不是唯一风险判定。生产环境、通知、支付、权限变更、批量删除不从“测一下”推导授权。
- 每条场景使用独立标识及本次创建资源台账；UI/API默认不用同一可变记录。共享账号或全局配置会造成冲突时串行并说明原因。
- 清理仅针对本任务可证明归属且获授权的数据；清理失败单独报告，不删除既有记录，也不为“清理”重放未知写入。
- 登录过期复用现有人工卡片机制；API上下文可持久化安全引用，不能用“浏览器仍在”作为纯API续接的必要条件。
- 响应解析失败、连接/TLS/DNS故障、断言失败、资料冲突分别分类；Schema不匹配不能不经分析就断言后端代码有bug。

## 9. 产物与报告模型

推荐保持当前UI路径不动，API使用独立子目录：

```text
<当前会话>/output/runs/<run_id>/
  inputs/                         原始资料及来源快照
  analysis/api_contract.json      分析角色产出的规范化接口契约和来源
  design/test_points.json         共用测试点，标记UI/API适用层及来源
  design/test_points.xmind        测试点阶段交付
  design/test_cases.json           已有共用设计，按执行层选取
  design/test_cases.xlsx          用例阶段交付，接口用例也在执行前形成
  execution/test_results.json      既有UI结果，不覆盖
  execution/api/
    contract.json                 本次执行使用的契约快照，引用分析来源
    cases.json                    用例适配后的可执行场景，保留设计引用
    test_results.json              API结果
    task.json                     本分支交付摘要
    evidence/                     脱敏逐请求及断言回执
    data-ledger.json               本次资源归属和清理记录
  quality/execution-summary.json  多分支只读派生汇总
  defects/                        统一缺陷分析
  report/                         当前报告格式与可点击交付
```

该目录是方案，不预创建。以统一目录上下文解析，不能硬编码`E:\Codex`或安装目录。

设计文件由对应设计角色负责，执行角色不覆盖原始预期；执行结果通过case_id关联设计版本，最终可导出带实际结果的用例Excel。独立执行任务允许引用用户已有用例及契约，不强制创建缺失的历史阶段记录；上面的目录布局不构成所有任务必备文件清单。

结果标识至少包含执行层、源case_id、scenario_id和attempt，避免UI/API相同case_id碰撞。原始业务用例数、实际执行场景数、请求数、断言数分别统计；重跑次数不增加业务用例总数。契约覆盖以选中的method+path集合为分母，排除或不支持项显式列出，不声称全面覆盖。

汇总保留源文件哈希、来源分支及未测原因，不改写源结果；同一业务问题可在缺陷阶段关联多条证据，但不因合并而丢掉原始失败。API成功不能证明页面成功，UI成功不能证明全部接口契约正确。

## 10. 分批实施顺序

预估为8至12个有效工作日的规划量级，不是完成承诺。企业认证、宿主兼容及基线回归问题会影响时间；每批以可验证交付为准，避免只完成提示词就进入长流程。

| 批次 | 工作 | 完成标准 |
| --- | --- | --- |
| 1. 角色与设计链路 | 注册API角色/阶段，扩展分析、测试点及用例角色的接口能力；明确Skill归属、执行层、产物及错误Schema；同步工具与写入边界，建立旧运行样本 | 文档可经分析、测试点、用例角色产出关联的契约、测试点JSON/XMind及用例JSON/Excel；已有用例可直接路由API执行入口而不强制补历史节点；UI与历史交付回归不受影响；未实现的执行能力不宣称可用 |
| 2. 独立HTTP闭环 | Playwright请求worker、认证引用、参数/响应处理、用例到声明式场景适配、增量证据；接通设计后执行链路 | 分别验证文档驱动的设计后执行、已有用例直接执行；在合成API上真实完成查询和获授权CRUD，脱离浏览器；执行前已有用例和预期，超时不重复写入，缺资料不假造预期 |
| 3. 并行与续接 | 生命周期依赖、短锁/worker、分支故障隔离、取消传播、人工认证续接、资源冲突 | UI/API实际重叠执行；一支失败另一支继续；取消与登录恢复不重复派发或请求 |
| 4. 汇总与交付 | 已有用例关联实际结果、多源缺陷和报告、统计口径、来源合同、点击链接 | API-only、UI-only、双分支和部分失败均可交付Word/PDF；执行前设计交付与执行后结果一致可追溯，没有未选节点阻塞和结果覆盖 |
| 5. 真实Agent验收与部署 | 合成故障矩阵、宿主真实派发、经授权业务样本、角色/工具同步、打包白名单、文档 | 工程侧自主完成验收，记录失败与耗时；干净安装所需依赖纳入产品发布，不在任务中临时安装 |

批次1同时建立批次3所需的集成测试，但先让独立接口任务可运行，再开放并行全流程，减少一次改动全部节点的风险。每批结束给出简短结果和剩余问题，不要求用户提交技术复核材料。

## 11. 验收矩阵

至少覆盖以下情形，并区分工程合成、真实Agent、实际产品以及客户端打开证据：

1. 已有接口用例可直接执行，不建浏览器，不强制补需求/测试点节点；只要测试点或用例时不发业务测试请求。
2. 文档驱动完整任务依次完成契约解析、测试点、用例、执行、缺陷和报告；参数、响应及认证有来源，执行前已有测试点与用例版本；未支持Schema及缺失预期明确可见，不跳过后报全通过，不要求用户逐节点技术解锁。
3. CRUD关联正确，负向/边界/204/文本/非JSON错误都能判定；HTTP 200业务失败不误报通过。
4. 文档与实测冲突保留原预期；真实失败不自动改断言或skip。
5. UI/API各一次派发且实际执行重叠；共享资源冲突时有局部串行证据。
6. 一分支故障，另一分支正常交付；合并报告显示失败、未执行和结果未知。
7. API写操作响应丢失后不重放；重复请求ID读取旧回执；重启/worker退出不捏造正常结束。
8. 登录等待保留原任务；确认续接无重复登录/写请求；取消传播到两分支。
9. 旧会话、旧dispatch、旧确认或另一分支结果不污染本次交付；重复handoff不增加完成事件。
10. 凭据、Cookie、签名、敏感响应不出现在公开文件；跨域重定向不泄露认证。
11. Excel和报告事实一致，可点击访问；文件结构、原生打开和版式分别记录，不以HTTP 200替代打开验收。
12. 相同小样本记录模型往返、工具调用、阶段墙钟时间、请求耗时和成功交付率，建立优化基线，不预先承诺提速倍数。

## 12. 建议下一步

先实施批次1，打通接口文档到测试点、接口用例的设计链路并明确各角色职责；再实施批次2，使接口执行角色消费这些用例或用户已有用例，形成无浏览器依赖的HTTP执行闭环；随后打通并行执行、多源缺陷和统一报告。首轮采用本地合成接口验证工程，不需要用户先准备业务环境；真实业务认证与允许写入范围在业务验收前确认一次即可。

本轮只整理并修订本方案文档，已纳入“先解析与设计，再执行，最后缺陷与报告”的流程要求；不改现有宿主、运行计划、会话、凭据及其他未提交的产品整合工作，不安装参考项目依赖，不进行Git提交或推送。
