# 部分成功通道（L-7 落地说明）

> 对应方案：§25.2 P1-1、§25.5 落地项 L-7。
> 代码：`scripts/partial-submit.mjs`。测试：`tests/acceptance/partial-submit.test.mjs`（10 条）。

## 1. 问题：把「完整性」当成了「原子性」

40 条需求抽到 38 条 → 整批阻塞 → 重试仍卡在那 2 条 → **为了 2 条，38 条一起等着**。

这不是严格，这是把两件事混成了一件：

| 概念 | 含义 | 该怎么处理 |
|---|---|---|
| **完整性** | 这批内容该有的都该有 | 缺了要记账、要表态 |
| **原子性** | 要么全成、要么全不成 | 只适用于「中途失败会留下半截状态」的场景 |

需求抽到 38 条并不会留下半截状态——那 38 条各自是完整的。所以这里该用完整性，不该用原子性。

## 2. 决策：一条 `partial` 通道

```json
{ "accept": true, "partial": true, "missing_ids": ["REQ-0039", "REQ-0040"], "coverage": 0.95 }
```

缺的进「待人工补」队列，其余照常进下一阶段。**阻塞的应该是那 2 条，不是整批。**

## 3. 四种判定

| 情况 | 判定 | 为什么 |
|---|---|---|
| 一条不缺 | `accepted` | 与旧行为一致 |
| 缺一部分，采到的都合规、覆盖率 ≥ 门槛 | `partial` | 值得往下走，但要记账 |
| **采到但不合规** | `blocked` | **这是「错」不是「缺」**：错要重做，缺才排队等补 |
| 缺的是范围声明本身 | `blocked` | 范围没定，部分放行会让下游拿半张图去设计 |
| 覆盖率 < 门槛（默认 80%） | `blocked` | 半张图不足以支撑下游设计 |
| 一条都没采到 | `blocked` | 那不叫部分成功 |

## 4. 三条守住的底线

1. **门槛不能关。** `minCoverage` 必须在 `(0, 1]`，传 `0` 会抛错——不提供「放行空集合」的设置。一条能关掉的闸，等于没有闸。
2. **「错」与「缺」必须分开。** 采到的条目 `validId()` 不通过时整批 `blocked`，不进待补队列。把错当成缺，会让人去「补录」一条本该重做的内容。
3. **下游必须知道这批不完整。** `downstreamNote()` 明确写出 `38/40`，并禁止下游表述为「已覆盖全部」。部分成功如果在上游被允许、下游被忘掉，报告里就会出现一句「已覆盖全部需求」。

## 5. 待补队列

```js
toBacklog(result, { stage: 'analysis' })
// [{ id: 'REQ-0040', stage: 'analysis', kind: 'awaiting_human_completion', reason: null, detected_at: '...' }]
```

`reason: null` 是刻意的：**「为什么缺」只有人知道**，代码在这里编一个理由（比如「源文档未包含」）就是在制造一个看起来可信的假解释。

## 6. 边界

- **不替代 schema 校验。** `validId` 只回答「这条算不算采到」，字段级校验仍由 `artifact-contracts.mjs` 负责。
- **不自动重试。** 待补队列是给人用的，不是给机器重试用的——同一份输入重试 40 次还是那 38 条。
- **没有接进 CLI。** 现在是一个可被调用的判定模块；接进具体阶段（比如 `analysis` 提交时）要改那条命令的参数与输出，属于后续批次。
