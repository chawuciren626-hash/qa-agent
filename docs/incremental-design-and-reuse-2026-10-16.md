更新日期：2026-10-16。本页对应最新六项整改的第4项，不涉及模型调整、界面样式或产品环境执行。

## 解决的问题

此前大批量设计依赖整段JSON写入和文本匹配修改，局部错误容易演变为全量重写；搬运已有用例仍让模型重新抄录。新入口负责机械保存、版本检查和字节复制，Agent继续负责需求理解、覆盖和预期判断，不新增人工技术审批。

## 分批保存

`draft_records`由当前设计子任务调用，支持test_points和test_cases。仍兼容原有文件工具，不强制迁移历史产物。

1. `operation.type=inspect`返回当前sha256、条目数和ID；可用ids读取最多20条待改记录，不返回全部长JSON。
2. `upsert`每批提交1至20条完整条目，以测试点id或用例case_id新增/替换，保留其他条目、顺序和已有外层包装。数量限制是单次传输粒度，不是阶段预算，不缩减总测试范围。
3. `base_sha256`引用当前版本，缺失文件使用missing。冲突时读取待改ID并合并，不覆盖别人或上一批的成果。
4. `request_id`标识同一批次。相同请求重放不重复新增；同ID不同内容拒绝。回执区分批次哈希与当前文件哈希，后续已有新批次时不回滚。
5. 保存使用现有原子JSON替换函数，保留前一版字节及批次审计。写入成功但回执未完成时，可由当前文件哈希识别已落盘批次；不能根据没有回执推定失败并重写全部。

保存成功不代表用例完整、业务依据正确、阶段完成或通过测试。全部批次结束后仍按原task/lifecycle契约诊断、导出并校验，不每批导出或增加人工确认。接口不提供删除条目或自动缩减覆盖功能。

### 请求示例

```json
{
  "action": "draft_records",
  "run_id": "run-example",
  "stage": "test_cases",
  "operation": {"type": "inspect", "ids": ["TC-001"]}
}
```

upsert需要request_id、base_sha256、entries。entries是完整的业务条目，不是仅有case_id的合格用例；具体必填字段继续使用既有Schema。可选samples为`[{"case_id":"TC-001","key":"name","unit":"a","count":51}]`，程序写入本批次对应条目的test_data并返回实际码点、UTF-16、UTF-8字节和字素长度。仅支持单码点重复样例，不能将测量口径冒充产品规则。

## 资产复用

优先在原run修订，不为绕过失败建立新run。确需复用时：

- 总控使用reuse_design，指定source_run_id、stage和name；只读取同一父会话、当前工作区中已交付且哈希一致的测试点/用例JSON。
- 程序原字节复制到目标run的inputs，并保存来源run、路径及哈希。不读取任意绝对路径、不扫描其他会话、不复制环境、脚本、凭据、执行记录或批准状态。
- 子任务派发前导入，避免任务执行中改变输入；同名不同内容不覆盖。
- 新设计可使用`operation:{"type":"seed","request_id":"seed-1","base_sha256":"missing","source_path":"inputs/reused.json"}`初始化缺失草稿。外层run_id适配当前任务，原输入字节及来源保留；原来源的规则ID、引用和语义不会自动变成当前任务有效依据，仍需专业核对和诊断。
- 已有草稿不允许seed覆盖。其他会话的产物继续使用正常附件导入渠道；本项不是跨会话资产库或批量迁移工具。

## 续接与无进展反馈

resolve_child_handle只读定位当前派发对应run_subagent工具回执中的原生后台subagent_id，不从dispatch_id或session_id截取推导。没有回执/多个不明确调用时返回unavailable，不触发新派发。已记录unknown句柄不再建议重复使用。

返回句柄不证明完成，也不保证应用重启后还能使用。正常返回使用原handoff；人工登录等待仍用第3项的resume_browser，保留原浏览器。不能把历史句柄查询当成新的执行授权或自动重放产品操作。

草稿错误沿用进展式恢复。对draft_records，重复错误指纹不计request_id变化，防止只换批次ID却重复同一冲突被当成进展。连续相同失败达到既有阈值时返回stalled及改变方法的建议，不增加固定阶段预算、不要求用户解锁。是否实际遵循反馈仍需真实Agent验收。
