# AITestWorker 软件测试 Agent 产品技术介绍

更新日期：2026-10-16

适用对象：产品负责人、测试负责人、测试工程师、Agent 开发及维护人员
工程位置：`E:\Codex\AITestWorker`

> 本文根据当前工程配置、角色指令、Skill 与运行脚本整理，不是未来功能清单。当前产品依托已适配的 PenguinHarness 桌面应用运行，尚未发布独立 AITestWorker 安装包。独立任务已有真实运行记录，但不能据此认定所有全流程场景均稳定通过。最新验收结论以[当前状态与下一步](current-status-and-next-steps.md)为准。

## 1. 产品定位

AITestWorker 是一套面向软件测试工作的多智能体协作工程。用户通过一个总控入口，用自然语言、Word 附件、测试环境 URL 或已有测试结果提出任务，由总控选择专业 Agent，完成分析、设计、执行、缺陷整理和报告交付。

产品目标不是让用户学习内部命令，而是把测试工作的技术推进交给系统：用户主要处理业务歧义、必要的人机交互和执行范围决策；不应反复处理文件格式、哈希、运行锁、技术解锁等工程事项。

### 1.1 主要使用场景

| 用户目标 | 典型输入 | 主要交付 |
| --- | --- | --- |
| 理解需求、梳理风险 | Word、需求文字 | 需求分析、风险和待澄清问题 |
| 提炼测试覆盖范围 | 需求文字、需求分析或其他有效材料 | 结构化测试点、XMind |
| 编写测试用例 | 需求、测试点、接口契约或页面观察 | JSON 用例、Excel |
| 探索或测试产品 | 测试环境 URL、测试目标、必要访问条件 | 页面观察、断言结果和证据 |
| 分析已有失败 | 结果、日志、截图 | 问题分类、缺陷草稿、调查建议 |
| 整理测试报告 | 已有执行结果、缺陷记录、历史材料 | Word、PDF、HTML 等报告 |
| 完成完整测试流程 | 明确要求全流程及相应需求、环境与执行范围 | 从需求到报告的关联产物 |

### 1.2 当前产品原则

- **默认独立任务**：只写报告不需要先跑需求分析；只写用例不强制先生成测试点。
- **按实际依赖协作**：需要真实执行结果的报告，应等待执行完成；这种数据依赖不等于新增人工审批。
- **显式全流程**：用户明确要求完整测试闭环时，才采用生命周期编排。
- **事实优先**：没有实际执行，就不能称为测试通过；模拟故障、导入历史数据与真实执行必须区分。
- **人负责必要决定**：明确范围外的高风险操作、影响预期的业务歧义、验证码/MFA 等才需要人介入。
- **模型可更换**：业务逻辑不绑定某一模型。当前使用 `tokendance / step-3.7-flash`，后续切换仍需做兼容与效果验收。

## 2. 整体架构

```text
用户：文字 / Word 附件 / URL / 已有结果
                    |
                    v
PenguinHarness 桌面宿主
会话、模型连接、原生工具、子 Agent 调用、文件交互
                    |
                    v
软件测试总控 test_agent
理解目标 -> 归档输入 -> 选择能力 -> 派发 -> 交接 -> 简短交付
                    |
       +------------+-------------+----------------+
       |            |             |                |
    需求分析      测试点设计     测试用例编写      自动化执行
       |            |             |                |
       +------------+-------------+----------------+
                    |                 |
                 缺陷分析          测试报告
                    |                 |
                    +--------+--------+
                             |
                     工程运行与交付层
          结构化动作 / 状态 / 锁 / 来源与证据 / 导出 / 校验
                             |
                     隔离会话工作区
          输入 / 任务产物 / 执行证据 / 审计 / 用户交付物
```

上图表示能力分工，不代表每个任务都必须依次经过所有 Agent。默认由总控组织调用，专业 Agent 通过约定输入、输出和交接结果关联，而不是任意互相调用。

### 2.1 各层职责

| 层次 | 主要组成 | 职责 |
| --- | --- | --- |
| 交互宿主 | PenguinHarness 与本项目适配 | 承载对话、模型调用、工具运行、子会话、交付文件操作 |
| 总控层 | `test_agent` | 选择任务范围、安排专业分工、推进依赖、处理真实人工事项 |
| 专业层 | 六个专业 Agent | 执行指定专业任务，形成结构化结果与业务结论 |
| 方法层 | `skills/` | 提供测试方法、步骤、参考材料和输出约束 |
| 运行层 | `scripts/`、hooks、配置 | 实际操作、状态维护、并发约束、产物检查与错误恢复 |
| 数据层 | `schemas/`、任务输入与证据 | 定义数据结构，保存来源、观察和历史记录 |
| 交付层 | 导出脚本、交付展示 | 将结构化内容导出为 XMind、Excel、Word/PDF/HTML，并提供链接 |

### 2.2 Agent、Skill、Tool 的区别

| 概念 | 在本工程中是什么 | 不能混淆为 |
| --- | --- | --- |
| Agent | 有独立角色指令与任务上下文的执行角色 | 一个固定脚本或一个 Skill |
| Skill | 按需读取的专业方法与操作规范，入口为 `SKILL.md` | 自动获得权限的插件、独立运行进程 |
| Tool / 结构化动作 | 能读取文件、调用浏览器、导出文档、更新任务状态的程序入口 | 仅靠提示词就能保证的能力 |
| 模型 | 理解目标、生成内容和选择工具的推理服务 | 状态数据库、事实记录或执行授权来源 |
| 任务契约 | 本次派发的角色、范围、输入、输出与约束 | 用户需要手工编写的配置文件 |

例如，报告 Agent 借助报告 Skill 解释执行材料，生成结构化草稿，再由导出工具形成 Word/PDF。不能把“模型说报告完成了”当作文件已经生成并通过交付检查。

## 3. 智能体角色清单

当前测试体系为 **1 个总控 + 6 个专业 Agent，共 7 个角色**。另有宿主 `default_agent` 的兜底入口适配，不计入六个测试专业角色。

| 中文角色 | Agent ID | 核心职责 | 安装的项目 Skill |
| --- | --- | --- | --- |
| 软件测试总控 | `test_agent` | 理解目标、独立任务/全流程选择、归档、派发、交接、用户沟通 | 不安装专业 Skill，使用总控指令与公共运行规则 |
| 需求分析 | `requirement_analysis_agent` | 提取业务规则、功能范围、风险与歧义，保留需求来源 | `requirement-analysis`、`test-design-methods` |
| 测试点设计 | `test_point_agent` | 梳理正常、异常、边界与状态场景，形成覆盖结构 | `test-point-design`、`test-design-methods` |
| 测试用例编写 | `test_case_agent` | 编写前置条件、数据、步骤、预期及依据，形成可执行用例 | `test-case-writing`、`test-design-methods`、`api-testing` |
| 自动化执行 | `automation_execution_agent` | URL 探索、浏览器交互测试、脚本准备与受控执行，记录证据 | `playwright-execution`、`api-testing` |
| 缺陷分析 | `defect_analysis_agent` | 分析失败原因，区分产品、自动化、环境、数据与未确认问题 | `bug-reporting`、`qa-investigation` |
| 测试报告 | `test_report_agent` | 汇总有效结果、缺陷和范围，形成多格式报告 | `test-report-writing` |

权威映射：[角色清单](../penguin/agents.json)。角色指令分别位于 `penguin/agents/<agent_id>/AGENTS.md`；公共规则位于 [command-runtime.md](../penguin/command-runtime.md)。

### 3.1 总控的边界

总控负责“安排与交付”，不是代替所有专业角色写产物。它不因报告失败就绕过报告 Agent 自行生成文件，不直接修改运行清单伪造完成，不为绕过问题创建另一份运行。

总控可以组织多个没有数据依赖的独立任务并行，但同一阶段或同一浏览器不能重复启动。已经开始、结果未知的业务操作不能盲目重放。

### 3.2 专业角色的独立与协作

- 独立：每个专业角色都可由总控根据本次材料直接派发，不要求补齐无关的前序产物。
- 关联：本次任务需要前序观察或分析时，将有效产物作为输入关联，不靠口头摘要替代证据。
- 专注：子 Agent 完成自己的专业范围，不替总控批准业务范围、登记其他阶段或修改全局状态。
- 可扩展：未来新增角色应登记能力及输入输出契约，不必把每个新角色加入所有任务的必经流程。

## 4. Skill 能力清单

仓库共有 **11 个项目 Skill**。其中 **9 个不同 Skill 已在当前角色清单中挂载**，另 **2 个保留为扩展能力**。一个 Skill 可被多个角色共享，因此安装数量不能按表格行简单相加。

| Skill | 能力说明 | 当前归属/状态 |
| --- | --- | --- |
| `requirement-analysis` | 提取功能、规则、风险、待澄清项；生命周期模式保留需求台账 | 需求分析 Agent |
| `test-point-design` | 测试点分层、场景覆盖、需求关联、XMind 交付 | 测试点 Agent |
| `test-case-writing` | 结构化用例、数据约束、预期依据、Excel 输出 | 用例 Agent |
| `playwright-execution` | 独立浏览器任务、生命周期脚本执行、断言与证据归档 | 自动化执行 Agent |
| `bug-reporting` | 问题分类、复现信息、影响与证据，输出可追溯缺陷草稿 | 缺陷分析 Agent |
| `test-report-writing` | 基于有效结果形成统计、结论、局限和多格式报告 | 报告 Agent |
| `test-design-methods` | 等价类、边界值、决策表、状态迁移等设计方法 | 需求分析、测试点、用例 Agent 共享 |
| `api-testing` | 接口契约、请求响应、错误与状态验证方法；具体执行受工具边界限制 | 用例、自动化执行 Agent 共享 |
| `qa-investigation` | 依据日志与证据调查失败，区分产品、脚本、环境与数据原因 | 缺陷分析 Agent |
| `test-asset-management` | 管理可复用规则、数据策略、定位器、断言、接口契约和缺陷模式 | 仓库保留，当前七角色未挂载 |
| `test-selection` | 按风险、范围、成本选择 smoke/core_regression/regression/full/targeted 测试集 | 仓库保留，当前七角色未挂载 |

每个 Skill 的主文件为 `skills/<skill-name>/SKILL.md`，复杂规范放入其 `references/` 目录按需读取。部分 Skill 来自外部方法资源的适配，具体来源、版本与许可保留在对应 Skill 中。

**安装 Skill 与阶段主 Skill 是两个层次。** 例如用例 Agent 安装三个 Skill，但阶段注册表默认派发的主 Skill 是 `test-case-writing`；辅助方法按当前专业需要加载，不代表每次都读取全部 Skill。

测试资产登记不是每次测试的前置步骤，测试选择器也不是所有任务的必经节点。当前不应将它们宣传为已自动参与每次运行的智能决策能力。

## 5. 三种任务推进方式

### 5.1 独立任务：默认模式

```text
用户提供材料并提出单项/组合目标
  -> 总控识别需要的能力
  -> 归档输入、创建本次任务计划
  -> 派发相关专业 Agent
  -> 验证专业结果并交接
  -> 交付成果，仅提出真实待确认问题
```

示例：“根据附件写测试用例，交付 Excel，不执行测试。”

该任务可以直接派给用例 Agent，不需要先跑需求分析、测试点、执行、缺陷和报告。

### 5.2 URL 驱动任务

示例：“探索这个测试环境的登录页，检查输入校验，输出结果和报告。”

总控识别用户是否要求访问实际产品；如果需要，先派执行 Agent 获取观察和测试证据，再将有效结果交给需要这些数据的用例或报告 Agent。用户不需要先手工登记一份环境 JSON。

必须区分：

- `explore_url`：只读探索与可达性观察，不等于登录、提交或完整功能测试。
- `browser_task`：在当前授权范围内执行页面操作、断言和证据记录。
- 文档中出现 URL：本身不等于用户要求访问或测试该产品。

### 5.3 全生命周期：用户明确要求时

```text
需求分析 -> 测试点 -> 测试用例 -> 执行准备与测试执行 -> 缺陷分析 -> 测试报告
```

生命周期模式使用明确的阶段依赖，关联需求规则、测试点、用例及执行结果。测试执行需有有效范围、计划与授权；准备脚本不等于已经执行。

| 确认策略 | 适用方式 |
| --- | --- |
| `auto` | 在已授权范围内自动推进，遇到真实业务歧义或必要人工交互才询问 |
| `staged` | 用户明确要求逐阶段确认时，在保存计划指定的节点停下展示成果 |

阶段配置中的默认确认标记与本次实际计划并非同一个概念；最终是否暂停应看本次保存的策略与授权。自动推进不代表擅自批准尚未确认的业务假设。

## 6. 技术执行机制

### 6.1 结构化动作入口

主要入口是 `scripts/project-action.mjs`，提供 `catalog`、`execute`、`summary`。模型通过结构化动作提交意图，工程程序负责校验参数、维护状态与执行实际操作。

| 动作类别 | 代表动作 | 用途 |
| --- | --- | --- |
| 任务编排 | `create_run`、`plan_run`、`extend_plan` | 创建任务、选择阶段、增加能力 |
| 输入处理 | `archive_input`、`extract_word`、`read_source` | 原文/附件归档、Word 提取、来源读取 |
| 派发与交接 | `dispatch`、`resolve_child`、`handoff` | 登记专业任务、关联真实子调用、核验交付 |
| 草稿诊断与导出 | `diagnose_task`、阶段诊断、导出、`validate_artifacts` | 集中检查草稿并形成正式产物 |
| 浏览器操作 | `explore_url`、`browser_task` | 探索、交互、断言、人工暂停与继续 |
| 状态与确认 | `run_status`、确认和修订动作 | 处理真实决定、维护状态、保留修改历史 |

动作是否可用还取决于角色、模式与本次派发，不是每个 Agent 都能调用全部动作。`project-command.mjs` 保留受控旧能力入口，不是任意绕过新入口的备用通道。

总控可通过 `exec_command.qa_request` 同时提供完整动作对象，工具先保存并核对请求再执行，减少“先写文件再执行”时序错误。专业子 Agent 仍使用相应任务契约约定的请求文件方式。普通用户无需编写上述参数。

### 6.2 子 Agent 派发

`dispatch` 生成本次派发记录及任务契约，实际启动通过 PenguinHarness 的 `run_subagent` 完成。登记派发不等于子任务已经运行。

当前调用约束：

- 目标 `agent_id` 必填，任务 `prompt` 必须与登记一致。
- `description` 是展示说明，可用中文改写，不改变任务授权。
- `yield_time_ms` 是调用等待时间，不是模型预算或业务权限；当前允许范围为 250 至 600000 毫秒。
- 原始登记记录、任务合同和关联资源保留哈希核验；禁止通过额外模型覆盖等参数绕过本次契约。
- 返回后核对真实子调用和产物，不以模型一句“完成”登记成功。

### 6.3 状态、锁与恢复

每个 run 保留运行清单、阶段状态、派发事件和动作回执。锁用于防止并发重复修改或重复执行，不应变成用户手工解锁流程。

可安全纠正的输入或草稿问题由 Agent 自行修正；重复无进展时换方法或交付部分结果。实际产品操作结果未知时不自动重放，避免重复创建、提交或删除。

### 6.4 技术组件

| 组件 | 当前用途 |
| --- | --- |
| PenguinHarness | 桌面对话宿主、模型与工具运行、子 Agent 会话 |
| Node.js / JavaScript `.mjs` | 编排入口、状态、守卫、浏览器控制、导出调度 |
| Playwright | 浏览器交互、自动化测试；生命周期脚本可使用其请求能力 |
| JSON Schema / AJV | 校验用例及相关结构化数据 |
| XMind 相关库与生成脚本 | 生成测试点脑图 |
| Python 文档导出组件 | Excel、报告等交付文件处理 |
| JSON / Markdown / 文件哈希 | 任务契约、原始记录、可读文档与一致性检查 |
| Git / GitHub / 工程测试 | 代码与配置版本管理、自动回归与维护记录 |

工程没有因为使用多 Agent 就自动具备任意模型兼容、长期学习或数据库级安全隔离。依赖由维护阶段准备，正常测试任务不应临时安装浏览器、文档插件或字体。

## 7. 执行证据与质量机制

### 7.1 来源与事实分层

- 用户需求：决定要测什么、预期是什么及允许的范围。
- 实际观察：页面、接口响应、断言、日志和截图，说明本轮发生了什么。
- 模型分析：对观察的解释和推断，不能冒充产品事实。
- 导入材料：来自用户或历史批次，不能描述为本 Agent 刚执行的测试。
- 模拟材料：故障注入或合成样例，不能直接当作真实后端缺陷。

生命周期模式使用需求台账及规则关联追溯；独立任务保持轻量契约，不为做一项任务补造全套台账。

### 7.2 已有工程能力

已有实现包括动态反馈采集、操作前置条件检查、证据时序、测试数据台账、用例与断言计数区分、可选历史对照，以及报告字段保真和多格式一致性检查。

这些机制降低错误风险，不等于保证模型分类、测试覆盖或根因判断全部正确。例如有效的文件格式并不能证明每个测试点都覆盖业务风险。

### 7.3 接口执行能力的实际边界

`api-testing` 提供较广的接口测试方法，但独立任务当前的执行入口是有限的：

- 已启动浏览器会话内，对已知、获准读取的同源 GET/HEAD 端点做受控验证。
- 可结合页面动作被动观察响应，分别校验 HTTP 与业务结果。
- 明确授权时，支持限定同源 GET 的单次异常模拟，并区分真实/模拟结果。
- 独立跨域、带查询参数、任意鉴权头、写接口以及无浏览器纯 API 执行，不属于当前这套通用入口已覆盖的能力。
- 生命周期中的 Playwright API 脚本仍需准备、计划校验和有效执行授权；不能用“已有 API Skill”宣称任意接口已可自主执行。

## 10. 模型、记忆与安全

### 10.1 模型与记忆

角色并不等于固定模型。模型选择与连接由宿主配置管理，专业方法放在 Skill，状态放在当前任务记录。

当前使用轻量的上下文与来源管理：按需读取专业 Skill，参考相关宿主记忆索引，但以本次用户输入、归档材料和运行证据为准。压缩摘要不是授权或执行证明。未启用本项目自动长期记忆写入，也不能宣传为已完成通用向量知识库或持续自学习系统。

### 10.2 权限与安全

- 父/子 hook 限制误调用、专业职责越界、敏感文件读取和重复派发。
- 当前授权不自动扩展到支付、通知、删除、权限变更或生产破坏性操作。
- 不把凭据、验证码、Token、Cookie 写入跨会话共享资产或提交到 Git。
- 测试失败不自动认定为产品缺陷；缺陷关闭需真实治理依据。
- hooks、目录规则和哈希校验是误操作防护，不是操作系统沙箱，也不等于凭据加密。

## 12. 开发与扩展入口

### 12.1 新增一个专业 Agent 的建议步骤

1. 明确输入、输出、专业责任和执行风险，判断它是否真需要独立角色，而非给已有角色增加 Skill。
2. 编写角色指令及相关 Skill，复用公共运行规则，不复制整套流程限制。
3. 在 `penguin/agents.json` 登记角色与 Skill；需要作为编排阶段时，更新阶段注册表与实际路由。
4. 定义 task/lifecycle 所需数据契约、产物及来源要求，不让独立任务强制依赖完整前序链。
5. 补齐结构化动作、写入/执行边界、导出或外部集成；不能只有提示词没有工具实现。
6. 增加工程测试，同步已有角色的持久化工具定义，而非只改宿主默认值。
7. 运行真实 Agent 验收，分别检查派发、业务结果、文件交付和用户介入次数。

增加配置项不等于自动接入成功；还需检查硬编码边界、角色权限、执行器和交付展示是否支持新角色。
