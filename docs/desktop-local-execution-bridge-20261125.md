## 通道与保护

1. Electron 主进程读取当前服务分区的登录 Cookie，为服务地址和用户生成并保存设备身份。凭据不通过 renderer/preload 暴露。
2. 主进程用安装配置的 Node 启动 `dist/execution-worker.js`。本机 worker 不监听公网端口；只用随机令牌保护的回环中继承载模型和受限项目 API。
3. worker 向 `/api/sessions/local-execution/register` 注册，通过 `/poll` 领取请求。服务端按账户和设备校验随机证明，绑定持久保存于既有 server_settings，不新增业务库或迁移。
4. 桌面请求始终带设备标记。未就绪、设备不匹配、历史远程会话或执行端离线会明确拒绝，不走 VM 兜底。请求一旦派发不自动重放，丢失确认时提示检查结果后继续。
5. 项目 Agent 状态、会话附件、个人 Skill、发布 Skill 和 Hook 按范围同步。运行指令中的受管引擎/资源路径转换为本机路径；附件原始字节不改写。真实渠道密钥不下发，vault 不复制。
6. 前景输出、后台子 Agent 状态、消息和完成通知回传；审批仍由服务端当前用户处理。子会话继承根会话的设备、用户及工作区归属，Windows 路径按跨平台规则解析。
7. 文件使用分片及 SHA-256 校验。只允许当前任务工作区、已授权子会话轨迹及 scratchpad，拒绝越界和符号链接。文件单个限 16 MiB、一次快照限 100 MiB；超限保留本机文件并明确报错。
8. 审核、修改阶段、人工验证码答复和交付文件打开转回原设备执行。扫码及短信等仍按产品人工动作处理。带附件的运行中输入进入后续正常输入队列，避免将尚未同步的服务端附件路径直接送入本机。

## 使用和已知边界

- 更新后重新打开客户端，登录日志应出现 `[executor] execution-ready`。新建会话使用本机环境。改造前在 VM 创建的会话保留历史，继续发起执行会收到新建会话提示，不静默搬迁已有执行历史。
- 当前只支持显式配置 endpoint 且协议为 `openai-chat`、`openai-responses`、`ant-messages` 的模型。其他协议会明确阻止新建本机会话，需要补适配后使用。
- 本机缓存位于 `host_data/execution-cache/<服务和用户哈希>`，不能当普通临时缓存随意删除；恢复执行需要本机轨迹。丢失轨迹时明确阻断，不从服务端镜像自动重建。
- 定时任务、外部 API 及管理员助手入口不在本次桌面执行绑定范围内。不要声称这些入口已经改为本机执行。
- 后台进程和浏览器的异常崩溃、完整业务阶段闭环及多设备并发仍须按实际项目单独验收。控制请求“已受理”不等于所有异步动作已成功，最终以状态回执为准。

## WebSocket 入口修复（2026-11-25）

真实会话 `session-2026-11-25-05-52-28-b874e7bc` 暴露了首轮验证遗漏：任务列表开工请求经 API WebSocket 发送，桌面端仅匹配 HTTP origin，未向 ws/wss 握手注入执行身份；服务端握手引用也没有将该身份传给逐帧构造的业务请求。因此执行端在线并不代表该会话已经绑定本机，实际在 VM 创建了工作区。本机没有该会话的工作区和执行轨迹。

修复在两个位置完成：桌面端将 ws/wss 与对应 http/https origin 对齐，仅对配置服务的 `/api/` 请求附加身份；服务端从已认证升级请求保存本机身份，经平台引用注入每个业务 Request。帧内提供的执行身份仍被丢弃，不能覆盖握手身份。握手时执行端未就绪的旧连接返回 421，让现有客户端经 HTTP 重试并注入最新身份；HTTP 中未就绪的桌面身份明确阻断，不能回退到 VM 创建会话。

任务列表“开始测试”和测试助手创建会话使用相同链路。本机安装配置决定 Node、Python、引擎和工作区目录；服务端会话 workspace 字段对本机会话仅保存展示镜像，判定执行位置需同时核对本机绑定与实际 Windows 工作区。此次修复不迁移已在远程运行的旧会话历史。

新增回归覆盖同源 HTTP/WS 标识、真实认证升级到业务层的身份传递、帧身份伪造拒绝、执行端未就绪回退，以及测试助手/任务开工对不可用执行端的拒绝且不新增远程会话。安装副本和真实执行端的最终验证另记部署记录。
