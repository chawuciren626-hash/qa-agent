# 基于 PenguinHarness 的多智能体软件测试桌面应用技术方案

## 1. 方案结论

可以基于 PenguinHarness 落地为一个桌面化的软件测试智能体系统，但建议分两步完成：

1. **先把 PenguinHarness 当作 Agent 运行底座**：在现有应用中创建一个测试总控 Agent，并让它按流程调用多个专业 Agent 或 Skill，优先跑通业务闭环。
2. **再把工作台做成独立桌面产品界面**：从 GitHub 获取 PenguinHarness 源码，在源码中新增“测试智能体工作台”页面，重新构建并打包为自己的 EXE。

不要直接修改 `D:\Program Files\PenguinHarness`。这里是已经安装好的应用目录，升级或重装可能覆盖改动，也不利于调试、版本管理和打包。

本项目第一阶段的可用形态是：用户在 PenguinHarness 内提交需求、选择测试环境、点击执行，总控 Agent 组织子 Agent 生成测试产物；测试点、用例、执行结果、Bug 草稿和报告统一保存在项目工作区。第二阶段才将这套流程做成专属桌面工作台。

## 2. 产品目标与边界

### 2.1 产品目标

面向测试人员、产品人员和开发人员，提供一个从需求到质量结论的测试协作助手：

- 输入需求文档或粘贴需求描述。
- 自动梳理测试范围和测试点。
- 自动生成可评审、可导出的结构化测试用例。
- 选择可自动化的用例，生成并执行 Playwright UI 自动化脚本。
- 从失败结果中生成带证据的 Bug 草稿。
- 汇总执行数据，生成测试报告和上线建议。
- 所有关键产物可查看、编辑、确认、导出和追溯。

### 2.2 MVP 边界

一个月内第一版只支持以下范围：

- Web 页面测试。
- Markdown 需求输入。
- Playwright UI 自动化测试。
- 本地文件保存产物。
- Bug 草稿和 Markdown 测试报告。
- 人工确认后再提交 Bug；不直接写入 Jira、禅道等外部系统。

第一版暂不承诺：移动端真机测试、性能压测、安全渗透、复杂接口编排、自动修复脚本、完全无人值守发布判断。

## 3. 总体架构

```text
用户
  │ 需求、环境、执行指令
  v
测试智能体工作台（PenguinHarness 页面 / 后续自定义桌面页面）
  │
  v
测试总控 Agent（QA Orchestrator）
  ├── 需求分析 Agent
  ├── 测试点设计 Agent
  ├── 测试用例 Agent
  ├── 自动化执行 Agent
  ├── Bug 分析 Agent
  └── 测试报告 Agent
  │
  v
共享工作区（inputs / output / tests / evidence / config）
  │
  ├── Playwright 浏览器与测试站点
  ├── 截图、Trace、日志
  └── 后续：Jira、禅道、GitHub Issues、CI/CD
```

核心原则是“总控负责流程，专业 Agent 负责专业产物，文件和结构化数据负责交接”。子 Agent 不依赖聊天上下文互相猜测，而是读取上一步已经保存并校验过的产物。

## 4. Agent 分工设计

| Agent | 职责 | 输入 | 输出 | 人工确认点 |
|---|---|---|---|---|
| 测试总控 Agent | 编排流程、检查前置条件、决定下一步、汇总状态 | 任务指令、项目配置、全部产物状态 | 任务状态、执行日志、调度指令 | 测试范围、执行授权、报告结论 |
| 需求分析 Agent | 提取功能、角色、规则、假设和疑问 | `inputs/requirements.md` | 需求分析结果、澄清问题 | 需求缺失或歧义 |
| 测试点设计 Agent | 从风险和场景角度设计测试点 | 需求分析结果 | `output/test_points.md` | 测试范围和优先级 |
| 测试用例 Agent | 输出可执行、可追踪的结构化用例 | 测试点、用例 Schema | `output/test_cases.json` | 关键业务用例 |
| 自动化执行 Agent | 筛选自动化用例、生成脚本、执行并保存证据 | 用例、环境配置 | `tests/generated/`、`output/test_results.json` | 目标环境、账号和执行范围 |
| Bug 分析 Agent | 判断失败类型，编写可复现 Bug 草稿 | 失败结果、日志、截图 | `output/bugs.json`、`output/bugs.md` | 是否确认为产品缺陷 |
| 测试报告 Agent | 基于真实数据生成质量报告 | 用例、结果、Bug | `output/test_report.md` | 上线建议 |

### 4.1 总控 Agent 的约束

总控 Agent 不是“把所有事情都自己写一遍”。它必须：

- 读取 `config/project.json` 和 `config/test-env.json`，确认项目、环境、允许执行的范围。
- 按固定状态机推进：需求分析 -> 测试点 -> 用例 -> 自动化筛选/执行 -> Bug 草稿 -> 报告。
- 每一步结束都检查产物是否存在、是否可解析、是否满足 Schema。
- 遇到需求不完整、环境不可达、账号缺失、结果矛盾时暂停并明确说明原因。
- 不得把测试脚本失败直接认定为产品 Bug，必须区分脚本、环境和产品问题。
- 未经用户确认，不得把 Bug 提交到外部缺陷系统，不得在生产环境执行破坏性操作。

### 4.2 初期的实现选择

PenguinHarness 初期可用一个名为 `qa_orchestrator_agent` 的主 Agent 承载总控逻辑；专业能力先以本项目中的 Skill 实现：

```text
skills/
  requirement-analysis/
  test-point-design/
  test-case-writing/
  playwright-execution/
  bug-reporting/
  test-report-writing/
```

这样可以最快验证流程。等每个步骤的输入、输出和失败处理稳定后，再把高频、边界清晰的 Skill 拆成独立子 Agent。对初学者而言，这是最可控的演进方式。

## 5. 数据与产物设计

### 5.1 工作区目录

```text
测试智能体/
  config/                  # 项目、环境、执行策略
  inputs/                  # 用户输入的需求、附件说明
  schemas/                 # JSON 数据契约
  skills/                  # 专业能力说明
  tests/generated/         # 生成的 Playwright 脚本
  evidence/                # 截图、trace、日志等执行证据
  output/                  # 每个阶段的正式产物
  docs/                    # 学习、设计、操作文档
  scripts/                 # 校验、运行、转换脚本
```

### 5.2 阶段交接标准

| 阶段 | 正式产物 | 核心要求 |
|---|---|---|
| 需求分析 | `output/requirement_analysis.json` | 功能、角色、规则、风险、待澄清项明确 |
| 测试点 | `output/test_points.md` | 覆盖正常、异常、边界、权限、兼容与风险场景 |
| 测试用例 | `output/test_cases.json` | 严格 JSON，符合 `schemas/test_case.schema.json` |
| 自动化执行 | `output/test_results.json` | 有用例 ID、状态、耗时、错误、证据路径 |
| Bug 草稿 | `output/bugs.json` / `output/bugs.md` | 有复现步骤、预期、实际、严重级别和证据 |
| 测试报告 | `output/test_report.md` | 只引用真实执行结果和确认后的缺陷 |

每个产物都应带上 `run_id`、`created_at`、`source_requirement_version` 等追踪字段。当前样例先保持简单；产品化前必须补充这些字段，否则多次执行后容易混淆“哪一批结果对应哪一版需求”。

### 5.3 数据质量与可追溯性

- 用例 ID、自动化脚本文件名、执行结果、Bug 必须可以相互关联。
- 结构化产物使用 UTF-8 编码，Windows PowerShell 读取时明确使用 `-Encoding UTF8`。
- JSON 必须在进入下一步骤前解析校验，不能把大模型文本直接当作可信数据。
- 截图、Trace、日志按 `run_id/case_id` 保存，报告只引用真实证据路径。
- 需求、用例、脚本被重新生成时保留历史版本，避免覆盖后无法复盘。

## 6. 桌面应用呈现方案

### 6.1 第一阶段：使用现有 PenguinHarness

用户不需要开发新的 EXE 就可以使用：打开 PenguinHarness，进入或手动创建“软件测试智能体”，导入本项目 `skills`，选择默认模型 `tokendance / step-3.7-flash`，在对话或任务界面发起测试任务。

建议主 Agent 配置：

| 配置项 | 推荐内容 |
|---|---|
| Agent ID | `qa_orchestrator_agent` |
| 名称 | 软件测试总控智能体 |
| 描述 | 统筹需求分析、测试设计、自动化执行、Bug 草稿和测试报告的测试全过程。 |
| 工作区 | `E:\Codex\测试智能体` |
| 默认模型 | `tokendance / step-3.7-flash` |
| 角色提示词 | 使用 `docs/orchestrator-prompt.md`，后续按本方案升级。 |
| Skills | 导入 `E:\Codex\测试智能体\skills` 下的六个 Skill。 |

在这一阶段，PenguinHarness 本身就是桌面入口；项目目录就是智能体的知识、规则和运行产物。用户可通过一句任务指令启动，例如：

```text
读取 inputs/requirements.md，先生成测试点和结构化测试用例；待我确认后再执行自动化测试。
```

### 6.2 第二阶段：定制“测试智能体工作台”

当流程稳定后，从 [PenguinHarness GitHub 源码](https://github.com/Prism-Shadow/penguin-harness) 创建自己的开发副本，在源码中增加专属页面与业务逻辑，然后重新打包为独立 EXE。不要以安装目录里的文件作为开发源代码。

建议工作台包含五个主视图：

```text
左侧：项目与任务
中间：当前步骤与产物预览
右侧：总控 Agent 执行日志 / 人工确认操作

需求 -> 测试点 -> 测试用例 -> 自动化执行 -> Bug -> 测试报告
```

具体页面能力：

- **项目页**：选择工作区、配置测试环境、保存账号引用和执行策略。
- **需求页**：输入或导入需求，展示需求分析和待澄清项。
- **测试设计页**：查看、编辑、确认测试点和用例，显示优先级与覆盖范围。
- **执行中心**：选择用例、启动/停止执行、查看实时状态、截图、日志和 Trace。
- **缺陷与报告页**：审核 Bug 草稿、导出 Markdown/HTML/PDF 报告，后续可提交 Jira/禅道。

页面需要以任务状态驱动按钮状态。例如没有确认测试用例时，“执行自动化测试”应禁用；没有失败结果时，“生成 Bug 草稿”不应出现可执行状态。

## 7. 核心工作流

```text
创建任务
  -> 导入需求
  -> 需求分析（有歧义则等待人工补充）
  -> 生成测试点（人工确认范围）
  -> 生成结构化用例（Schema 校验、人工确认关键用例）
  -> 自动化筛选与脚本生成
  -> 用户选择环境后执行 Playwright
  -> 收集结果、截图、Trace、日志
  -> 分析失败并生成 Bug 草稿（人工确认）
  -> 生成测试报告（人工确认上线结论）
  -> 归档本次 run 的全部产物
```

这里的“人工确认”不是削弱智能体，而是软件测试的必要控制点：需求和风险判断需要业务责任人确认，执行环境涉及安全，Bug 和上线结论涉及项目决策。

## 8. 技术选型

| 模块 | 第一阶段选型 | 后续演进 |
|---|---|---|
| Agent 运行底座 | PenguinHarness | 基于其源码定制和打包 |
| 默认模型 | `tokendance / step-3.7-flash` | 按任务类型增加模型路由与备用模型 |
| 工作流 | 总控 Prompt + Skill + 文件状态 | 显式状态机、队列和任务恢复 |
| UI 自动化 | Playwright | 并行执行、设备矩阵、Allure |
| 数据格式 | Markdown + JSON Schema | SQLite/本地数据库，后续服务端数据库 |
| 证据保存 | 本地目录 | 对象存储、报告平台 |
| 缺陷系统 | 本地 Bug 草稿 | Jira、禅道、GitHub Issues API |
| 桌面壳 | 现有 PenguinHarness | 从源码定制其桌面壳或独立 Electron/Tauri 前端 |

关于桌面壳的选择：如果 PenguinHarness 源码的 UI 扩展成本较低，优先在其上增加测试工作台；如果源码结构、打包方式或插件机制不适合承载大量测试业务页面，则保留 PenguinHarness 作为 Agent 后端，另建 Electron 或 Tauri 桌面前端调用本地服务。这个判断需要在拿到源码、确认技术栈后再做，不能现在凭空决定。

## 9. 一个月实施计划

### 第 1 周：流程与单 Agent MVP

- 完成需求 -> 测试点 -> 结构化用例的链路。
- 固化输出 Schema、目录和命名规范。
- 在 PenguinHarness 中创建并配置测试总控 Agent。
- 产出可演示的登录功能样例。

验收：可以在 PenguinHarness 中下达任务并获得已校验的测试点、测试用例。

### 第 2 周：自动化执行闭环

- 接入 Playwright，配置测试环境。
- 从用例筛选可自动化场景，生成至少 3 条脚本。
- 统一保存执行结果、截图、日志。
- 增加产物校验脚本。

验收：一次任务能执行自动化用例并输出明确的通过/失败结果。

### 第 3 周：缺陷、报告与多 Agent 拆分

- 从失败结果生成 Bug 草稿，区分产品/环境/脚本问题。
- 基于真实数据生成测试报告。
- 将稳定的专业步骤从 Skill 拆分为独立子 Agent 或明确的子任务模板。
- 增加总控 Agent 的异常处理和人工确认节点。

验收：测试全过程能形成可追溯闭环，任何失败都能找到证据。

### 第 4 周：桌面化验证与交付

- 整理 PenguinHarness 内的 Agent 配置与操作流程。
- 设计测试工作台页面原型和任务状态模型。
- 拉取 PenguinHarness 源码，完成“能否直接改造”的技术验证。
- 输出定制开发工作量评估，完成 MVP 演示和使用文档。

验收：现有 PenguinHarness 内可完整演示；明确下一阶段是“直接改造其 UI”还是“独立桌面前端”。

## 10. 风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 大模型输出不稳定 | 用例字段错漏、报告失真 | Schema 校验、模板约束、人工审核、固定样例回归评估 |
| 需求不完整 | 测试范围不准确 | 输出待澄清项，禁止 Agent 自行假设关键业务规则 |
| 自动化定位不稳定 | 误报失败 | 优先语义定位、保存 Trace、区分脚本失败与产品失败 |
| 测试环境/账号敏感 | 安全和数据污染 | 配置脱敏、权限最小化、非生产环境优先、危险操作需确认 |
| 多次任务相互覆盖 | 结果难追溯 | 引入 `run_id`、版本目录和不可变执行证据 |
| 直接改安装 EXE | 更新覆盖、不可维护 | 始终从 GitHub 源码分支进行定制、独立构建打包 |
| 初学者一次引入过多技术 | 项目停滞 | 先用现成 PenguinHarness 跑通，按周增加一个能力 |

## 11. 当前项目对应关系

当前工作区已经具备了第一阶段的基础：

- `skills/`：六项专业测试能力的初版规则。
- `inputs/requirements.md`：样例需求。
- `output/test_points.md`：已生成的测试点。
- `output/test_cases.json`：已生成并验证的结构化测试用例。
- `docs/orchestrator-prompt.md`：测试总控的初版提示词。
- `config/` 和 `schemas/`：测试项目配置与数据约束。

下一步应该优先建设“自动化执行 Agent”的最小闭环，而不是立即改桌面界面：安装并配置 Playwright、生成一条可执行脚本、保存结果和证据。只有业务闭环证明有效，桌面工作台才有稳定的功能可以承载。

## 12. 后续开发任务清单

可以按以下顺序继续执行：

1. 更新 `docs/orchestrator-prompt.md`，使其符合本方案的状态机与人工确认规则。
2. 创建 `output/requirement_analysis.json` 及对应 Schema。
3. 初始化 Playwright，生成并运行第一条登录用例。
4. 实现执行结果转换和产物校验脚本。
5. 生成 Bug 草稿和测试报告。
6. 在 PenguinHarness 中完成 `qa_orchestrator_agent` 的手动创建与 Skill 导入。
7. 拉取 PenguinHarness 源码，分析其桌面 UI、Agent 配置与打包结构，再决定定制方案。

## 13. MVP 成功标准

一个月后，系统达到以下标准即可称为可用 MVP：

- 在 PenguinHarness 桌面应用中能启动测试总控 Agent。
- Agent 能从一份需求生成测试点和结构化用例。
- 至少 3 条 Web 用例可以由 Playwright 自动执行。
- 每次执行都会保存结果、日志和失败证据。
- 失败结果可生成可审核的 Bug 草稿。
- 可基于真实数据生成测试报告与上线风险说明。
- 用户能在一个清晰的任务流程中查看每一步产物并决定是否继续。

这套 MVP 的重点不是追求完全自动化，而是让测试过程自动化、结构化、可追溯，并在关键质量决策前保留人的判断。
