# 基于 PenguinHarness 的多 Agent 软件测试桌面应用方案

## 结论

当前应继续以已安装的 PenguinHarness 作为桌面入口和 Agent 运行底座，不直接修改 `D:\Program Files\PenguinHarness`。该安装目录会被升级覆盖，且不属于本项目的可版本化源码。

独立测试工作台可行，但应在“配置可复现、通用闭环可验证、核心接口稳定”后再实施。当前工程尚处于该前置阶段。

## 当前架构

```text
PenguinHarness 桌面应用
  -> test_agent 总控
     -> requirement_analysis_agent
     -> test_point_agent
     -> test_case_agent
     -> automation_execution_agent
     -> defect_analysis_agent
     -> test_report_agent
  -> E:\Codex\测试智能体
     -> 工作流、Skill、脚本、Schema、资产目录、run_id 产物
```

总控根据用户输入选择阶段，运行计划负责依赖、审批和审计。工作区保存最终产物，PenguinHarness 保存各 Agent 的运行时配置与对话入口。

## 当前可用交互

用户在总控对话中直接提供需求文字、文档或链接。总控应先描述将使用的阶段与风险，再生成可审阅产物；需要访问真实环境时，必须在执行前请求确认。

用户可获得：

- XMind 测试点和 Excel 测试用例。
- 选择范围、执行计划、失败证据和本地 Bug 草稿。
- 带质量门的 Markdown、Word 和 PDF 报告。

## 独立工作台的目标形态

当满足前置条件后，工作台应围绕任务而非聊天记录组织：

| 页面 | 核心能力 |
|---|---|
| 项目与环境 | 工作区、环境引用、执行策略、权限状态 |
| 需求与设计 | 导入需求、查看待澄清项、编辑和确认测试点/用例 |
| 执行中心 | 查看选择结果、计划、实时状态、截图、trace 和日志 |
| 缺陷与报告 | 审核问题、查看质量门、导出报告、后续接入外部平台 |
| 资产中心 | 管理验证过的定位器、断言、数据策略和接口契约 |

按钮状态必须由运行状态机控制。例如未确认用例时不允许执行，证据不足时不允许报告“通过”。

## 实施前置条件

独立桌面应用开发前必须完成：

1. Agent 配置可从仓库同步到新环境，且不包含密钥。
2. 通用 Mock 验收基座能验证完整闭环。
3. 运行、产物、错误和状态机接口已由 Schema 和测试覆盖。
4. 对桌面界面究竟改造 PenguinHarness 源码还是新建本地前端完成技术调研。

## 技术决策原则

- 若 PenguinHarness 源码提供稳定的扩展点和可维护的构建链，可在其源码副本上开发专属工作台。
- 若其 UI 扩展成本高，则保持 PenguinHarness 作为 Agent 运行器，另建本地 Electron/Tauri 前端调用本地服务。
- 无论选择哪种方式，运行计划、执行器、资产、质量治理必须继续由本仓库的版本化核心承载，不能复制到界面层。
