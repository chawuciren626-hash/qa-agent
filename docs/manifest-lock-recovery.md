# 清单写入锁安全恢复

日期：2026-10-15。二轮审阅修复第2项，范围是`withRunLock`管理的`manifest.json.lock`，不是所有锁的通用自动删除器。

## 行为

旧实现以排他创建文件防止清单并发写入，但进程异常退出后锁会永久残留；释放时也没有确认锁仍属于自己。

新锁记录version、run_id、host、随机token、pid和时间。创建仍使用`wx`，成功后只调用一次当前操作，不在锁层重试业务操作。

发生冲突时：

1. 只识别字段完整、本机、本run的新格式锁。损坏或不明来源记录原样保留。
2. 使用进程存在性探测。仅`ESRCH`代表确认持锁进程不存在；存活、权限错误和其他不确定情况均不接管。不采用TTL，也不因锁很旧就杀进程。PID被复用且当前存在时同样保守保留。
3. 核对清单身份和当前会话目录，拒绝目录联接/链接逃逸。
4. 以旧锁完整字节的SHA256创建唯一恢复认领文件，`wx`保证同一旧锁只能有一个移除者；认领文件永久保留，不轮流争抢移除权限。
5. 再次比较原锁字节，未变才删除；记录移除时间，然后重新排他创建新锁。若被其他当前请求先取得，新请求仍按已有竞争机制处理，不越过互斥。
6. 回调结束时，仅删除完整内容仍属于本次调用的锁；锁缺失或已替换则报告工程异常，不删除别人的锁。

审计路径：`output/runs/<run-id>/audit/manifest-lock-recovery/<旧锁SHA256>.json`，包含原锁完整内容、原因、恢复进程和时间。`claimed`表示认领意图，`lock_removed`表示旧锁已移除，均不代表业务操作完成。

## 不改变的边界

- 不修改manifest阶段、批准记录或历史派发；当前操作仍须通过原有状态与审计检查。
- 不清除`execution.lock.json`、浏览器执行锁或控制会话状态锁，不停止产品进程、不自动重试提交，不把“清单可写”解释为“产品动作安全重做”。
- 独立任务模式不增加前序阶段依赖；不增加用户确认节点或解锁材料。
- 旧格式仅有pid/at，缺少可信主机归属，不自动迁移或猜测。当前修复对以后生成的新格式锁提供自动恢复；历史不明确锁由维护侧核对。
- 恢复者在认领后、移除前再次崩溃时，保留认领及原锁，不允许第二个移除者盲目接管。这是明确的保守边界，不宣称任意多重崩溃均零干预恢复。锁创建中断留下损坏内容时同样保留。
- 本地文件系统上的进程互斥，不是分布式锁、OS沙箱或恶意本机进程防护；主机重名、磁盘故障、外部手工改锁不在自动恢复保证内。
- `withRunLock`保持同步回调契约。本轮未改模型、代理、凭据、宿主代码或用户运行数据。
