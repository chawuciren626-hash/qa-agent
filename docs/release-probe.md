# 发版探针（L-5）

## 要防的那一幕

发版了，`maps_staleness` 还在按「14 天没更新」判资产新鲜。平台拿着按旧版页面建档的元素库跑一整轮回归，出一份 300 条的报告——里面 40% 的失败其实是「页面改版了」。

这份报告发出去，客户不会认为「资产过期了」，只会认为「你们的测试不准」。而且**每次发版都会重演一遍**。

正确顺序：

```
构建号 / 资源指纹变化 → 20 条冒烟探针（3 分钟）→ 失败率 >20% → 不出全量报告
```

## 判定链

| 状态 | 触发条件 | 是否拦全量报告 |
|---|---|---|
| `no_baseline` | 第一次记录基线 | 否——**第一次上线不能被自己的规则拦住** |
| `unchanged` | 构建号与资源指纹都没变 | 否（跳过探针，省 3 分钟） |
| `unknown` | 既没构建号也没资源指纹 | 否，但明确「此状态不代表未发版」 |
| `changed` + 无探针结果 | 有变化但还没跑探针 | **是**，提示先跑 N 条探针 |
| `changed` + `probe_passed` | 失败率 ≤ 20% | 否 |
| `changed` + `probe_failed` | 失败率 > 20% | **是**，且指向「重建档」 |
| `inconclusive` | 无结果 / 超预算 / 过半不可判 | 否，但给出「此时给结论就是猜」 |

## 四个刻意的口径

**一、阈值是 `> 20%` 不是 `>= 20%`。**
20 条里 4 条失败正好 20%，不拦；5 条才拦。用整数比较（`failed*100 > threshold*100*total`）避免浮点误差把 4/20 判成通过率问题。结果里直接给算式：`5/20 = 25.0% > 20%`，省得事后扯皮。

**二、`inconclusive` 不进失败率。**
算成失败会误拦发版；算成通过会掩盖环境问题。它单独计数，过半则整体判不可判。

**三、被拦的是「全量报告」，不是「本次结论」。**
探针报告照常出，`blocked_reason` 直说「先按失败探针重建档」。**不允许建议"重试"**——重试解决不了资产过期。

**四、选样确定性。**
按 S1/P0 → smoke → 其余排序，同优先级按 `case_id`；先保证每个模块至少 1 条。随机抽样会让同一版本两次探针结论不同，那比不探针更糟。

## 用法

```bash
node scripts/release-probe.mjs --build=2026.11.15-rc1
node scripts/release-probe.mjs --build=2026.11.15-rc1 --assets='[{"path":"/app.js","sha256":"abc"}]'
# 基线写在 output/runtime/release-baseline.json
```

编排层调用 `inspectReleaseProbe({previous, current, cases, results})`，只看一个字段：

```js
result.gate.allow_full_report  // false → 不出全量报告
result.gate.why                // 一句话原因，可直接写进报告首页
```

## 诚实边界

| 做得到 | 做不到 |
|---|---|
| 构建号/资源指纹变化检测 | 没有构建号也没有资源清单时判断是否发版 |
| 探针选样、阈值判定、拦截决策 | 真正执行探针（要真实环境，属 M2） |
| 明确区分「没变化」「判不了」「首次」 | 自动重建档（那需要探索器，属 M2） |
