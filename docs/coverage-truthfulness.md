# 覆盖度的诚实口径（P2-4）

## 问题

矩阵里标了「这一格需要性能验证」，执行层没有压测能力，但覆盖度报表把它算成「已覆盖」。于是报告上的 92% 里有 15 个百分点是**分配出来的**，不是**验出来的**。

这种数字经不起追问，一次就够毁掉整份报告。

## 两个口径并排

```
coverage_rate   = executed / designed                       （诚实的那个）
optimistic_rate = (executed + assigned_only) / designed     （旧口径，仅用于对比）
```

报告里两个都给，是为了让「差在哪」看得见，而不是让人以为旧数字是错的。

## 什么算「已执行」

有结果记录，且状态 ∈ `passed / failed / inconclusive`。

`blocked` / `skipped` **不算**——那是「没跑成」，算进覆盖是另一种注水。

同一条用例多次执行，任一次真跑过就算已执行。

## 输出

```json
{ "designed": 10, "executed": 7, "assigned_only": 3,
  "coverage_rate": 0.7, "optimistic_rate": 1,
  "by_layer": { "UI": { "designed": 7, "executed": 7, "assigned_only": 0 },
                "性能": { "designed": 3, "executed": 0, "assigned_only": 3 } },
  "warnings": ["3 条设计用例只有验证方式分配、没有执行结果，不得计入已覆盖。"] }
```

报告段落会明写：

> 覆盖度（按设计用例计）：已执行 7/10 = 70.0%。
> 其中 3 条仅分配了验证方式、没有执行结果，**不计入覆盖**（若按旧口径会显示为 100.0%）。
> 仅分配未执行的分布：性能 3 条。性能/安全类当前只做到「分配」，未做到「执行」——报表不把它们算作覆盖是刻意的。

## 两个入口

| 场景 | 做法 |
|---|---|
| 独立检查 | `node scripts/coverage-split.mjs --run-id=run-xxx` → `execution/coverage-split.json` |
| 报告生成时 | 文件不存在就**现算**（标 `derived: true`，说明这不是独立存证） |

报告不能要求人先手动跑 CLI 才肯显示覆盖度——那样这段永远空着。

## 与需求完备性的分工

| 模块 | 修的是哪个分母 |
|---|---|
| 覆盖度拆分 | 「设计用例」里有多少真跑了 |
| 需求完备性 | 「设计用例」本身漏了哪些业务维度 |

前者管执行缺口，后者管需求缺口。两个都做，覆盖率才有可信度——**只做前者，分母仍然可能只覆盖了真实业务的 40%**。
