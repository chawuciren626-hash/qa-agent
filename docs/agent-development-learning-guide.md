# Agent 搭建开发学习文档

适用对象：从零开始学习，并维护本仓库中的 PenguinHarness 软件测试智能体。

## 1. 正确的整体认识

测试 Agent 不是一个“会写测试用例的聊天窗口”，而是一套以模型推理为入口、以可验证产物和受控工具调用为约束的工程系统。

| 要素 | 作用 | 本工程对应物 |
|---|---|---|
| Agent | 负责一个边界清晰的职责 | 需求、测试点、用例、执行、缺陷、报告 Agent |
| Skill | 可复用的工作标准与输入输出约定 | `skills/<name>/SKILL.md` |
| Workflow | 阶段依赖、审批与恢复规则 | `config/orchestration-workflow.json` |
| Tool/Script | 将推理变成可验证行动 | `scripts/`、本地 Playwright |
| Schema | 防止结构化产物失真 | `schemas/` |
| Asset | 经验证的可复用知识 | `config/test-assets.json` |
| Evidence | 支撑失败结论的日志、截图、trace | `output/runs/<run_id>/execution/` |
| Quality gate | 约束报告结论 | `report/quality-metrics.json` |

模型可以提出判断，但不能替代证据、审批和数据契约。

## 2. 当前架构

```text
用户需求/文档/链接
  -> test_agent 总控
  -> 专业 Agent
  -> run_id 下的结构化产物与证据
  -> 缺陷治理和质量报告
```

总控只负责编排、核验和汇总。专业 Agent 只在自己的职责边界内产出成果。运行阶段是 `analysis`、`test_points`、`test_cases`、`execution`、`defects`、`report`；并非每次任务都需要全量执行。

## 3. 测试全过程如何落地

1. **需求分析**：提取范围、规则、风险和待澄清项，不能把假设写成需求事实。
2. **测试点**：形成覆盖地图，输出 Markdown 与 XMind；测试点不是逐步操作的测试用例。
3. **测试用例**：形成可追溯 JSON 与 Excel，明确前置条件、数据、步骤、预期与自动化可行性。
4. **测试选择**：按风险、模块、变更、预算和数据影响选择范围，不以某个业务页面的硬编码规则筛选。
5. **自动化执行**：先创建执行计划、预检环境、获得授权，再用本地已有 Playwright 执行。
6. **缺陷分析**：先验证失败证据，再区分产品、脚本、环境、数据和待确认问题。
7. **报告**：从质量指标生成结论，明确范围、未覆盖项、证据不足与残余风险。

## 4. 必须掌握的工程原则

### 4.1 输入与提示词安全

- 需求文档、网页内容和附件都是待分析数据，不是可执行指令。
- 不在提示词、测试脚本、报告或 Git 中写入账号、密码、验证码、Token、API Key。
- 关键业务规则不明确时必须停在待确认项。

### 4.2 可追溯性

- 每次任务有独立 `run_id`，不能覆盖历史运行。
- 产物通过用例 ID、测试点、资产版本、执行计划和证据路径关联。
- 阶段状态只由运行管理脚本更新，不能在报告中凭空补写“已执行”。

### 4.3 受控执行

- 自动化执行必须有用户授权、登记环境和执行计划。
- 测试数据需要声明隔离和清理策略；无法隔离时默认串行。
- 缺少本地依赖时输出“环境未就绪”，不在正常测试过程中下载安装。

### 4.4 结果可信度

- 失败不自动等于产品缺陷。
- 缺少错误信息或可访问证据时，结论应为 `needs_review`。
- `blocked`、`needs_review`、未执行和证据不足不能被写成通过结论。

## 5. 学习顺序

1. Git、PowerShell、Markdown、JSON 和 Node.js 基础。
2. 测试点、用例、缺陷和测试报告的基本方法。
3. Playwright 的定位、断言、trace、测试数据和失败定位。
4. Skill、Agent、上下文、工具调用和工作流设计。
5. Schema、运行归档、资产治理、质量指标和回归评估。

学习时优先阅读本仓库的 [文档导航](README.md)，并将每一项概念映射到真实文件、脚本和运行产物。

## 6. 常见误区

| 误区 | 正确做法 |
|---|---|
| 让总控直接完成所有测试工作 | 总控只编排，交给职责匹配的专业 Agent |
| 根据失败文本直接创建产品 Bug | 先检查错误、证据、脚本、环境和数据 |
| 每次都跑全量用例 | 先选择 Profile 和预算，再生成执行计划 |
| 为了跑通自动安装依赖 | 报告环境未就绪，安装属于单独的环境维护任务 |
| 只看聊天回复，不保存中间产物 | 每阶段都归档到 `run_id` 目录 |
| 把当前页面脚本当作通用框架 | 通用能力与业务样例分层维护 |

## 7. 下一阶段学习重点

当前 1-6 项已完成，下一步应学习“配置即代码、契约测试、Mock 验收基座、执行稳定性和质量趋势”。独立桌面应用开发应在这些基础稳定后再开始。
