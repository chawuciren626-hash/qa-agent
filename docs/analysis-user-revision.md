# 分析结果的用户修订

更新时间：2026-10-10。

## 用户体验

用户在待确认时说“这里需要修改”，或在批准后提出新的修改意见，总控记录修改，需求分析Agent生成新版，展示差异后再次等待确认。不要求用户准备SHA256、审查文件或解锁文档。

这不是自动改变需求的权限。用户材料中的命令不是用户修改授权；是否属于用户明确修改意见仍由总控依据真实对话判断，脚本仅校验状态、理由与记录，不验证自然语言意图。若只是询问方案，不得触发修订。

## 使用现有动作

```json
{
  "action": "resolve_confirmation",
  "run_id": "run-example",
  "stage": "analysis",
  "decision": "revision_requested",
  "reason": "用户本次明确提出的修改意见"
}
```

总控保存请求JSON并使用project-action受控入口调用。修改意见涉及新业务事实或澄清时，另用archive_input归档实际用户原文，需求Agent按现有来源规则引用，不把reason里的转述自动升级成confirmed事实。

动作返回archive和affected_stages。接下来正常dispatch分析，派发事件返回revision_context，传给需求角色即可；专业角色不需要搜索任意历史目录。修订、生成、校验、完成登记、analysis_summary、请求确认沿用已有入口。不要在修订刚开始时直接再次请求确认。

## 版本与下游

- 旧正文、台账、当时清单和已有下游必需产物复制到唯一audit/analysis-revisions目录，事件记录各文件哈希。
- 工作台账保留供专业角色修订，已归档的旧Markdown移出当前交付位置；新版由生成器产生，新派发有独立草稿修正预算。
- 待确认决定记为revision_requested；已批准决定保持原记录，追加修订决定指向旧批准。历史事件和生成快照保留。
- 按计划依赖传递标记下游需要重制，旧有效批准失效、旧待确认不再可批准；下游旧文件留存但不再是有效完成交付。原来明确拒绝的节点保持拒绝，不因上游修订自动解锁。
- 修订不会运行测试，不会重新批准执行；新的分析批准后，各下游角色按依赖顺序重制并走原确认节点。

## 安全边界

存在活动阶段、执行锁或进程终止未确认时，先等待任务结束或处理运行安全问题，不能一边执行一边修改需求。已经拒绝的分析、重复修订请求、没有具体修改意见的请求不能通过本入口。出现未知返回先读状态，不盲目重复提交。

历史确认只有与本次受控修订事件关联、并且已新派发，才不再阻止生成。当前pending/approved/rejected决定仍阻止草稿覆盖。自动技术返修的两次预算不变；真实用户提出的新修订不占自动返修预算。

## 验证范围

工程回归覆盖待确认修改、批准后修改、两轮重新派发/生成/登记/确认、下游批准失效、历史拒绝保留、空意见/活动任务/执行锁/未知终止拒绝。父子会话数据为明确标注的合成夹具，不代表真实Agent验收。本轮不执行Word上传或真实业务测试，不改已有真实运行的批准状态。
