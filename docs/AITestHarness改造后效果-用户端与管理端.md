# 改造后效果：用户端与管理端

依据《架构重构方案 v3》第 2、4、10、11、15、17、18、24 章，结合工程现状（Windows 本机工具、`localhost:18766` 本地服务、md/docx 资料库、10 Agent + 15 Skill、七阶段编排）。
**每项能力都标了里程碑（M1~M5），不写"全部做完就怎样"的空头支票。**

---

## 0. 一句话

> **用户端从「每次让 AI 重新认识一遍系统」变成「一次建档、长期复用」；管理端从「改提示词试运气」变成「发版本、控权限、看指标」。**

七个字概括变化：**进得去、测得稳、说得清。**

---

## 1. 改造前后总对照

| 维度 | 现在 | 改造后 | 里程碑 |
|---|---|---|---|
| 进可测状态 | 给 URL+账号，agent 从零点，十几分钟没好 | 建档 10 秒出页面清单；登录片段固化后 ≤1 分钟 | M1 / M2 |
| 每次会话读什么 | 每轮读整份资料库，token 随库存线性涨 | 按 scope 切片，只喂相关条款，装载量记账 | M1 |
| 执行路径谁决定 | LLM 运行时看截图决定下一步 | 固化 DSL，重放零 LLM | M1 |
| 两次结果不一致 | 说不清是 bug 还是抖动 | 五档结论 + N=3 + 版本冻结，判 `flaky` 或 `inconclusive` | M1 / M3 |
| 失败原因 | 一段 AI 解释 | 取证包七分区 + 与上次成功的 diff | M2 |
| 资产 | 每轮从零 | 元素库/片段库/地图/回归集逐轮增长 | M2 / M3 |
| 断网 | 依赖云 | 本地全功能可跑 | M1 |
| 更新 | 整体重装 | 能力包热更 + 代码整包，页面分类型提示 | M1（框架）/ 随各 M 增量 |

## 2. 用户端（测试工程师，装在自己电脑上）

### 2.1 装完第一次打开

现状：装完不知道从哪开始，要么空着，要么随便点。

改造后：

1. 启动即连本地服务（`localhost:18766`），**不检查云端可达性**——后台挂了也能用，拉不到策略就用内置快照，并在界面标注"策略非最新"；
2. 左栏是项目列表（每个项目 = 一份资料库 + 一份环境地图 + 一套资产）；
3. 首页只有一个主动作：**新建项目**。

### 2.2 新建项目：从「填一堆表单」变成「给个地址」

| 步骤 | 用户动作 | 系统动作（零 LLM） | 耗时 |
|---|---|---|---|
| 1 | 填项目名 | 建目录：`knowledge/` `maps/` `plans/` `elements/` `evidence/` | 瞬时 |
| 2 | 贴环境地址 | `bootstrap()` 抓首页 + JS bundle（限 12 文件 / 2MB / 8MB）→ 解路由表 → 识别技术栈 → 探登录表单与验证码类型 → 探 OpenAPI（6 个常见路径）→ 扫危险文案 | **10 秒级** |
| 3 | 上传或粘贴需求文档（md/docx） | 解析章节树 → 条款化（**无原文位置即丢弃**）→ 按 statement 去重 → 出知识缺口清单 | 秒级 |
| 4 | 看报告 | 建档报告：路由 N 条、接口 M 个、登录方式、验证码类型、**未建档页面 K 个**、`next_steps` 渲染成向导 | — |

**用户能感知到的差别**：以前这一步是 agent 点着看，现在是一份清单直接摆出来，而且**明确告诉他哪些页面还没建档**——不是假装全都认完了。

> 诚实边界：建档只做静态抓取，拿到的是「路由 + 接口 + 登录特征」，**控件清单要等探索阶段**。界面上不会写"已识别全部控件"。

### 2.3 两条入口，不再硬塞进同一条链

这是上次演示翻车的直接原因：只有"从需求开始"这一条路，于是"只有 URL+账号"的场景被硬塞进七阶段，前三阶段凭空产出。

| 入口 | 适用 | 用户看到什么 |
|---|---|---|
| **A. 从需求开始** | 有 PRD / 迭代需求 | 需求 → 测试点 → 用例 → 计划 → 执行 → 缺陷 → 报告，每步有确认卡点 |
| **B. 从地址开始（探索）** | 无需求，只有环境 + 账号；新系统摸底 | 建档 → 结构巡检 → 功能试触 → 固化沉淀，**跑完给探索度报告** |

### 2.4 探索模式：这次是"有边界地看"，不是"撒手让它点"

用户点了「开始探索」之后：

```
① 环境建档    零 LLM，10 秒，出路由清单
② 结构巡检    广度优先，≤50 页，每页 LLM ≤2 次，只登记不深入
③ 功能试触    ≤10 页，每页 ≤5 次动作，只在首页/一级导航/用户指定入口
④ 固化沉淀    应用地图 + 元素库 + 登录片段 + 首版测试点 + 待探索队列
```

**关键：达到预算就停，不管还剩多少没试。**

用户看到的是「探索度报告」而不是「跑到一半崩了」：

> 巡检覆盖 38/52 页 · 试触 8/10 页 · 未探索 14 项 · 建议下轮重点：订单管理、报表导出

**这就是上次"十几分钟 100 万 token 还没进去"的解药**：不是模型变聪明了，是预算由工程定死，不靠模型自觉。

**危险动作白名单**（产品级功能）：删除、批量改、支付、发消息这类动作默认禁止，要探索得用户显式放行——避免在客户环境里点出事故。

### 2.5 日常测试循环：每一步都有一道闸拦住 agent

| 阶段 | 用户做什么 | 程序强制什么（agent 越不过去） |
|---|---|---|
| 需求分析 | 上传文档，看条款清单 | 每条必须挂原文位置，**没位置直接丢弃**；每条打模块标签（自动跳过 `api/v1` 噪声段） |
| 测试点 | 看矩阵，补空格子 | **矩阵由程序算**（控件×维度），agent 只填空缺；验证方式强制分配（业务逻辑→接口，呈现→UI），接口可验却被分到 UI 的比例 >30% 报警 |
| 用例 | 审用例 | 断言必须回指测试点预期（不许看页面反推）；条数预算 N+1 硬限；枚举清单双向对账找漏 |
| 固化 | 看一眼计划，改两行 | **五道闸**：元素库命中 / matcher 白名单 / 断言来自测试点 / 无空步骤 / 重放已验（N=3 回填） |
| 执行 | 点"跑" | 重放零 LLM；五档结论；observe/decide 断言分级；等待条件封闭枚举（禁 driver 专有写法） |
| 缺陷 | 看缺陷单 | 证据包由程序组装（不是 agent 编）；去重指纹 = 失败断言 + 目标元素 + 异常签名 + 环境键 |
| 报告 | 看报告 | **数字只读**（全部来自 exec IR，agent 不许改写）；洞察必须挂引用；允许空输出 |

**用户能感知到的差别**：以前是"AI 说它测完了"，现在是"每一步都有东西拦着它，拦不住的就是真问题"。

### 2.6 回归与上线节奏

现状：没有回归集，改一版全量重跑或者凭感觉挑。

改造后：

- **五触发源选题**（可解释，每条给理由）：显式指定 / 需求变更 / 代码变更（touched 页与接口）/ 片段依赖 / 历史相似；
- **三档选集**：smoke（冒烟，flaky 率必须 0、语义断言禁入）/ core / full；
- **执行前报未建档页面**：`scope_coverage` 直接告诉用户"这次要测的 3 个页面还没建档，结果可能不准"；
- **地图过期提醒**：`maps_staleness` 超 14 天或检测到版本变更 → 提示重跑建档（10 秒，成本极低）；
- **flaky 判定**：同计划 + 同环境 + 同数据 + **同版本**跑 N 次，版本一变不算 flaky，判 `inconclusive(version_changed)`。

**准入结论**不再是"通过率 85%"，而是带置信度的组合判断：哪些是稳定通过、哪些是抖动、哪些是版本变了没法比。

### 2.7 更新体验：两种提示，边界划死

用户看到的只有两种卡片：

| 卡片文案 | 触发条件 | 用户动作 |
|---|---|---|
| 「发现新版本客户端」 | 引擎 / Driver Adapter / 校验器 / DSL 解释器 / 探索器 **任一 `.py` 变更** | 下载安装包，覆盖安装 |
| 「发现能力更新」 | 提示词 / skill 定义 / 分权表 / 阈值 / 白名单 / 控件×维度映射 / 片段库 / 审阅口径 | 一键拉取，**不用重启** |

**为什么工具代码绝不热更**：工具、DSL schema、IR 契约三者必须同版本；单独替换一个 `.py` = 制造一个从未测试过的组合。判据一句话——**能被 `import` 的代码一律走整包。**

用户感知：以前"小更新"也得重装，现在策略调优、提示词改版这类高频调整不用动安装包。

### 2.8 用户端「不会变」的部分

现有工程做对的地方**全保留**：十个业务 Agent 一个不砍、七阶段编排不动、三层任务模式（task/lifecycle/staged）不动、结构化动作/工具守卫/派发回执/阶段状态机/attempt 账本/产物 Schema/设计冻结/文件哈希这一整套治理机制不动。

改的是**权限**，不是角色：

| 收什么 | 做法 |
|---|---|
| 输入来源 | agent 只能吃上游 IR，不许自由读原始材料自行总结 |
| 输出格式 | 必须过 schema 硬校验，不合格即阻塞 |
| 决策权 | 阶段派发交给状态机，agent **不能决定跳过阶段** |
| 自由空间 | 能形式化的一律下沉为程序（矩阵、checklist、边界值字典） |

## 3. 管理端（发布者，一套云后台，单租户多用户）

### 3.1 管理员的一天

| 时段 | 做什么 | 在哪 |
|---|---|---|
| 早上 | 看昨晚的用户执行统计（用例数、通过率、flaky 率、版本分布） | 后台看板 |
| 上午 | 改一条阈值 / 换一版测试点提示词 → 发能力包（灰度 10% → 全量） | 能力发布页 |
| 中午 | 有用户报"结果不对"→ 查审计日志：昨天谁改了哪条策略 | 审计日志 |
| 下午 | 引擎改了代码 → 打整包、签名、发版；用户端弹"发现新版本客户端" | 版本管理 |
| 随时 | 给新同事开账号、配权限（有没有 App 测试权限） | 账号权限 |

### 3.2 能力发布：三档，各有各的通道

| 档 | 内容 | 分发方式 | 管理员操作 |
|---|---|---|---|
| **① 内置安装包** | 校验器（irval）、Driver Adapter、DSL 解释器/固化编译器、探索器本体——**所有能被 import 的代码** | 随客户端整包 | 打版、签名、发版；**不能热更** |
| **② 服务端下发** | 分权表、阈值、白名单、matcher 表、控件×维度映射、弹窗策略链、agent 提示词、审阅口径 | 能力包（manifest + 签名 + 版本区间） | 编辑 → 灰度 → 全量 → 随时回滚 |
| **③ 依赖下载** | Playwright 内核、Appium 驱动、小程序调试桥、OCR | 首次使用按需下载，落本地缓存 | 只管声明兼容版本 |

**判据**：能被 `import` 的一律发整包，纯数据/声明/提示词才热更。想知道某个改动要不要发版，看它是不是代码。

### 3.3 权限：能力下发按账号过滤

不是"发下去再限制"，是**没权限就不下发**——没有 App 测试权限的账号，连 native 驱动依赖包都拿不到。既省带宽，也避免"装得上却用不了"的困惑和越权尝试。

三处隔离都不靠"能力包 scope"实现（manifest 的 `scope` 恒为 `global`）：

| 维度 | 做法 |
|---|---|
| 权限 | 能力下发按账号权限过滤 |
| 数据 | 每台机器资产库各自独立，**控制面只收统计与状态，不收 IR、不收取证包** |
| 偏好 | 用户级配置（默认环境、阈值覆盖）存本机，不进能力包 |

### 3.4 审计：单管理员更要不留白

记录四类事件，不可删改：

- 谁、何时、发布了哪版能力包（含 manifest 摘要与签名）；
- 改了哪条阈值 / 白名单，改前值改后值；
- 回滚了什么，回滚到哪一版；
- 谁开了账号、提了什么权限。

**理由**：出事故时唯一能回答"这次失败是不是我昨天改的那条策略引起的"的就是这份日志。发布者只有一个人，没有第二双眼睛，日志就是那双眼睛。

### 3.5 看板口径：只收统计

| 收 | 不收 |
|---|---|
| 用例数、通过率、flaky 率、平均耗时 | DOM 快照 |
| `engine_version` / `schema_version` / `capability_versions` 分布 | 请求/响应正文 |
| 错误码计数、阻塞原因分类 | 截图、录屏 |
| 资产积累量（计划数、元素数、知识条款数） | 账号会话、cookie |

**这条对金融/政企客户是一票否决项**，也是"本机工具"区别于"云测试平台"的分界线。数据不出域。

### 3.6 管理端明确不做的事

- **不执行任何测试**，不接触被测系统；
- 不保存用户产出的 IR 与取证包；
- 不做"云端跑一遍给你看结果"；
- 不为内网离线包开"免签名/免校验"后门（要离线就整包拷，校验照做）。

### 3.7 未来转多租户的预留

给 manifest 加 `scope: tenant|project`、改后台数据模型即可，**客户端协议与校验链完全不变**（`requires_engine` 兼容性门与签名机制与租户数无关）。

## 4. 可汇报的量化口径

按方案 §20.2 的排序，**token 不放第一位**——它是结构化之后的自然结果，不是目标。

| 优先级 | 指标 | 改造后目标 | 里程碑 |
|---|---|---|---|
| 1 | 同用例 N=3 一致性 | 100% | M1 |
| 2 | 首次执行通过率（不含重试） | 建基线后逐季提升 | M2 起 |
| 3 | 需求→用例覆盖率 | 可计算、可对账（V-33） | M1 |
| 4 | 缺陷召回率 / 误报率 / 错误通过率 | 召回 70%+ / 错误通过 ≤5%（种子缺陷集） | M3 |
| 5 | flaky 率、隔离区存量 | 可度量、可归因到五类根因 | M3 |
| 6 | token 与耗时 | 建档 10 秒；探索受硬预算约束；重放零 LLM | M1 / M2 |
| 7 | 资产积累量 | 逐轮单调增长（这是护城河证据） | 持续 |

**三次演示三个主张**（方案 §20.3）：

1. 冷启动：给 URL + 账号 → 1 分钟内进可测状态 → 出应用地图。主张「**进得去、看得见**」
2. 可复现：同一用例连跑 3 次 → 结果一致 + 取证包 + diff。主张「**测得稳、可归因**」
3. 有效性：种子缺陷集 → 召回 70%+ / 错误通过 ≤5%。主张「**测得准、能量化**」

**永不再演示**：无预算的开放式探索——那就是上一次翻车的场景。

## 5. 诚实的边界（改造后仍然做不到的）

| 做不到 | 原因 | 什么时候能解决 |
|---|---|---|
| 建档就拿到控件清单 | 静态抓取只能拿路由和接口，控件要真实渲染 | M2（探索阶段②） |
| 无需求也能出高覆盖率用例 | 探索是"看一眼登记"，不是理解业务 | 永远做不到，这是产品边界 |
| App / 小程序 / Web UI 执行 | 四类 Adapter 只有接口先行落地 | M2 |
| 缺陷自动修复 | 明确不做——偶发 bug 要上报，不许自动改脚本掩盖 | 永不 |
| 云端代跑 | 执行面只在本地 | 永不（数据不出域是硬约束） |
| 模型能力不够时照样出好结果 | LLM 能力取决于用户自己配的模型；差模型走降级，`manual` 档直接转人工 | 靠 `plan_tasks(tier)` 兜底，不靠祈祷 |

**最后一句话**：改造不是把 AI 变强，是**把"什么算对"提前写死、"探索"加上硬预算、"稳定"用 N=3 验收**。这三件事做完，用户才敢把它放进自己的迭代节奏里。
