# 下游技术返修与重新导出

## 用法

专业角色在当前派发中通过project-action提交JSON请求。例如：

```json
{"action":"export_test_cases","run_id":"run-example"}
```

| 阶段 | 动作 | 产物 |
| --- | --- | --- |
| 测试点 | export_test_points | XMind，来源为test_points.json |
| 测试用例 | export_test_cases | Excel，来源为test_cases.json |
| 缺陷分析 | assess_evidence、normalize_defects | 证据评估与标准缺陷记录 |
| 测试报告 | build_report_metrics、export_report | 度量、reportable-results、Word/PDF |

路径由入口按run固定推导，用户无需提供脚本参数。先生成所需结构化源文件，再调用对应动作。报告先刷新度量、编写Markdown，再导出。生成成功后仍须validate_artifacts，子Agent返回后由总控登记完成，按原规则请求业务确认。

## 修正策略

只有进程已确认结束的普通生成失败可返回artifact_revision：recovery.retry_allowed=true时，原专业角色可以修正JSON格式、字段或导出输入后再次调用。取消固定追加次数；累计失败保留，成功清除连续失败提示。连续相同请求和诊断无进展时stalled=true，应改变方法或报告部分结果，不锁定动作，不让用户提交解锁文档。详见draft-revision-budgets.md。

超时、中断、未知终止、缺失运行时、实际越权写入、当前待确认/已批准/拒绝状态以及上游证据变化不会获得此技术修正许可。若子Agent已返回且产物确需修改，沿用总控revise_stage和新派发流程，不伪造继续工作的子会话。业务修改或已批准内容更改仍走用户决定，不借技术动作覆盖。

必交产物及可选阅读版由阶段注册表定义，写入前守卫与交接共用规则。明确匹配的原生拒绝记录证明写入未执行，或宿主request_end证明流式参数解析失败且未进入工具时，不再将这些历史尝试当成实际越权。没有回执本身不构成未执行证明；真正交接仍需当前产物校验、正确父子派发和已完成的子任务。普通草稿revise_stage先保存原字节快照，再更新状态，工作文件保留在原路径；新派发按问题局部修订。既有审计不删除，业务执行与人工决定边界不变。

## 留档与边界

每次调用在audit/artifact-generations下独立保存调用前的已存在输入/输出、调用后的输出及哈希、派发身份和命令证据。缺失项明确标记，空文件和损坏文件也留存。该快照记录调用时的实际字节，不保证包含此前每一次文件工具编辑，也不代表旧文件已验证。

命令失败后不把部分产物当作完成，不自动回滚或清除失败文件；下一次重导出前再次快照。持有运行锁期间执行生成，避免正式确认与导出同时修改状态。当前完成产物、确认和审批不会由本入口修改。

缺陷归一化仍使用原生命周期登记逻辑。已登记观察不得改写或静默移除；遇到冲突必须保留原记录并走治理流程，不反复改ID或删除lifecycle.json。跨运行缺陷索引/趋势不属于本项重试许可，旧直接CLI也不会因此被泛化为可自动重试。

## 验证边界

工程夹具覆盖XMind/Excel失败后修正、Word/PDF度量失败后重导出、缺陷处理、快照留存、回执、预算、当前确认和所有权拒绝及中断停止。测试会实际运行本机导出脚本，但不是实际业务测试或真实Agent端到端验证，也不能替代WPS/XMind客户端打开和版式检查。工程验证不修改现有真实运行。
