# 独立任务并行与调度误停修复

更新日期：2026-10-13。

## 本次根因

会话session-2026-10-13-15-55-23-47f27109先登记execution，再登记test_cases。入口只检查待派任务自身，底层却仍要求整个run只能有一个in_progress阶段。第二次登记因此抛出“Another stage is active in this run”，被当作脚本事故写入全局stopped。接下来的执行子Agent调用被守卫拒绝。

这不是浏览器超时、真实测试失败或用户缺少批准。检查时子会话事件为零，实际浏览器尚未启动。总控随后多次查找内部恢复文件，进一步浪费了用户等待时间。

## 工程调整

- 独立task的不同专业任务可同时在执行中；同一阶段仍禁止重复派发。lifecycle保留依赖顺序，但调度冲突由入口预检，不升级成全局停止。
- 委派守卫按明确的dispatch_id选择任务，不再要求run只有一个活动阶段。子会话还须匹配角色、原始派发提示和原生工具返回记录，不能仅凭时间重叠或对话文字猜测归属。
- 控制器修改命令内部排队，短时状态文件锁重试只发生在进入操作前；不重复执行产品动作。未知中断、停止状态或已死亡的拥有进程不能借排队绕过。排队取消不会执行该动作。
- 真实运行中的已知命令不阻止其他有效子派发；未知运行状态仍保留诊断。尚未返回的子任务不作为交付审查错误；多个已返回任务逐个交接，不要求用户处理“多个待交接”。
- 派发时记录可用已完成来源，后续并行任务完成不会悄悄改变当前任务的输入契约。报告导出与校验使用同一来源快照，不能偷读另一个Agent的未交付草稿。

## 使用原则

并行不是强制。根据已提供需求写用例可以与页面探索并行；若用例依赖探索到的交互，或者报告需要本轮执行结果，应由总控先等对应产物，再派发消费它的任务。用户无须确认锁、阶段编号或技术顺序。

各任务中的浏览器操作仍受同一浏览器会话约束；本轮没有增加浏览器多开、重复提交或绕过产品授权的能力。

## 原会话恢复

核实失败命令正常终止、拒绝发生在清单修改和子任务启动之前后，工程侧使用已有审计恢复入口将控制器恢复为ready。原清单哈希不变，执行派发保留，用例与报告仍为planned，旧失败记录保留。未启动产品测试，未伪造完成或新增用户授权。用户无需重建会话或提交恢复材料。

## 验证边界

专项使用真实结构化命令、真实文件锁与合成父子Agent轨迹，覆盖并行登记、重叠子调用绑定、独立交接、排队取消及生命周期冲突。该验证不是PenguinHarness模型端到端产品测试，目标功能仍未在这次误停会话中执行。

工程回归203项通过，独立任务及交互专项12项通过；新增调度专项还覆盖两个独立Node进程争用同一控制器、多个已返回任务逐个交接、来源快照不漂移，以及清单一致但控制器stopped时的准确提示。启动前取消不会改变控制器状态；真正已启动后的中断仍保留停止保护，不自动重复产品操作。
