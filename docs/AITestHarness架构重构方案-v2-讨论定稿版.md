## 1. 问题诊断：为什么必须重建而不是修补

### 1.1 现状（依据 codex 交接文档《aitestharness-current-architecture-workbuddy-handoff-2026-11-11》）

- Windows 本机安装工具，桌面端 + 本机 Web 共用本机服务（`localhost:18766`），浏览器在本机/内置，明确**不迁入 WSL 沙箱**；
- 已有 10 个业务 Agent、15 个 Skill、七阶段编排（analysis→test_points→test_cases→execution/api_execution→defects→report）；
- 已有大量治理机制：结构化动作、工具守卫、派发回执、阶段状态机、执行 attempt 账本、产物 Schema、来源台账、设计冻结、文件哈希、缺陷生命周期、报告证据校验；
- 自评：**真实测试有效性基线未建立**（无固定项目、无种子缺陷集、无召回/漏报/误报/错误通过率）。

### 1.2 领导反馈（2026-11 演示）

- 场景：给一个内网系统地址 + 账号密码，做**登录功能**探索性测试；
- 只跑了**执行阶段**，耗时十几分钟、消耗 100 万+ token，**未能完成**；
- 结论：“不如直接用通用 agent（codex）”，并要求“自己写工具插件优化执行流程”。

### 1.3 诊断结论（本次讨论的核心判断）

1. **现状是「运行期审计」，不是「编译期结构化」**。阶段校验、产物合同、派发回执都是 LLM 跑完之后的检查。
   审计再严也不能改变执行本身是概率性的事实 → **两次执行结果不一致是必然，不是 bug**。
2. **探索与执行没有分离**。每次执行都在重新探索，所以既慢、又贵、又不可复现。
3. **失败根因分两层**：
   - 工程层：登录、验证码、环境准备这类确定性工作交给了 LLM；
   - 产品层：**没有验证过“到底能测出什么”**（无基线、无种子缺陷集），导致“流程完成”被误认为“测试有效”。
4. **缺口清单**（现状完全没有或形同虚设）：
   - 编译层（阶段之间只传文本，没有真正的 IR 与硬校验）
   - 元素库（跨用例共享的稳定定位）
   - 执行计划资产（可读、可改、可 diff、可版本化）
   - 回归集与影响分析（用例生成完就结束，没有“跑哪些、凭什么叫没问题”）
   - flaky 治理（attempt 账本把“重试成功”当成了通过）
   - 探索模式（无需求输入时如何产出，无定义）

## 2. 核心模型：探索 — 固化 — 重放

这是整个重构的心脏。

| 阶段 | 执行者 | 频次 | 特征 |
|---|---|---|---|
| **探索 Explore** | LLM 主导，允许慢、允许贵 | 一次性 / 局部 | 摸清页面结构、交互路径、登录方式、数据依赖，产出“事实”（轨迹） |
| **固化 Compile** | 程序为主 + LLM 辅助翻译 | 一次性，可重入 | 把轨迹编译为执行计划：步骤 + 元素指纹 + 断言 + 数据引用；过五道硬闸 |
| **重放 Replay** | **纯代码，零 LLM** | N 次 | 按计划执行，路径完全一致，成功失败可归因 |

### 2.1 已确认的准确表述（重要，勿再退回旧说法）

> **不是“探索只做一次”，而是“执行进程里不允许探索”。**
> 约束对象是**执行进程**，不是**资产生命周期**。资产是活的：允许人改、允许局部重探索、允许增量新增。

### 2.2 与行业实践（录制→调整→增量→回归）的对应关系

- 用户/行业实践：首次录制脚本 → 人工调整 → 后续迭代在原始脚本上做增量修改 → 上线前跑回归；
- 本方案与此**完全相容**：执行计划就是“脚本”，重放就是“跑脚本”，增量维护就是“改计划”；
- 差异在两点：
  1. 脚本由机器**从探索轨迹生成**（人不必从零写），且**人可读写可改**；
  2. 录制回放在业界失败两次（Selenium IDE / 低代码录制）的根因是**录了“位置和操作序列”，录不出“意图和断言”**；本方案用「意图 + 多指纹 + 可判定断言」解决，并明确 **断言来自测试点/需求，不能从鼠标动作反推**。

### 2.3 三层定位（与通用 agent 的本质区别）

> **把 agent 当“写脚本的人”（只写一次、持续复用），而不是当“执行测试的那个进程”（每次从头摸索）。**

通用 agent 只做探索层，每次从零开始；本产品的价值增量在固化层与重放层。

## 3. 架构：四层 + 单执行引擎

```
入口层    桌面端 / 本机Web / CLI / 定时调度     ← 全部连本机服务，单一执行节点
   ↓
决策层    探索器 · 归因器 · 语义断言器          ← LLM 仅此一层，每步留痕
   ↓
编译层    各级编译器（需求→测试点→用例→执行计划）+ 硬校验闸
   ↓
资产层    IR / 执行计划 / 元素库 / 片段 / 数据字典 / 回归集   ← 可版本化、可 diff
   ↑
执行引擎  本机 Playwright 进程 · 步骤执行器 · 断言 · 取证 · 自愈 · 一致性检测
```

### 3.1 已确认的架构决策

1. **不做服务端无头浏览器集群**。执行只有一个节点：本机服务。桌面端 / 本机 Web / CLI / 调度都是入口，不是不同通道。
2. **“双通道”改为“同一引擎的两种显示模式”**：演示与人工接管时有头 + 高亮 + 录屏；批量回归时无头。**不因场景不同造两套执行器**。
3. **决策层是唯一允许 LLM 的地方**，且该层**不能修改资产中已固化的部分**，只能产出“待编译的候选”。
4. **编译层是新增核心**，也是现有工程最大的缺失。

### 3.2 各阶段的确定性边界

| 阶段 | 程序（确定性） | LLM（决策） | 产物 |
|---|---|---|---|
| 需求分析 | 文档解析、条款切分、接口 schema 抽取 | 隐含约束识别、可测性判断 | 需求项 IR |
| 测试点 | 知识库检索、维度矩阵匹配、覆盖度计算 | 知识库未覆盖处补齐 | 测试点 IR |
| 用例生成 | 模板填充、数据工厂、覆盖校验 | 断言语义表述、步骤意图描述 | 用例 IR |
| **执行计划编译** | **步骤结构化、指纹生成、可执行性校验** | **仅辅助补 selector / 命名意图** | **执行计划** |
| 执行 | **全部（重放零 LLM）** | 仅未固化路径探索 | 结果 IR + 取证包 |
| 缺陷分析 | 取证包组装、去重匹配、模板渲染 | 根因分类 + 置信度 | 缺陷 IR |
| 报告 | 指标聚合、准入判定、模板渲染（**数字唯一来源**） | **审阅**：风险识别 + 监控建议（必须挂指标/证据 ID，不得生成数字） | 报告 + 风险台账 |

### 3.3 阶段可单独执行（保留现有设计意图）

保留“只跑某一阶段”的口子（实际工作中确实存在），但**必须满足前置产物契约**：只跑执行阶段 = 消费已有执行计划；只跑报告 = 消费已有结果 IR。**不允许缺前置产物时由 LLM 现场编造**——这是上次演示翻车的机制根源。

## 4. 执行计划 DSL 规范

### 4.1 形态选择（已定）

**采用 YAML/DSL + 编译成代码执行**，即：**DSL 是源码，编译产物是确定性指令树（或 Playwright 脚本）**。
理由：人可读可手改（做增量维护）、机器可硬校验（schema + 闸门）、规避“LLM 直接生成代码”的幻觉风险（LLM 只生成 DSL）。

| 备选 | 结论 |
|---|---|
| 机器 JSON | 否决：人无法改，无法做增量 |
| LLM 直出 Playwright 代码 | 否决：幻觉风险高、diff 噪声大、难以做意图级差异 |
| **YAML/DSL + 编译** | **采纳** |

### 4.2 固化什么、不固化什么

| 不固化（脆弱） | 固化（稳定） |
|---|---|
| 屏幕坐标 | 语义意图（“在用户名输入框填写账号”） |
| XPath / CSS 绝对路径 | 多指纹定位集合（按优先级） |
| 操作序列号的连续性 | 可判定的断言 |
| 硬编码的值 | 数据引用（多环境/多数据集复用） |

### 4.3 计划骨架（示例，可直接作为实现参考）

```yaml
case_id: CASE-00123
title: 登录 - 错误密码提示
source:                              # 强制溯源，防"不知从哪冒出来的用例"
  requirement: REQ-045
  test_point: TP-045-2
  compiled_from: explore-20261113-1420
touched:                             # 探索轨迹自动提取，用于影响分析
  pages: [/login, /dashboard]
  apis: [POST /api/auth/login]
environment:
  target: internal-login-env
data:
  username: ${account.user}
  password: ${invalid_password}      # 引用数据工厂，禁止硬编码
steps:
  - id: s1
    intent: 打开登录页
    action: goto
    target: {url: /login}
    assert:
      - {type: url_contains, value: /login}
      - {type: visible, target: {testid: login-form}}
    critical: true

  - id: s2
    intent: 在用户名输入框填写账号
    action: fill
    target:
      locators:                      # 多指纹，按优先级降级
        - {testid: login-username}
        - {role: textbox, name: 用户名}
        - {label: 用户名}
        - {css: "input[placeholder*=账号]"}
    value: ${data.username}
    assert:
      - {type: value_equals, expected: ${data.username}}
    critical: false

  - id: s3
    intent: 点击登录按钮
    action: click
    target:
      locators:
        - {testid: login-submit}
        - {role: button, name: 登录}
    wait: network_idle
    assert:
      - {type: text_visible, value: 密码错误}
    critical: true

teardown:
  - {action: reset_session}
```

## 5. 固化编译器：五道硬闸

固化的目标不是“把轨迹抄下来”，而是**把轨迹升级为可信资产**。五道闸任何一道不过，不允许入库。

| 闸 | 校验内容 | 不通过处置 |
|---|---|---|
| 1. 定位闸 | 每个 locator 在快照中**唯一命中**；多指纹必须指向同一元素 | 打回，重新挑指纹 |
| 2. 断言闸 | 关键步骤必须有**可判定**断言；语义断言须给结构化判断依据 | 打回，不允许无断言固化 |
| 3. 数据闸 | 禁止硬编码敏感值/环境相关值，必须引用数据字典 | 自动替换为引用 + 提示补字典 |
| 4. 溯源闸 | 必须挂到需求项/测试点（探索模式例外，见 5.2） | 标记“探索性”，不进正式回归集 |
| 5. **一致性闸** | **固化后立即重放 N=3 次，结果必须一致且成功** | 打回，不允许“编译成功但跑不稳” |

> 第 5 闸是整个方案的枢纽：它把“编译正确”与“实际可跑且稳定”硬绑定，同时是 flaky 的第一道拦截。

### 5.1 LLM 在固化中的合法边界（红线，勿放宽）

**只允许两件事，都是“翻译”不是“创作”**：
1. **意图命名**：把 `click(#btn-3)` 翻译成“点击登录按钮”（人类可读，元素失效时也能理解原意）；
2. **断言推荐**：依据“操作前后状态差异”推荐断言候选（如点击后出现“密码错误” → 推荐 `text_visible`），**必须标注为候选，需规则/人确认**。

**禁止**：
- 自行增加/删除步骤；
- 自行改变动作类型；
- 自行编造预期结果。

（一旦放开，固化就退化为“又一次生成”，前面所有工作白做。）

### 5.2 探索模式的特殊处置

无需求输入时（领导演示场景）：产物为「应用地图 + 首轮测试点 + 待固化轨迹」，`source` 标记 `exploratory`，**不进入正式回归集**，但完全符合“探索→固化”链路。待人工归类后升级为正式用例。

## 7. 已确认的三个设计决策

1. **DSL 支持人工从零手写**（不探索也能写计划）——让老测试工程师直接迁移经验，产品不排斥人。
2. **执行计划支持片段复用**（登录等作为共享片段被 N 条用例引用）——否则 500 条用例要维护 500 份登录步骤。
3. **断言粒度分级**：**关键步骤强制可判定断言，普通步骤只记录状态不判定**（避免断言冗余与误报）。

### 7.1 关键步骤的判定规则（防止 LLM 全标关键）

- 来自“正常流程类测试点” → 默认关键；
- 来自“数据校验类测试点” → 强制关键；
- 导航/填充/跳转等支撑性步骤 → 默认非关键；
- **允许人工覆写**。

### 7.2 三个必须警惕的副作用与对策

| 副作用 | 对策 |
|---|---|
| **片段隐式耦合**（改一处炸 500 条） | ①片段契约化：对外只暴露入参和输出（会话状态），内部实现自由；②修改前自动列出受影响用例清单；③**版本化 `login@1` / `login@2`**，存量继续引用旧版本，按批升级 |
| **“关键步骤”判定权失衡** | 见 7.1 规则，LLM 不参与判定 |
| **人工手写计划质量不可控** | **人工计划必须过同一套五道闸**，不因“人写的”就放行 |

## 8. 回归集与影响分析（已确认）

### 8.1 回归集要回答三个问题

1. 这次该跑哪些？（选集）
2. 跑完之后能否说“没问题”？（置信度）
3. 没跑的用例风险是什么？（覆盖缺口）

只回答第一个问题的系统，在真实团队里会被质疑“只跑 30 条就敢上线？”

### 8.2 选集触发源（按可靠性排序）

| 触发源 | 输入 | 可靠性 |
|---|---|---|
| ① 显式指定 | 人勾选用例/目录 | 最高 |
| ② 需求变更溯源 | 需求项变更 → 关联用例 | 高 |
| ③ **依赖传递** | 用例引用的片段变更（`login@1` → 命中全部引用者） | 高 |
| ④ 代码变更影响 | 改动 → 模块/接口 → 命中 `touched` 的用例 | 中高 |
| ⑤ 历史相似 | 向量检索相似用例（兜底补漏） | 中 |

**纪律：选集结果必须可解释**——每条给出理由（`source:REQ-045` / `fragment:login@1 变更` / `touched_api: POST /api/order`）。可解释性是团队信任的前提。

### 8.3 分层回归（三道闸，非“大中小三档”）

| 层 | 时机 | 时长预算 | 内容 | 判定标准 |
|---|---|---|---|---|
| Smoke 冒烟 | 每次构建/部署 | ≤ 5 分钟 | 核心链路 20~50 条 | 只判通/不通，不通即阻断 |
| Core 核心 | 每日 / 提测 | ≤ 1 小时 | 主流程 + 本次影响范围 | 失败需 triage（bug/脚本/环境） |
| Full 全量 | 上线前 / 夜间 | 数小时，可分片 | 全部可信用例 | 生成上线准入报告 |

三条纪律：冒烟集必须小而稳（flaky=0，否则团队会绕过）；核心集按变更动态生成；全量集必须支持分片并行（本机多浏览器上下文）。

> 修正一个行业常见误解：“每次上线跑全部脚本”在真实团队多数做不到（全量跑不动）。真实做法是**按影响范围选回归集**。

### 8.4 置信度与准入结论

| 指标 | 算法 | 回答什么 |
|---|---|---|
| 需求覆盖率 | 本次变动需求项中有执行用例的比例 | 改的东西测了吗 |
| 影响覆盖度 | 受影响用例中实际执行的比例 | 波及的东西测了吗 |
| 资产健康度 | 执行用例中非 flaky、非跳过、非长期失败的比例 | 测的可信吗 |

准入结论：
- 三项达标 → 可上线；
- 需求覆盖达标但影响覆盖不足 → 有条件上线（列出未测风险）；
- **资产健康度低于阈值 → 不能给出结论**（先修资产，不是先上线）。

> 第三条是“诚实性设计”：宁可说“我的用例不可信”，也不虚报“全部通过”。

### 8.5 影响分析的关键发现（已确认）

**`touched`（触达页面/接口）由探索轨迹自动提取，是最优主数据源**：
- 探索轨迹天然记录访问过的 URL 与接口，编译时顺手写入，**零额外维护**；
- 重放时**自动刷新 `touched`**，映射始终与真实执行一致（资产随执行自更新）——这是传统自动化做不到的（脚本里没有此信息）；
- 辅以需求项打模块标签做粗粒度补充。

## 9. flaky 治理（已确认）

### 9.1 定义

> flaky = **同一份执行计划、同一环境、同一数据**，连续执行 N 次，结果不一致。
> 任何一项变化都不算 flaky（分别归入数据问题/环境问题/用例错误）。

| 现象 | 性质 | 处置 |
|---|---|---|
| 同条件 3 次 2 过 1 败 | flaky | 标记，禁止进入可信结论 |
| 数据变化导致失败 | 数据问题 | 数据工厂 / 隔离 |
| 环境抖动 | 环境问题 | 健康检查 + 重试 |
| 稳定失败但功能正常 | 用例错误 | 修资产 |
| **稳定通过但功能实际是坏的** | **错误通过（最危险）** | 断言缺失，必须补 |

### 9.2 五大根因（对因不对症）

| 根因 | 处理方式 |
|---|---|
| 同步失效（最常见） | 智能等待（网络空闲 + 元素稳定态），**不是 sleep、不是重试** |
| 定位歧义 | 定位必须校验唯一性，多命中即拒绝执行 |
| 数据污染 | 用例级数据隔离 + teardown 复原 + 唯一数据生成 |
| 时序竞争 | 显式等待业务信号（特定请求完成），而非时间等待 |
| 环境不稳 | 环境健康检查前置 + 归因到环境 |

> **flaky 是要治的病，不是能盖的症状。** 重试只会把“偶然通过”混进“通过”，让结论彻底不可信。业界要求 flaky 率 < 5%（SRE 视角要求 0）。

### 9.3 检测三步

1. **入库一致性检测**：新用例/变更用例入库前必跑 N=3；不一致直接打回。已入库用例按周期抽样重跑（每周核心集）。
2. **重放期可疑信号（零成本顺带记录）**：命中降级定位、等待超阈（>3s）、发生重试、断言通过但控制台/网络异常、时长波动 >50%。
3. **分类归因**：复用取证包（截图/DOM/网络/控制台/轨迹/历史结果）+ LLM 分类五类根因 + 置信度，低置信度转人工。
   **红线：LLM 只做分类，不做“通过与否”判定。**

### 9.4 生命周期与隔离区

```
新用例 → 一致性闸(N=3) → 入库
   ↓ 重放中出现不一致
标记 flaky(置信度/根因候选) → 自动降级：移出冒烟/核心集
   ↓ triage
A 修资产（定位/等待/数据）→ 重跑 N=3 通过 → 恢复
B 判定真实偶发 bug → 转缺陷单，标记"预期不稳定"
C 无法修复 → 隔离区 quarantine（不进任何回归集，超期提醒/升级）
```

### 9.5 指标

| 指标 | 阈值 |
|---|---|
| Flaky 率 | < 5%，冒烟集 0 |
| 错误通过风险数（无关键断言用例） | 0 |
| 隔离区存量 | 持续下降 |
| 平均修复时长 | < 5 工作日 |
| **首次执行通过率** | 真实健康度（**禁用“含重试的最终通过率”**） |

### 9.6 对现有工程的直接要求

现有「执行 attempt 账本」方向错了：它记录“尝试几次、最后成功了”，等于把重试当正常流程。
**改为：账本记录每次执行的事实；一致性判定标准不受重试结果影响；重试只能用于判断环境抖动，不能用于让用例通过。**

## 10. 登录与确定性场景的标准解法（示例性说明）

以上次演示翻车的“内网系统登录”为例，说明工具化后应有的形态：

1. **探测（规则，毫秒级）**：拉 DOM，找 `input[type=password]` 及相邻 input 判定为登录表单；iframe/canvas 才降级视觉；
2. **填表（代码）**：按配置写入账号密码；
3. **验证码分类（规则 + 小模型）**：检测类型（图形码/滑块/短信/无）→ 策略链处理，失败即挂起人工接管（**不重试**）；
4. **固化**：一次成功即写为 `fragments/login.yaml` 入库（含表单特征、提交路径、会话存储位置）；
5. **重放**：注入会话，**秒级**进入可测状态，零 LLM。

即：**3~5 个专用工具替代十几分钟自由探索**——本质是删除不确定性，不是省 token。

## 11. 执行引擎设计（已确认）

> 定位：**引擎只执行已编译好的计划，自身不含任何决策**。对外只输出「结果 IR + 取证包」。

### 11.1 进程与隔离模型

| 项 | 设计 |
|---|---|
| 节点 | 本机服务单节点 |
| 并行 | **独立 worker 进程池**（已定：不用同进程多 Context），并发数可配、默认按 CPU 核心 |
| 隔离 | 每条用例独立 Browser Context；用例结束销毁，杜绝 cookie/缓存污染 |
| 会话 | 登录态由会话管理器统一注入，**不依赖上一条用例的残留状态** |
| 显示模式 | 同一引擎两种模式：无头批量 / 有头演示（高亮 + 录屏 + 可接管） |

> 选 worker 进程而非同进程 Context 的理由：浏览器崩溃与内存泄漏在长时间回归中常见，进程级隔离可崩溃恢复。

### 11.2 步骤执行：动作 — 同步契约 — 断言 三段式

```yaml
action: click
wait:                                    # 类型化等待条件，禁止 sleep
  - {type: network_idle, idle_ms: 500}
  - {type: element_visible, target: {testid: result-list}}
assert:
  - {type: text_visible, value: 密码错误, level: decide}
```

**关键设计：等待条件由编译器从探索轨迹中自动提取。**
探索时天然记录“点击后多久稳定、哪个接口返回后才出结果、元素稳定态出现在第几毫秒”，编译时提取为显式等待条件 —— 这是“学来的同步策略”，比人工写 `waitForTimeout(3000)` 可靠，且不会随时间腐烂。

等待条件类型必须**封闭枚举**（不允许 LLM 自由发挥）：
`element_visible` / `element_enabled` / `element_stable`（位置尺寸连续 N 帧不变）/ `network_idle` / `request_done(pattern)` / `text_changed` / `url_matches` / `attribute_equals`。

### 11.3 定位解析器

- 按 `locators` 优先级依次尝试，命中即停；
- **多命中必须拒绝执行**（不取“第一个”）；
- 每次降级命中必须**记录**（`命中第 3 指纹`），计入资产健康度，是 flaky 前兆；
- 全部失效 → `locator_not_found` → 仅交 L1 自愈。

### 11.4 断言引擎：判定性 vs 观察性

| 级别 | 作用 | 失败时 |
|---|---|---|
| `decide` | 决定用例结论 | fail + 触发取证 |
| `observe` | 只记录，供归因 | 不判 fail，计入异常信号 |

语义断言（LLM 判定）只能吃**结构化摘要**，结果落 `decide` 级但**必须标注“由模型判定”**，以便审计追溯。
**已定：语义断言不允许进入冒烟集**——冒烟集必须 100% 规则判定，否则自身稳定性无法保证。

### 11.5 取证包（固定 schema）

| 分区 | 内容 |
|---|---|
| context | 计划 ID、步骤 ID、环境、数据版本、引擎版本、时间戳、执行 ID |
| visual | 失败截图、全流程录屏片段、**与上次成功执行的同步骤截图 diff** |
| dom | 当前 DOM 快照、目标元素外层摘要、**与上次成功的 DOM diff** |
| network | 本步骤相关请求/响应（状态码、耗时、payload 摘要） |
| console | 控制台报错与警告 |
| trace | 前 N 步操作与结果轨迹 |
| history | 该用例最近 5 次执行结果（判断是否 flaky） |

> “与上次成功的 diff”是归因最直接的证据 —— 大部分失败是“哪里变了”。此能力**依赖资产历史**，通用 agent 天然拿不到。

### 11.6 登录器与验证码策略链

策略链：**探测分类 → 按项目配置排序 → 逐策略尝试 → 全部失败转人工**。

四条实战纪律：
1. **先分类再处理**：图形码 / 滑块 / 点选 / 短信 / 无，链路完全不同，严禁盲目试；
2. **验证码失败最多重试 1 次**：反复尝试触发风控锁号，会把“一次失败”变成“账号被封”（实战红线）；
3. **策略成功率按项目维度统计排序**：不同项目可用策略不同，不做全局一刀切；
4. **会话复用是终极解法**：把验证码从“每次执行遇到”降到“每周遇到一次”。登录器的首要价值是**固化会话**，而非“能登录”。

### 11.7 人工接管：三种模式 + 状态重新对齐（易漏关键点）

| 模式 | 场景 | 设计 |
|---|---|---|
| 阻塞式接管 | 验证码、短信、扫码 | 引擎暂停，交控制权，人操作后点“继续” |
| 断点式接管 | 调试、排查 | 任意步骤可设断点，单步执行，查看状态 |
| 修正式接管 | 人工走完异常路径 | 记录人操作，**可编译为计划片段**入库 |

**接管边界（易漏）**：接管不是“人替引擎跑”，而是“人只补引擎做不到的那一小段，然后交回”。交回时必须做**状态重新对齐**：
1. 重抓 DOM 快照并更新元素映射；
2. 刷新 `touched`；
3. 校验“当前状态是否满足下一步前置条件”，不满足即明确报错，不许硬跑。

不做这三步，接管后续步骤基于过期状态执行，失败还查不出原因 —— 这是多数平台接管功能的通病。

### 11.8 自愈分级与红线

| 级别 | 动作 | 自动 | 记录 |
|---|---|---|---|
| L1 定位自愈 | 换指纹 | 是 | 必记，计入健康度 |
| L2 等待自愈 | 延长等待 / 追加等待条件（限一次） | 是 | 必记 |
| L3 步骤自愈 | 跳过/替换步骤、改变操作目标 | **禁止** | 转人工或直接 fail |

> **红线：自愈只允许让用例“能跑通”，绝不允许让“该失败的变成通过”。** 任何自愈动作必须留痕，并降低该用例健康度评分。

### 11.9 结果 IR：五种结论

```yaml
case: CASE-00123
verdict: inconclusive        # pass | fail | flaky | skipped | inconclusive
steps:
  - {id: s2, status: pass, duration_ms: 130, locator_hit: 3}
  - {id: s3, status: fail, failed_assert: text_visible, evidence: evidence://exec-8821/s3}
touched: {pages: [...], apis: [...]}      # 执行后自动刷新
retries: 0
self_heal: [L2@s2]
```

**`inconclusive`（无法判定）必须有，且已定：在准入结论中单独统计。**
环境不可达、前置不满足、会话获取失败 —— 既不该算 pass 也不该算 fail。缺这一档，平台只能在“谎报通过”和“诬告失败”之间二选一。单独统计是为了避免它被当作“没跑”而掩盖环境问题。

### 11.10 可单步调试（刚需）

原生支持：断点、单步、查看当前 DOM 与变量、断点处接管。
**“单步调试”与“演示可见”是同一套能力**（有头模式 + 步骤级暂停 + 状态可视化），做一份两处受益 —— 演示能力应内建于引擎，而非外挂。

| # | 决策 |
|---|---|
| 1 | 准确表述：**执行进程里零探索**；资产是活的，允许人改/局部重探索/增量 |
| 2 | 推翻“服务端无头集群”；**单执行节点 = 本机服务**，多入口接入 |
| 3 | “双通道”→“同一引擎两种显示模式”（有头演示/无头批量） |
| 4 | 架构四层：入口 / 决策(LLM) / 编译 / 资产 + 执行引擎 |
| 5 | 执行计划形态：**YAML/DSL（源码）→ 编译为确定性指令树** |
| 6 | 固化「意图 + 多指纹 + 可判定断言 + 数据引用」，不固化坐标/绝对路径/硬编码值 |
| 7 | **编译五道闸**：定位唯一性、断言可判定、数据不硬编码、溯源、**N=3 一致性** |
| 8 | LLM 在固化中只做「意图命名」和「断言推荐」，禁改步骤/动作/预期 |
| 9 | 三个设计决策：**DSL 可人工手写**、**片段复用**、**关键步骤强制断言** |
| 10 | 片段必须**契约化 + 版本化（login@1）**，变更前列受影响用例 |
| 11 | 人工手写计划**必须过同一套闸** |
| 12 | 回归集三问、五触发源、三层闸（Smoke≤5min / Core≤1h / Full 夜间可分片） |
| 13 | 选集必须**可解释**（每条给理由） |
| 14 | 置信度三指标 + 准入结论（资产健康度不达标→不给结论） |
| 15 | 影响分析主数据源 = **探索轨迹自动提取的 `touched`**，重放时自动刷新 |
| 16 | flaky 定义限定三同条件；五大根因对因处理；**禁止靠重试让用例通过** |
| 17 | 入库前必跑 **N=3 一致性**；flaky 用例进隔离区（quarantine）并超期升级 |
| 18 | 指标用**首次执行通过率**，禁用含重试的最终通过率 |
| 19 | attempt 账本改造：记录事实，不参与通过判定 |
| 20 | 保留“单阶段可执行”能力，但**必须满足前置产物契约**，禁止 LLM 现场编造 |
| 21 | 执行引擎并行模型 = **独立 worker 进程池**（非同进程多 Context），崩溃可恢复 |
| 22 | 结果结论五档，**`inconclusive` 必须在准入结论中单独统计** |
| 23 | **语义断言不进冒烟集**，冒烟集 100% 规则判定 |
| 24 | 等待条件由编译器从探索轨迹**自动提取**，条件类型封闭枚举，禁止 sleep |
| 25 | 自愈分 L1/L2/L3，**L3 禁止自动**；自愈不得让“该失败”变通过 |
| 26 | 人工接管必须做**状态重新对齐**（DOM/`touched`/前置条件校验） |
| 27 | 验证码失败**最多重试 1 次**（防风控锁号）；登录器首要价值是固化会话 |
| 28 | 取证包必须含**与上次成功的 diff**；单步调试与演示可见共用一套能力 |
| 29 | **报告 agent 保留**，定位从“写报告”改为“审报告”——数字全部由程序算，LLM 只产出风险洞察与监控建议，且每条洞察必须挂指标/证据 ID；另建质量风险台账 |
| 30 | **11 个 Agent 全部保留**（撤回“合并为 8”）：阶段边界按“人工确认卡点 / 可独立重跑 / 可独立失效”划分，不按 LLM 调用次数划分；要收的是**权限**（输入来源、输出校验、决策权、自由空间）而非数量 |
| 31 | 需求变更靠**产物血缘 + 增量重算**控制影响范围：全链路稳定 ID、`derived_from` 由程序写入、**语义指纹去噪**（表述变更不触发重算）、只把受影响子图喂给 agent 并产出 diff 交人审 |

## 13. 与现有工程的处置建议

### 13.1 十条不变量（现有约束的正确部分，全保留）

`checked_condition` / `case_ref` / `untested` / `partial` / “无断言不算通过” / “写结果未知不换 ID 重放” / “fixed 只是修复声明，关闭须绑独立复测” —— 这些约束质量超过多数商用产品，**全部保留**。

但必须看清它们的性质：**全是“防造假”类**（别骗我），解决不了“两次跑不一样”。

### 13.2 约束类型需要补的一半

| 现有（防造假） | 缺失（防不可复现） |
|---|---|
| 无断言不算通过 | **同用例 N=3 结果一致性** |
| 未执行不算通过 | **定位降级记录与计数**（命中第几指纹必须留痕） |
| 写结果未知不换 ID 重放 | **等待条件必须类型化声明，禁止 sleep** |
| 证据要可直达 | **失败证据必须含与上次成功的 diff** |
| 来源可追溯 | **计划入库前五道闸**（定位唯一性 / 断言可判定 / 数据不硬编码 / 溯源 / N=3） |

> 一句话：现有工程和 Hifox 都在解决“Agent 会不会说谎”；上次演示的失败是“Agent 没说谎，但它跑不动、跑不稳”。**这两件事的护栏不一样。**

### 13.3 Agent 判决：11 个全部保留，但权限必须收窄（撤回上一版“合并为 8”的结论）

**上一版判断错在哪**：把“LLM 调用边界”和“阶段边界”混为一谈了。阶段边界不能按调用次数划，要按三件事划：

| 阶段边界的正确依据 | 说明 |
|---|---|
| ① **人工确认卡点** | 需求理解对不对 / 测试点全不全，是两个独立的人工评审动作，合并就只剩一次确认 |
| ② **可独立重跑单元** | 需求变更时，要能只重跑“需求分析”，不能被迫连用例生成一起重跑 |
| ③ **可独立失效** | 上游结论被推翻时，下游产物必须整体作废；三者失效条件不同，不能混在一个容器里 |

三条都指向同一个结论：**需求分析、测试点、用例生成必须是三个独立阶段、三份独立产物、三个独立确认点**。质疑“三份产物都要变”是成立的——但要说清：**这三份产物本来就是链式依赖，需求变了它们必然都要变**；真正的问题不是“要不要变”，而是“**能不能只变受影响的那一部分**”，这靠的是血缘与增量重算（见 13.5），跟是否合并三阶段无关。

**修正后的判决表**：

| Agent | 判决 | 收窄要求 |
|---|---|---|
| `default_agent` | 保留 | 入口，不算业务 agent |
| `test_agent` | 保留 | **派发决策从 LLM 判断改为状态机 + 规则表**；不得自行决定跳过阶段 |
| `requirement_analysis_agent` | **保留** | 输入只能是解析后的条款（不得直读整份 PRD 自由总结）；输出必须逐条挂原文位置；需求项必须打模块标签 |
| `test_point_agent` | **保留** | **覆盖矩阵由程序算，agent 只补空格子**；输出必须过“矩阵无空缺”校验 |
| `test_case_agent` | **保留** | 断言必须来自测试点的预期结果，不许看页面反推；必须过用例条数预算与枚举对账 |
| `automation_execution_agent` | 保留 | 载体独立（Playwright）；必须吃执行计划，不许现场重探索（M1 可降级为“计划驱动 + 受控探索”） |
| `api_automation_agent` | 保留 | 载体独立（HTTP worker），且“只执行不设计”边界干净 |
| `android_test_agent` | 保留 | 载体独立（ADB/Android） |
| `miniprogram_test_agent` | 保留 | 载体独立（微信开发者工具） |
| `defect_analysis_agent` | 保留 | 有真判断成分（归因分类 + 置信度）；取证包必须由程序组装 |
| `test_report_agent` | 保留 | 见 13.4——定位从“写报告”改为“审报告” |

**结论：主要矛盾不是 agent 数量，是 agent 的权限。** 11 个 agent 每个都有独立交付物、独立确认点、独立失效条件，砍掉反而损害产品形态。要收的是四样东西：输入来源（只能吃上游 IR）、输出格式（必须过 schema 硬校验）、决策权（派发交给状态机）、自由发挥空间（能形式化的全部下沉为程序资产）。

**关于“三个 agent 都绑 `test-design-methods`”这个重叠信号——解法不是合并，是下沉**：把该 skill 里可确定的部分（维度矩阵、checklist 检索、边界值字典）变成**程序级资产**，agent 只在缺口处调用判断。这样三个 agent 共享同一份规则，却不会各自解释出不同结果。职责重叠的根因是“规则散在提示词里被各自解释”，不是“角色划分重复”。

### 13.4 报告 Agent 的正确形态：从“写报告”改为“审报告”

保留是对的，但必须换定位，否则会出现两个致命问题：**数字可能被 LLM 编造**、**报告变成套话**。

| | 错误形态（写报告） | 正确形态（审报告） |
|---|---|---|
| 输入 | 原始执行数据 | **已算好的结构化指标包**（只读） |
| 职责 | 生成数字 + 写结论 | **解释数字、识别风险、给监控建议** |
| 输出 | 一段报告正文 | **风险洞察对象列表**（结构化，可入库跟踪） |
| 数字权威 | LLM | **程序**，LLM 无权修改 |

**为什么这个角色值得保留一次独立调用**：它是全链路唯一能看到“全局交叉”的角色。单看指标都不惊人，交叉起来才有洞察，例如：

- 某模块失败率上升，但失败全是 `inconclusive` → **环境不稳，不是质量下降**（若误判会白改代码）
- 覆盖率 100%，但 60% 用例是 `observe` 级断言 → **覆盖率虚高，错误通过风险大**
- flaky 率稳定，但定位降级命中率上升 → **UI 正在漂移，两周后可能批量失效**
- 缺陷集中在新模块，而该模块需求覆盖最低 → **投入结构错配**

这些都要求跨指标 + 跨轮次比对，程序写不出规则（组合爆炸），通用 agent 也做不了（它没有历史资产）。

**四条硬约束（缺一条这个 agent 就会退化成套话生成器）**：

1. **数字只读**：LLM 输出的任何数字若与指标包不一致，直接被校验器丢弃并告警；
2. **每条洞察必须挂引用**：`evidence: [metric:flaky_rate@v3, exec:8821]`，挂不上引用的洞察一律丢弃；
3. **允许“无风险”输出**：显式支持 `risks: []`，并统计空输出率——**若不支持，模型会为了交差硬凑风险**，这是这类 agent 最常见的退化；
4. **输出分两段、来源可辨**：`facts`（程序生成，只读）与 `insights`（LLM 生成，带 model 标记与置信度），二者在报告里视觉区分。

**加分设计：风险台账（对应你说的“风险点监控”）**
把每轮洞察写入**质量风险台账**（risk register），带状态机：`new → tracking → mitigated / accepted / escalated`。这样报告从“一次性产出”变成“持续监控”：上轮提的风险这轮还在不在、有没有恶化，都能追踪。**这一条会显著提升产品在管理层视角的价值**——领导要的不是一份报告，是“风险有没有在收敛”。

### 13.5 产物血缘与增量重算（回答“需求变了三份产物都要变”的正解）

需求变更必然导致下游三份产物都要变，这是链式依赖的物理事实。能优化的是**变更的范围与成本**，靠下面三层设计：

**(1) 全链路稳定 ID + 血缘边**

```
REQ-045 (v3)  →  TP-045-2  →  CASE-00123  →  STEP s1..s5  →  ASSERT a1,a2
     │                │              │
     └─ module: order └─ dimension: 边界 └─ touched: [POST /api/order]
```

- 每份产物带 `id + version + derived_from[]`；
- 血缘边由程序维护（抽取/生成时自动写入，不靠 LLM 声明）；
- **没有血缘的产物不允许入库**（与“无断言不算通过”同级）。

**(2) 变更影响闭包计算（纯代码，零 LLM）**

需求项 `REQ-045` 从 v2 升到 v3 时：

1. 沿血缘边向下求闭包 → 得到「待重算集合」（只含受影响测试点 / 用例 / 计划片段）；
2. 未被影响的产物**一个字节都不动**（不动 = 不引入新风险 = 不用重新确认）；
3. 只把受影响子图作为输入喂给对应 agent，产出**增量 diff**；
4. 人工只审 diff（不是重新审全量）。

这直接回答了你的担忧：**三份产物确实都要变，但变的是“REQ-045 那一支”，不是“全部重来”**。500 条用例的项目里，一次需求变更通常触及 2~5 条用例，重算成本是可接受的。

**(3) 两种变更要分开处理**（这一点很关键）

| 变更类型 | 例子 | 处理方式 |
|---|---|---|
| **语义变更** | 需求改了规则（“满 100 减 10”改成“满 200 减 30”） | 必须重算下游闭包，人工审 diff |
| **表述变更** | 需求文档措辞调整、章节重排 | 只更新 `content_hash`，**不触发重算**（否则每次文档小改都全量重跑，团队会崩溃） |

判据：**用正文语义指纹（去噪后规范化文本的 hash）判断，而不是文档 hash**。这是增量重算能不能落地的前提——绝大多数需求文档的“合并单元格微调”“错别字修正”都不该触发任何重算。

**(4) 血缘图的第二个用途（免费获得）**

同一张图同时支撑两件事：
- **产物重算**：哪些产物要重新生成（本节）；
- **回归选集**：哪些用例要重新执行（第 8 章）。

两者共用 `derived_from` + `touched`，不需要维护两套映射。这也是“资产随执行自动更新”的价值所在。

### 13.6 两块已定义但从未接线的 Skill（M1 最该先接）

| Skill | 定义内容 | 现状 | 接上后的作用 |
|---|---|---|---|
| `test-asset-management` | 可复用规则、数据策略、**定位器**、断言、接口契约、缺陷模式 | **未绑定任何 Agent** | 一切“可复现”的地基（元素库 + 断言库） |
| `test-selection` | 按风险、变更范围、**预算**选测试集 | **未绑定任何 Agent** | 回归集与影响分析的落点 |

> 这两块恰好就是讨论中反复出现的“资产库”和“回归集”。说明架构判断没错，**缺口不是没有设计，而是没接线**。

### 13.7 M1 改造五步（按依赖顺序，可当任务表）

1. **接上 `test-asset-management`**（元素库 / 定位器库 / 断言库）——所有可复现的前提，定义已有；
2. **接上 `test-selection`**（回归集 + 影响分析）——产品能被真实团队用起来的关键；
3. **建立产物血缘与增量重算机制**（13.5）：全链路稳定 ID、`derived_from` 自动写入、语义指纹去噪、变更闭包计算。**七阶段一律保留，靠血缘控制重算范围，不靠合并减少阶段**；
4. **`automation_execution_agent` 加“计划驱动模式”**：把现有 `browser-case-plan.json` 从“文字步骤”升级为**可执行计划**（多指纹 + 类型化等待 + 断言 + `touched`）。**这是最省力的改造路径——不新增架构，只升级已有产物的表达力**，可从“探索执行”平滑过渡到“半固化执行”；
5. **报告 agent 改造为审阅者**（13.4），同时上线风险台账。
