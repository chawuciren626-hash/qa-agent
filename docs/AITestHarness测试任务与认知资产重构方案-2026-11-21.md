## 0. 设计原则

1. **目标架构优先**：本方案从"工程应该长什么样"出发设计；现有实现一律视为可替换的复用件，只有被目标架构引用的才保留，其余可删可重写。
2. **确定性优先**：判定可信、可复现、可审计的路径必须是确定性的；LLM 的自由度只存在于阶段内部的生产性工作中。
3. **资产为中心**：页面锚点、接口契约、断言规则、脚本、业务规则都是带状态与溯源的资产；流水线消费资产，也生产资产。
4. **上下文可见**：用户在任何页面都知道自己处在哪个项目、哪个任务、哪个阶段；系统在任何产物上都能回答"它从哪来"。
5. **权限即过滤**：所有可见性由权限过滤决定，不做"看见但点不动"的假入口。

## 1. 问题诊断（保留作为设计依据）

| # | 问题 | 根因 |
| --- | --- | --- |
| P1 | 会话即任务：执行痕迹无登记、状态靠考古 | 任务身份寄生在会话上 |
| P2 | LLM 总控无边界：调度决策不可复现 | 非确定性放在控制流层 |
| P3 | 认知资产缺位：资料与流水线无关、探索不可复核 | 组织按文档状态而非消费场景；探索未接触真实系统 |
| P4 | 执行层漂移：找不到按钮、需求二次转写漂移 | 无锚点约束；无真实系统/代码证据源 |
| P5 | 阶段校验拖慢交付 | 出厂校验由 LLM 逐个执行 |
| P6 | 导航层级深：项目是导航容器，跨项目能力（全局助手、全局任务）无法实现 | 信息架构把"项目"当成了容器而非维度 |
| P7 | 缺陷闭环缺失：缺陷止步于报告，修复回环（回传→修复→复测→关闭）无编排入口 | 状态机/确定性选集/指标均在脚本层，未接入编排与 UI |

## 2. 信息架构与导航（P6 的解法）

**核心动作：项目从"导航容器"降级为"上下文维度"。**登录后直接进入全局菜单，不再有"项目工作区"壳层。

### 2.1 全局菜单

| 菜单 | 类型 | 内容 |
| --- | --- | --- |
| 测试助手 | 全局页 | 跨项目问答与单阶段任务承接；会话列表在此（原工作空间位置） |
| 测试任务 | 全局页 | **平台同步 + 本地新建合并列表**：来源列、项目筛选器、状态分组；`origin: assistant` 记录不在此显示 |
| 项目管理 | 全局页 | 项目列表/新建/成员/权限（项目所有者与管理者视角） |
| 定时任务 | 全局页 | 定时作业 |
| 项目视图 | 项目页 | 当前项目总览：任务进度、用例、缺陷、报告、运行记录 |
| 项目环境 | 项目页 | 当前项目环境清单、探索建档入口（见 §7） |
| 项目资料 | 项目页 | 当前项目资产中心：系统地图/业务知识/测试资产/历史档案/草稿待确认（见 §6） |
| 后台管理 | 管理员 | 用户/角色/智能体/MCP 服务目录/发布资源/工具台账 |

### 2.2 上下文规则

1. **头部常驻项目选择器**：全局唯一的项目上下文；项目页读取它，全局页提供项目筛选。未选项目时项目页显示空态并引导。
2. **权限即过滤**：所有列表按 ACL 过滤；无权项目不出现在选择器与列表；深链带 project 参数可分享。
3. **测试助手跨项目**：问答范围 = 用户权限内项目；回答跨项目汇总时显式声明项目集合；写回项目数据仍走「保存为项目资料/候选资产」显式动作。
4. 动线：新建项目在「项目管理」；新建任务在「测试任务」列表；探索建档在「项目环境」。

### 2.3 权限模型（已定稿：单账号全权制）

当前不引入项目成员/协作角色。平台任务由**配置的接收账号**统一接收，该账号对其名下项目拥有全部权限；确认门禁由账号本人执行。两条配套约束：

1. **任务归属字段保留**：任务/运行记录归属账号，多账号环境下不出现无主任务；后续若引入成员模型，归属字段是扩展基座。
2. **全权账号 = 审计焦点**：其模型凭据、执行授权、清理操作全部进入操作审计；并发资源互斥不因单账号消失——环境锁与 resource_keys 照常生效（同一账号可并行多任务）。

## 3. 双入口与角色

### 3.1 正式侧：测试任务

入口 = 平台任务同步 + 本地新建（同一列表、来源列区分）。任务 = 产品上一个变更的测试；**上游任务在任务详情声明涉及端**（映射与归一化见 §3.3）。**本地新建任务确认永不回传**；平台同步任务单任务单回传，回传负载为最小集：分析结论、执行摘要、缺陷列表。

**阶段状态机**：配置即代码（`config/orchestration-workflow.json`）。UI 固定六节点：①需求分析 ②场景与测试点 ③用例设计 ④测试执行 ⑤缺陷分析 ⑥测试报告。映射规则：

- UI 节点 2 = `test_points`；
- **UI 节点 4 内部为按端动态通道**（§3.3）：每条通道 = 端 × 类型 × 环境，各持独立批次列表；单端任务只显示单条；
- UI 节点**从 run 的 plan stages 渲染，不硬编码**：引擎把 stage id 映射到节点槽位，节点④槽位接受执行阶段的全部通道；
- 仅阶段定义实质变化才升 `workflow_version`；存量 run 按不可变 plan 渲染，不受影响。

**test_agent = 队长模型**：

职责（保留智能）：审题（轻量预处理：理解任务/判轨道/材料缺口/装配阶段简报）→ 派发队员 → 预审催改（给出"建议通过/返工+问题清单"）→ 传递产出（上阶段产物装配进下阶段简报）→ 收尾交付沟通（专业产物是报告 agent 写的，队长只做交付）。

三道栏杆（机械强制）：

| 栏杆 | 实现 |
| --- | --- |
| 确认权在人 | 预审结论是门禁输入不是审批；confirm-gate 三层挂在 UI 确认按钮后 |
| 路线钉在墙上 | stage-registry 依赖校验 + 加锁 dispatched 入口 + 登记前移 |
| 审题不答题 | 不产出专业产物；保留"总控不代写"纪律 |

**登记前移**：run 创建即写 `qa_runs`，先登记后派发。**登记单位 = attempt（阶段版本）**；会话 = 阶段工作会话，可承载同阶段多个 attempt（v1 分析 + 修订 v2 + v3），一个 attempt 不跨会话；`run_id + stage + attempt + session` 于派发/续接时写入元数据。工作区出现"有痕迹无登记"的 run 在结构上不可能。

**重做循环（已定稿）**：同 run 内阶段修订，产物按时间批次分组展示，**不设修订次数上限**；仅范围变化开新 run。**修订默认同会话续接，重启为受控兜底；适用于全部阶段**：

- **续接优先（全部阶段）**：用户修订意见经 UI 结构化动作归档（沿用 `apply_analysis_feedback` 机制）后，直接注入原阶段会话（`input_subagent` 原子会话续接，不新开会话）；队员在保留的工作上下文与台账上做增量修订并产出新版本；**队长不再为新会话重新派发**，只做新版本预审。修订产物同样经引擎收口校验 + 用户门禁；旧版本自动归档。阶段 4 的区分：LLM 面修订（脚本修正、计划调整、通道增减）走同会话续接；**批次重跑是确定性 attempt，不需要会话续接**。
- **重启兜底**：三种触发——原会话已死（中断/宿主重启）、修订轮次超阈值、预审判定上下文污染（锚定旧结论）。重启会话以「修订简报」装配：当前台账 + 最新版本产物 + 未决问题清单 + 用户反馈历史。台账完备度决定重启修订质量——"台账先行"纪律的价值所在。
- **上下文承载机制（宿主已有，直接复用）**：PenguinHarness 内核自带自动压缩——`compaction.max_context_length` 阈值（按模型窗口减 headroom 派生）触发 LLM 摘要后经 `openNextContext` 续开上下文，会话不因上下文耗尽而死亡。运行时规则已明确：压缩摘要只是检索线索，**状态权威永远在产物（台账/回执/证据）**。因此同会话续接天然安全；"修订简报"只在重启路径（新会话冷启动）需要。配套要求：模型配置必须如实填写 `context_window`，否则压缩阈值派生失准——纳入模型配置校验规则。

### 3.2 助手侧：测试助手（`default_agent` 承载，不新建 agent）

三重身份合一：宿主通用兜底 + 后台管理员维护 + 测试助手。显示名"测试助手"。

**单阶段任务承接**：用户提出某阶段任务 → 助手审题 → 指派对应阶段 agent → 输出结果。登记为 `origin: assistant` 独立任务，正式任务列表过滤，仅会话内可见。**原则："不进列表" ≠ "不登记"。**

**派发边界（已定稿）**：

| 阶段 | 助手可派 |
| --- | --- |
| 1 需求分析 / 2 测试点 / 3 用例设计 | ✅ 开放 |
| 5 缺陷分析 / 6 报告 | ❌ **暂不开放**，后续按需建设 |
| 4 测试执行 | ❌ 永不开放（执行授权必须走正式任务门禁） |

其余约束：产物默认留会话；显式保存才入项目（candidate 态）；复用设计类 skill（方法同源）；写权限由运行时守卫强制；模型配置走账号级回退。

### 3.3 多端任务模型（项目 = 产品，端 = 项目内维度）

一个业务产品（如前台用户端、管理后台、App、小程序）是**一个项目**；端是项目内部的维度，不是项目的切分依据。

**端的标准枚举（初版六类，可扩展）**：`web`（用户端网页）/ `web_admin`（管理后台）/ `app` / `miniprogram` / `desktop` / `api`（接口后端）。上游任务详情的端标签经管理端维护的映射表归一化到标准枚举；未知端进待映射池人工指定。

**落点**：

1. **环境**：每条环境声明所属端；探索建档、锚点资产、账号策略都挂 端 × 环境。
2. **任务声明涉及端**：同步/创建任务时确定端集合（来源=上游任务详情；可在任务接受时人工修正），任务全程可追溯端集合变更。
3. **设计阶段（1-3）单管线**：设计一次，产物带端标签——测试点/用例 IR 向后兼容扩展 `end` 字段；锚点验证按端对应该端 × 环境的系统地图；锚定率按端统计。
4. **执行阶段（4）按端出通道**：通道 = 端 × 类型 × 环境；通道映射执行 agent（web/web_admin → `automation_execution_agent`，app → `android_test_agent`，miniprogram → `miniprogram_test_agent`，desktop → `desktop_test_agent`，api → `api_automation_agent`）；各通道独立批次与证据；run 仍是一条。
5. **汇总阶段（5-6）跨通道聚合**：缺陷覆盖全部通道；报告一份、按端分节（各端结论/未测范围/风险）。
6. **执行授权一次覆盖全部通道**：授权界面逐通道列明目标环境与数据影响，一次确认。
7. **回传单任务单份**：与上游任务 1:1。

**边界**：跨端链路用例（单用例跨多端操作，如前台下单→后台审核→App 收推送）**本期不支持**，用"多端用例 + 测试点关联同一业务流"覆盖；单用例跨端编排明确后置。

**上游映射配置（管理端）**：产品线 → 项目（产品）映射；上游端标签 → 标准端枚举归一化映射。上游若未来按端拆分为 N 个任务，则按项目内 1:1 落位为 N 个任务（各自管线各自回传），不引入跨项目聚合层。

## 4. 阶段工具协议（P5 的解法）

**原则：阶段内工具自由，阶段口校验强制**——强制的是"必须被校验"，不是"必须由 LLM 执行校验"。

| 类别 | 归属 |
| --- | --- |
| 工作工具（read_source、extract_word、查系统地图、查资产） | LLM 按需自由调用 |
| 出厂校验（testability/acceptance/irval/diagnose/validate） | **引擎在阶段收口批量执行，不占 LLM 回合**；不通过 → 带违规清单定向重派一次 |
| 语义检查（范围交叉一致性、材料完整性） | 队员 LLM 在工作阶段完成 |

现状 5-7 个 LLM 工具回合收敛为"工作 + 一次引擎校验 +（至多）一次定向修复"。

## 5. 执行架构（P4 的解法，本方案重心）

### 5.1 三层时序：锚点先行、脚本资产化

```
探索期（项目级）：探索产出锚点资产 → 人审 verified
执行阶段入口（准备子步骤）：AI 按已确认用例生成执行脚本/剧本
  —— 只绑定 verified 锚点与断言资产，禁自造选择器；脚本含坐标即缺陷
首跑通过：脚本晋升为「脚本资产」（candidate→verified；绑定 用例版本+锚点版本+环境版本）
复跑/回归：直接执行 verified 脚本，零生成成本
失效再生：用例改版或锚点 stale → 仅增量再生受影响脚本
```

**生产路径 = 确定性执行**；agent 驱动浏览器只用于探索（§7）与失败诊断（复核现场、归因），不是逐用例的生产路径。

### 5.2 grounding 三后端（正交可插拔）

被测对象跨 Web/桌面/小程序/App，统一的是**动作/定位/断言抽象，不是引擎**（driver 抽象 + 多实现）：

| 后端 | 定位方式 | 适用 |
| --- | --- | --- |
| 结构层（零模型） | DOM/UIA 控件树 + ≥2 指纹锚点 | 首选；回归重放 |
| 语义层（混合） | DOM+视觉混合 grounding（Midscene 类），命中降级为结构锚点 | 结构层失效时的生成期定位 |
| 视觉层（computer-use） | 截图+坐标，命中必须反查结构锚点 | 无 DOM 目标（桌面/远程/老旧系统）兜底 |

**无 data-testid 假设（已定稿）**：平台面向测试人员使用，不依赖前端配合。补偿策略 = 探索期锚点 bundle + 多指纹回退链（文本→语义角色→CSS 结构→视觉）+ grounding 缓存。锚点 verified 是执行确定性的唯一来源，因此资产治理是硬前提。

### 5.3 浏览器形态与并行

- **托管浏览器**（Playwright 托管，版本受控、上下文隔离、trace/视频证据），不用用户日常浏览器；批量执行 headless，登录验证码/MFA 时 headed + 人工卡片续接。
- **并行不是全局开关，按片解锁**：
  1. 分片 = 模块 × 数据画像（模块内用例共享锚点与数据准备）；
  2. 数据隔离决定并行度：`read_only` 自由并行 / `isolated` 按 worker 铺数据（账号池容量为上限）/ `shared` 声明 `resource_keys` 跨片串行；
  3. 片内受限并行：池模型引用 v2.3（接口 20~50、Web=CPU 核数、设备/小程序 1~2，可配）；
  4. 批次检查点可恢复：沿用 attempts 结构，按分片出批次，单片失败不阻塞他片；
  5. 优先级分层：用例 schema 带优先级，每模块冒烟子集快速反馈，全量回归进批量窗口。
- **环境级互斥**：指向同一测试环境的批次（含跨端、跨任务场景，如前台端与管理后台端共用同一后端环境）按环境锁串行——环境是共享资源，锁挂环境不挂任务。

## 6. 认知资产体系（P3 的解法）

资料模块按流水线消费场景组织，映射资产 schema（candidate→verified→deprecated）。菜单见 §2.1「项目资料」。

| 子菜单 | 内容 | 消费者 |
| --- | --- | --- |
| 系统地图 | 按端分区的页面清单/路由/锚点 bundle/接口清单（条目带端标签） | 阶段 2 锚点验证、阶段 4 执行 |
| 业务知识 | 需求/PRD、业务规则、术语表 | 阶段 1/2/3 |
| 测试资产 | 断言规则、接口契约、数据策略、缺陷模式、**脚本资产** | 阶段 3/4/5 |
| 历史档案 | 历次 run 产物（只读，关联 run_id） | 阶段 1/2/5/6 |
| 草稿待确认 | candidate 条目 | 人审晋升 |

元数据三件套：状态 / 来源（上传/探索/任务产出/平台同步/助手保存）/ 被引用记录。边界：环境信息归「项目环境」；**凭据绝不入知识库**（仅 secret reference）。

## 7. 探索管线（env_explorer_agent）

**归属**：专职 agent，项目级动作，从「项目环境」触发（探索建档/增量重探按钮；**探索对象 = 端 × 环境**；阶段 4 门禁可"建议探索"，用户确认发起）。登记 `origin: environment`，任务列表过滤。队长不参与探索。

**探索深度（已定稿）**：目标越全越好——广度优先拉全清单；"有界"的目的不是省成本，是防失控与可完成性：限授权范围、不提交有副作用表单（探索授权≠执行授权）、长爬取断点续爬、未探索分支显式列出。

**三层取法**（引用 v2.3 §3.5.2）：静态解析 → 结构巡检 → 视觉兜底；**产出必须降级为结构化锚点**进资产中心。

**凭据纪律**：环境配置由人在 UI 录入，凭据不经过任何 LLM；agent 拿引用走 `captcha_chain` 登录。

**晋升**：产出全部 candidate → 人审 verified（可 AI 预筛）。

## 8. MCP 工具面

**目标架构**：平台全部工具能力收敛到一个 MCP 面，agent（宿主内或外部）按装配消费：

1. **引擎工具出口**：阶段工具、资产查询、系统地图检索、`stage_finalize` 校验、执行控制等，以 MCP server 形态暴露（stdio/HTTP 按部署形态）；工具清单来自运行期注册表，"列出来的就是能调的"。
2. **外部标准 server 目录**：管理后台 MCP 目录统一登记外部标准服务（Playwright MCP、filesystem 等），连通测试、下发装配、审计闭环；替代自研底层工具。
3. **装配即能力**：agent 的 `tools.mcpServers` 决定其工具面；派发合同按阶段声明所需工具，未装配即 blocked，不静默降级。
4. 与 §4 的关系：出厂校验工具同时是 MCP 工具——队长/队员不直接执行校验，校验由引擎收口，结果经 MCP 面可查可审。

## 10. 缺陷闭环与回归测试（P7 的解法）

**现状盘点（代码扫描结论）**：零件大部分已存在，缺的是编排层与 UI 接线。

| 已有零件 | 位置 | 能力 |
| --- | --- | --- |
| 缺陷生命周期状态机 | `scripts/defect-lifecycle.mjs` | 草稿→确认/驳回→已修复→复测→关闭/重开；复测证据强校验（须引用未用 attempt、证据不可变、closed 需失败复测才可 reopen） |
| 复测跨 run 挂接 | `scripts/manage-defect-lifecycle.mjs` | retest 事件可引用独立 run 的 attempt（`retest_run_id`） |
| 回归影响选集 | `scripts/regression-impact.mjs` | 同一变更两次选集必须逐字节一致（确定性、可复算） |
| 质量指标 | `scripts/build-quality-metrics.mjs`、`quality-index.mjs`、`defect-severity.mjs` | run 级质量门 + 严重度分布 + 跨 run 质量索引 |
| 台账对账 | `scripts/reconcile-defect-ledgers.mjs` | 跨会话缺陷台账对账 |

**缺口（"建设过但没串起来"的准确含义）**：以上全部停在脚本/CLI 层——UI 无缺陷动作入口（确认/标记修复/发起复测/关闭）、任务模型无"回归任务"类型、项目视图无缺陷台账与指标面板、对账未进例行流程。

### 10.1 DoD 与任务状态

- **任务与上游任务 id 1:1**，全生命周期不变；**轮次 = run**（沿用既有"一任务多 run"模型与轮次列语义）。
- **报告确认 = 当前轮次结束**（run 态：进行中 → 已完成）；任务态：进行中 → 验证中（有缺陷待复测）→ 已完成 → 已归档。
- **变更验证完成**为派生视图：当前轮次报告确认 + 关联缺陷全部 closed/rejected（无待复测项）。
- 缺陷生命周期主体 = **项目级缺陷台账**；单次 run 的缺陷产物引用缺陷 id（run 产物是事实记录，台账是生命周期主体）——解决"项目缺陷状态与 run 缺陷产物两套记录"的对账问题；`reconcile-defect-ledgers` 进例行流程（B1 登记前移后对账才有可靠基线）。

### 10.2 回归轮次模型

- **回归复测 = 原任务下新一轮 run（轮次 +1），不是新任务**——从上游视角只有一个任务 id，流程节点推回测试即开新轮次。
- 回归 run 的计划**只声明阶段集 `[执行, 缺陷, 报告]`**：阶段 1-3 不重跑，设计产物（用例/契约/锚点引用）以不可变引用继承自原轮次 run；报告出**回归测试报告**（按轮次列示，原轮次报告不动）。
- 触发两路：上游流程节点推回测试（同步发现轮次推进/状态回测）→ 预建回归 run 待授权；平台内对原任务"发起复测轮次"。
- **复测范围三层**：① 缺陷关联用例直接复测（验证修复）；② `regression-impact` 确定性影响选集（修复波及用例）；③ 可选冒烟。范围经执行授权门禁（人审）。
- 执行后复测证据自动挂回缺陷状态机（`retest_run_id` 指向回归 run 的 attempt，机制已有）：通过 → closed；失败 → reopened（回到 confirmed）。轮次报告回传上游（含缺陷关闭状态），上游节点推进。
- **外部缺陷平台提交与状态回流**：bug-reporting 能力已有，提交入口与回流对接后置（开放项 §14）。
