## 1. 结论先行

当前工程已经不是只有提示词的演示系统：七个业务角色、独立任务与全流程编排、浏览器动作、防重放、持续证据、异常部分交付以及 Office/XMind 导出均有实现基础。应保留这些成果，不建议推倒重做。

主要矛盾已经转为：**实现和保护机制较多，但任务状态、工具合同、能力边界、安装状态与用户体验还没有完全收敛到同一套清晰语义。**继续增加审查节点、长提示词或更多 Agent，不会自然解决这个问题。

建议下一阶段坚持：

1. 先完成用户正在进行的真实验收，用实际会话定位当前主链路断点。
2. 优先修复会误判、误续接、误报就绪或造成重复工作的确定性问题。
3. 将确定性的参数、状态、统计和交付工作下沉到代码，让模型集中处理需求理解、测试设计、探索与缺陷判断。
4. 用户只处理业务歧义、必要人工操作和授权范围变化，不承担内部状态修复。
5. 当前版本仍按“受控试用、稳定性待验收”定位，不宣称已达到任意网站全自动测试或独立桌面产品交付水平。

本次未发现并证实必须立即停止当前验收的 P0 问题；这不构成全面安全认证。下面列出的风险也不等于你当前会话已经触发。

## 4. 问题与优化清单

### R01 / P1：人工回复识别可能把非登录完成消息判为可续接

**状态：已复现；人工交互整体改造仍延后。**

依据：`scripts/browser-task-resume.mjs:8` 的 `nativeBrowserContinuation` 依靠否定词和“继续、完成”等正则识别，`assertBrowserResume` 在第 33 行使用它作为人工回应校验。

本次输入均为等待时间之后的合成人类消息：

| 回复 | 函数结果 | 评价 |
| --- | --- | --- |
| 已登录 | true | 符合预期 |
| 登录失败了，继续分析原因 | true | 不能据此认定登录完成 |
| 已完成用例文档，不是登录 | true | 与登录完成无关 |
| 登录尚未成功 | false | 被正确拦住 |

目前子 Agent 应先 snapshot 再继续，因此这不是“已经证明会未登录提交”的证据；问题是人工完成判定本身过宽，可能导致无效重派发和误导状态。

建议：为人工等待建立绑定 run、dispatch、等待请求的回答记录；卡片与自然语言回复走同一入口。只做继续分析的消息不能被当作登录完成，恢复后还需实际登录状态检查。验证码、MFA 等敏感内容不要进入普通报告。

验收：上表歧义消息不产生“登录完成”事件；重复点击只续接一次；等待不标任务完成；原浏览器与已执行结果保留。按用户既定要求，暂不启动该改造。

### R02 / P1：设计用例关联不能证明整条用例执行完整

**状态：代码确认的能力缺口，不是已证实的虚假报告。**

依据：`scripts/browser-lifecycle.mjs:49` 按 `case_ref` 建立已关联集合；`scripts/execution-counts.mjs` 明确将交互计数定义为 assertion_records；`scripts/browser-task.mjs:595` 将完整业务覆盖标为 not_established。当前提示与报告已有正确免责声明，应保留。

剩余问题：一条用例包含创建、字段核对、刷新回查三部分，只关联一次“标题可见”断言就进入已关联集合；当前无法确定这条用例的所有必要验证点是否执行。未关联为未测是合理下限，但“已关联”还不是完整覆盖账本。

建议：按需增加稳定的 `check_id` / 步骤或预期检查映射，将执行状态分为未测、部分验证、验证完成，并独立记录 passed/failed。探索任务没有设计分母时显示“覆盖未建立”，不要求补造设计文件。

验收：多预期用例只验证一项时仍为部分验证；失败可表示已执行但不通过；一个断言不得代替整条复合预期；报告分别列设计用例、已验证检查和未测范围。

### R03 / P1：隐私扫描达到上限时，复杂页面可能失去可用观察信息

**状态：代码确认，真实复杂页面触发率待验证。**

依据：`scripts/browser-privacy.mjs:72`、`:78` 对超过 500 个输入类元素、4000 个候选文本节点标记 truncated；`privateSnapshot` 在隐私状态不是 observed 时扣留整个结构，截图同样不降级为无掩码。

本次纯函数检查确认：privacy=incomplete 时返回 content_withheld，而不是原文本和控件。对大型表格、复杂管理后台，这可能表现为“页面有内容，但 Agent 无法观察”，进而反复 snapshot 或提前部分交付。

建议：保留不泄露原则，做区域化、可见范围和分段脱敏观察；完整扫描超限时允许交付已经安全处理的局部结构及明确遗漏范围，不以关闭脱敏或无限提高阈值解决。

验收：大量节点页面仍能安全读取当前操作区域；超限被归类为工具观察限制，不是产品空白页；缺失片段不被用于证明元素不存在。

### R04 / P2：最终派发合同仍同时出现旧文件调用与新单次调用说明

**状态：代码确认存在文本双轨；真实重复调用是否由此引起待验证。**

依据：`scripts/structured-actions.mjs:675` 在完整独立任务合同中要求先保存动作 JSON、等待写入、运行 CLI，并在后续更新同一请求文件；第 708 行又追加“支持 qa_request 时不另写请求文件、不同请求不能复用文件名”。catalog 第 78 行已经有新旧宿主条件分支。

虽然末尾新指令能覆盖旧说明，但模型仍要自行消解冲突。此前已优化总控及角色说明，不等于所有派发文本来源均已统一。

建议：由实际宿主能力决定合同只输出一种调用路径；旧文件入口仅在兼容模式出现。对生成后的完整合同增加断言，不只检查单个提示词片段是否存在。

验收：支持 qa_request 的真实子任务不再为每个动作另写文件；旧宿主仍能执行；不同请求文件策略前后一致；调用失败不通过重派业务任务修复。

### R05 / P2：证据生成能力与可点击预览白名单未完全对应

**状态：已复现。**

依据：`scripts/browser-task.mjs:561` 生成 `.api.json`；`scripts/browser-sequence.mjs:20` 生成 `.sequence.json`。`scripts/delivery-evidence.mjs` 和 `penguin/ui/delivery-ui.mjs` 的白名单只列部分汇总 JSON 与 `.observation.json`。

纯函数结果：`test_results.json`、`check.observation.json` 被识别为 json；`check.api.json`、`check.sequence.json` 均为 null。普通动作回执等其他证据也需要逐类盘点，不能宣称所有证据都支持点击预览。

建议：建立共享的“可交付证据类型”注册表，由服务端作为安全裁决方，前端消费能力元数据；按内容安全评估逐类开放，而不是允许任意 JSON。目录超过 200 条提供分页或筛选，大文件给出受控下载或摘要。

验收：API、sequence、断言、截图的报告引用均有明确可用交互；私有连接文件仍拒绝；越界、符号链接和未授权访问仍拒绝；超限不让用户自行搜索目录。

### R06 / P1（适用场景触发）：浏览器能力限制可能被误归因为登录或产品故障

**状态：代码确认的能力边界。**

依据：`scripts/browser-task.mjs:539` 禁用 Service Worker 和下载；`:540` 关闭 WebSocket；`:557` 自动关闭新页面；导航限定同源。结束时的 limitations 已披露部分限制，不应删除。

影响：SSO 新窗口或跨域认证、导出下载、依赖 WebSocket 的业务以及离线页面，可能无法按正常浏览器行为完成。不是所有网站都会受影响，也不能因此认定当前登录故障必然由这些策略造成。

建议：在执行中识别能力缺口，及时说明受影响范围并继续其他项目；按真实需求分批补“受控新标签页/SSO”“下载验真”“必要实时连接”。授权依赖域应任务级记录，不能全局放开。

验收：能力不支持与产品失败分开统计；首次识别后不反复准备环境；需要的新能力不强制用户先填写完整环境 JSON。

### R07 / P1：安装版本指纹未覆盖宿主实际导入的完整工程模块

**状态：代码确认；是否已发生本次运行版本漂移未验证。**

依据：`scripts/install-penguin-runtime.mjs:141` 的 runtime 指纹仅列五个文件。宿主通过工程绝对模块地址加载入口；例如文件打开入口导出的证据读取功能依赖单独的 `delivery-evidence.mjs`，但后者不在该 runtime 列表中。

影响：只修改传递依赖时，安装检查可能看不到 runtimeChanged；运行中进程又可能持有旧模块缓存。于是“源码已修、检查未提示变化、进程仍用旧逻辑”可能同时成立。仅对 UI bundle 做版本号不能覆盖这些服务端模块。

建议：建立发布所需模块及传递依赖的确定性指纹，区分源码版本、磁盘安装版本、进程加载版本。中期将运行包与可编辑源码分离；不在用户验收过程中热更新。

验收：只修改一个间接依赖也能识别更新和重启需求；启动后可核对加载版本；回滚指向完整一致版本，不混合新旧模块。

### R08 / P2：只读自检可能把需要更新或恢复的宿主标为 ready

**状态：代码确认。**

依据：`scripts/engineering-preflight.mjs` 对 `installPenguinRuntime(...,'check')` 只要没有抛错，就记录 `add('host','ready',...)`。安装检查本身可能正常返回 `status:'recovery_required'` 或 `changed:true`，不是只有“就绪”与“抛异常”两种结果。

影响：外层状态可能 ready，但嵌套安装结果并不就绪；自动诊断和用户摘要可能据外层误判。

建议：显式映射 installed、update_required、recovery_required、incompatible 等工程状态；同时明确这些状态不代表业务测试授权，也不自动暂停正在执行的任务。

验收：用模拟返回值覆盖恢复事务、模块变化、原版未安装、真正就绪等状态，外层与内层结论一致。

### R09 / P2：部分锁仍只按 PID 存活判断所有者

**状态：代码确认；PID 复用导致误阻塞为待验证风险。**

依据：`scripts/orchestration-state.mjs:43` 至 `:48` 的 manifest 锁含 host、pid、token、时间，但存活判断只调用 `process.kill(pid,0)`；`scripts/install-penguin-runtime.mjs:34` 至 `:35` 的安装锁也只查 PID。浏览器所有者另有 `process-identity.mjs`，不要把该处已做的增强误认为所有锁都已采用。

影响：旧锁进程退出后，PID 被其他进程复用，可能长期认定“所有者仍运行”。现有策略偏保守，不能说已发现会误杀或接管他人进程。

建议：在对应锁中采用可核验的进程身份或启动标识，兼容旧锁为未知状态；工程诊断处理不确定所有者，不把它转成用户解锁手续。

验收：PID 复用、身份不可读、崩溃遗留、并发抢占各有测试；不误杀、不删除新锁、不重放产品操作。

### R10 / P2：宿主改造依赖精确构建产物，升级维护成本高

**状态：代码确认的架构约束。**

依据：`scripts/install-penguin-runtime.mjs:116` 只支持 0.2.13；`scripts/penguin-runtime-patches.mjs` 使用精确文本和压缩函数名定位前端、服务端锚点。

当前的唯一锚点检查、文件校验、备份和事务回退是正确防护，不应改成“尽量匹配后覆盖”。问题是这种方式不适合长期追随任意上游更新。

建议：短期锁定兼容版本并保留升级合约测试；中期评估正式源码分支或稳定扩展接口，将 UI、任务事件和工具适配纳入可构建模块。独立 EXE 在运行闭环稳定后再推进。

验收：不兼容升级在安装前被识别；回滚可验证；用户工作区和历史会话不随应用升级被搬动或覆盖。

### R11 / P1：跨域 API 策略不是完整的目标隔离或外传防护

**状态：策略已复现；真实攻击与数据外传未验证。**

依据：`scripts/browser-task.mjs:94` 对原授权页面发起的跨域 xhr/fetch 返回 application_api，没有在该函数中逐域限制方法和目标。

纯函数输入：页面 origin 为 `https://test.invalid`，向 `https://outside.invalid/collect` 发起 POST fetch，结果为 application_api。这个检查没有真的发送请求。

这是为正常跨域后端依赖提供兼容的合理需求，但若把被测页面视为潜在恶意内容，该策略不足以阻止页面自己向其他地址发请求。受控工具拒绝 curl/eval，并不自动等于浏览器网络无外传风险。

建议：定义页面/依赖信任模型；按任务允许的目标和观察到的依赖分类，只在真正新增敏感目标或风险变化时询问。保留跨域正常业务能力，不简单封死全部请求，也不默认允许访问任意内部服务。

验收：正常前后端分域可用；未授权敏感外传场景被阻止或明确提示；重定向与新文档规则可解释。当前不能宣称已实现完整网络沙箱。

### R12 / P2：热点编排仍反复扫描完整历史，长会话存在成本增长风险

**状态：代码确认扫描方式；实际性能瓶颈待测。**

依据：`scripts/controller-handoff.mjs` 从父会话全量 rows 搜集 run、寻找调用，再嵌套寻找回执；`run-status-summary.mjs` 多次按 stage 过滤事件和确认；`structured-actions.mjs` 反复构造完整上下文及合同。

风险：随着会话增长，重复文件读取、JSON 解析、嵌套查找及模型重新读合同会增加成本。但本次没有时序测量，不能把历史“跑一小时”直接归因于此，也不能宣称改成数据库一定提速。

建议：先利用已有耗时关联确定模型、工具、文件、等待占比；对确定热点构建按 session/run/dispatch 的可失效索引与增量视图。保留原事件作为审计事实，不立即全量迁移数据库。

## 5. 各专业视角的重点建议

### 5.1 软件测试：从“产物齐全”转向“结论可证明”

- 测试点、用例、断言、缺陷、报告之间使用稳定关联，不根据标题相似度和编号前缀猜测覆盖。
- 每条失败区分产品问题、自动化工程问题、环境问题和未定原因；证据不足不能自动登记为产品缺陷。
- 将未测、部分验证、已验证失败分开；零断言也能交付探索观察，但不能叫通过率 100%。
- 关键成功路径按业务需要组合 UI、实际响应及只读回查，不能所有操作只验证 toast，也不强制每条用例查数据库。
- 保留本次数据归属和残留清单，清理失败不自动换手段删除数据。
- 设计质量审查优先关注遗漏和错误预期，不以表格条数、文档页数作为能力指标。

### 5.2 Agent 开发：模型做判断，程序做确定性推进

- 总控决定需要哪些角色；独立任务不要求不存在的上游产物，完整流程只在用户明确要求时启用。
- 将“任务已登记、调用运行中、等待人工、结果待交接、已交付”投影成简单用户状态；内部不需要只保留一个粗糙布尔值。
- 已执行动作、结果、人工等待以工具事实为准；会话摘要不是执行回执或授权来源。
- 修复技术错误优先返回结构化、可操作的内部纠正结果；无需用户补技术确认文件。
- 不把无限模型循环当自主性；出现相同错误且无新信息时，保留结果并转入明确可处理的工程故障或部分交付。
- 记忆优先复用经过验证的测试资产与规则版本，不自动跨任务复用账号、登录态和旧测试结论；无需现在引入向量数据库。

### 5.3 全栈开发：统一交付与状态 API

- 前端消费业务状态、人工操作和交付清单，不依赖拼接模型文本猜流程状态。
- 文档与证据按类型注册可预览、下载、本机打开能力；无权限、缺文件、超限、接口失败各有简短可执行反馈。
- 保留“执行详情”折叠入口；最终回复只列完成内容、可点击产物、未测范围和真正需要人工处理的事项。
- 对有副作用的卡片操作做请求去重；取消后禁止旧回答恢复已取消任务。
- 发布与安装以完整版本为单位，工作区、应用数据、源码和安装包保持分离。

### 5.4 安全与运维：明确保护范围，不做过度承诺

- 页面、附件、日志都是数据，不得提升为系统指令或用户授权；已有工具边界继续保留。
- DPAPI/加密引用解决特定本机落盘问题，不等于对同用户恶意程序、所有模型外发或历史文件都完成防护。
- 隐私、网络范围和能力限制需要明确可读解释，不能最后都变成一个 blocked。
- 依赖风险继续按已有兼容方案处理；本次未联网重新审计 XMind 间接依赖，不能宣布告警已清零，也不建议强制升级破坏导出。
- 历史数据留存、删除和凭据轮换独立计划，必须按用户授权和业务政策执行。

## 7. 最小验收场景与指标

### 7.1 场景集

| 场景 | 必须观察的结果 |
| --- | --- |
| 仅 URL 的独立探索与报告 | 不要求先交需求/用例文件；观察与已断言结果分开；报告可打开 |
| 文字或 Word 的独立设计 | 不强制执行测试；测试点/XMind、用例/Excel按请求交付 |
| 明确完整流程 | 各角色完成真实交接；无需人工技术解锁；未测与失败如实进入报告 |
| 人工登录 | 真正等待、同浏览器续接；非完成回复不误触发；取消和重复回应处理正确 |
| 产品断言失败 | 不是 Agent 工程崩溃；保留证据并进入缺陷分析及部分/失败报告 |
| 环境或工具故障 | 不伪造产品缺陷；不为补结果重放未知提交；可交付已取得的事实 |
| 多步骤用例只验证一项 | 标记部分验证，不计为整条成功 |
| 长页面与大量证据 | 不因全局扫描上限完全失去安全观察；目录/大文件交付有可用降级 |
| 独立并行任务与取消 | 任务/数据隔离，等待回应不串任务；取消不遗留继续执行的子任务 |
| 候选版安装与恢复 | 源码、安装、进程版本可对齐；恢复状态不误报就绪 |

工程故障注入仅在自建夹具；真实产品不为验收而制造破坏。可合并覆盖多个修复点，不要求先跑大量模型轮次才能修复。

### 7.2 建议记录的指标

- 无技术人工介入完成率：指定范围任务中，无需用户处理内部报错/解锁即可交付的比例；必要登录单独计数。
- 交接成功率：真实子任务返回后成功登记并进入正确后续动作的比例，不按模型声称完成计数。
- 无效调用率：参数拒绝、重复读取、已知错误重复调用分别统计；不能把合法的新测试动作算作重复。
- 业务覆盖：设计用例覆盖、必要检查覆盖、探索未建立分母分别展示；不只显示通过率。
- 结论可追溯率：最终结论中能关联真实来源及对应检查的比例，语义仍需抽查。
- 执行时长：总时长、人工等待、模型请求、工具执行、排队、交付耗时分别记录；并行区间不简单相加。
- 交付可用率：请求的文件是否生成、链接是否有效、是否可打开；三个结果分开记录。
- 模型迁移指标：同一小型场景集下的调用成功、质量和耗时。模型未要求调整时不改配置。

本次不设没有基线的“提速 80%”或“95% 全自动”承诺。先测当前候选版，再共同确定合理目标。

## 8. 中期建设路线与暂不做的事

### 8.1 三个建设阶段

1. **稳定可用**：独立任务和明确全流程都能交付；技术纠错内部完成；失败不丢证据；原生文档可用。
2. **可维护与可扩展**：动作/产物/角色契约单源，候选版与回滚可复现，增加角色无需复制整套编排逻辑；复用验证过的测试资产。
3. **产品化交付**：在稳定源码构建或扩展机制上封装桌面产品，补安装升级、环境诊断、团队权限、数据政策及按需求接入的缺陷平台。

### 8.2 目前不建议

- 为体现“多 Agent”继续增加一串审查 Agent，导致交接和模型往返翻倍。
- 为跑通删掉全部安全校验，或者把工程故障都改成用户确认。
- 先上向量数据库、全面迁 SQLite、复杂多租户或大型评测平台，再解决基本交付。
- 将浏览器无限重试、重复登录或重新派发等同于自恢复。
- 在当前验收期间迁目录、升级宿主、改变模型/代理或清理历史数据。
- 重复展开已明确延后的字体、装饰版式与独立 EXE 封装。
