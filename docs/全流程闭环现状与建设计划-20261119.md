## 1. 结论摘要

骨架是完整的：管理端 7 个页面都在；用户端两层结构（项目层资产 / 任务层七段）在代码里写死（`plan/phases.py` 九阶段 + 110 张表）；11 个 agent、15 个 skill、5 份任务契约、33 个工具台账全部就位。**单点都能演示，但端到端跑不起来**，原因收敛为一句话：

> **五条链是断的，外加一个能力空洞。**

| # | 断链 | 一句话 | 代码证据 | 归属 |
|---|---|---|---|---|
| 断1 | 能力装配链（管理端→运行时） | 提示词/skill/工具的能力声明在 4 处各说一遍，管理端改配置不必然到达运行时 | `skills/`(15) + `TASK_CONTRACTS`(5) + `central_tools`(33) + `tool-gate` 绑定；33 工具中 **14 处 description 指向不存在的 `qa/scripts/`**（R3） | M1 + R4 + R3 |
| 断2 | 层间咬合链（项目层→任务层） | 任务不是实体、地图没有版本，`plan requires ["cases","maps"]` 名存实亡 | UI 路由 `/qa/project/tasks/:sessionId`（任务=会话，G7）；maps 只有路径+摘要列，无 revision/content_hash（G9） | G7 + G9 |
| 断3 | 可比性链（执行→结论） | 无 run 实体、env 未贯通、无被测版本、无环境基线，回归结论不可比 | 110 表无 `qa_runs`（G2）；仅 **4** 表带 env（G8，含今日新增 `qa_environment_explorations`）；无 `sut_version`（G3）；无 reset/restore（G1） | G1-G3 + G8 |
| 断4 | 能力空洞（浏览器自动化） | 探索与执行共同依赖的"取原料层"是空的——这不是串联问题，是根本没有 | 全包外部依赖仅 `requests`；`exec/snapshot.py` 写明 Playwright 只取原料但**从未接入**；`native_mini.py` 明写"M2 建" | M2a + M2b |
| 断5 | 回流链（结果→资产） | 三条回流通道只有"规则"是通的，资产只进不出 | 漏测→`qa_exploration_hypotheses`、地图增量→`qa_environment_knowledge` 未接线；缺陷只挂 case、测试点无跨批次稳定身份（G4）；无治理定时任务（G6） | G4 + G6 |

除上述五条链，还有**五类不属于业务逻辑、但同样让流程跑不起来的前提**（v1 遗漏，v2 补录于 §6）：账号与确认权限、模型渠道可用性、设备并发容量、**发布升级链（11-19 当天两次真实故障）**、可观测性与排障路径。其中"确认卡点没有权限校验"与"绕过官方脚本更新会让安装版拒启"两条，属于**今天就会踩到**的问题，不是技术债。

## 2. 全流程全景与五处断点

![图1：全流程闭环全景图](assets/20261119/fig1-closure-panorama.svg)

**图1 说明**：上层是管理端 7 个配置模块（配置资产），下层用户端分项目层（新建项目→环境→建档→探索→地图/知识/规则，建一次长期复用）与任务层（新建任务→①需求→②测试点→③用例→④计划→⑤执行→⑥缺陷→⑦报告，每次按需求重走、逐段确认），末尾经"结果回流"回到项目层资产。红色编号 1-5 即上表五处断点：

## 5. 浏览器自动化的补法：computer-use 与 MCP 怎么接入

![图2：computer-use 与 MCP 接入架构](assets/20261119/fig2-computeruse-mcp.svg)

**图2 说明**：computer-use（定位方式）与 MCP（调用协议）正交。**默认路径（实线）**：探索流水线零 LLM 直跑——①静态解析 `fetch_bundle`（0 token）→②结构巡检 `flat_dom`（0 token）→产物写 maps 带 `source` 标记；不经 agent、不经 MCP。**异常路径（虚线）**：仅 ①② 失败的页面抛 `PartialFailure` 上抛启 agent，经 MCP 装 `explore.visual_probe`，Midscene **接管 probe 已持有的 page**（不另起浏览器），仍失败标 `unresolved` 交人工。

要点：

1. **computer-use 三个落点**：建档第③层兜底（M2b，canvas/图片按钮/图表类页面）；执行首轮固化（M4，视觉走一遍反查稳定指纹）；headed 人工调试（M4）。**均不在一期关键路径**。
2. **硬约束**：视觉产出必须当场降级为结构化锚点（selector/testid/a11y/接口断言），**坐标禁止进剧本**；重放层零模型——重放出现任何 VLM 调用即质量缺陷（若 30 条用例每日回归走视觉重放，每月 1.8-3.6 万次 VLM 调用，成本不可控）。
3. **"视觉+MCP"不成立**：MCP 入参是 JSON，视觉定位依赖"屏幕当前长什么样"这个隐含上下文，协议里没有屏幕状态——v1 链路跑不起来的根因即此。
4. **MCP 工具盘子**：33 个自有工具由 `central-tools.ts` 在 TS 侧**同进程**暴露 MCP 出口（M1，非新建服务）；Python 侧 `aitestharness_tools` 用 FastMCP；适配器工具（playwright-mcp/mobile-mcp）单独白名单，每任务只暴露 **8-12 个**；子集装配唯一真源 = `TASK_CONTRACTS.tools`，超白名单不在 `tools/list` 返回。
5. **顺序铁律**：修描述漂移（R3）→ **M2a probe 与 M1 出口（互不依赖，可并行）** → M2b 视觉兜底。**先让"取原料"存在，再让能力"可被调用"，最后才让"视觉兜底"上场**——M2b 若抢在 M2a 前面，会重蹈 v1"agent 拿着 MCP 工具到处探索"的覆辙。
   > **v3 订正**：原文写作 `R3 → M1 → M2a → M2b` 的严格串行。实际执行时 M2a 已提前到 P1 完成、M1 仍在 P5，这是**允许**的：M2a 是 Python 侧本地 probe（零 LLM、零 MCP），不需要 MCP 出口就能取原料；真正不能反的是 **M2b 必须在 M2a 之后**（视觉兜底要接管 probe 已持有的 page，不能另起浏览器）。

## 6. 跑通前提与两条工程链（v2 补录）

前五节讲的是"业务逻辑断在哪"，本节补的是**不属于业务逻辑、但同样让流程跑不起来**的五件事。v1 漏了这一段，而其中 6.4 恰是 11-19 当天真实踩坑的地方（两次部署故障），不是理论风险。

### 6.1 账号 / 登录 / 权限 / 凭据（跑通前提，非技术债）

用户流程第一步是"打开客户端登录后新建项目"，但 v1 全文未提。实际涉及四层，现状如下：

| 层 | 落点 | 对流程的影响 |
|---|---|---|
| 平台账号与登录 | `server/src/auth/*` + `admin-users-page.tsx` | 已落地。会话/令牌机制是任务派发的前置 |
| 项目成员与权限 | 项目→成员关系 | **已核实：有"谁确认了"，没有"谁能确认"**。`qa-confirm-gate.ts` 的 `approve`/`reject` 取 `userId` 并落 `confirmed_by`，但路由内**没有任何角色/权限判断**——任何进入该项目的账号都能确认卡点 |
| 环境账号与登录墙 | `qa_secret://` 凭据引用 + 建档 `loginUrl` 字段 | 已落地，但**探索与执行共用同一份凭据**，视觉兜底起 agent 时凭据如何下传、如何避免进 trace/log，需明确红线条目 |
| 凭据治理 | `qa_secret://` 引用式（不落明文） | 设计正确；但**轮换/失效无检测**——环境密码改了，任务会在⑤执行时以"登录失败"的形式暴露，归因容易误判成脚本坏了 |

**结论**：这一层不是"缺功能"，是**缺权限语义与凭据生命周期**。建议并入 P2（新增 `qa_tasks` 时一并落 `owner_id`/`confirmed_by`），凭据轮换检测并入 P3a 环境基线（基线快照里记 `credential_fingerprint`，不一致即前置告警）。

### 6.2 模型渠道可用性与配额（管理端配了 ≠ 运行时能用）

管理端"模型配置"（`admin-channels-page.tsx`）维护渠道，但运行时取用是否与之一致、限流与额度耗尽如何降级，v1 未作为跑通前提列出。风险点有三个：

1. **渠道配置与 agent 实际取用可能不同源**——与断1（能力装配链）同型的问题，只是发生在模型而非工具上；
2. **额度耗尽的表现是"阶段 agent 静默降级或报错"**，用户看到的是"这一步卡住了"，排障成本高；
3. **探索有视觉预算（BudgetGuard），任务层没有**——⑦报告、⑥归因这类长上下文阶段若无 token 预算，单次任务成本不可控。

**建议**：渠道配置加"连通性自检"按钮 → 结果写入运行时可见的健康状态；每个阶段 agent 的 token 上限与超限行为（降级/中止/交人工）在契约里显式声明。归入 P5（配置生效）一起做，因为两者都是"管理端 → 运行时"的生效链。

### 6.3 设备与并发容量（接上就并发崩的坑）

四池约束是硬约束，v1 只在 P7 提 M3 而未写容量：

| 资源池 | 容量 | 后果 |
|---|---|---|
| Web 浏览器 | 单机可多实例，但受内存限制 | ⑤执行并发需排队 |
| Android 设备 | **1-2 台** | 多任务并行必然争抢 |
| 小程序 | **1-2 个** | 同上 |
| 探索 | 与执行争同一浏览器资源 | 建档探索与回归执行同时跑会互相拖慢/失败 |

**结论**：任务调度必须懂"资源池"这个概念，现在没有。最小做法是在 `qa_runs` 上加 `resource_pool` + `lease_until`（P2 一并加字段，成本几乎为零），由调度侧串行化同池任务；不做这一条，P4 之后一旦多人同时用就会看到"偶发失败"，且会被误归因为 flaky。

### 6.4 发布与升级链（今天真实故障来源）

**这是"跑不起来"最现实的原因之一：不是代码逻辑，是发布链。** 11-19 当天连续踩到两个：

| 故障 | 现象 | 根因 |
|---|---|---|
| 版本错配 | 派发探索 → 404 | `web-dist` 与 `server.js` 不是同一次构建产物；前端调了后端没有的路由 |
| 清单校验拒绝启动 | `Source runtime checksum mismatch` | 直接 `robocopy` 覆盖 `web-dist`，与 `aitest-source-runtime.json`（**1132 条路径 → SHA256**）不一致，安装版拒绝启动 |

**机制说明**：安装版启动时校验 `aitest-source-runtime.json` 里 1132 条路径的哈希，任一条不匹配即拒启——这是**正确设计**（防篡改/防半更新），代价是"任何绕过官方脚本的更新都会让应用变砖"。

**红线（写进交接清单）**：
1. 更新前端**禁止**直拷 `web-dist`，必须走 `scripts/deploy-project-management-local.mjs`（备份 → 换 dist → 重签 manifest → 自校验）；
2. 部署前必须 `local-service.mjs pause`，部署后 `resume`，否则运行中的进程会持有旧文件句柄；
3. 数据库 schema 迁移（P2 的 `qa_tasks`/`qa_runs`）**同样要走部署链**，不能只在源码目录跑 migration——否则源码有表、安装版没表，表现为"功能点了没反应"。

**已落地（2026-11-19）**：`scripts/release.mjs` 把这三件事收敛成一条命令——`--stamp` 打构建号戳、`--check` 断言产物与戳一致、`<installed>` 执行 check→pause→官方部署→resume→复核（失败也会 resume，不让服务停着）。红线 3（schema 迁移走部署链）仍需人工保证：迁移脚本不在发布链里。

### 6.5 可观测性与排障路径（跑不通时怎么定位）

v1 只写了验收判据，没写"没通过时看哪里"。已有资产其实不少，但没成体系：

| 资产 | 位置 | 回答什么问题 |
|---|---|---|
| 会话轨迹 | `traces/*.jsonl` | 这个阶段 agent 到底想了什么、调了什么 |
| 工具调用流水 | `tool-usage.jsonl` + `central_tool_audit` 表 | 工具选错/被白名单拒/参数不合法 |
| 执行产物 | `output/runs/<run_id>/` | 截图、快照、断言中间态 |
| 会话审计脚本 | `scripts/` 下审计工具 | 批量复盘历史会话 |

**缺口有三个**：① 没有统一 `run_id` 贯穿"派发 → 工具调用 → 执行 → 报告"（这正是 G2 的副作用——**run 不是实体，所以 trace 也串不起来**）；② 没有"一次任务的健康摘要"（多少工具调用、多少被拒、多少自愈、多少 VLM 调用）；③ 用户侧看不到排障入口，出问题只能找开发。

**建议**：P2 落 `qa_runs` 时同步把 `run_id` 打进三条流水（trace / tool-usage / output 目录），P4 验收时加一条"任一次失败 run 能在 5 分钟内定位到阶段与原因"。**可观测性不是运维附加项，它是"端到端能跑通"的验证手段**——没有它，P4 的"连跑 5 次全过"无法解释失败原因。

## 7. agent—阶段—工具—skill 对应关系

![图3：agent 阶段工具 skill 串接图](assets/20261119/fig3-agent-stage-skill.svg)

**图3 说明**：左侧总控 `test_agent` 逐段派发（虚线）、核验、交接，执行一旦派发设计即冻结；中间是七段主线；右侧每段标注派发的 agent、契约工具白名单（①-④⑥⑦）、消费的 skill。**⑤ 那一格是橙色底**：它的授权来自 run 派发模板与受控动作，不属于契约工具白名单（详见下条）。

- **11 个 agent**：`test_agent` 总控（不产出阶段产物）+ 7 个专业 agent（requirement_analysis / test_point / test_case / automation_execution / api_automation / android / miniprogram_test）+ defect_analysis + test_report + `default_agent`（会话兜底，不参与流程）。
- **三重约束**（`TASK_CONTRACTS` 5 份契约）：工具白名单精确到函数名（白名单外调用即拒）；`must_not` 防越权（②禁改矩阵、③禁改闸门、⑥禁碰证据与结论、⑦禁改 facts）；①②③三个 confirm 卡点，产物确认后才进下一段。④计划固化无 agent——编译器+irval 五道闸，**有意设计**。
- **⚠️ ⑤ 的授权机制与 ①-④ 不同（v2 修正）**：`TASK_CONTRACTS` 只有 5 类，**全部是设计分析类阶段**（需求/测试点/用例/归因/报告），**执行段不在其中**。⑤ 的工具授权来自 **`run` 派发模板 + 受控动作**（`browser_task` / `api_task` / `android_task` / `miniprogram_task`）+ `qa-stage-boundary` hook，**不是契约白名单**。图3 中⑤ 那格已改为橙色底并标注"受控动作（run 派发）"，与①-④ 的灰底"契约工具"区分——v1 把两种授权画成同一列，会让人误以为执行也受契约白名单管辖。

> **这两套授权为什么会分家（值得记一笔）**：①-④ 是"agent 拿工具做判断"，需要严控工具集以防越权；⑤ 是"agent 只负责起一个受控执行、然后交出控制权"，它的安全边界不在工具清单，而在**动作白名单 + 阶段边界 hook + 断言由程序判**。所以⑤真正该收的不是"少给工具"，而是"给的 action 必须可枚举、且不许自己写证据"。
- **15 个 skill 两类用法**：执行类 4 个（playwright / api-test / android / miniprogram-execution）只被⑤消费；知识包按阶段挂（①requirement-analysis，②test-point-design+test-design-methods，③test-case-writing+test-design-methods+api-contract-analysis，⑥bug-reporting+qa-investigation，⑦test-report-writing）；跨段两个（test-asset-management / test-selection）属**回流侧**，供下轮任务 pin 消费。
- **图上可见的缺口**：项目层整段无 agent/skill（设计使然，但 probe 未建=没动力）；⑤的四个执行 agent 依赖的受控动作层同样建立在 probe/driver 之上——skill 写好了、通道未接通；回流侧两个 skill 的消费前提（漏测/地图增量接线）尚不存在（G4）。

### 8.2 P4 的正确定义：E2E-1，而不只是"剧本能重放"

v1 把 P4 写成"3 条手写剧本连跑 5 次全过、VLM=0"，这条判据**只证明执行底座确定性**，它不经过"用例 → 计划 → 剧本"的编译链，也不经过七段联动。按 v1 的排期走完 P4，得到的结论是"执行引擎可用"，**不是"流程跑通"**——这恰好会原样重演"单点都能演示、端到端跑不通"。

**E2E-1 定义**：选 1 个真实小需求（建议 3-5 条用例规模、单环境、Web 端），从**新建任务**开始，顺序经过 ①需求 → ②测试点 → ③用例 → ④计划固化 → ⑤执行 → ⑥缺陷 → ⑦报告，**全程只用产品界面与真实派发**，不用脚本拼接、不手工改库。

**四条判据**：

1. **贯通性**：一次任务内 `qa_tasks` / `qa_runs` 记录完整，`run_id` 能从派发一直追到报告（对应 6.5 的三条流水）；
2. **确定性**：M2.5 子集成立——3 条剧本连跑 5 次结果一致、重放 VLM 调用 = 0；
3. **卡点有效性**：①②③ 三处 confirm 均真实阻断过（有人不点就不往下走），且**确认人受权限校验**（依赖 P2 先补 6.1 那条权限空洞，否则此判据无法成立）；
4. **可解释**：任一次失败能在 5 分钟内定位到"哪个阶段、什么原因"，且区分得出"脚本问题 / 环境问题 / 产品缺陷"。

> **判据 2 的循环依赖（v1 未写）**："连跑 5 次全过"隐含"每次环境可重置"，而重置依赖 P3b（外部）。**最小可接受做法**：P3b 未就位前，用固定数据集跑 5 次，报告标 `inconclusive (baseline=manual)`，不冒充 pass；P3b 就位后再升级为严格判据。**不要因为缺 G1b 就不做 P4**，那会让整个计划停在"等外部"。
>
> **补充（v3，2026-11-19 实测）**：这条降级路径已经跑通（`exec/replay.py`）。两个必须钉住的细节：
> ① **"恢复成功"不能采信被测系统自报**——`restore.sh` 返回 0 只说明它跑完了，可能只恢复了部分表或没重置 mock；必须用 P3a 同一套指纹反验（`verify_restored`）。这是 G1a 的第二重意义：它不只判"环境漂了"，还验"真的回来了"。
> ② **基线必须存在环境级目录、不能只活在 `runs/<id>/` 下**——否则每个新 run 都读不到上一个，每次判"首次运行"，闸装上了却永远在放行。已按 `output/environments/<env>/baseline.json`（判据）+ `output/runs/<id>/baseline.json`（证据）拆分。

### 8.3 R4 的落地判据：三条 CI，缺一条就不算"单一真源"

只把能力声明收到 `TASK_CONTRACTS` 而不做 **M6（skill 三类分离：判据 / 知识 / 执行步骤）**，skill 仍会私自扩权，"单一真源"落不了地。P5 必须同时满足三条断言，全部进 CI：

1. **`skills` 里引用的工具 ⊆ 该阶段契约的 `tools`**——防止 skill 文档教 agent 用契约外的工具；
2. **契约 `tools` ⊆ MCP 实际 `tools/list` 返回**——防止契约承诺了但运行时没暴露（M1 的直接验收）；
3. **`central_tools.impl_path` 指向的文件必须存在**——防止 P0 修完又漂回去。

配套一条：**适配器工具（playwright-mcp 等）不进 `TASK_CONTRACTS`，单独白名单，每任务 8-12 个**；两条白名单的关系是"契约管自有工具、适配器白名单管外部工具"，二者在同一个装配点合并，不在 prompt 里劝。

### 8.4 P6 的两项迁移决策（v1 缺）

1. **`point_uid` 的生成与回填**：现有测试点是 `(batch_id, point_key)`，每批次重建，天然不稳定。做法：新增 `point_uid`，**按"需求引用 + 模块 + 功能 + 描述"生成确定性哈希**（v15 订正：v1 写的"需求条目 + 归一化标题 + 断言目标"里，"断言目标"实际对不到库中的列，而 `risk`/`coverageType`/`executionLayer` 是设计期的可调项，算进身份会让"调一次风险等级"变成"换一条测试点"）；回填历史批次只补 `point_uid IS NULL` 的行，可重复执行；新批次双写（`point_key` 保留给 UI，`point_uid` 供回流）。**必须加防冲突校验**：同批次内 uid 相撞 → 拒绝整批并区分"描述一致（该合并）/ 归一化拉平（该改描述）"，不悄悄合并（同"招投标去重"那类坑，宁可多不合并错）。**已知代价**：早期批次若缺 `documentId`，同一测试点与现在算出的 uid 不同，按 uid 分组时看不到老批次那条，而不是硬合并。
2. **`maps_hash` 的回写时机**：地图变更后由探索流水线写入 `project_environments.maps_hash`；plan 固化时快照当时值。**判 stale 只在 `plan` 固化点与执行前置检查点做**，不在每次读地图时做（否则每次读都要重算 hash，成本高且会误伤运行中的任务）。

### 8.5 "开环 ≠ 闭环"的显式声明

**P1-P6 之前跑通的是开环主线，只有 P6 落地后才是闭环。** 具体差别：

- 开环（P4 达成）：一个需求能从 ① 走到 ⑦，产出报告，**下一个任务从零开始**；
- 闭环（P6 达成）：⑦ 的结论（漏测、缺陷模式、地图增量）沉淀为资产，**下一个任务的起点踩在上一个任务的终点上**。

v1 把 P4 称作"端到端跑通"的验收里程碑，容易被读成"跑通=闭环"。准确表述是：**P4 验收"主干能走通"，P6 验收"跑得越多越省力"**。这两件事的验收方法完全不同——前者看一次任务，后者看第二次任务比第一次少做了什么。

### 8.6 依赖与并行边界

- **P0、P1、P2 三者无相互依赖，可同时开工**（v1 写成 P0→P1 串行，浪费了并行窗口）；
- **P3a 依赖 P2**（要往 `qa_runs` 写基线指纹）；**P3b 依赖外部环境**，不阻塞其他阶段；
- **P4 依赖 P1+P2+P3a**（P3b 可按 §8.2 降级处理）；
- **P5 依赖 P0**（先修漂移再收真源），与 P4 可并行（一个改装配、一个验流程，文件面重叠小）；
- **P6 依赖 P4**（需先有稳定 run 记录与真实缺陷数据）。

**文件面冲突边界**（避免并行时互踩，这是上一次并行写 `backups/` 出问题的教训）：`central-tools.ts`/`skills/`（P0、P5）与 `probe/`/`explore/`（P1）与 schema/`plan/`（P2、P6）是三个不相交的面；P4 只读不写这三面，它改的是验收脚本与测试数据。

### 8.7 一条元建议（v2 §10.5）

把"文档声称 vs 代码现状"的对账放进 CI（`impl_path` 存在性、契约工具 ⊆ MCP 实际暴露、`run_id` 必须能回查 `qa_runs` 等 7 条规则）——这次 gap-inventory 两天过期、排期按它排而踩空，就是不做对账的代价。**本文 v1 自身也引用了两处过期数字（76 表 / 3 张带 env），已在 v2 订正**，这不是笔误，是不做对账的必然结果。
