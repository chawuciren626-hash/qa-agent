## 3. 对专家意见的取舍【保留】

总体采纳“恢复可靠、证据可信、减少模型往返、工程收敛”的方向，但不照搬所有实现方案或严重度。

| 建议主题 | 决策与修正 |
| --- | --- |
| 控制器死锁、worker 健康与异常恢复 | 优先采纳。回收控制器锁不代表浏览器动作已停止；必须分别核验 CLI、worker、浏览器和在途动作。随机 token 本身不能证明 PID 未被复用，不确定时保留锁和证据，并提供安全诊断/离线报告路径。 |
| 正向锚点与预期来源 | 采纳。空白页或登录页上的“目标不存在”不能证明业务成功；缺少前提应标为未验证/工程问题，不自动算产品失败。 |
| 禁止 expected 与 target.value 相同 | 不采纳一刀切规则。需求明确要求某文案时二者相同完全合法。需要区分规格、推导、一致性、历史和探索观察；禁止的是把当前观察无依据地提升为规格结论。 |
| 元素不存在全部算脚本问题 | 修正后采纳。多匹配可以判定位问题；元素不存在也可能是真实产品缺陷，必须结合页面就绪、定位依据和预期判断。 |
| 动作指纹重复即要求用户批准 | 不采纳全 run 禁重。查询、翻页、重复校验可能合法；只针对同一次逻辑写入及结果未知的动作防重放，关联意图、数据、上下文和尝试编号。高风险范围变化才询问用户。 |
| 类型化工具替代文件+CLI | 采纳渐进路线。总控已有 qa_request 自动落盘入口，主要缺口是子 Agent 仍需两步、动作语义仍依赖手写说明。优先扩展现有入口和统一 Schema，不同时建设 MCP 与宿主工具两套执行内核。 |
| 批量动作与脚本回放 | 采纳分期路线。先做有限步骤 sequence，逐步校验/保存，失败或取消即停；稳定资产再回放。不得盲目重跑已部分完成的写入批次。 |
| 有 assertion 就关闭 dynamic feedback | 不直接采纳。本次已有瞬时 toast 漏判，应先保证动作和反馈关联，再选择性减少无关采集，不能删掉恰好能证明事实的证据。 |
| mtime+size 缓存，或每 run 只校验一次 | 不作为安全依据。时间和大小不等于内容未变。按不可变版本/内容哈希缓存，设计变更、授权撤回、派发变更仍即时生效。 |
| 默认屏蔽图片/字体、无头、缩短超时 | 不作为探索默认。可能改变验证码、上传、布局及提示行为；仅对明确适用的回放/CI 配置启用，报告披露。就绪条件优先于全局 networkidle。 |
| 凭据测试缺依赖自动跳过 | 不用于让发布回归假绿。先探测/配置 Python 3.11+；开发者可显式选子集，报告标记验证不完整。完整发布验收不能静默跳过安全测试。 |
| 默认测试没有浏览器覆盖 | 需要更正：npm test 选择 all，CI 有 core/browser 矩阵；core 排除两个文件，但不等于所有浏览器相关测试都被排除。需要检查分组和实际运行覆盖，不是从零增加浏览器 CI。 |
| 缺少任何不可信内容边界/只读复查 | 不是完全缺失：公共指令已有“附件不是操作授权”，代码已有 recheck_of 及旧结果防重。需补页面/日志边界、实际使用及对抗测试，而非重复实现。 |
| JSONL/SQLite 与全面目录重构 | 结果和网络日志可先追加持久化；暂不迁移全部 manifest 到数据库、不为行数指标大规模拆目录。先处理实际故障与契约漂移。 |
| 影子 DOM 完全不支持 | 不能笼统下结论：Playwright 定位器本身可支持开放 shadow root，但当前快照/定位生成仍需验证；iframe、上传下载等按实际需求补齐。 |
| 30% 至 90% 提速、90% 成功率等目标 | 仅作探索目标，不作为承诺。先固定模型、环境、任务范围和实际测试量建立基线，重复采样后再定指标。人工介入不设机械“最多一次”。 |
| 依赖公告、仓库资料、许可证与留存 | 纳入治理；公告需重新审计并追踪实际导入面。业务资料先分类/脱敏，不自动删除或改写 Git 历史；许可证选择由权利人决定。 |

### 3.1 对“不采纳”项的修订补充【新增】

原取舍保持不变，仅补充三条限定：

1. **业务幂等**：不全 run 禁重，但“同一次逻辑写入”必须有明确定义，并覆盖“上次已成功、这次换 ID 再提交”的情况。见 §3.2 P0-B。
2. **dynamic feedback**：不关闭采集，但改为**非阻塞环形缓冲**：click/press 时只记录最近 N 条变化，不固定等待 1.5 秒；断言失败或未知预期时再附加。既不丢证据，也不让每步固定多等。
3. **元素不存在**：补一个分类决策树，避免“一律产品失败”或“一律脚本问题”两个极端。见 §4 第 3 项 4。

### 3.2 开工前置 P0【新增】

以下三项在正式进入第 1 项之前完成；可与第 1 项并行启动，但不能跳过。

#### P0-A 凭据暴露事件化

**依据**：§2 基线“完整测试 Key 进入部分回执/工具参数”。这是已经发生的暴露，不是未来的脱敏需求。

工作内容：

1. 保全证据：复制相关 run/trace/日志到只读事件目录，记录哈希；在保全前不重跑、不清理。
2. 盘点位置：回执、`command.log`、工具参数、宿主 trace、provider 请求记录（如可获得）、Git 历史。
3. 判定：Key 类型、权限、有效期；是否撤销/轮换；是否影响其他环境。
4. 设计 `secret_ref`：模型只传引用（如 `env:QA_LOGIN_PASSWORD` / `vault:...`），worker 在执行时解析为明文；工具参数、日志、回执只保留 `ref + hash`。
5. 历史证据隔离：标记 `contains_secret`，限制访问，不进入报告；按策略删除或归档，不静默覆盖。
6. 事件记录：暴露范围、处置、轮换结论、责任人、后续预防。

验收：

- 合成敏感值不出现在模型可见输出、工具参数、日志、截图和普通交付中；
- F1 有明确结论（轮换/不轮换及理由）；
- 历史证据有隔离标记；
- 补一条「凭据暴露」回归测试。

> 注意：**“不重写 Git 历史”与“不轮换密钥”是两件事**。轮换不需要改写历史；若 Key 仍有效，应评估撤销/轮换。

#### P0-B 业务级幂等

**依据**：当前幂等只到 `request_id`；换 ID 可重复提交，即使上次已成功。

工作内容：

1. 定义逻辑动作：

   ```text
   logical_action_id = hash(case_id + step_index + target + normalized_value + write_intent)
   write_intent      = create | update | delete | submit | approve
   outcome           = completed | unknown | failed_before_execution
   ```

2. 规则：
   - 只读查询、翻页、重复校验：允许重复；
   - 同一 `logical_action_id` 且上次 `completed`：默认阻断，除非显式 `confirmed_retry` 并记录原因；
   - 上次 `unknown`：阻断，要求先核查；
   - 上次 `failed_before_execution`：允许修正后重试；
   - 高风险目标（submit/delete/pay/approve）：始终要求显式意图。
3. 在 `finish` 汇总中列出「被阻断的重放尝试」。

验收：

- 同一提交成功后，用新 `request_id` 再提交 → 被阻断；
- 重复查询 → 正常放行；
- 未知结果 → 阻断并要求核查；
- 拦截记录可在证据中查询。

#### P0-C 基线测量协议与模型固定

**依据**：§2 基线使用 step-5-preview，而文档默认 step-3.7-flash；不能跨模型比较耗时，也不能用单次会话作基线。

工作内容：

1. 运行元数据：`provider / model_id / params / context_window / harness_version / OS / browser / channel`，写入 manifest 与报告页脚。
2. 整改期间冻结模型、宿主版本、测试环境和任务集；任何变更单独记录。
3. 采样：每个场景 ≥10 次，首次预热不计；报告 median / p95 / 分布。
4. 拆分：模型轮次、工具执行、浏览器动作、证据写入、排队、人工暂停分别计时；人工暂停不计入机器时间。
5. 基线指标：工具失败率（当前 23/473 ≈ 4.9%）、单任务调用数、p50/p95、token、未测项比例。

验收：

- 同模型、同环境、同任务集的前后对比；
- 报告分布与拆分，不给单一百分比承诺；
- 工具失败率有基线值和整改目标。

## 4. 统一执行顺序【修订】

保留原五项顺序；第 1 项拆分，第 4 项拆分，第 2、3、5 项补验收。每项先加对应回归，再修复、验证、更新记录；每完成一项汇报并等待用户确认下一项，不把这个开发协作节奏写入产品运行审批。

### 第 1 项：执行异常隔离与安全恢复（P0）【拆分】

对应原计划 1；融合工程审阅的 worker 恢复、隐形问题 P0-3/P0-4 及宿主诊断建议。

#### 1A 证据保全与时序重建

工作内容：

1. **先保全，再分析**：复制本次 run、trace、回执、日志到只读事件目录并计算哈希；保全前不重跑、不清理、不改状态。
2. 重建 fill 超时链路：Playwright 动作、worker 返回、HTTP 客户端、CLI 退出、外层超时、控制器状态转换分别记录时序；统一使用 UTC + 单调时钟，标注时钟偏差。
3. 超时现场：启用 Playwright trace（超时即保留），记录页面状态、在途请求、worker 阶段；不只延长 65 秒。
4. 分类：业务动作未知、可纠正输入、只读失败、进程故障、用户明确停止分开；每类对应不同的恢复与交付路径。

验收：

- 事件目录包含原始证据哈希与时间线；
- 能回答“超时发生在哪一段、当时在途动作是什么”；
- 不依赖重跑产品操作。

#### 1B 恢复与幂等

工作内容：

1. 控制器 running 残留、锁文件残留、worker 失联：所有者核验 + 唯一恢复认领；不删除活跃锁，不仅按时间或 PID 猜测进程死亡。
   - owner 记录：`host + boot_id + pid + process_start_time + token + heartbeat`；
   - 恢复条件：进程不存在 + heartbeat 过期 + boot_id 匹配 + 唯一认领审计；
   - Windows 用进程创建时间，避免 PID 复用。
2. worker 健康/在途动作查询：`/health` 返回 `status / busy / in_flight_request / phase / last_activity / dispatch_id / pid / started_at`；启动时扫描 stale private 文件并回收孤儿；设置最大生命周期与受管退出。
3. 业务级幂等按 §3.2 P0-B 落地。
4. 用户停止与工程故障分开：用户取消不恢复产品测试；工程故障只恢复只读/证据；未知写入必须核查。

验收：

- 在 6 个状态转换点各 kill CLI 20 次：0 次永久 running；恢复 ≤2 条命令；每次有审计记录；
- 两个并发 run，其中一个崩溃，另一个不受影响；
- worker 被杀后可恢复只读证据，不重放未知提交；
- 同一提交成功后换 ID 再提交 → 被阻断。

回滚：

- 新恢复逻辑用 feature flag 控制；旧路径保留；
- 若出现误接管（>0 次），立即回滚并保留现场。

主要位置：`scripts/controller-command-session.mjs`、`scripts/recovery-policy.mjs`、`scripts/structured-actions.mjs`、`scripts/browser-task.mjs`、`scripts/managed-process.mjs`。

### 第 2 项：结果持续保存与异常交付（P0）【修订】

对应原计划 2；融合隐形问题的 worker 内存丢失、计数污染和证据生命周期建议。依赖 1A 的证据保全与 1B 的收口边界。

工作内容：

1. **增量持久化**：每条动作和断言增量写入 JSONL；定义 schema：
   `seq / event_type / request_id / payload_sha256 / schema_version / at`。
   - 单写者；单行 <4KB；flush/fsync 策略；按大小轮转；
   - 处理半行、重复事件、磁盘失败、版本兼容；
   - 提供 `rebuild` 命令，从日志重建结果。
2. **recovered 结果 schema**：正式结果不再只由 finish 生成；增加：
   - `result_origin: live | recovered`
   - `result_status: completed | partial | partial_recovered | blocked`
   - `browser_closed: true | false`
   - `finished_at: null`（无真实 finish 时）
   - `recovered_at / recovery_reason`
   - `source_receipt_sha256[]`
   - `limitations[]`
   下游报告/缺陷必须检查 `result_status`；recovered 不得标成 completed。
3. **reducer 规范**：
   - 按 `request_id` 去重，优先 completed 回执；
   - 任何 `started` 但无结果的回执 → `unknown`，不丢弃；
   - 保留 evidence_mode / simulation / fault 标记；
   - 按 seq/at 排序；冲突时保留全部并标 `conflict`；
   - 在 3 个历史 run 上验证，不只对本次 50 条过拟合。
4. **对账**：68 条设计用例 / 50 条断言 / 25 条关联用例；其余约 43 条逐条标「未测/部分/无断言/仅观察」；不得用 25 条代表全部完成。
5. **统计单源**：报告、Excel、HTML、Word、PDF 使用同一份确定性统计；各格式计数一致，附 canonical stats 哈希。
6. **partial 交付**：工程受阻时也可输出 partial 缺陷分析与 Word/PDF；契约明确接受有证据的部分执行，不伪造 finish 时间或浏览器关闭。

验收：

- 执行 3 条断言后终止自建 worker：恢复这 3 条事实并生成 partial 报告；
- 本次历史回执可在 3 个 run 上重复得到 50/46/4/25，unknown/partial 有明确处理；
- 报告、Excel、HTML、Word、PDF 计数一致；
- 68/50/25 对账表完整，未测项单独列出；
- 不伪造 `finished_at` 或 `browser_closed`。

回滚：

- 保留旧 finish 路径；新日志格式带版本，旧读端可忽略；
- recovered 结果只读，不可被旧代码当成 completed。

### 第 3 项：断言可信度与必要浏览器能力（P1，假通过风险优先）【修订】

对应原计划 3；融合工程审阅的 Oracle/覆盖深度、隐形问题 P0-1/P0-2 及原生 dialog 问题。

工作内容：

1. **只读状态断言**：补 `readonly / editable / enabled / disabled / checked / value` 等查询与断言，使“不可编辑”不再靠 fill 试探；快照返回可见范围与截断标记。
2. **正向锚点**：每个用例至少一条锚点（origin + path + title + 关键元素）；锚点随导航、登录、页面变化失效；`hidden` / `count:0` 必须绑定锚点，否则 `needs_review`；页面未就绪 → `not_ready`。
3. **Oracle 类型**：
   - `oracle_type: specified | derived | consistency | historical | exploratory`
   - `oracle_ref`：规则原文/公式/历史批次/两次观察；
   - 只有 `specified` / `derived` 能产生 `passed`；
   - `consistency` 产生 `consistent / inconsistent`；
   - `exploratory` 只产生 `observed`，不得算通过；
   - `expected == target.value` 仅在 `specified` 且有引用时允许。
4. **失败分类决策树**：
   - 页面未就绪 → `not_ready`（重观察，不是产品失败）
   - 定位器多匹配/非法 → `locator_issue`
   - 锚点不在 → `page_identity_issue`
   - 锚点在、唯一元素缺失、预期不明确 → `needs_evidence`
   - 锚点在、唯一元素在、值与 specified 预期不符 → `product_failure`
5. **dialog 策略**：默认记录并暂停/决定，不静默 dismiss；`beforeunload` 可单独放行；证据记录 `type / message / timestamp / decision`。
6. **dynamic feedback**：改为非阻塞环形缓冲（最近 N 条，带时间戳）；有 assertion 时不固定等待 1.5 秒；断言失败/未知预期时附加；不删除恰好能证明事实的证据。
7. **边界样本**：复用已生成的 128 字符样本；补 Unicode（code point/UTF-16/UTF-8/grapheme）、空值、控制字符。
8. **报告**：只向用户询问缺少的业务事实（如分页序号规则）；不要求用户裁决智能体自己制造的“共 0 条”预期。

验收：

- 空白页/错误页上的 `hidden` / `count:0` 检查不能形成业务通过；
- 有规格依据且定位文字等于预期时正常通过；
- 多匹配定位单列 `locator_issue`，不计产品失败；
- 合法 128 字符样本不因比较串抄错误报；
- 瞬时 toast 与原生确认框有准确时序和处理记录；
- exploratory 结果只标 `observed`，报告不显示为通过。

回滚：

- 断言 schema 向后兼容；旧结果可读；
- 新分类默认只影响新 run，历史 run 不改写。

### 第 4 项：调用效率、数据安全及工程基座（P1）【拆分】

对应原计划 4；融合三份意见的传输、性能、安全和工程维护建议。**拆为 4A/4B/4C 三个可独立交付的包**，每包独立验收与回滚，不在一个提交内更换整个架构。

#### 4A 安全与数据

工作内容：

1. 凭据/个人信息在各边界处理：模型可见输出、工具参数、文本回执、日志、截图；只读查看凭证也需脱敏；`secret_ref` 见 §3.2 P0-A。
2. 测试数据台账：记录归属、创建、清理结果；清理失败不阻止报告；未知写入不自动补偿；本次 3 条残留按 F2 结论处理，不按名称模糊删除。
3. 不可信材料边界：页面、附件、工具日志明确标记为不可信；补提示注入样例；范围校验不依赖文本标签本身。
4. 结构化授权 scope：origin/路径/允许方法/数据影响/有效期；`source_text` 只作证据；执行前校验动作集合 ⊆ scope。
5. 时间采集：模型往返、工具、浏览器、证据写入、排队、人工暂停；模型时间从宿主 trace 计算；并行跨度不重复累加；无价格信息不伪造费用。

验收：

- 合成敏感值不出现在模型可见输出、工具参数、日志、截图、普通交付；
- 提示注入页面不能让 Agent 扩大范围或伪造结果；
- 超出 scope 的动作被拒绝；
- 每个 run 有时间拆分与 token 记录。

回滚：redaction / scope 用 feature flag；旧 run 只读不改。

#### 4B 调用与证据成本

工作内容：

1. 子 Agent 结构化调用：从现有 `qa_request` 扩展；child hook 校验 `dispatch_id + contract_sha256 + allowed_actions`；与文件入口共享同一 handler，做等价性测试；旧文件入口保留为回退。
2. 动作 Schema 单源：参数、catalog、短错误码、文档由同一 schema 生成/校验；迁移期保留兼容层。
3. `sequence`：仅支持已观察、可确定的连续步骤；每步独立超时 + 整批总预算；逐步授权检查、回执落盘、取消检查；一步超时/取消/未知，后续不执行并记 `not_executed`；不假设事务回滚，不全批重放。
4. 网络日志：追加/有界刷新；失败请求、业务请求优先保留；静态资源可采样；保留 dropped 计数。
5. snapshot：按需/差量；返回 `truncated` 与总数；默认不返回全量 14k 文本。
6. 缓存：按内容哈希/不可变版本；来源变更、授权撤回、设计变化即时失效；不使用 mtime+size 作为安全依据。
7. 截图：通过项可采样；失败证据、瞬时反馈、最低结构化证据不丢失。

验收：

- 至少 5 个高频动作（dispatch、handoff、diagnose、export、browser_task）走单步入口，且有等价性测试；
- 合法重复查询不被误拦；批次失败不重放已执行提交；
- 网络日志不丢失败请求；
- snapshot 截断可见；
- 缓存不会因 mtime 变化而误用旧内容。

回滚：新旧入口并行；sequence 默认关闭，按需启用。

#### 4C 工程可复现

工作内容：

1. 运行时能力探测：`probePython(requirements)` 按用途探测；`QA_SECURITY_PYTHON` 用于 tomllib；Python <3.11 用 `tomli` 兜底；补 `engines`、`.nvmrc`、CI Node 20/22 矩阵。
   > 修正：本机问题是 **Python 3.9 能力不足**，不是“误选解释器”；不要用“换一个解释器”掩盖 tomllib 缺失。
2. 生产安装依赖：核对 `@playwright/test` 运行时依赖；确保 `npm ci --omit=dev` 后 URL 测试可运行；必要时改用 `playwright`/`playwright-core`。
3. 依赖治理：复核 xlsx/xmind 公告与实际导入面；三选一并记录：换 `exceljs` / SheetJS 官方 CDN 固定版本 / 接受风险并限制输入；补生成文件兼容性测试。
4. 宿主兼容：最小兼容矩阵 + 启动自检；区分“版本不兼容”与“越权”；兼容问题给只读诊断，不直接放行；不因 trace 格式变化静默 deny 全部动作。
5. 提示词：只去除真实重复，保留角色职责与技术规则单源；统计重复句与每角色字符预算；CI 检查；不做全仓格式化。
6. 代码：按修改边界渐进抽取；Prettier/ESLint 只作用于改动文件；增加覆盖率基线（c8）。
7. 测试资产：CI 校验真实 `test-assets.json` 的脱敏副本；browser 测试拆 `browser-contract` / `browser-e2e`。
8. 文档与配置：状态页改能力矩阵；历史记录保留且旧链接可用；删除或标注 `artifact_retention` 等死键；区分 11 个项目 Skill 与实际挂载集合；临时脚本/业务资产先分类，不以清理名义删除用户数据。

验收：

- 干净 Windows VM（Node 20.11/22、Python 3.11+）按 README 跑通 `npm test`；
- `npm ci --omit=dev` 后 URL 测试可运行；
- 依赖决策有记录，生成文件兼容性通过；
- 宿主版本不匹配有明确诊断；
- 提示词重复句下降，且有预算检查；
- 覆盖率报告可下载；
- 真实资产结构在 CI 中被校验。

回滚：依赖替换保留旧生成器；宿主补丁保留 restore；文档改动不删历史。

### 第 5 项：针对性复验、真实验收与版本固化（P1）【修订】

对应原计划 5；融合专家的 Canary、确定性评分、交付边界与文档收敛。

验收顺序：

1. **Canary 套件进 CI**（见 §8）：超时收口、死锁、worker 退出、重复提交、空白页负向断言、定位错误、提示注入、敏感证据、超长 Excel。
2. **测量协议**（按 §3.2 P0-C）：固定模型/环境/任务集；每场景 ≥10 次；median/p95；拆分时间；人工暂停单列；跨模型不比较。
3. **真实任务**：在 PenguinHarness 运行短小任务，验证“局部异常后仍生成 partial 报告”和“一步结构化调用”；不得手工改 manifest 或代写业务结果。
4. **场景矩阵**：独立 URL、直接用例/报告、同类规模全流程；每个修复项至少对应一个 canary + 一个真实任务 + 一个产物检查（traceability matrix）。
5. **交付边界**：
   - Excel 32,767 字符上限、XML 控制字符、重复 case_id、`related_cases` 类型；
   - PDF 字体嵌入（无 SimSun 机器可读）；
   - HTML 行内 Markdown/相对链接；
   - 时区统一并标注；
   - XMind 兼容性。
6. **Release gate**：
   - `npm test` 全绿（干净环境、明确版本）；
   - canary 全绿；
   - 无永久 running、无重复提交、无敏感值出现在交付；
   - 报告/Excel/HTML/Word/PDF 计数一致；
   - 未测项单独列出；
   - 回退步骤可用。
7. **固化**：能力矩阵、测试结果、剩余限制、回退步骤；按工作包提交；当前计划不包含新的 Git 推送授权。

完成标准：不因内部技术问题要求用户解锁；执行故障仍能交付可信部分结果；结果数字与原始记录一致；未测不算通过；未知写入不重复；中文回复简洁且提供可点击交付。真实产品测试失败不等于工程验收失败，无法安全恢复时如实报告而非强行成功。

> 例外：安全事件（如 Key 暴露）与真实业务决定是合法的用户介入点，不受“不要求用户解锁”限制。

## 5. 明确延后【保留 + 风险接受表】

以下有价值，但不应拖延当前主链路修复：

- 20 至 30 个真实模型场景的大型评测平台、夜间任务和模型路由：先做本次必要回归；此前暂停的题库评测和模型调整不自动恢复，不创建定时任务。

- 性能、可访问性、安全冒烟、国际化及变更影响选测：独立能力迭代，不作为本轮完成前置。
- 自动留存删除、根 LICENSE、客户数据流向和对外分发：先盘点、dry-run 和确认政策，再实施删除或授权声明；不自动改写 Git 历史或轮换密钥。
- 字体、装饰样式、商业平台采购和独立 EXE 封装：继续延后。

## 6. 执行原则与状态【保留 + 管理表】

- 本计划以通用机制实现，不把运营 Key、服务类别、具体 URL、业务文案或当前模型写死到框架。
- 不取消全部守卫，不增加技术审批文档，不把技术异常变成业务确认问题。
- 先恢复事实和交付，再恢复产品操作；未知副作用宁可保留不确定状态，不自动重放。
- 工程回归可以使用隔离合成站点；真实 Agent 验收必须在 PenguinHarness 完成，两者分别标注。
- 每项结束给出：实际修改、验证结果、用户影响、剩余风险。性能数字来自测量，完成状态来自证据。

### 6.1 管理表【新增】

规模为粗估：S ≤2 人天，M 3–5 人天，L 6–10 人天。

| 工作包 | Owner | 规模 | 依赖 | 回滚 |
| --- | --- | --- | --- | --- |

### 6.2 停止条件【新增】

出现以下任一情况，暂停整改，先处理现场：

1. F1 未闭环且 Key 仍有效；
2. 基线连续 3 次无法复现，或模型/宿主版本在整改期间变化；
3. 恢复逻辑出现误接管（>0 次），或删除活跃锁；
4. 真实用户数据/凭据可能再次进入证据；
5. 宿主升级导致 hooks 全面 deny，且无诊断路径。
