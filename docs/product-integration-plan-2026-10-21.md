# 软件测试智能体产品整合计划

日期：2026-10-21。状态：已进入实施，统一入口、兼容配置、版本检测及隔离安装原型已完成首批实现；完整发行验收尚未完成。进度和验证证据见[实施记录](product-integration-progress-2026-10-21.md)。依据：用户确认长期保留 PenguinHarness 底座，持续检测上游版本并进行兼容性更新。

本计划取代可行性研究中“后期替换宿主内核”的路线。目标是统一目录与启动入口、建立兼容层、完善独立测试业务和界面，并长期跟随宿主升级。保留多 Agent 实现，模型接入与通用执行能力继续使用 PenguinHarness。

**新增最终验收要求：本次改造完成后，其他人能够从项目 GitHub Releases 下载应用安装包，在没有本工程、PenguinHarness 或开发环境的受支持电脑上安装使用。仅提供源码、启动脚本或本机目录整合不算完成。** 首版按当前平台以 Windows 10/11 x64 为目标支持范围，实际最低系统版本须经安装验证；其他平台另行验收。

## 计划制定时的基础与差距

| 项目 | 已有基础 | 还缺什么 |
| --- | --- | --- |
| 宿主 | 本机已安装适配后的 0.2.16 | 产品级兼容清单及升级协调入口 |
| 启动 | start-penguin-qa.mjs 设置 Shell、编码并启动 | 统一路径解析、版本检查、健康反馈、已有实例识别 |
| 路径 | QA_APP_DATA_ROOT、PENGUIN_AGENT_ROOT、目录上下文 | 集中配置、旧路径兼容及迁移工具 |
| 安装 | 补丁事务、哈希校验、恢复、品牌检查 | 宿主安装、适配、数据迁移之间的完整升级事务 |
| 测试业务 | 阶段状态、派发合同、执行证据、质量与交付规则 | 收拢宿主依赖，明确业务事实来源及对外服务接口 |
| 界面 | workspace-ui、delivery-ui、人工操作界面 | 减少依赖宿主内部组件，统一任务状态和业务操作 |
| 发布 | 源码资源白名单 | 完整运行依赖、可复现打包、干净机器验证；当前不是独立安装包 |

现有 core 回归的三项失败已在升级前代码复现，另有浏览器恢复组未完成。实施前保留基线和未解决项，新批次必须证明没有引入回归，不能将已有失败隐藏为全绿。

## 目标边界

- 宿主负责：模型接入、通用 Agent 循环、会话、工具基础设施、流式消息及通用能力升级。
- 自有业务负责：测试项目、业务 run、阶段推进规则、执行授权、证据、质量判断、交付与业务恢复决策。
- 适配层负责：宿主会话及子 Agent 句柄、事件与 trace 转换、hook、插件、接口及版本差异。
- 产品入口负责：路径、启动诊断、版本展示、兼容检查和升级过程的协调。

业务完成状态不能仅根据模型最后一句答复推断，继续使用现有确定性校验和产物证据。保留宿主原始 trace，通过适配器建立与业务事件的关联。

## 第一阶段：统一目录与启动入口

### 批次 A：统一入口和兼容基线——当前可直接实施

1. 增加安装路径配置格式与解析器，集中描述产品根、业务引擎、宿主程序、宿主数据、QA 应用数据、工作区及运行依赖。
2. 区分两种布局：现有分散安装兼容模式、未来统一根目录模式。先让当前环境通过新入口启动，再做物理迁移。
3. 增加兼容清单：产品/适配器版本、支持的宿主版本及制品摘要、所需能力、数据格式和验证状态。未知版本标记为“未验证”，不自动安装补丁。
4. 建立统一启动入口，复用现有启动器、安装器的只读检查能力，检查路径、宿主版本、补丁、角色同步和依赖。
5. 识别已有实例及其数据根；正确实例可复用或提示打开，归属不明时报告冲突，不强制终止。应用有任务运行时不自动修复安装或覆盖文件。
6. 提供机器可读诊断及用户可理解的错误，覆盖端口陈旧、服务未就绪、认证失败、版本不兼容。只读检查不触发模型、不安装依赖、不输出凭据。

交付物：路径配置 Schema/示例、解析模块、兼容清单、统一启动脚本和快捷入口、诊断报告、针对性测试。

验收：现有布局可正常使用；改变路径可在隔离环境解析正确；未知版本和冲突实例有明确处理；原任务与配置不变；新入口可以明确区分“进程已启动”和“服务已就绪”。第一批不要求先做新的自有 EXE。

### 批次 B：统一目录原型与正式迁移——可开发工具，切换须先通过验证

建议目标布局（路径示例，尚未创建）：

```text
E:\AITestHarness\
  launcher\                 统一启动与维护入口
  app\engine\              自有业务工程的稳定真实路径
  app\adapters\penguin\    宿主兼容层
  runtime\penguin\         受管理的宿主安装
  runtime\tools\           Node/Python/浏览器等依赖
  data\penguin\            宿主数据
  data\qa\                 自有应用数据
  data\desktop-profile\    桌面状态（需验证桌面路径支持）
  workspaces\               新任务及交付物
  updates\                  暂存、版本清单、事务日志
```

1. 先生成只读迁移清单：文件来源、目标、容量、路径引用、数据所有者及冲突。
2. 在隔离目录验证复制部署、依赖完整性、宿主身份与启动；不让两个实例写同一数据根。副本中禁用真实计划任务、外部连接及自动执行。
3. 验证 PENGUIN_HOME 与桌面 userData 的分别配置；后者若需要改动桌面壳，作为显式适配项，不宣称单靠环境变量完成全部迁移。
4. 处理 hook/project.json、工作区索引、运行记录和历史文件引用的绝对路径。使用有记录、可恢复的迁移映射，不能全盘字符串替换。
5. 处理官方安装器的目标目录、卸载注册、快捷方式和后续升级行为；不能只复制 EXE 就宣布安装完成。
6. 正式切换前正常退出应用，取得一致的数据备份，复制校验后再切换入口；旧位置和外部备份保留。

验收分开记录：新任务可运行、历史交付可读取、旧会话可查看、旧任务可续接、桌面状态可恢复。续接不通过时保留原实例访问方案，不将“可以打开页面”视为迁移完成。

不使用目录链接规避现有隔离检查。业务引擎初期保持稳定真实路径，防止版本目录切换破坏运行记录中的 engine_root。默认集中管理，用户指定的外部工作区仍保留。

## 第二阶段：建立清晰兼容层

### 批次 C：依赖清单与适配接口——当前可开始

1. 分类登记全部宿主依赖：HTTP/SSE、trace、子任务句柄、工具参数、hook、前端、桌面及安装器。
2. 将精确版本配方和现有校验入口收拢到兼容模块；保留旧脚本薄入口，避免移动文件即破坏已安装引用。
3. 定义业务所需的小接口：读取会话证据、映射事件、关联派发与子任务、提交输入、取消/续接、读取交付、人工操作和能力查询。先以现有调用需要为准，不另造泛用框架。
4. 优先迁出直接读取宿主 trace 的逻辑；使用合成与脱敏样本验证同样输入得到同样业务结论，保留原始来源、消息标识及顺序。

验收：至少一条业务链路只经适配器访问宿主；现有恢复、部分结果交付和阶段校验语义保持一致；业务代码不新增宿主编译符号依赖。

### 批次 D：插件替代补丁原型——需要实验验证

先验证一个带会话鉴权的只读交付接口能否由服务端插件提供。检查授权、路径边界、错误反馈、重启和版本不兼容处理。通过后再扩展至人工操作、工作台页面及角色资源。

子 Agent 生命周期、工具边界及中断恢复补丁复杂度更高，暂保留精确版本适配，只有等价验证通过后才移除。公开扩展点不足时保留最小源码适配，不改为无法审查的宽松文本替换。

## 第三阶段：完善测试业务和界面

### 批次 E：统一任务视图——可设计，依赖前述业务接口逐项落地

1. 用业务 run 和阶段状态驱动任务列表与详情，区分规划、执行、等待人工、受阻、取消、部分完成及完成，避免仅依赖聊天文本。
2. 统一呈现需求来源、测试设计、执行结果、缺陷及报告；保留证据链接与未验证范围。
3. 将人工登录/确认、继续、重试、返修分别映射到已有合法业务操作，防重复提交，不把“继续”误做再次派发。
4. 保留按需调用一个专业 Agent 和显式全流程两种入口，避免强迫所有任务跑六阶段。
5. 继续复用宿主窗口、会话、模型设置和可用页面扩展点；独立业务界面不要求先重写 Electron 桌面壳。

验收：用户能从任务视图理解当前状态、操作原因和交付结果；单阶段与六阶段样本交付、中断续接及人工操作可追溯。产品执行失败应如实显示，不能用界面验收通过替代业务测试通过。

## 第四阶段：长期跟随宿主升级

### 批次 F：版本检测与兼容报告——第一阶段即可并行开发

实现用户触发的版本检查入口：读取官方稳定 Release，与已安装、已验证版本比较，保存检查时间、来源和兼容结果。支持超时、离线、限流和缓存，不把“发现新版本”等同于“可以安装”。

状态至少区分：已验证可用、新版待验证、不兼容、检查失败。预发布版本不默认进入正式通道。此计划不创建定时后台监控；周期检测可在产品内另行实现，避免把“制定升级方案”当成已启用自动任务。

### 批次 G：受控更新——依赖迁移与兼容验证

流程：发现版本 → 核验制品 → 暂存适配 → 专项/迁移验证 → 等任务安全结束 → 一致备份 → 安装与适配 → 健康检查 → 标记成功。

优先复用官方安装制品及签名验证，将自己的兼容步骤包在产品维护入口内；如后续必须自行构建桌面壳，再评估自有签名与分发渠道。仍只有一个入口协调最终更新，不允许官方覆盖与自己的适配器并行写安装目录。

单独审查桌面更新、CLI 更新及热更新路径。PENGUIN_UPDATE_CHECK=off 只关闭检查，不能当成所有更新入口的控制措施。

验收：不支持的版本不会覆盖当前安装；下载/适配/启动失败可恢复；数据迁移不兼容时按数据策略回退；升级后的新增数据不会被旧快照静默覆盖。没有新上游版本时可演练重复部署及受控故障，不能冒称未来版本兼容性已验证。

## 必须完成的发行批次 H：GitHub 下载安装即用

本批次属于本次改造的必交付范围。打包原型与批次 A/B 同期开始，尽早暴露依赖、宿主身份和安装问题；正式发布验收在业务与兼容验证完成后进行。

### 用户体验

仓库 README 的下载入口 → GitHub Releases 的 Windows 安装包 → 安装 → 打开 AITestHarness → 首次模型配置 → 创建测试任务 → 查看交付物。

用户无需克隆源码、运行 npm/pip、安装开发工具、单独部署 PenguinHarness、手工创建七个角色、安装补丁或编辑 JSON。首次模型使用仍需要用户自己的可用服务账号/API Key 或已支持的其他认证方式；界面完成配置和连接验证，不分发维护者密钥，也不承诺应用自带免费模型额度。测试目标的账号和人工登录按实际业务提供。

### 安装包与初始化

1. 提供带版本的 Windows 安装包。默认包含固定且经过验证的宿主、业务代码、适配资源、工具运行时、Python 报告依赖、必需浏览器与字体等实际依赖；任何必要的联网下载都须由安装器明确管理并校验，不让用户自行准备环境。
2. 不直接打包维护者的已使用安装目录或用户配置。宿主从可验证的官方制品或固定源码构建取得，自有资源按发布白名单纳入；生成依赖与许可证清单、SHA256 和版本信息。
3. 初始化角色、Skills、hook、默认工作区和干净数据目录，保证重复启动幂等。当前 sync-penguin-agents 要求目标角色已存在，必须补齐自动创建流程；首次安装不能依赖本机已有七个角色。
4. 安装路径可配置，不含维护者的 E:/D: 盘绝对路径。正式支持普通用户权限路径、中文与空格用户名/路径，并验证系统依赖；不能以降低路径边界检查换取兼容。
5. 提供快捷方式、升级和卸载入口。与用户原有 PenguinHarness 的数据根、实例锁、安装/卸载身份及端口明确隔离，不能覆盖其他用途的宿主配置。
6. 卸载默认保留用户数据；升级保留模型配置、会话和交付。若安装程序保留在受保护目录，数据仍需放在用户可写且不被更新覆盖的位置；单目录布局优先采用合适的用户可写产品根。
7. 明确安装包签名状态。上游签名不能替代自有安装器签名；签名能力取决于发布者证书或签名服务，未配置时如实标注，不能通过关闭系统安全检查完成安装验收。

### GitHub 构建与发布

- 增加 Windows 发行构建工作流，固定宿主与工具依赖来源和版本，打包只使用明确允许的资源。现有工程 CI 不是安装包构建流程，也不能因为 runner 已装开发工具而认定依赖已内置。
- Tag/手动构建生成安装包、摘要、版本兼容信息、第三方声明及验收结果。先形成可审核的发行候选，再按实际发布授权上传 Releases；用户提交源码本身不会自动变成可下载安装的应用。
- README 提供下载、支持平台、首次配置和升级说明。安装包通过 Releases 分发，不把大体积制品及私人数据提交到 Git 历史。
- 校验包内不含维护者凭据、私人站点配置、Cookie、历史聊天、业务输入、输出或备份。生成示例数据与私有配置严格分开。

### 最终验收矩阵

| 场景 | 必须达到的结果 |
| --- | --- |
| 干净 Windows，无 Node/Python/Git/PenguinHarness | 安装后可启动，必需依赖就绪，不要求用户开终端 |
| 首次运行 | 自动初始化角色和目录，在界面配置用户模型后可发起任务 |
| 单阶段任务 | 使用实际宿主及模型完成最小用例交付，可读取 Excel |
| 六阶段合成流程 | 在本地测试基座完成需求到报告，能展示真实结果与部分失败，不要求所有测试断言都成功 |
| 文档和浏览器 | 必需浏览器可启动，XMind/Excel/Word/PDF 生成并可下载或由支持的预览方式查看；外部编辑软件不默认视为已安装 |
| 共存与不同路径 | 既有 PenguinHarness 不受影响，中文/空格及自定义安装位置可用 |
| 重启和恢复 | 会话和交付保留，中断后不重复派发实际任务 |
| 覆盖升级与失败回退 | 新旧产品版本按兼容规则升级，配置保留；失败可恢复且不丢失新增数据 |
| 卸载 | 程序可卸载，用户数据按明确策略保留 |
| 制品来源 | 在测试机下载实际发行候选安装，而非直接运行源码；记录版本、摘要和环境 |

若当前环境没有干净 Windows 测试机/虚拟机或可用的模型验收条件，相关项必须明确标记未完成，不以静态检查或 CI 构建成功替代。本次最终完成标准为：**安装发行批次 H 和适用的整合验收通过，生成可供用户发布的安装制品与说明**；公网正式发布状态单独记录。

每个批次提交实现、必要的针对性测试、验收证据和状态更新。当前工作区已有升级及界面改动，实施时保留这些内容，不通过清理工作区覆盖已有成果。工期在批次 A 与隔离原型完成后再估算，不提前把待验证能力承诺为已可交付。
