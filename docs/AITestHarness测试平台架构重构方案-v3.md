## 0. 文档说明

### 0.1 这份文档要解决什么问题

当前工程（Windows 本机安装的测试工程师工具）在 2026-11 的演示中暴露了严重问题：给一个测试环境地址和账号密码做探索性测试，耗时十几分钟、消耗 100 万+ token，实际没有完成有效测试，领导评价"不如直接用通用 agent（codex）"，并要求"自己写工具插件优化执行流程"。

本方案的核心判断是：**问题的根源不是工具不够，而是执行路径本身由 LLM 在运行时自由决定**。因此优化的方向不是"给 agent 多配几个工具"，而是把流程从"agent 自主完成"改为"编排驱动的确定性节点 + 少量决策节点"。

## 1. 执行摘要

### 1.1 三句话结论

1. **现状是"运行期审计"，不是"编译期结构化"**。阶段产物校验、派发回执、证据哈希，全是 LLM 跑完之后检查它有没有胡来；真正的结构化应该是事前把路径定死，让胡来没有空间。审计再严，改变不了执行本身是概率性的事实——**所以"两次结果不一致"是必然结果，不是 bug**。
2. **通用 agent 永远停在"探索"，产品价值必须落在"固化 + 重放"**。Hifox 的实践证明探索式执行也能用，但它靠的是极强的人工指令纪律 + 外部工具承载资产；我们要做的是把这份纪律变成代码级校验器和可复用资产，这是可持续的形态。
3. **短期要解决"进得去、看得见"，中期要解决"测得准、可复现"**。上次演示失败只暴露了第一层；如果只修第一层，下次演示依然是"跑得动但没用"。

### 1.2 方案主干（四层 + 一条主链路）

```
入口层   桌面端 / 本机 Web / CLI / 定时调度        ← 全部连本机服务，单通道
   ↓
决策层   探索器 · 翻译器 · 归因器 · 审阅器          ← LLM 只在这一层，且每步留痕
   ↓
编译层   各级编译器 + 五道硬闸 + 血缘/增量重算       ← 新增的核心，现有工程完全缺失
   ↓
资产层   IR + 元素库 + 用例库 + 片段库 + 应用地图 + 数据字典 + 回归集   ← 可版本化
   ↑
执行引擎  Playwright / HTTP / Appium / 小程序 · worker 池 · 断言 · 取证 · 自愈
```

### 1.3 关键数字目标

| 指标            | 现状        | 目标                 | 性质    |
| ------------- | --------- | ------------------ | ----- |
| 冷启动到可测状态      | 十几分钟（未成功） | **≤1 分钟**（会话固化后秒级） | 演示可见  |
| 单次探索 token    | 100 万+    | **≤20 万**（工程硬预算）   | 成本可控  |
| 同用例 N=3 结果一致性 | 无法保证      | **100%**（不达标不许入库）  | 质量门槛  |
| 缺陷召回率         | 未建立       | **≥70%**（种子缺陷集）    | 有效性证明 |
| 错误通过率         | 未建立       | **≤5%**            | 最不可容忍 |
| 误报率           | 未建立       | **≤10%**           | 团队信任  |

### 1.4 路线与工期

M1 执行底座（重放可复现）→ M2 探索器与四类 Adapter → M3 回归集与 flaky 治理 → M4 全链路编译 → M5 缺陷闭环。

核心链路 M1~~M3 约 \*\*2.5~~3.5 个月\*\*（3~4 人全职），每个里程碑都有可展示的量化效果，不存在"做到最后才知道行不行"。

## 2. 问题诊断

### 2.1 现状（依据 codex 交接文档 2026-11-11）

**产品定位**：Windows 本机安装的公司内部测试工程师工具，桌面端与本机 Web 共用本机服务（`localhost:18766`），服务端只负责账号、权限、Agent/Skill/插件发布。

**已有能力**（源码存在级）：10 个业务 Agent + 15 个 Skill，`orchestration-workflow.json` 七阶段（analysis → test_points → test_cases → execution / 4A api_execution → defects → report）；三层任务模式（`task/auto`、`lifecycle/auto`、`staged`）；较完整的治理机制（结构化动作、工具守卫、派发回执、阶段状态机、attempt 账本、产物 Schema、来源台账、设计冻结、文件哈希、缺陷生命周期、报告证据校验）；浏览器跑在本机/内置浏览器，有"人工登录接力"卡片雏形。

|                                                                                           |        |
| ----------------------------------------------------------------------------------------- | ------ |
| **自我诊断的三大风险**：① 工程完整性高于真实测试有效性；② 源码/候选/安装版/工作区四层漂移；③ Agent/Skill/提示词偏多偏重。文档自评：\`真实测试有效性基线 | 未建立\`。 |

### 2.2 领导反馈（2026-11 演示）

- 场景：给一个测试环境地址 + 账号密码，做探索性测试（公司内部系统，登录功能）；
- 结果：十几分钟未真正进入可测状态，token 消耗 100 万+，没有产出有价值结果；
- 结论：「不如用 codex」「很鸡肋」；
- 建议：「自己写工具插件来优化执行流程，例如登录时遇到验证码的情况」。

### 2.3 根因分析（本方案的立论基础）

| 层面      | 具体问题                                                                         | 后果                             |
| ------- | ---------------------------------------------------------------------------- | ------------------------------ |
| **架构层** | 执行路径由 LLM 运行时决定（截图 → 理解 → 猜 → 点 → 确认，每步都问模型）                                 | 路径不可复现、token 随步数线性爆炸、演示不可控     |
| **模式层** | 只有"从需求开始"的七阶段，**没有"只有 URL+账号"的探索模式**                                         | 演示场景被硬塞进需求链路，前三阶段在无输入下凭空产出     |
| **治理层** | 校验是"事后审计 + LLM 自查"，不是"事前编译 + 程序硬校验"                                          | 约束解决" Agent 会不会说谎"，解决不了"跑得稳不稳" |
| **资产层** | `test-asset-management`（元素/定位器/断言库）、`test-selection`（回归集）**定义了但未绑定任何 Agent** | 每轮都从零开始，没有可积累的东西               |
| **度量层** | 没有种子缺陷集、召回率、误报率、错误通过率                                                        | 无法回答"你到底有没有用"                  |

> **一句话**：工程把"流程正确"做成了目标，"测出缺陷"从未被验证过。100 万 token 的大部分消耗在阶段产物、Schema 校验、派发回执、证据链这些**治理开销**上，而不是在测功能。

### 2.4 六项能力缺口

| # | 缺口                 | 影响              | 对应章节   |
| - | ------------------ | --------------- | ------ |
| 1 | 探索模式缺失（无需求场景无定义）   | 演示翻车的直接原因       | 15     |
| 2 | 编译层缺失（无固化、无硬闸、无重放） | 结果不可复现          | 7、8、9  |
| 3 | 资产层未接线             | 每轮从零，无护城河       | 9、17.5 |
| 4 | 回归集与影响分析未落地        | 无法支撑真实上线节奏      | 13     |
| 5 | flaky 无治理          | "两次结果不一致"，结论不可信 | 14     |
| 6 | 有效性基线缺失            | 无法量化价值，也无法向领导证明 | 19     |

### 2.5 对标 Hifox 的结论（基于其 11 份内部材料）

**Hifox 的真实做法**：5 个专项 Agent（白小浅预检 / 测小案用例 / 凤小九 Web 执行 / 测小口接口 / 端小九客户端）+ 1 个队长 + 1 个事务；执行层是 **Playwright 无头 + Agent 现场看页面找元素**，**没有用例脚本、没有录一次重跑多次**；接口测试 1008 个接口 / 62 个场景 / Agent 运行 25 小时 / 848 万 token / 覆盖率 99%+。

**它靠什么保证可信（三层，全部可封装成工具）**：

| 层   | 机制                                                                                              | 我们要学的                                                       |
| --- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 执行前 | 用例已结构化到表（ID/优先级/分类/前置数据/步骤/预期/失败判定）；输入优先级七级排序；载体与环境预先固定                                         | 编译层的"硬编码版"：产物先结构化，agent 只负责填                                |
| 执行中 | 定位连续失败 5 轮立即阻塞；2.5 小时自计时收尾；环境错误即停不重试；测试账号+万能码+邮件验证码链路；每账号独立浏览器上下文；**结论六档**（通过/失败/部分/阻塞/低置信/未执行） | 与我们的自愈分级、预算截断、验证码策略链、独立 Context、五档结论几乎一致——**说明这些设计是生产验证过的** |
| 执行后 | 覆盖率自己解析路由做双向 diff（不信生成器）；清理后连续跑 3 轮全绿才算完；接口定义改了引用它的场景必须重新保存                                     | N=3 一致性闸、覆盖率校验器、依赖失效检测                                      |

> Hifox 自己的总结：**"测试 Agent 靠不靠谱，不靠模型聪明，靠把'预期、边界、证据'写死在指令里。"**

**我们必须承认的修正**：执行层"零探索"不能作为全流程强制要求。Hifox 能接受探索，是因为**预期被事先固定、探索有工程边界、稳定由验收标准保证**。所以准确表述是——**执行可以探索，但"什么算对"必须事先固定，"探索"必须有硬预算，"稳定"必须由 N=3 验收**。我们的固化链路是把"稳定"从验收环节提前到编译环节，成本更低、复用更好。

**Hifox 的三个弱点 = 我们的差异化空间**：

| Hifox 弱点                                 | 我们的机会                              |
| ---------------------------------------- | ---------------------------------- |
| 执行靠自由探索，必然 flaky，靠"连跑 3 轮全绿"筛，成本是重复 3 次  | 固化后 1 次即可，且改动可 diff                |
| 用例资产散在评论/Apifox 里，无可视化维护，改一版靠 agent 重新理解 | 执行计划是可读可改可评审的 DSL                  |
| 可靠性建立在"指令写得足够好"（运营能力），模型换代或上下文压缩即退化      | 可靠性建立在"校验器拦得住"（工程能力），对 3~4 人团队更可持续 |

### 2.6 一句话定位（对外话术）

> **通用 agent 每次都在重新认识环境，我们把认识结果保存成可复用资产。**  
> 它的成本结构是"每次消耗 token"，我们的成本结构是"一次投入、长期复用、逐轮增值"。

## 3. 核心原则（三条，不可让步）

### 3.1 原则一：资产化优先

> **每一步先问：这个环节能否沉淀为可复用的工程资产？凡是能结构化的，必须结构化并入库复用；LLM 只保留在真正的开放决策点。**

这条原则的落点不是"省钱"，而是**产品立身之本**：如果全流程都靠 LLM 自由发挥，本工程与"拿 codex 跑一遍"没有任何区别，搭建它的意义就不存在。确定性组件（登录器、定位符库、执行计划、归因规则）是**工程资产**，每跑一轮都在积累；通用 agent 每次都是**消耗品**。

### 3.2 原则二：可复现优先

> **任何执行路径必须可复现；凡依赖 LLM 的步骤必须可回放、可审计。**

理由：一个测试系统如果执行路径本身不确定，就分不清失败是"产品缺陷"还是"agent 抽风"。**测试系统自己必须先可信，它测出的结果才有价值**——这是稳定性硬要求，不是成本优化。

### 3.3 原则三：LLM 边界白纸黑字

> **LLM 出现在哪、不出现在哪，由架构文档明确定义，不允许运行时随缘。**

LLM 的正确定位是**大脑而非四肢**：结构化组件负责"走"（可靠执行已知路径），LLM 负责"想"（决定走哪条路、遇到未知怎么办、判断结果对不对）。四肢全交给 LLM，等于让大脑亲自控制每根手指，又慢又抖。

三条原则的可执行判据：

| 判据                       | 不满足时           |
| ------------------------ | -------------- |
| 环节能否形式化？能 → 程序做          | 若交给 LLM，视为架构违规 |
| 产物能否写成 schema？不能 → 没有结构化 | 视为不可复现，不许入库    |
| 失败能否被归因？不能 → 不可信         | 该结果不计入准入结论     |

## 4. 核心模型：探索 — 固化 — 重放

### 4.1 准确定义（勿再退回旧说法）

| 阶段             | 谁执行                   | 频次       | 特征                                       |
| -------------- | --------------------- | -------- | ---------------------------------------- |
| **探索 Explore** | LLM 主导，允许慢、允许贵（但有硬预算） | 一次性 / 增量 | 摸清页面结构、交互路径、登录方式、数据依赖，产出**事实**           |
| **固化 Compile** | 程序 + 少量 LLM 辅助（仅翻译）   | 一次性，可重入  | 把事实编译成确定性执行计划：步骤 + 元素指纹 + 等待 + 断言 + 数据引用 |
| **重放 Replay**  | **纯代码，零 LLM**         | N 次      | 按计划执行，路径一致，成败皆可归因                        |

**关键的准确表述（v2 曾表述错误，此处定稿）**：

> **约束的对象是"执行进程"，不是"资产生命周期"。**  
> 即：**执行时不允许临场摸索，但资产是活的**——允许人改、允许局部重探索、允许增量新增。

"探索只做一次、之后永远重放"是错的，因为它会把资产冻结，堵死"增量修改、新功能迭代"这条真实工作方式。

### 4.2 与行业实践（录制 → 调整 → 增量 → 回归）的对应

真实自动化测试的组织方式：Pytest/TestNG + Selenium/Playwright + Allure + CI；Page Object / Screenplay 模式（元素与操作分离、用例与数据分离）；集中元素库 + 命名约定；**分层回归**（冒烟分钟级 / 核心小时级 / 全量夜间）；失败自动截图录像、标 flaky、人工 triage。维护成本占总投入 60% 以上。

两处必须纠正的认知：

1. **"每次上线前跑整个脚本"在真实团队大多做不到**（几千条用例跑不动）。真实做法是**按影响范围选集**——改了哪个模块就跑该模块及其依赖。这才是"增量"的工程含义。
2. **行业头号痛点不是"脚本写不出来"，而是 flaky 与脚本腐烂**（成熟团队要求 flaky < 5%；UI 大改一次废掉 20~30% 脚本）。

**录制回放两次失败史（Selenium IDE、低代码录制）的启示**：

> **能录的只有"怎么走"，录不出"走到哪算对"。断言必须来自测试点/需求，不能来自录制。**

这恰好是我们的优势：测试点与需求是上游产物，断言从那里生成，而不是从鼠标动作反推。

### 4.3 三层定位（与通用 agent 的本质区别）

```
【第一层 探索层】LLM 主导，工具是"感官+手脚"
   snapshot / click / fill / 读网络 / 读控制台 …
   产出：一次成功轨迹 + 语义化步骤意图

【第二层 固化层】程序主导，工具是"编译器"
   轨迹 → 执行计划（多指纹 + 类型化等待 + 断言 + 数据引用）→ 五道闸 → 入库 → 可 diff 评审

【第三层 重放层】纯代码，LLM 不参与
   执行计划 → 执行 → 结果 IR + 取证包 → 归因（LLM 仅分类）
```

> **通用 agent 只做第一层，每次都从零来。我们的增量在于把第一层成果沉淀到第二、三层：第一层用 LLM 解决"不知道怎么写"，第二三层用工程解决"写了就要稳"。**

## 5. 总体架构

### 5.1 四层结构

| 层        | 职责                                                         | 关键约束                                  |
| -------- | ---------------------------------------------------------- | ------------------------------------- |
| **入口层**  | 桌面端 / 本机 Web / CLI / 定时调度                                  | 全部连本机服务，**单通道**；不造第二套执行架构             |
| **决策层**  | 探索器、翻译器（轨迹→DSL 意图/断言推荐）、归因器、审阅器（报告）                        | 唯一允许 LLM 的层；只能产出"待编译候选"，**不得修改已固化资产** |
| **编译层**  | 需求→测试点→用例→执行计划的各级编译 + 五道硬闸 + 血缘/增量重算                       | 纯程序；校验不通过即阻塞，不允许"让模型想想办法"             |
| **资产层**  | IR、元素库、片段库、用例库、应用地图、数据字典、回归集、风险台账                          | 可版本化、可 diff、可人工手写                     |
| **执行引擎** | Playwright / HTTP / Appium / 小程序 · worker 池 · 断言 · 取证 · 自愈 | 只执行已编译计划，**自身不做决策**                   |

### 5.2 已确认的架构决策

| #  | 决策                                 | 说明                                  |
| -- | ---------------------------------- | ----------------------------------- |
| A1 | **浏览器只用本机/内置，不建服务端无头集群**           | 与产品定位一致（Windows 本机工具）；批量回归也在本机多进程完成 |
| A2 | **没有"双通道"，只有"一个执行引擎的两种显示模式"**      | 有头（演示/接管/录屏/高亮）与无头（批量），同一进程不同参数     |
| A3 | **并行按 worker 进程隔离**，不用同进程多 Context | 浏览器崩溃、内存泄漏在长回归中常见，进程级隔离可恢复          |
| A4 | **混合 driver 支持用例内混用**，但带四条约束       | 见 11.5                              |
| A5 | **接口自动化是一等公民**，与 UI 平级             | 见 11.6                              |
| A6 | **单阶段可单独执行**，但必须满足前置产物契约           | 见 5.4                               |

### 5.3 各阶段确定性边界

| 阶段         | 程序（确定性）                     | LLM（决策）                    | 产物          |
| ---------- | --------------------------- | -------------------------- | ----------- |
| 需求分析       | 文档解析、条款切分、OpenAPI schema 抽取 | 隐含约束识别、可测性判断               | 需求项 IR      |
| 测试点        | 知识库检索、维度矩阵、覆盖度计算、**验证方式分配** | 仅补矩阵空格子                    | 测试点 IR      |
| 用例生成       | 模板填充、数据工厂、覆盖校验、条数预算         | 步骤意图描述、断言语义表述              | 用例 IR       |
| **执行计划编译** | **步骤结构化、多指纹生成、等待提取、可执行性校验** | 仅辅助补 selector / 命名意图       | 执行计划        |
| 执行         | **全部（重放零 LLM）**             | 仅未固化路径（探索模式）               | 结果 IR + 取证包 |
| 缺陷分析       | 取证包组装、去重指纹匹配、模板渲染           | 根因分类 + 置信度                 | 缺陷 IR       |
| 报告         | 指标聚合、准入判定、模板渲染（**数字唯一来源**）  | **审阅**：风险识别 + 监控建议（不得生成数字） | 报告 + 风险台账   |

### 5.4 阶段可单独执行（保留现有设计意图）

保留"只跑某一阶段"的口子（真实工作中确实存在），但**必须满足前置产物契约**：只跑执行 = 消费已有执行计划；只跑报告 = 消费已有结果 IR。**不允许缺前置产物时由 LLM 现场编造**——这是上次演示翻车的机制根源。

### 5.5 阶段边界 vs LLM 调用边界（重要区分，v2 曾犯错）

**阶段边界不能按 LLM 调用次数划，要按三件事划**：

| 判据       | 含义                                  |
| -------- | ----------------------------------- |
| ① 人工确认卡点 | "需求理解对不对""测试点全不全"是两个独立评审动作，合并只剩一次确认 |
| ② 可独立重跑  | 需求变更时能只重跑需求分析，不必连用例生成一起重跑           |
| ③ 可独立失效  | 上游结论被推翻时下游整体作废；三者失效条件不同，不能混装        |

**结论**：需求分析、测试点、用例生成必须是**三个独立阶段、三份独立产物、三个独立确认点**。

**"需求变了三份产物都要变"是链式依赖的物理事实，无法回避**。能优化的不是"要不要变"，而是"**能不能只变受影响的那一部分**"——靠产物血缘与增量重算（6.2），与是否合并阶段无关。

**关于"三个阶段都绑 `test-design-methods` 是职责重叠"的正解**：重叠根因是"规则散在提示词里被各自解释"，解法是**下沉**——把该 skill 中可确定的部分（维度矩阵、checklist 检索、边界值字典）变成程序资产，agent 只在缺口处判断。合并 agent 会让规则更集中地依赖模型自觉，方向相反。

**补充：什么时候可以合并**——只有探索/轻量模式（本来没有需求和人工确认流程）可以用一次调用产出三份。正规模式一律分开。

## 6. 产物契约层（IR）与血缘

### 6.1 六份 IR 与公共血缘头（已定稿，详见《IR 契约规范 v1》）

> 本节为摘要。字段级定义、枚举字典、**38 条校验规则**、端到端示例见独立文档 **《AITestHarness-IR契约规范-v1.md》**，开发实现以该文档为准。规范第 10 章的 7 项待确认问题已于 2026-11-13 全部拍板（决议摘要见 23.1）。

**公共头（所有产物强制，缺字段不许入库）**：

```yaml
# 公共头 —— 所有 IR 的第一段
id: REQ-0001                  # 全局稳定 ID，前缀区分类型
type: requirement | test_point | case | plan | exec | defect | report
version: 3                    # 语义变更才 +1（表述变更不升版，见 6.3）
status: draft | reviewing | approved | deprecated
project: proj-internal-crm
module: order                 # 影响分析粗粒度入口
derived_from: [REQ-0001@2]    # 血缘上游（程序写入，不许 LLM 声明）
content_hash: sha256:...      # 正文语义指纹（去噪后规范化文本）
created_at: 2026-11-13T17:00+08:00
updated_at: 2026-11-13T17:00+08:00
author: agent:test_case_agent | human:zhangsan | program:compiler
approved_by: human:lisi        # 人工确认记录，approved 态必备
```

**六份 IR 的关键字段**：

| IR       | 关键字段                                                                                                                                            |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **需求项**  | 标题、描述、**原文引用**（doc / page / para / quote，必填）、类型（功能/约束/非功能）、业务规则、数据约束、验收口径、可测性标记、澄清问题清单                                                          |
| **测试点**  | 来源需求项、维度（功能/边界/异常/权限/兼容/性能/安全/数据一致性）、**验证方式**（api/ui/native/mini/db，强制分配）、控件类型、预期结果、优先级、知识库命中项、矩阵坐标                                             |
| **用例**   | 来源测试点、`primary_driver`、前置条件、数据集引用、步骤列表（动作 + 目标 + 数据引用）、断言（decide/observe）、teardown、**步骤数预算**、`touched`                                          |
| **执行计划** | 编译产物：`locators` 多指纹、类型化 `wait`、断言、`context_flow`、`fragment` 引用、`case_ref`、`gates` 五闸结果、`touched`；**环境差异放 `variants/`，一 plan 一血缘**               |
| **结果**   | 五档 verdict、步骤状态、`locator_hit`（命中第几指纹）、`self_heal` 记录、`retries`、证据引用、`touched` 刷新值、耗时、token、**`consistency`（N=3，含 baseline_exec + diff_detail）** |
| **缺陷**   | 指纹签名、去重向量、归因分类 + 置信度、证据 ID 列表、严重度、生命周期状态、关联用例                                                                                                   |


**字段级纪律**：

- `derived_from` 由程序在生成时写入，**LLM 无权声明**；
- `content_hash` 用语义指纹（6.3），不用文档 hash；
- `approved_by` 缺失的产物一律视为 `draft`，**不得进入回归集**；
- 无断言用例、无血缘产物、无原文引用的需求项，**不允许入库**。

### 6.2 产物血缘与增量重算

```
REQ-045 (v3)  →  TP-045-2  →  CASE-00123  →  STEP s1..s5  →  ASSERT a1,a2
     │                │              │
     └─ module: order └─ dimension: 边界 └─ touched: [POST /api/order]
```

**变更处理流程（纯代码，零 LLM）**：

1. 需求项 `REQ-045` 从 v2 升到 v3；
2. 沿血缘边向下求闭包 → 得到「待重算集合」；
3. **未被影响的产物一个字节都不动**（不动 = 不引入新风险 = 不用重新确认）；
4. 只把受影响子图喂给对应 agent，产出**增量 diff**；
5. 人工只审 diff，不重新审全量。

**效果**：500 条用例的项目，一次需求变更通常只触及 2~5 条用例。

**血缘图的第二个用途（免费获得）**：同一张图同时支撑 ① 产物重算（哪些要重新生成）② 回归选集（哪些要重新执行）。两者共用 `derived_from + touched`，不必维护两套映射。

### 6.3 语义指纹（增量重算能否落地的前提）

| 变更类型 | 例子 | 处理 |
|---|---|---|
| **语义变更** | "满 100 减 10" → "满 200 减 30" | 重算闭包，人工审 diff |
| **表述变更** | 措辞调整、章节重排、错别字 | 只更新指纹，**不触发重算** |

判据：**正文语义指纹**（去除格式噪音、规范化空白与标点后的文本 hash），**不是文档 hash**。

不做这一步，每次文档小改都会触发全量重跑，团队一个月内就会放弃使用这套机制。

## 7. 执行计划 DSL 规范

### 7.1 形态选择（已定）

| 方案 | 优点 | 致命问题 |
|---|---|---|
| A. 机器 JSON | 程序好读、幂等 | **人无法改**，"在原始脚本上做增量"无从谈起 |
| B. 纯代码（生成 Playwright 脚本） | 人熟悉、生态成熟、CI 友好 | LLM 生成代码幻觉风险高，diff 噪音大，难做意图级差异 |
| C. **YAML/DSL + 编译成指令树执行**（选定） | 人可读可手改，机器可硬校验 | 需自研 DSL 与编译器 |

**关系定位**：**DSL 是源码，Playwright 脚本是编译产物**（等价于 TS 与 JS）。LLM 只生成 DSL，编译器保证语义合法，既保留"人可维护"又规避"LLM 直接写代码"的风险。

**已定**：DSL **支持人工从零手写**（老测试工程师可直接迁移经验，产品不排斥人）；人工计划**必须过同一套五道闸**，不得放行。

### 7.2 固化什么、不固化什么

| 固化 | 不固化 |
|---|---|
| ✅ 语义意图（"在用户名框填账号"） | ❌ 坐标 |
| ✅ 多指纹定位集合 | ❌ XPath / CSS 绝对路径 |
| ✅ 可判定的断言 | ❌ 操作序列号连续性 |
| ✅ 数据引用（不硬编码值） | ❌ 硬编码的账号/密码/环境值 |

> 一句话：**固化"要达成什么"，不固化"在屏幕哪个像素点"。**

### 7.3 计划骨架（可直接作为实现参考）

```yaml
case_id: CASE-00123
title: 登录 - 错误密码提示
version: 1
source:
  requirement: REQ-045
  test_point: TP-045-2
  compiled_from: explore-run-20261113-1420
primary_driver: web

environment:
  target: internal-login-env
  variant: chrome-1280

data:
  username: ${account.user}
  password: ${invalid_password}          # 引用数据工厂，禁止硬编码

steps:
  - id: s1
    intent: 打开登录页
    action: goto
    target:
      url: /login
    assert:
      - {type: url_contains, value: /login, level: decide}
      - {type: visible, target: {testid: login-form}, level: decide}

  - id: s2
    intent: 在用户名输入框填写账号
    action: fill
    target:
      locators:                          # 多指纹，按优先级
        - {testid: login-username}
        - {role: textbox, name: 用户名}
        - {label: 用户名}
        - {css: "input[placeholder*=账号]"}
    value: ${data.username}
    assert:
      - {type: value_equals, expected: ${data.username}, level: observe}

  - id: s3
    intent: 点击登录按钮
    action: click
    target:
      locators:
        - {testid: login-submit}
        - {role: button, name: 登录}
    wait:
      - {type: network_idle, idle_ms: 500}
      - {type: text_changed, target: {testid: login-tip}}
    assert:
      - {type: text_visible, value: 密码错误, level: decide}

teardown:
  - {action: reset_session}
```

**设计要点**：每步有 `intent`（人读）+ `locators`（机用）；每个动作带断言；数据全部引用；`source` 强制溯源（无来源标"探索性"，不进正式回归集）。

### 7.4 片段复用与契约化

**已定：支持流程片段复用**（登录作为一个片段被所有用例引用，否则 500 条用例维护 500 份登录步骤）。

```
项目
├── fragments/   login.yaml  ← 被 N 条用例引用
├── cases/       CASE-00123.yaml → 引用 fragments.login
├── elements/    login_page.yaml
├── data/        dict.yaml, env-internal.yaml
├── variants/    locator variant / 数据映射
└── suites/      smoke.yaml, core.yaml, full.yaml
```

**片段必须契约化 + 影响分析**（否则共享层半年内无人敢改，这是很多 AI 测试平台第二年失去活力的原因）：

- 对外只暴露输入（账号、环境）与输出（会话状态），内部实现可改；
- 修改前自动列出受影响用例并估算回归规模；
- 变更走高版本号策略（`login@2`），存量继续引用旧版本，**按批升级**。

## 8. 固化编译器：五道硬闸

**输入**：探索轨迹（每步含动作与实际结果、DOM 快照、网络请求、前后状态差异）。

| 闸 | 校验内容 | 不通过处置 |
|---|---|---|
| 1. 定位闸 | 每个 locator 在快照中**唯一命中**；多指纹必须指向同一元素 | 打回重新挑选指纹 |
| 2. 断言闸 | 每步至少一个**可判定**断言；语义断言须给出结构化判断依据 | 打回（无断言不许固化） |
| 3. 数据闸 | 禁止硬编码敏感值/环境相关值，必须引用数据字典 | 自动替换引用 + 提示补字典 |
| 4. 溯源闸 | 必须挂到需求项/测试点（探索模式例外） | 标"探索性"，不进正式集 |
| 5. **语义一致闸** | **固化后立即重放一遍刚生成的计划，必须成功** | 打回 |

> **第 5 道闸最关键**：把"编译正确"与"实际可跑"硬绑在一起，杜绝"看起来对但跑不通"。

### 8.1 LLM 在固化中的合法边界（红线）

**只允许两个职能，都是"翻译"不是"创作"**：

1. **意图命名**：把 `click(#btn-3)` 翻译成"点击登录按钮"；
2. **断言推荐**：根据前后状态差异推荐断言候选，**标注为候选**，由人或规则确认。

**禁止**：自行增加步骤、自行改变动作类型、自行编造预期结果。三条一旦放开，固化退化成"又一次生成"。

### 8.2 探索模式的特殊处置

探索产物没有需求来源，第 4 道闸降级为标记（`source: exploratory`），其余四道闸不放宽。**探索性用例不得进入冒烟集与核心回归集**，只能进入"待归类"区，等人归类后才升级。

## 9. 资产库结构

```
项目
├── requirements/   需求项 IR
├── testpoints/     测试点 IR + 覆盖矩阵
├── cases/          用例 IR
├── plans/          执行计划（DSL）
├── fragments/      流程片段（契约化 + 版本化）
├── elements/       元素库（多指纹 / 环境变体 / 失效历史）
├── data/           数据字典 + 数据集（多环境）
├── variants/       环境变体
├── suites/         回归集（smoke / core / full，动态生成）
├── maps/           应用地图（探索产物）
├── evidence/       取证包（按执行 ID 分区）
├── risks/          质量风险台账
└── quarantine/     flaky 隔离区
```

**三条资产纪律**：

1. **元素库是一等公民**：多指纹兜底（`data-testid` → role+name → label → 文本 → 结构路径）、环境变体、失效历史。改元素库一处，全用例生效——这是"维护成本占 60%"的正解。
2. **资产随执行自动更新**：每次重放刷新 `touched`（实际触及的页面与接口），映射永不过期。
3. **所有改动必须产生 diff 并留痕**，不允许运行期悄悄修改资产。

## 10. 分阶段工具清单（需求 / 测试点 / 用例 / 缺陷 / 报告）

### 10.1 划分总原则

每阶段只问两个问题：① 判断依据能否形式化？能 → 程序做。② 产物能否写成 schema？不能 → 等于没结构化。

对应三种工具类型：**解析器 Parser**（非结构化→结构化，纯代码）、**校验器 Validator**（检查契约，纯代码）、**建议器 Advisor**（在结构化缺口处补内容，LLM，输出必须过校验器）。

> 每阶段都是"解析 → LLM 建议 → 校验器拦截"三段式，而不是"agent 自主完成本阶段"。

### 10.2 阶段一：需求分析

| 工具 | 类型 | 输入 → 输出 | 关键设计 |
|---|---|---|---|
| 文档解析器 | Parser | docx/pdf/md → 章节树 + 条款列表 | 保留原文位置（页码/段落），供溯源 |
| 接口规格解析器 | Parser | OpenAPI/Swagger → 接口清单 IR | **零 LLM**；结构化程度最高，优先使用 |
| 原型解析器 | Parser | Figma 导出 → 页面/控件清单 | 只提取控件类型与文案，不做语义 |
| 需求项抽取器 | Advisor | 条款列表 → 需求项 IR | 必须引用原文位置；抽不出位置的丢弃 |
| 可测性检查器 | Validator | 需求项 IR → 问题清单 | 纯规则：无预期结果/无边界/缺前置/表述歧义 |

**陷阱**：让 LLM 读整篇 PRD 再"总结需求"。正确做法是**先解析成条款，再逐条抽取**（条款粒度小，不易遗漏），且**每条必须带原文位置**（否则无法评审、无法追变更）。

**必做补充**：需求项打**模块标签**（人工 + 从接口路径推断），这是回归影响分析的粗粒度入口。

### 10.3 阶段二：测试点分析

| 工具 | 类型 | 说明 |
|---|---|---|
| 知识库检索引擎 | 查询 | 按"控件类型 × 测试维度"检索 checklist，**覆盖率的骨架** |
| 维度矩阵生成器 | Program | 需求项 × 维度 → 待覆盖矩阵 |
| 覆盖度计算器 | Validator | 矩阵中哪些格子没填 → 缺口清单（零 LLM） |
| **验证方式分配器** | Program | 按测试点类型强制分配 api / ui / native / mini / db（见 11.6） |
| 测试点补齐器 | Advisor | **只对缺口格子**生成测试点 |

**关键设计：矩阵由程序算，LLM 只补空格子。** 与"让 agent 自由想测试点"有本质区别——自由想的覆盖率不可控、不可度量；矩阵法能算出"还差多少"。

**知识库实用建议**：初期**不要自研向量库**。用"控件类型 → checklist"的**结构化映射表**（几十个控件类型 × 十几条维度）即可覆盖大部分场景，比 RAG 更准更便宜；RAG 只用于"相似历史项目"这一种查询。

### 10.4 阶段三：用例生成

| 工具 | 类型 | 说明 |
|---|---|---|
| 用例骨架生成器 | Program | 测试点 → 计划模板（步骤占位 + 断言占位） |
| 数据工厂 | Program | 按字段类型/约束生成边界数据；产出**数据集 ID**，与用例分离 |
| 步骤补全器 | Advisor | 只补"怎么走"（动作 + 定位意图），**不写断言** |
| 断言生成器 | Advisor | **从测试点的预期结果生成**，不从鼠标动作反推 |
| 用例预算校验器 | Validator | N+1 条硬限制（防 agent 铺用例失控） |
| 枚举清单对账器 | Validator | 需求能力项 ↔ 用例，双向 diff 找漏 |
| 计划校验器 | Validator | 五道闸（第 8 章） |

**必须坚持的分工**：**步骤让 LLM 补，断言必须从测试点来。** 断言若是 LLM 看着页面"觉得对"写出来的，这个用例通过与否完全没意义——这正是通用 agent 做测试的根本缺陷。

### 10.5 阶段五：缺陷分析

> 阶段四"测试执行"的工具清单见第 11 章（四类自动化）与第 12 章（执行引擎），不在此重复。

| 工具 | 类型 | 说明 |
|---|---|---|
| 取证包组装器 | Program | 从结果 IR 拉齐证据（12.5） |
| 归因器 | Advisor | 五分类 + 置信度；低置信转人工 |
| 缺陷去重器 | Program | 指纹匹配（失败断言 + 目标元素 + 异常签名）+ 向量相似 |
| 缺陷单渲染器 | Program | 模板渲染，接 Jira/禅道/内置 |
| **偶发 bug 识别器** | Validator | 标记"预期不稳定"的用例失败 → 提示可能是真实偶发缺陷 |

**实战判断**：flaky 用例中有一类其实是**真实偶发 bug**（并发、缓存、时序）。归因器必须能识别上报，否则会把客户真实缺陷"修"没了。

**归因应下沉到执行末端**：失败那一刻取证包还在手上，立即判"产品 bug / 脚本问题 / 环境问题"，脚本问题立刻自愈重跑。放到最后阶段分析，上下文已凉，还要多花 token 重新理解。

### 10.6 阶段六：报告

见第 16 章（审阅者形态 + 风险台账）。

### 10.7 一个横切判断：阶段数要不要减？

**保留七阶段，但让其中三个阶段"几乎零 LLM"**：需求分析（有 OpenAPI 时接近零）、测试点（矩阵 + 知识库，只补缺口）、报告（聚合 + 模板，只写洞察）。

**真正重度用 LLM 的只有四处**：探索（新场景）、用例步骤补全、失败归因、报告风险洞察。这四处是"不可形式化"的地方，也是模型真正的价值所在。

## 11. 执行层：四类自动化（Web UI / 接口 / App / 小程序）

### 11.1 架构判断：四类不能各做一套

如果 Web、接口、App、小程序各自一套计划格式、执行器、断言和取证，就是四套工程，维护成本翻 4 倍，且资产（元素库、片段、回归集）无法互通。

**正确做法：共用一套 DSL 与一套引擎骨架，只把驱动层做成可替换的 Adapter**：

```
统一 DSL（同一套步骤 / 等待 / 断言 / 取证语义）
        ↓
Driver Adapter（四选一，同接口）
├── WebDriver      Playwright（本机浏览器）
├── ApiDriver      原生 HTTP client（无浏览器）
├── NativeDriver   Appium（Android UiAutomator2 / iOS XCUITest）
└── MiniDriver     小程序自动化（宿主内运行）
```

**Adapter 必须实现同一组原语**：`resolve(找目标)` / `act(动作)` / `wait(同步契约)` / `snapshot(结构化状态)` / `evidence(取证)`。

**DSL 中只允许出现动作语义与等待类型，不允许任何 driver 专有写法**，差异全部由 `target` 块承载。

### 11.2 同一份 DSL，target 随类型不同

```yaml
target: {kind: web, locators: [{testid: login-username}, {role: textbox, name: 用户名}]}

target: {kind: api, method: POST, path: /api/auth/login,
         body: {username: "${data.user}", password: "${data.pwd}"}}

target: {kind: native, strategy: accessibility_id, value: btn_login}   # 备选 id/xpath/class_chain

target: {kind: miniprogram, selector: ".login-btn", context: webview}  # webview | native
```

### 11.3 四类共用的工具（真正要做的核心工作）

| 工具 | 说明 |
|---|---|
| 等待条件库 | 同一套封闭枚举，各 Adapter 自行实现（`element_stable` 在 Web 看位置、在 native 看 bounds） |
| 断言引擎 | 判定性 / 观察性两级；结构断言通用，语义断言吃结构化摘要 |
| 取证包组装 | 统一 schema，evidence 内容各 driver 自填（截图 / 原生层级树 / 请求响应） |
| 结果 IR 与结论 | 五档结论、`locator_hit` 降级记录、`touched` 刷新 |
| 自愈分级 | L1/L2/L3 规则通用，实现各异 |
| 会话与凭证管理 | Web 用 cookie/token 注入；接口用 token 刷新；App/小程序用登录态与设备绑定账号 |
| 凭证与配置中心 | 账号、环境、密钥集中管理，**禁止写进计划**（数据闸已约束） |
| 执行记录与一致性检测 | N=3 判定、flaky 标记，与 driver 无关 |

### 11.4 各类差异工具与真实风险

| 类别 | 专有工具 | 风险 |
|---|---|---|
| **接口** | 鉴权 token 管理器、响应契约校验器（schema）、**数据库断言器**、**异步结果轮询器**（MQ/任务轮询）、接口间变量提取传递、环境域名切换 | **低**。确定性强、速度快、几乎零 flaky |
| **Web UI** | 多指纹定位、结构化 DOM 快照、iframe/shadow DOM 处理、上传下载、截图基线 diff | **中**。同步与定位是主要 flaky 源 |
| **App** | **设备/模拟器池管理**（Appium server 生命周期、端口分配、设备排队）、安装包版本管理（装/卸/清数据）、**系统权限弹窗策略链**、混合应用 webview 上下文切换、崩溃/ANR 检测 | **高**。设备管理本身是独立基础设施，最容易拖垮进度 |
| **小程序** | 宿主环境准备（开发者工具或真机）、开发者权限与扫码授权、**宿主级弹窗处理**（授权/更新提示）、WXML 组件树快照、分包/多页栈处理 | **中高**。宿主限制多、调试链路长 |

**明确建议**：App 自动化的"设备池"是独立子系统。**初期不做真机矩阵，只做"单设备串行 + 指定设备指定用例"**，有真实客户需求再上池化。否则一上来就被设备管理拖住。

### 11.5 混合 driver：做，但要带四条约束

真实业务几乎不可能纯 UI 或纯接口（UI 操作后查库、接口造数后 UI 验证、App 内打开 H5、小程序调后端）。因此**允许步骤级指定 driver**，但必须同时定四条约束，否则引擎失控：

| # | 约束 | 说明 |
|---|---|---|
| 1 | **必须声明主 driver** | 决定语句上下文、默认等待策略、证据格式；其他为辅助。避免"接口起头→UI 收尾→再接接口"的怪物用例 |
| 2 | **最多 2 段，切走不许切回** | 典型场景都在 2 段内；超过 2 段说明用例该拆 |
| 3 | **上下文传递必须显式声明** | 唯一耦合点是变量传递，必须写 `context_flow`，禁止隐式共享 |
| 4 | **结论按最弱一环判定** | 任一 driver 失败即失败；归因必须标注失败发生在哪个 driver |

```yaml
context_flow:
  - {from: s3.output.orderId, to: "${ctx.order_id}"}     # UI 步骤提取
  - {from: "${ctx.order_id}", to: s5.params.order_id}    # 接口步骤引用
```


> 不加这四条，混合 driver 会变成"什么都混、什么都查不清"；加上之后，它是真实业务的表达能力，而不是复杂度负担。

### 11.6 验证方式分配：接口必须是一等公民

这不是技术偏好，而是**产品定位决策**，对 flaky 率与执行速度的影响最大。

| 维度 | 接口自动化 | UI 自动化 |
|---|---|---|
| 确定性 | 接近 100% | 受渲染/时序影响 |
| 速度 | 毫秒级 | 秒级 |
| flaky 率 | 极低 | 高 |
| 能发现的缺陷 | 业务逻辑、边界、权限、数据一致性 | 呈现、交互、兼容性 |
| 成本 | 低 | 高 |

**分配规则（做成测试点阶段的强校验，不是建议）**：

| 测试点类型 | 主验证方式 |
|---|---|
| 业务逻辑、计算、状态机流转 | **接口** |
| 边界值、异常分支、错误码 | **接口** |
| 权限、越权、数据隔离 | **接口** |
| 数据一致性（落库、缓存、消息） | **接口 + 数据库** |
| 并发、幂等、重复提交 | **接口** |
| 界面呈现、布局、文案 | UI |
| 交互反馈（提示、loading、禁用态） | UI |
| 前端校验（必填、格式、长度） | **UI + 接口双写** |
| 兼容性（多浏览器/分辨率） | UI |
| 端到端关键业务流 | UI（冒烟集主体，每模块 1~2 条） |

**落成校验器**：测试点阶段结束时，程序统计"接口可验证但被分配为 UI"的比例，超过 30% 提示不合理。这是防止开发者习惯性写 UI 用例的闸门。

**双产物要求**：如"前端必填校验"，必须同时产出 ① UI 用例（不填直接提交→前端提示）② 接口用例（绕过前端 POST 空值→后端必须拒绝）。**只做前者会漏掉后端未兜底的严重问题**，这类问题在真实项目非常常见。

### 11.7 调度分池

```
调度层
├── 接口池     高并发（默认 20~50），无资源限制
├── Web 池     受浏览器实例数限制（默认 = CPU 核心数）
├── 设备池     受在线设备数限制（默认 1~2）
└── 小程序池   受宿主实例数限制（默认 1~2）
混合用例 → 分配到主 driver 的池；执行中向辅助池申请资源
```

**关键细节**：混合用例的**辅助步骤走优先级通道**（不排队、直通）。否则 UI 用例执行到一半要调接口查库，接口池排队满了就把它拖成 flaky——很多平台做混合编排失败就败在这里。

## 12. 执行引擎设计

**定位：引擎只负责执行已编译计划，自身不做决策。对外只输出两样东西——结果 IR 与取证包。**

### 12.1 进程与隔离模型

| 项 | 设计 |
|---|---|
| 节点 | 本机服务单节点 |
| 并行 | **独立 worker 进程池**（非同一进程多 Context）；并发数可配，默认按 CPU 核心数 |
| 隔离 | 每条用例独立 Context（隔离 cookie/缓存/localStorage），用例结束销毁 |
| 会话 | 登录态由会话管理器统一注入，**不依赖上一条用例残留** |
| 显示模式 | 同一引擎两种模式：无头批量 / 有头演示（高亮 + 录屏 + 可接管） |

### 12.2 步骤执行：动作 — 同步契约 — 断言

```yaml
action: click
wait:                                    # 类型化等待，不是 sleep
  - {type: network_idle, idle_ms: 500}
  - {type: element_visible, target: {testid: result-list}}
assert:
  - {type: text_visible, value: 密码错误, level: decide}
```

**关键设计：等待条件由编译器从探索轨迹自动提取，不由人凭感觉猜。** 探索时天然会观察到"点击后多久页面趋稳、哪个接口返回后才出结果、元素稳定态出现在第几毫秒"——把这些提取为显式等待条件，就是"学来的同步策略"，比手写 `waitForTimeout(3000)` 可靠且不会随时间腐坏。

**等待条件类型必须封闭枚举**（不能由 LLM 自由发挥）：`element_visible`、`element_enabled`、`element_stable`（位置尺寸连续 N 帧不变）、`network_idle`、`request_done(pattern)`、`text_changed`、`url_matches`、`attribute_equals`。

### 12.3 定位解析器

- 按 `locators` 优先级依次尝试，命中即停；
- **多命中必须拒绝执行**（要求唯一性，不允许"取第一个"）；
- 每次降级**必须记录**（`命中第 3 个指纹`）——这是 flaky 前兆，计入健康度；
- 全部失效 → 抛 `locator_not_found`，交自愈器（仅 L1）。

### 12.4 断言引擎：判定性 vs 观察性

| 级别 | 作用 | 失败时 |
|---|---|---|
| `decide` | 决定用例结论 | 用例 fail，触发取证 |
| `observe` | 只记录状态，供归因 | 不判 fail，但计入证据与异常信号 |

**断言分级已定**：关键步骤强制 `decide`，普通步骤默认 `observe`（避免断言冗余与误报）。关键步骤判定规则：来自"正常流程类测试点"的步骤默认关键；来自"数据校验类测试点"的强制关键；导航/填充/跳转等支撑性步骤默认非关键。**判定权在程序 + 人工可覆写，不交给 LLM**（LLM 倾向把一切都标关键）。

语义断言（如"是否真的搜到了结果"）只给 LLM **结构化摘要输入**，结果落为 `decide` 级但**必须标注"由模型判定"**，以便审计。

### 12.5 取证包（固定 schema，含与历史基线的 diff）

| 分区 | 内容 |
|---|---|
| context | 计划 ID、步骤 ID、环境、数据版本、引擎版本、时间戳、执行 ID |
| visual | 失败截图、全流程录屏片段、**与上次成功执行同步骤的截图 diff** |
| dom | 当前 DOM 快照、目标元素外层摘要、**与上次成功的 DOM diff** |
| network | 本步骤相关请求与响应（状态码、耗时、payload 摘要） |
| console | 控制台报错与警告 |
| trace | 前 N 步的操作与结果轨迹 |
| history | 该用例最近 5 次结果（判断是否 flaky） |

> **"与上次成功的 diff"往往是最直接的归因证据**——大部分失败是"某处变了"，人一眼能看出来。通用 agent 拿不到这个信息，因为它没有历史资产。

### 12.6 登录器与验证码策略链

**策略链**：探测分类 → 按项目配置排序 → 逐策略尝试 → 全部失败转人工。

四条实战红线：

1. **先分类再处理**：图形码/滑块/点选/短信/无验证码的处理链路完全不同，不要盲目尝试；
2. **验证码失败最多重试 1 次**——反复尝试触发风控锁号，把"一次失败"变成"账号被封"；
3. **策略成功率按项目维度统计并排序**——A 项目滑块靠打码平台能过，B 项目可能只接受测试万能码；
4. **会话复用是终极解法**：把验证码从"每次执行都遇到"降到"每周一次"。**登录器的首要价值不是"能登录"，而是固化会话。**

**登录场景的标准解法（可作为工具化效果示例）**：

| 步 | 做法 | 成本 |
|---|---|---|
| 1 探测 | 拉 DOM 找 `input[type=password]` 及相邻 input → 识别登录表单；iframe/canvas 才降级视觉 | 毫秒级，零 LLM |
| 2 填表 | 账号密码按配置写入 | 零 LLM |
| 3 验证码 | 检测元素类型 → 分类 → 策略链（万能码 → 打码平台 → OCR → 人工接管） | 仅此步可能需要外部服务 |
| 4 固化 | 一次成功即把"表单特征 + 提交路径 + 会话存储位置"写入登录配置 | 一次性 |
| 5 重放 | 下次注入会话，**1 秒内**进入可测状态 | 零 LLM |

### 12.7 人工接管：三种模式 + 状态重新对齐

| 模式 | 场景 | 设计 |
|---|---|---|
| **阻塞式** | 验证码、短信、扫码 | 引擎暂停，交控给人，人操作完点"继续" |
| **断点式** | 调试、排查 | 任意步骤设断点，单步执行，查看状态 |
| **修正式** | 人工走完某段异常路径 | 人操作一段，引擎记录并**可编译为计划片段** |

**最易漏的边界**：接管不是"人替引擎跑"，而是"人只完成引擎做不到的那一小段，然后交回"。交回时必须做**状态重新对齐**：

1. 重新抓 DOM 快照，更新元素映射；
2. 刷新 `touched`（页面或接口可能变了）；
3. 校验"当前状态是否满足下一步前置条件"，不满足就明确报错，不要硬跑。

不做这三步，接管后的后续步骤会基于过期状态执行，失败原因还查不出来——这是很多平台接管功能的通病。

### 12.8 自愈分级与红线

| 级别 | 动作 | 自动 | 记录 |
|---|---|---|---|
| L1 定位自愈 | 换指纹 | 是 | 必记（计入健康度） |
| L2 等待自愈 | 延长等待 / 追加等待条件（限一次） | 是 | 必记 |
| L3 步骤自愈 | 跳过步骤、替换步骤、改变操作目标 | **禁止** | 转人工或直接 fail |

> **红线：自愈只允许让用例"能跑通"，绝不允许让"该失败的变成通过"。** 任何自愈动作必须留痕并降低该用例资产健康度评分。

### 12.9 结果 IR：五种结论

```yaml
case: CASE-00123
verdict: inconclusive        # pass | fail | flaky | skipped | inconclusive
steps:
  - {id: s1, status: pass, duration_ms: 210}
  - {id: s2, status: pass, duration_ms: 130, locator_hit: 3}
  - {id: s3, status: fail, failed_assert: text_visible, evidence: evidence://exec-8821/s3}
touched: {pages: [...], apis: [...]}
retries: 0
self_heal: [L2@s2]
```

**`inconclusive` 必须存在**：环境不可达、前置条件不满足、会话获取失败——既不该算 pass 也不该算 fail。缺这一档，平台只能在"谎报通过"与"诬告失败"之间二选一，最终两边都失去信任。**准入结论中必须单独统计。**

### 12.10 可单步调试（刚需，容易被低估）

测试工程师不会信任黑盒。引擎必须原生支持：**断点、单步、查看当前 DOM 与变量、断点处接管**。

好消息：**"单步调试"与"演示可见"是同一套能力**（有头 + 步骤级暂停 + 状态可视化）。做一份，两个场景都受益——这也是把演示能力做成引擎内建而非外挂的理由。

## 13. 回归集与影响分析

### 13.1 回归集要回答三个问题

1. **这次该跑哪些？**（选集）
2. **跑完之后，我能不能说"没问题"？**（置信度）
3. **没跑的用例，风险是什么？**（覆盖缺口）

只回答第一个问题的系统，会被质疑"你只跑了 30 条，就敢说能上线？"

### 13.2 选集触发源（按可靠性排序）

| 触发源 | 输入 | 可靠性 | 说明 |
|---|---|---|---|
| ① 显式指定 | 人勾选用例/目录 | 最高 | 覆盖"我知道改了哪里" |
| ② 需求变更溯源 | 需求项 ID 变更 → 关联用例 | 高 | 依赖 IR 的 `source`/`derived_from` |
| ③ 代码变更影响 | 改动文件 → 模块 → 用例 | 中高 | 依赖用例与模块映射 |
| ④ 依赖传递 | 用例引用 `login@1` → 片段变更即命中 | 高 | 片段契约化的回报 |
| ⑤ 历史相似 | 向量检索相似用例 | 中 | 兜底补漏，**只选不判** |

**关键原则：选集结果必须可解释**——不能只说"AI 帮你选了 42 条"，要给出每条理由（`source:REQ-045` / `fragment:login@1` / `module:order-service`）。**可解释性是测试团队信任的前提。**

### 13.3 分层回归（三道闸）

| 层 | 时机 | 时长预算 | 内容 | 判定 |
|---|---|---|---|---|
| **冒烟 Smoke** | 每次构建/部署后 | ≤5 分钟 | 核心链路 20~50 条 | 只判通/不通，不通即阻断 |
| **核心 Core** | 每日/提测 | ≤1 小时 | 主流程 + 本次影响范围 | 有失败即 triage |
| **全量 Full** | 上线前/夜间 | 数小时（可分片） | 全部可信用例 | 生成准入报告 |

三条纪律：冒烟集必须小而稳（**flaky 率 0**，否则团队会绕过它）；核心集按本次变更**动态生成**，不是固定集合；全量必须支持**分片并行**（本机多 worker 进程）。

**冒烟集已定约束：100% 规则断言，语义断言（LLM 判定）不得进入。** 否则冒烟集自身的稳定性无法保证。

### 13.4 置信度与准入结论

| 指标 | 算法 | 回答 |
|---|---|---|
| **需求覆盖率** | 本次变动需求项中有执行用例的比例 | 改的东西测了吗 |
| **影响覆盖度** | 受影响用例中实际执行的比例 | 波及的东西测了吗 |
| **资产健康度** | 执行用例中非 flaky、非跳过、非长期失败的比例 | 测的本身可信吗 |

合成准入结论：三项达标 → 可上线；需求覆盖达标但影响覆盖不足 → 有条件上线（列未测风险）；**资产健康度低于阈值 → 不给结论**（先修资产，而不是先上线）。

> 第三条最重要：它诚实地承认"我的用例不可信，所以我的结论也不可信"。这比虚报"全部通过"可信得多。

### 13.5 影响分析的关键发现（已确认）

**代码变更 → 模块 → 用例，中间缺一层映射。三条路**：A 需求项打模块标签（推荐补充）；B 用例维护"触达接口和页面"清单（**推荐主路**）；C 代码目录 → 模块映射（成本高，易腐烂）。

**B 路几乎免费**：探索轨迹天然记录了"这条用例碰了哪些页面和接口"，编译时顺手写入 `touched: {pages: [...], apis: [...]}`。代码变更时匹配路由与接口，命中的用例就是候选。

> 这是本轮最有价值的发现之一：**影响分析的数据源已经存在于探索轨迹中，不需要额外维护。** 传统自动化做不到，是因为脚本里没有这个信息；我们有，因为它来自探索。

**映射腐烂的对策**：重放时自动刷新 `touched`，映射始终与真实执行一致。**资产随执行自动更新**，这才是"活资产"。

## 14. flaky 治理

### 14.1 定义（定义不清，后面全错）

> **flaky = 同一份执行计划、同一环境、同一数据，连续执行 N 次，结果不一致。**

三者任一变化都不算 flaky，属其他类问题。这个边界把"偶发 bug"与"脚本不稳"分开了：

| 现象 | 性质 | 处置 |
|---|---|---|
| 同计划同环境跑 3 次，2 过 1 败 | flaky（脚本/系统不稳） | 标记，禁入可信结论 |
| 数据变了导致失败 | 数据问题 | 数据工厂/隔离 |
| 环境抖动（依赖服务超时） | 环境问题 | 环境健康检查 + 重试 |
| **稳定失败但功能正常** | 用例错误（断言过严/定位错） | 修资产 |
| **稳定通过但功能实际是坏的** | **错误通过（最危险）** | 断言缺失，需补 |

> 第五类最危险：它比失败严重得多，因为会让团队对系统失去信任，而指标上完全看不见。这是"关键步骤必须有可判定断言"的原因。

### 14.2 五大根因（对症不对因就会一刀切重试）

| 根因 | 表现 | 处理 |
|---|---|---|
| ① 同步失效（占大头） | 点了没反应、元素没渲染完就断言 | 智能等待（网络空闲 + 元素稳定态），**不是 sleep，不是重试** |
| ② 定位歧义 | 页面多个"确定"，取到第一个 | 定位必须校验唯一性，多命中拒绝执行（编译闸已覆盖） |
| ③ 数据污染 | 上次数据还在、账号状态被改 | 用例级数据隔离 + teardown 复原 + 唯一数据生成 |
| ④ 时序竞争 | 并发偶发失败、异步请求未返回 | 显式等待业务信号（特定请求完成） |
| ⑤ 环境不稳 | 依赖服务偶发超时 | 环境健康检查前置 + 失败归因到环境 |

> **核心观点：flaky 是必须根治的缺陷，不是靠重试掩盖的症状。** 重试只会把"偶然通过"混进"通过"。一条 flaky 用例进入回归集后，团队会开始无视所有失败，这才是真正的灾难。

### 14.3 检测三步

**第一步：内建一致性检测（平台默认行为）** — 新增/变更用例入库前必跑 N=3，不一致直接打回；已入库用例按周期抽样重跑（如每周核心集跑 3 次）。

**第二步：重放期的可疑信号（零额外成本）** — 命中降级定位（非首选指纹）、等待超阈值（>3s）、发生过重试、断言通过但伴随控制台/网络异常、执行时长波动 >50%。

**第三步：分类归因** — 用 LLM 但输入是结构化证据（截图/DOM/网络/控制台/轨迹/**前几次历史结果**），五类根因 + 置信度，低置信转人工。

> LLM 在此只做"分类"，不做"判定通过与否"。**通过与否必须由断言判定，这是红线。**

### 14.4 生命周期与隔离区

```
新用例 → 编译闸 N=3 → 入库
   ↓ 重放出现不一致
标记 flaky(置信度, 根因候选) → 自动从冒烟/核心集移除
   ↓ 人工 triage（或 LLM 高置信自动开修单）
三种出口：A 修资产 → 重跑 N=3 → 恢复
         B 判定真实偶发 bug → 转缺陷单，用例保留但标"预期不稳定"
         C 无法修复 → 隔离区 quarantine，超期提醒负责人
```

**隔离区是必需设计**：没有它，flaky 用例会一直污染回归结果，团队最终只能全部忽略失败。规则：**超过 X 天未处理自动上报**，避免永久沉淀。

### 14.5 指标

| 指标 | 定义 | 阈值 |
|---|---|---|
| Flaky 率 | flaky 用例数 / 可执行用例数 | <5%，冒烟集要求 0 |
| 错误通过风险数 | 无关键断言的用例数 | 目标 0 |
| 隔离区存量 | quarantine 用例数 | 持续下降 |
| 平均修复时长 | flaky 标记到恢复 | <5 个工作日 |
| **首次执行通过率** | 首次重放（非重试）通过率 | 真实健康度 |

> **禁用"最终通过率（含重试）"**：这个数字好看但无意义，因为它不含任何遮掩。**首次执行通过率才是真实信号。**

**建议分别统计接口 flaky 率（目标 0）与 UI flaky 率（<5%）**，混在一起会掩盖问题。

### 14.6 对现有工程的直接要求

现有"执行 attempt 账本"方向错了：它记录"尝试几次、最后成功"，等于把重试当成正常流程。**必须改为：账本记录每次执行的事实，但一致性判定标准不受重试结果影响**；重试只用于判断环境是否抖动，不能让用例"通过"。

### 14.7 对产品定位的意义

它是唯一能正面回答"这东西靠谱吗"的机制：

> **平台会主动告诉你"我这条结果不可信"，而不是把所有结果都包装成通过/失败。**

这是**诚实性设计**。一个测试工具最宝贵的品质是"失败时你知道该信它"，通用 agent 永远给不了。

## 15. 探索器（探索模式）

### 15.1 探索到底产出什么（先纠正认知）

| 错误认知 | 正确认知 |
|---|---|
| 探索 = 随便点，点着点着就测出 bug | 探索 = **低成本建立应用画像**，bug 是副产品 |
| 探索产物 = 一份报告 | 探索产物 = **可固化资产**（地图 + 元素库 + 首版测试点） |
| 探索要跑很久、很全面 | 探索**分轮次、有硬预算**，第一轮只求"地形清晰" |

> **核心定位：探索构建地图，不承担验收职责。** 这样定位有两个好处：不再追求"点得全"（避免 token 失控）；产物可立即兑现（第二轮就上线重放）。

### 15.2 四个阶段（每阶段有硬预算与产出）

```
① 环境建档 → ② 结构巡检 → ③ 功能试触 → ④ 固化沉淀
 （判定型，零LLM）  （广度优先）   （有限深度）    （资产产出）
```

**① 环境建档（零 LLM，纯代码，目标 10 秒内）**

| 动作 | 产出 |
|---|---|
| 可达性检查（DNS/TCP/HTTP） | 环境健康结论 |
| 拉取 robots / sitemap / manifest | 站点骨架 |
| **解析前端路由**（从 JS bundle 提取路由表、menu 配置、i18n 语言包） | **路由清单（最高价值）** |
| 识别技术栈（React/Vue、是否 SPA） | 渲染策略（决定等待方式） |
| 登录归类（登录页/登录接口） | 登录方案候选 |

> **关键发现**：现代 Web 应用的**路由表几乎都在 JS 里**，直接解析比"点着看"快 100 倍且零 token。上次演示若做了这一步，页面清单 10 秒就能拿到。

**② 结构巡检（广度优先，每页 LLM ≤2 次）** — 打开页面→结构化 DOM 快照→判定页面类型（列表/表单/详情）→**规则提取控件清单（零 LLM）**→记录元素指纹→记录触达接口。**只做"看一眼、登记"，不做业务流程。**

**③ 功能试触（有限深度，最高 LLM 消耗区，必须严控）** — 只在少量关键页面（首页、一级导航、用户指定入口）做：表单填 3 个字段提交 1 次、列表查询 1 次、导航跳转（不做深度业务流程）、空值/非法值提交 1 次观察前端校验。

**默认硬预算**：巡检 ≤50 页，试触 ≤10 页，每页 ≤5 次动作。**达到上限就停，无论还有多少没试**——预算由工程制定，不靠模型自觉。这正是解决"十几分钟 100 万 token"的关键手段。

**④ 固化沉淀（探索的真正价值）**

| 产出 | 用途 |
|---|---|
| 应用地图（页面 + 路由 + 控件 + 接口归属） | 后续所有测试的参照；也是新成员的上手文档 |
| 元素库（各页面控件多指纹） | 直接可用 |
| 登录片段 `login.yaml` | 直接可用，后续秒级进入 |
| 首版测试点（页面控件 ↔ 知识库映射自动生成） | **LLM 价值最高处**：映射是确定性的，只补缺口 |
| 首批可固化轨迹 | 走五道闸 → 入库为正式用例 |
| 待探索队列（超预算未做） | 下一轮输入 |


### 15.3 怎么"停下来"（上次失败的部分原因）

三条终止条件：① **预算耗尽**（优先，工程硬性）；② 路由清单全覆盖（巡检完成）；③ 连续 N 次动作无新信息（收益递减）。

**必须输出"探索度报告"**：巡检覆盖 38/52 页、试触 8/10 页、未探索队列 14 项、建议下一轮重点。**让"没探索完"变成可见、可解释的状态，而不是"跑崩了"。**

### 15.4 危险动作白名单（产品级功能）

| 风险 | 对策 |
|---|---|
| 试触触发真实业务（发短信、下单、扣款） | **危险动作清单**：提交类只在测试数据上做；无法确认时只做"表单校验"不做"业务提交"；页面白名单显式声明"允许提交" |
| 试触产生垃圾数据 | 探索账号隔离 + 尽量 teardown；记录"我创建的数据"供清理 |
| 巡检触发风控/限流 | 限速（每页 ≥1s 间隔）、并发 ≤2 |
| 单页 DOM 过大导致 token 暴涨 | 快照裁剪（只留可交互元素 + 文本）+ **强制上限**（超限截断并提示） |

> 客户第一次用探索模式时**默认只允许只读类探查**（浏览、查询、校验），提交类需显式开启。宁可一开始不完美，也不能造成事故。

### 15.5 附加价值：探索是获取需求的最快路径（逆向需求）

真实场景经常没有需求文档，只有系统。探索产物可反向生成"逆向需求"：页面控件清单 → 字段与约束（必填/长度/格式）；试触反馈 → 校验规则与错误提示；接口抓取 → 业务能力清单。

这些可直接作为**需求项 IR 的初版**（`source: reverse_engineering`），再进入正常测试点→用例流程。**这解决了"没有需求怎么办"的长期痛点**，对无文档的老系统（原开发已离职）价值极高。

### 15.6 与通用 agent 探索的本质区别（汇报用）

| 维度 | 通用 agent 探索 | 我们的探索器 |
|---|---|---|
| 目标 | 尽可能多地点，找 bug | 建立可复用地图与资产 |
| 预算 | 无上限，跑到模型觉得完成为止 | **工程硬预算**，按阶段截断 |
| 广度获取 | 逐个点击 | **解析路由表 + 规则提取控件**（快百倍） |
| 产出 | 一份文字结论 | 地图/元素库/片段/测试点/可固化轨迹 |
| 第二轮成本 | 又一次 100 万 token | **接近零**（走重放） |
| 结果可复现 | 否 | 是 |

## 16. 报告 Agent：从"写报告"改为"审报告"

报告 agent 保留，但必须换定位，否则会出现两个致命问题：**数字可能被 LLM 编造**、**报告变成套话**。

| | 错误形态（写报告） | 正确形态（审报告） |
|---|---|---|
| 输入 | 原始执行数据 | **已算好的结构化指标包**（只读） |
| 职责 | 生成数字 + 写结论 | **解释数字、识别风险、给监控建议** |
| 输出 | 一段报告正文 | **风险洞察对象列表**（可入库跟踪） |
| 数字权威 | LLM | **程序**，LLM 无权修改 |

### 16.1 为什么这个角色值得一次独立调用

它是全链路**唯一能看到"全局交叉"**的角色。单看指标都不惊人，交叉起来才有洞察：

- 某模块失败率上升，但失败全是 `inconclusive` → **环境不稳而非质量下降**（误判会白改代码）
- 覆盖率 100%，但 60% 用例只有 `observe` 断言 → **覆盖率虚高**，错误通过风险大
- flaky 率稳定，但**定位降级命中率上升** → UI 正在漂移，两周后可能批量失效
- 缺陷集中在新模块，而该模块需求覆盖最低 → **投入结构错配**

这些都要求跨指标 + 跨轮次比对。程序写不出规则（组合爆炸），通用 agent 也做不了（没有历史资产）。

### 16.2 四条硬约束（缺一条就退化为套话生成器）

1. **数字只读**：LLM 输出的数字与指标包不一致 → 校验器丢弃并告警；
2. **每条洞察必须挂引用**（`evidence: [metric:flaky_rate@v3, exec:8821]`），挂不上一律丢弃；
3. **允许"无风险"输出**（`risks: []`），并统计空输出率——**若不支持，模型会为交差硬凑风险**；
4. **输出分两段、来源可辨**：`facts`（程序生成，只读）与 `insights`（LLM 生成，带 model 标记与置信度），报告里视觉区分。

### 16.3 质量风险台账（风险点监控的落点）

把每轮洞察写入**质量风险台账**，带状态机：`new → tracking → mitigated / accepted / escalated`。

这样报告从"一次性产出"变成"持续监控"：上轮风险这轮还在不在、是否恶化、谁负责，都可追踪。**对管理层的价值远高于报告本身**——领导要的不是一份报告，是"风险有没有在收敛"。

### 16.4 报告结构

```
① 准入口径（程序）：需求覆盖率 / 影响覆盖度 / 资产健康度 / 准入结论
② 执行事实（程序）：通过 / 失败 / flaky / inconclusive / skipped（inconclusive 单独列）
③ 缺陷概况（程序）：新增 / 复现 / 关闭 / 按模块与严重度分布
④ 风险与趋势（LLM，挂引用）：风险点、依据、建议动作、置信度
⑤ 风险台账变化（程序 + LLM）：上轮风险状态迁移
```

> **纪律：报告里所有数字由程序算，LLM 只能解释不能生成数字。** 让 LLM 写报告最危险的一点是会自己"编"一个通过率。

## 17. 与现有工程的处置

### 17.1 十条不变量（现有约束的正确部分，全保留）

`checked_condition` / `case_ref` / `untested` / `partial` / "无断言不算通过" / "写结果未知不换 ID 重放" / "fixed 只是修复声明，关闭须绑独立复测" —— 这些约束质量超过多数商用产品，**全部保留**。

但必须看清性质：**它们全是"防造假"类**（别骗我），解决不了"两次跑不一样"。

### 17.2 约束类型需要补的另一半

| 现有（防造假） | 缺失（防不可复现） |
|---|---|
| 无断言不算通过 | **同用例 N=3 结果一致性** |
| 未执行不算通过 | **定位降级记录与计数**（命中第几指纹必须留痕） |
| 写结果未知不换 ID 重放 | **等待条件必须类型化声明，禁止 sleep** |
| 证据要可直达 | **失败证据必须含与上次成功的 diff** |
| 来源可追溯 | **计划入库前五道闸** |

> 现有工程与 Hifox 都在解决"Agent 会不会说谎"；上次演示的失败是"Agent 没说谎，但它跑不动、跑不稳"。**这两件事的护栏不一样。**

### 17.3 Agent 判决：11 个全部保留，但权限必须收窄

**判据修正（v2 曾用"产物是否被消费"砍掉两个 agent，是错的）**：阶段边界应按"人工确认卡点 / 可独立重跑 / 可独立失效"三条划分（见 5.5），不按 LLM 调用次数划分。

| Agent | 判决 | 收窄要求 |
|---|---|---|
| `default_agent` | 保留 | 入口，不算业务 agent |
| `test_agent` | 保留 | **派发决策从 LLM 判断改为状态机 + 规则表**；不得自行决定跳过阶段 |
| `requirement_analysis_agent` | 保留 | 输入只能是解析后的条款（不得直读整份 PRD 自由总结）；输出逐条挂原文位置；需求项必须打模块标签 |
| `test_point_agent` | 保留 | **覆盖矩阵由程序算，agent 只补空格子**；必须过"矩阵无空缺"校验；必须完成验证方式分配 |
| `test_case_agent` | 保留 | 断言必须来自测试点预期，不许看页面反推；必须过条数预算与枚举对账 |
| `automation_execution_agent` | 保留 | 载体独立（Playwright）；必须吃执行计划，不许现场重探索（M1 可降级为"计划驱动 + 受控探索"） |
| `api_automation_agent` | 保留 | 载体独立（HTTP worker），"只执行不设计"边界干净 |
| `android_test_agent` | 保留 | 载体独立（ADB/Android） |
| `miniprogram_test_agent` | 保留 | 载体独立（微信开发者工具） |
| `defect_analysis_agent` | 保留 | 有真判断成分（归因分类 + 置信度）；取证包必须由程序组装 |
| `test_report_agent` | 保留 | 定位从"写报告"改为"审报告"（第 16 章） |

**结论：主要矛盾不是 agent 数量，是 agent 的权限。** 11 个 agent 每个都有独立交付物、独立确认点、独立失效条件，砍掉反而损害产品形态。要收的是四样东西：

| 收什么 | 具体做法 |
|---|---|
| 输入来源 | 只能吃上游 IR，不许自由读原始材料自行总结 |
| 输出格式 | 必须过 schema 硬校验，不合格即阻塞 |
| 决策权 | 阶段派发交给状态机，agent 不能决定跳过阶段 |
| 自由空间 | 能形式化的一律下沉为程序资产 |

**关于"三个 agent 都绑 `test-design-methods`"的重叠信号——解法不是合并，是下沉**：把该 skill 中可确定的部分（维度矩阵、checklist 检索、边界值字典）变成程序级资产，agent 只在缺口处判断。这样三个 agent 共享同一份规则，却不会各自解释出不同结果。**职责重叠的根因是"规则散在提示词里被各自解释"，不是"角色划分重复"。**

### 17.4 两块已定义但从未接线的 Skill（M1 最该先接）

| Skill | 定义内容 | 现状 | 接上后的作用 |
|---|---|---|---|
| `test-asset-management` | 可复用规则、数据策略、**定位器**、断言、接口契约、缺陷模式 | **未绑定任何 Agent** | 一切"可复现"的地基（元素库 + 断言库） |
| `test-selection` | 按风险、变更范围、**预算**选测试集 | **未绑定任何 Agent** | 回归集与影响分析的落点 |

> 这两块恰好就是本方案反复强调的"资产库"和"回归集"。说明架构判断没错，**缺口不是没有设计，而是没接线**。

### 17.5 处置路线：主干重建 + 复用零件（C 方案）

| 方案 | 做法 | 风险 |
|---|---|---|
| A. 渐进改造 | 在现有 10 Agent + 15 Skill 上逐个替换 | 旧治理机制的 token 开销一直拖累，容易改不完 |
| B. 新建并行 | 新架构独立开发，跑通后迁移 | 两套并存期维护成本高 |
| **C. 主干重建 + 复用零件（选定）** | 以新架构为主干，把可用零件搬过来 | 需一次性投入，可能两周内没有产出 |

**C 的本质：用"编排 + 工具"替代 Agent 的自主权，不是删减 agent 数量。** 若只加工具不收自主权，agent 依然可以不用、乱用。

**可复用零件**：产物 Schema 思路（升级为 IR）、来源台账/溯源（强化为 `source`/`derived_from`）、证据包与报告证据校验（直接搬）、缺陷生命周期（直接搬）、结构化动作定义（升级为 DSL 动作语义）、工具守卫思路（升级为前置条件校验 + 危险动作白名单）、阶段状态机（作为编排流程定义）、插件/连接器接口（作为 Adapter 扩展点）。

**丢弃**：Agent 自主编排逻辑、自由生成的提示词体系、派发回执/设计冻结/文件哈希（对探索模式是纯开销）、attempt 账本原逻辑。

**工作量结构**（需心里有数）：

| 工作类型 | 占比 | 说明 |
|---|---|---|
| 从现有工程搬运 | 20% | 证据链、缺陷生命周期、schema 设计 |
| **新写（编译层 + 执行引擎）** | 45% | 真正的核心工作量 |
| 重写（Agent 流程改为编排 + 工具） | 25% | 工作量不大，但要重新理解业务意图 |
| 删除/清理 | 10% | **拆除比新建更麻烦** |

> **提醒**：旧的回执、冻结、账本机制可能已被前端或其他模块依赖，直接删会连带出问题。**M1 第一步是盘点依赖，不是开始画新架构。**

### 17.6 M1 改造五步（可当任务表）

1. **接上 `test-asset-management`**（元素库 / 定位器库 / 断言库）；
2. **接上 `test-selection`**（回归集 + 影响分析）；
3. **建立产物血缘与增量重算**（6.2、6.3）：稳定 ID、`derived_from` 自动写入、语义指纹去噪、变更闭包；
4. **`automation_execution_agent` 加"计划驱动模式"**：把 `browser-case-plan.json` 从"文字步骤"升级为**可执行计划**（多指纹 + 类型化等待 + 断言 + `touched`）。**最省力的改造路径——不新增架构，只升级已有产物的表达力**，可从"探索执行"平滑过渡到"半固化执行"；
5. **报告 agent 改造为审阅者**（第 16 章），上线风险台账。

### 17.7 其余处置

| 现有内容 | 处置 | 说明 |
|---|---|---|
| 七阶段编排骨架 | 保留 | 阶段划分合理，阶段间从"传文本"改为"传 IR + 硬校验" |
| 产物 Schema / 来源台账 | 保留并强化 | 校验必须是**程序硬校验**，不许 LLM 自查声明合规 |
| 派发回执 / 阶段状态机 | 保留 | 需评估 token 开销，探索/轻量模式可降级 |
| 执行 attempt 账本 | **改造** | 见 14.6，不参与通过判定 |
| 报告证据校验 / 缺陷生命周期 | 保留 | 基础较好 |
| 结构化动作 / 工具守卫 | 保留并升级 | 升级为多指纹 + 唯一性校验 |
| 提示词体系 | **重构** | 从"让 agent 自主完成阶段"改为"让 LLM 做有限翻译/分类/审阅" |
| 设计冻结 / 文件哈希 | 降级 | 对探索模式是负担，仅对已入库资产启用 |
| 浏览器位置（本机/内置） | 保留 | 与本次架构一致，不迁沙箱 |

## 18. 实施路线图

### 18.1 总原则：每个里程碑都必须有可展示的效果

上次汇报失败的核心不是"功能不够多"，而是**拿不出证据证明有效**。因此路线图要求：**任何里程碑完成时，都能立刻演示一个量化结果**，不允许把验证推到最后一个阶段。

| 阶段 | 交付 | 可展示的效果 |
|---|---|---|
| **M1** | 执行引擎 + 固化链路 + 冒烟集（单类型打通） | **同一用例跑 3 次结果一致**，有取证与报表 |
| **M2** | 探索器 + 四类 Adapter（接口优先） | **从给地址到可测 ≤1 分钟**，生成应用地图 |
| **M3** | 回归集 / 影响分析 / flaky 治理 | 变更 → 选回归集 → 准入结论全流程 |
| **M4** | 编译层扩展到需求→测试点→用例 | 有需求文档时全流程自动化 |
| **M5** | 缺陷闭环 + 报告 + 知识沉淀 | 发现→归因→提单→复测闭环 |

**M1 明确不放探索器**：先把"资产能跑稳"做扎实。这与上次失败的教训直接对应——上次是**探索先行**，这次是**重放先行**。

### 18.2 M1 具体范围（最需要说清的一段）

**做**：
- 单系统、单类型（Web UI 或接口二选一，**建议接口**）；
- 手工写 3~5 条 DSL 计划（验证人工手写这条已定决策）；
- 元素库、登录片段、五道闸的完整实现；
- 执行引擎（worker 进程、五档结论、取证包）与结果 IR；
- **N=3 一致性检测 + 一张简单报表**。

**不做**（明确排除，防范围蔓延）：探索器、LLM 生成计划、App、小程序、回归集、缺陷闭环、报告美化。

**M1 验收标准（可量化，直接用于汇报）**：

1. 5 条用例 × 3 次执行 = 15 次，**结果 100% 一致**；
2. 失败时取证包能定位原因（人工抽检 10 个失败，8 个能从取证包直接判断根因）；
3. 单条用例执行耗时与资源占用被记录；
4. 计划改动能产出**可读 diff**，人能在 10 分钟内改完一条用例。

**这 4 条不达标就不进 M2。**

### 18.3 M2~M5 要点

**M2 探索器验收**：

| 验收项 | 标准 |
|---|---|
| 冷启动到可测 | ≤1 分钟（登录片段固化后）；首次探索 ≤10 分钟 |
| 探索 token | 硬上限可控（默认 ≤20 万，可配） |
| 地图完整性 | 路由覆盖 ≥80%，核心页面 100% |
| 产物可用性 | 元素库中 ≥70% 控件在重放中稳定命中 |
| 危险动作 | 默认只读，提交类需显式开启 |

> **这是把上次翻车的项目"重跑一遍"的最佳时机**：同一环境、同样输入，对比"十几分钟 / 100 万 token"与"1 分钟 / 20 万 token"。**这个对比本身就是最有说服力的汇报材料。**

**M3**：回归集三闸（冒烟/核心/全量）+ 影响分析（`touched` 主路）+ flaky 检测与隔离区上线。

**M4**：需求解析（含 OpenAPI 零 LLM 路径）→ 测试点矩阵 → 用例生成三段编译 + 血缘增量重算。

**M5**：缺陷归因下沉执行末端 + 去重 + 提单集成 + 风险台账 + 知识回流（人工修改回写知识库）。

### 18.4 工期与资源

| 项 | 估算 |
|---|---|
| 核心链路 M1~M3 | **2.5~3.5 个月** |
| 前提 | 3~4 人全职，其中 1 人专职前端/DOM 快照与可视化调试（易被忽略但很耗人） |
| Adapter 顺序 | **接口 → Web → 小程序 → App** |
| App/小程序 | 建议 M2 之后单独立项，尤其 App 涉及设备池，容易拖垮节奏 |

### 18.5 折中执行建议（最现实的一条路）

考虑"既是产品负责人又是开发"的现实，建议：**M1 只做一条纵向切片的 C 模式**（单类型 + 3~5 条手工计划 + 编译五闸 + 执行引擎），**先证明"重放可复现"这件事成立**，同时不碰其他 Agent。

- 切片成功 → 按 C 推进，逐步替换其余环节；
- 切片发现成本远超预期 → 退回 A，把投入集中在最有价值处。

**这样不必现在就决定"要不要推翻重构"，让证据决定。这是唯一不会赌错的路径。**

## 19. 真实有效性基线

### 19.1 为什么必须建（这是"你到底有没有用"的唯一答案）

交接文档把"真实测试有效性基线"标为未建立，这是对的。没有基线，所有优化都是自说自话，也无法回答领导那句"不如用 codex"。

**基线必须有被测对象**，所以要与 M1 同期准备（人工工作，可与开发并行）。

### 19.2 种子缺陷集做法

1. 选一个可控的真实系统（或专门部署的测试版）；
2. **人工植入 20~30 个已知缺陷**，典型分布：逻辑错误、边界未处理、权限缺失、前端校验缺失、数据不一致；
3. 用平台跑，看能发现几个；
4. 计算三个指标。

> 植入缺陷听起来像造假，但它是业界标准做法（变异测试思路），**只需要做一次**，之后用来度量每一次架构改动的效果。

### 19.3 三个指标

| 指标 | 定义 | 目标 |
|---|---|---|
| **召回率** | 发现的植入缺陷数 / 植入总数 | ≥70%（第一版） |
| **误报率** | 报的失败中实际非缺陷的比例 | ≤10% |
| **错误通过率** | 有缺陷但用例判通过的比例 | **≤5%（最不能容忍）** |

**错误通过率必须单独设阈值**：它最隐蔽——客户看到的是"全部通过"，实际漏了 bug，比误报危险得多。

### 19.4 基线的第二个用途

它同时是 **flaky 治理的对照**：同一批用例重复跑，能区分"用例不稳"与"系统偶发缺陷"。没有基线，这两者永远分不清。

## 20. 成效度量与汇报口径

### 20.1 核心叙事（回答"为什么不直接用 codex"）

> **我们把测试工程做成了可积累、可复现的资产体系，这是通用 agent 永远不具备的。**

三个支撑点：

1. **可复现**：同一计划跑 N 次结果一致（通用 agent 做不到，因为它每次重新探索）；
2. **资产积累**：登录配置、selector 库、执行计划、归因规则逐轮增长（通用 agent 每次归零）；
3. **可归因**：失败时给你取证包 + 与上次成功的 diff + 五档结论（通用 agent 给你一段解释）。

### 20.2 指标排序（不要以 token 为首）

| 优先级 | 指标 | 说明 |
|---|---|---|
| 1 | **同用例 N=3 一致性** | 可复现性，底线 |
| 2 | 首次执行通过率（不含重试） | 真实健康度 |
| 3 | 需求→用例覆盖率、影响覆盖度 | 测得全不全 |
| 4 | 缺陷召回率 / 误报率 / 错误通过率 | 有效性 |
| 5 | flaky 率、隔离区存量 | 资产健康度 |
| 6 | token 消耗与耗时 | **结构化的自然结果，不是目标本身** |
| 7 | 资产积累量（配置/selector/知识库条目逐轮增长） | 护城河证据 |

> 把 token 放第一位是错的：如果只追求便宜，结论会变成"能不用 LLM 就不用"，最后做出一个传统自动化框架加一点 AI 点缀，方向就歪了。

### 20.3 演示策略（三次演示三个主张）

| 场景 | 演示什么 | 主张 |
|---|---|---|
| 第一次（冷启动） | 给 URL + 账号 → 1 分钟内进可测状态 → 生成应用地图 | "进得去、看得见" |
| 第二次（可复现） | 同一用例连跑 3 次 → 结果一致 + 取证包 + diff | "测得稳、可归因" |
| 第三次（有效性） | 种子缺陷集 → 召回 70%+ / 错误通过 ≤5% | "测得准、能量化" |

**永不演示**：无预算的开放式探索（那是上次翻车的场景）。

### 20.4 必须提前对齐的一个认知

验证码插件这类能力做完后，产品的护城河就从"agent 有多聪明"转移到"**执行底座有多稳、配置生态有多全**"。这更接近商用真实需求——**客户买的是"能稳定跑起来"，不是"会像人一样探索"**。

## 22. 风险登记与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **强验证码无法自动化** | 登录卡死，演示失败 | 策略链 + 测试万能码/后门 + 打码平台 + **人工接管兜底**；向研发要测试环境后门是首选 |
| **内网环境不可达** | 云端沙箱访问不到客户环境 | 本机执行架构本身就解决（浏览器在本机跑） |
| **UI 频繁改版导致资产失效** | 脚本腐烂，团队弃用 | 多指纹 + 元素库集中管理 + 局部重探索 + diff 人审 |
| **共享片段一改全崩** | 无人敢动共享层 | 片段契约化 + 版本号 + 引用影响分析 + 按批升级 |
| **混合 driver 被滥用** | 用例难查清 | 四条约束强制 |
| **App 设备池拖垮进度** | M2 延期 | 初期只做单设备串行，池化延后 |
| **LLM 换代导致行为漂移** | 约束失效 | 约束写成代码校验器（不写提示词）；语义断言标注"由模型判定"以便审计 |
| **报告 agent 硬凑风险** | 报告失真 | 允许空输出 + 引用强制 + 空输出率统计 |
| **拆旧机制引发连带故障** | 新老都不稳 | M1 第一步盘点依赖；旧机制先"降级"不直接删 |
| **只修登录不等效于产品可用** | 下次汇报仍被否 | 两条腿走路：短期进得去，中期有效性基线 |
| **团队绕过冒烟集** | 质量门失效 | 冒烟集必须 ≤5 分钟且 flaky 率 0 |
| **token 至上导致方向跑偏** | 做成传统框架 + AI 点缀 | 指标排序以可复现性为首，token 为副产品 |

## 24. 能力分发与版本管理（2026-11-13 新增）

> 背景：agent、skill、插件等能力由管理员在服务端后台维护，用户安装客户端后获取能力进行本地测试。本章回答：**各阶段建设的工具，随安装包内置，还是服务端下发？**

### 24.1 结论：三档分发策略

原则一句话：**会变的"策略"放服务端，会坏的"执行代码"放本地，两者靠契约版本对齐。**

两种极端方案都不可取：全部服务端下发 → 本机执行工具与本地环境（浏览器内核、HTTP 栈）强耦合，远程推一个跑不起来的版本直接瘫痪客户端，且断网/服务端故障时测试全停；全部内置安装包 → 每修一个 bug 都要发版，且 IR 契约升级后老客户端校验不过新产物，版本碎片化。

| 档位 | 内容 | 特征 |
|---|---|---|
| **① 内置安装包** | 校验器 `irval`、Driver Adapter（web/api/native/mini）、DSL 解释器/固化编译器、五闸执行检查、探索器本体（环境建档解析器等零 LLM 工具） | 确定性基础设施，与客户端环境深度集成，必须与资产契约**版本强一致**；随大版本升级（M1→M2 节奏），不追周更 |
| **② 服务端下发** | 分权表（PERM_ownership）、可放宽配置（V-16 步骤预算、口令白名单）、matcher 白名单、flaky 隔离区规则、回归准入三闸阈值、回归选集策略、报告审阅者提示词/汇报口径；沉淀资产：fragments 片段库、种子用例模板、种子缺陷集 | 管理员后台改完即生效，客户端下次会话拉取；不发包。下发内容必须带 `version`，服务端可强制刷新 |
| **③ 下载分发 + 签名校验 + 本地缓存** | Playwright 集成包、小程序调试桥、App 驱动依赖（appium/uiautomator 类）、OCR/验证码处理插件 | 体积大、平台相关（Win/mac 分包）、第三方组件自带版本节奏；安装包只带"加载器"，按需拉取落本地缓存；下发须带签名 + 与底座的兼容性声明 |

| 报告审阅者提示词、汇报口径 | ② 服务端下发（产品负责人高频调整项） |
| Hifox 式验收标准（连续 N 轮全绿） | ② 服务端下发 |

### 24.3 客户端版本协商机制（必须实现）

存在"内置 + 下发"两种来源，必须有一致性保障：

1. 客户端在**启动或测试会话开始时**上报底座版本号（schema_version / engine_version / adapter_versions）。
2. 服务端返回**与该底座版本兼容的策略版本**——M1 底座的客户端不得收到 M2 才定义的五闸规则。
3. 版本兼容性用**契约版本区间**声明（如策略声明 `compatible_engine: ">=1.0,<2.0"`），不匹配时策略不下发并提示升级。
4. **失效兜底**：下发策略拉取失败时，客户端使用随安装包内置的最近一次快照继续工作（离线可测），并在报告中标注"策略非最新"。

> 反面事故这条机制要防住：老客户端 + 新策略 = 全部产物校验失败。

### 24.4 对路线图的影响

- **M1**：校验器随安装包（①档），规则元数据先用内置默认值，服务端下发通道 M2 接入。
- **M2**：上线策略下发通道 + 版本协商（本协议是 M2 的交付物之一）；App/小程序依赖走 ③ 档。
- **M3 起**：fragments 库、隔离区规则、回归阈值全部迁到 ② 档，实现"管理员改阈值不发版"。

## 附录 B：术语表

| 术语 | 含义 |
|---|---|
| **IR** | 中间表示，各阶段的结构化产物（需求项/测试点/用例/计划/结果/缺陷） |
| **五道闸** | 固化编译的五项硬校验：定位唯一、断言可判定、数据不硬编码、溯源、固化后重放 |
| **N=3 一致性** | 同一计划同环境同数据连跑 3 次结果必须相同，否则不许入库 |
| **`touched`** | 用例实际触及的页面与接口清单，编译时自动提取、重放时自动刷新 |
| **`inconclusive`** | 无法判定（环境不可达/前置不满足/会话失败），既非通过也非失败 |
| **隔离区 quarantine** | 无法修复的 flaky 用例的存放处，不进入任何回归集 |
| **片段 fragment** | 被多条用例引用的流程单元（如登录），契约化 + 版本化 |
| **风险台账** | 每轮报告洞察沉淀成的风险清单，带状态机跟踪 |
| **语义指纹** | 去噪规范化后的文本 hash，用于区分"语义变更"与"表述变更" |
| **能力分发** | 平台能力（agent/skill/插件/工具）到达客户端的方式；本方案定为内置 / 服务端下发 / 下载分发三档，见第 24 章 |
| **版本协商** | 客户端上报底座版本、服务端返回兼容策略版本的握手机制，防止"老客户端 + 新策略"事故 |
