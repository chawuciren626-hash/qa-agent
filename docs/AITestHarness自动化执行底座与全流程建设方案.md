# AITestHarness 自动化执行底座与全流程工具体系建设方案

> 背景：当前模式依赖 LLM 通用探索能力执行测试，导致冷启动慢（十几分钟）、token 消耗失控（百万级）、演示效果差。本方案核心思想：**每一步先问"这个环节能否沉淀为可复用的工程资产"——凡是能结构化的，必须结构化并入库复用；LLM 只保留在真正的开放决策点**，并以知识沉淀驱动全流程越用越准。
>
> 立身之本：如果全流程都靠 LLM 自由发挥，本工程与"拿通用 agent 跑一遍测试"没有任何区别。通用 agent 每次从零摸索、消耗 token 且行为不可复现；AITestHarness 的价值是沉淀下来的工程资产体系（登录器、验证码策略链、执行计划编译器、知识库），每跑一轮都在积累、复用、变强——**前者是消耗品，后者是资产积累**。测试系统自身必须先可信（行为可复现、可归因），其测试结果才有价值，这是稳定性层面的硬要求，而非成本优化。

## 一、总体架构

```
┌─────────────────────────────────────────────────────────┐
│                      用户端 / 管理端                       │
│   （可见浏览器执行视图 · 实时日志 · 人工接管面板 · 报告）      │
├─────────────────────────────────────────────────────────┤
│                    编排层（Orchestrator）                  │
│  需求分析 → 测试点 → 用例生成 → 执行 → 缺陷分析 → 报告        │
├─────────────────────────────────────────────────────────┤
│                     执行层（本次重点）                      │
│  执行计划编译器 · 登录器 · 验证码处理器 · 环境检查 ·           │
│  登录态管理 · 浏览器双通道 · 操作工具集 · 断言 · 自愈 ·        │
│  人工接管通道 · 执行遥测                                    │
├─────────────────────────────────────────────────────────┤
│  知识库层：测试点知识库 · 历史用例库 · 缺陷库 · 元素库(自愈)   │
│  基础设施：Playwright 服务集群 · 客户端 CDP 探针 · 打码平台   │
└─────────────────────────────────────────────────────────┘
```

核心原则：

1. **资产化优先**：每一步先问"能否沉淀为可复用的工程资产"，凡能结构化的必须结构化并入库复用；LLM 只保留在真正的开放决策点。
2. **可复现优先**：任何执行路径必须可复现，凡依赖 LLM 的步骤必须可回放、可审计——测试系统自身先可信，测试结果才有价值。
3. **LLM 边界明确**：LLM 出现在哪、不出现在哪，由架构定义白纸黑字约定，而非运行时随缘。LLM 是结构化工程的"大脑"（决定走哪条路、面对未知怎么办、判断结果对不对），结构化组件是"四肢"（可靠执行已知路径），而非让大脑亲自控制每一根手指。
4. **结构化输入输出**：agent 之间不传原始截图/长文本，传结构化摘要。
5. **全链路可观测**：每个阶段记录 token、耗时、成功率，为持续优化和向管理层汇报提供数据。
6. **人机协作兜底**：每阶段都有"拿不准就暂停问人"的通道，卡住≠死掉。

## 二、逐阶段建设方案

### 阶段 1：需求分析

**职责**：把 PRD/原型/接口文档转化为结构化需求项，识别可测性问题与澄清点。

**工具建设**：

| 工具     | 职责          | 实现要点                                                          |
| ------ | ----------- | ------------------------------------------------------------- |
| 需求解析器  | 多源文档→结构化需求项 | 支持 docx/pdf/figma 导出图/OpenAPI；输出 schema：功能点、前置条件、边界、异常分支、隐含约束 |
| 需求澄清器  | 自动生成澄清问题清单  | 规则检测（缺失字段、矛盾条款）+ LLM 生成问题，问题清单交需求方确认，禁止 agent 自行脑补            |
| 需求基线管理 | 需求项版本化      | 需求项全局 ID，变更时 diff，下游测试点/用例标记"受影响待重算"                          |

**验收指标**：需求项抽取准确率（人工抽检）；澄清问题被采纳率 > 60%。

### 阶段 2：测试点分析

**职责**：需求项拆解为全维度测试点。

| 工具     | 职责                  | 实现要点                                                              |
| ------ | ------------------- | ----------------------------------------------------------------- |
| 测试点知识库 | 通用测试维度 checklist 注入 | 按"控件类型×测试维度"组织（如：上传控件→超限/格式/并发/断网/重复提交）；结构化条目 + RAG 检索注入，不靠模型回忆常识 |
| 历史参考器  | 检索相似历史测试点           | 向量检索历史项目，prompt 里"对照改"而非"从零想"                                     |
| 覆盖率校验器 | 需求项×测试点映射矩阵         | 规则实现，零 token；输出缺口清单（无测试点覆盖的需求项）供 LLM 补齐                           |

**验收指标**：需求项覆盖率 100%；知识库条目数逐月增长。

### 阶段 3：测试用例生成

**职责**：测试点→可执行结构化用例。

| 工具     | 职责              | 实现要点                                                        |
| ------ | --------------- | ----------------------------------------------------------- |
| 用例模板库  | 按测试类型定用例 schema | Web 步骤/接口断言/App 操作分别定义 JSON Schema，生成即结构化                   |
| 测试数据工厂 | 自动生成边界数据        | 内置数据字典：maxint、超长串、emoji、XSS/SQLi 串、合法/非法文件；按标注规则生成，不花 token |
| 用例评审器  | 生成后自动规则校验       | 校验：步骤可执行性（每步有明确操作对象）、断言明确性、依赖完整性；不合格自动回流重写，人只审最终版           |
| 用例沉淀回流 | 人工修改回写知识库       | 人工编辑 diff 自动学习，优先级/写法偏好入库                                   |

**验收指标**：用例评审一次通过率；人工修改率（越低越好，跟踪下降趋势）。

### 阶段 4：测试执行（核心投入区）

#### 4.1 执行计划编译器（执行稳定性与资产化的最大杠杆）

- 把用例编译为执行计划，每一步标注类型：
  - **确定性步骤**：登录、固定导航、表单填写、API 调用 → 结构化组件执行，路径可复现、可审计、可复用
  - **决策步骤**：页面语义判断、异常分支探索、结果语义确认 → LLM 执行，且必须记录决策依据供回放
- 划分规则：凡"操作对象+操作+预期"三者明确的步骤一律结构化；只有"需要看页面理解再决定"的才交给 LLM（LLM 边界由架构显式定义，而非运行时随缘）。
- 目标：执行路径高度可复现，LLM 调用量占执行全过程的 10~20%（token 下降 80%+ 是结构化的自然结果，而非目标本身）。

#### 4.2 环境与登录准备（演示翻车根源）

| 工具      | 职责       | 实现要点                                                                           |
| ------- | -------- | ------------------------------------------------------------------------------ |
| 环境健康检查器 | 执行前探测    | 首页可达、依赖服务状态、超时/失败直接终止并出报告，不给 agent 摸索机会                                        |
| 登录器插件   | 配置化登录    | 策略链：API 登录 → 表单自动填充 → token/cookie 注入 → SSO；每环境一配置（地址+账号+策略），项目级预置             |
| 验证码处理器  | 策略链解决验证码 | ① 测试万能码/后门（推动研发配合，优先）② 滑块/点选→打码平台 API ③ 简单图形码→OCR ④ 全部失败→挂起转人工接管；每策略记录成功率，自动优选 |
| 登录态管理器  | 复用登录态    | 按"环境+账号"持久化 cookie/token/localStorage，过期检测，未过期直接注入                             |

#### 4.3 浏览器双通道

| 通道       | 技术                               | 用途                    |
| -------- | -------------------------------- | --------------------- |
| 客户端托管浏览器 | CDP 驱动用户本机 Chromium，操作高亮+实时日志+录屏 | 用户端交互执行、探索性测试、演示、人工接管 |
| 服务端无头集群  | Playwright 服务化，可并发、可录像           | 批量回归、定时任务、管理端执行       |

> 演示场景强制使用可见浏览器通道：领导能看到每一步在做什么，观感问题直接解决。

#### 4.4 页面操作工具集

| 工具         | 要点                                                                      |
| ---------- | ----------------------------------------------------------------------- |
| 结构化 DOM 视图 | 返回简化 DOM（可交互元素+语义 selector+文本），替代截图 OCR，token 降一个数量级                    |
| 操作原语       | click/fill/select/hover/scroll/upload，基于语义 selector，操作后自动返回新页面状态（省一轮确认） |
| 智能等待       | 网络空闲+元素就绪，杜绝假失败                                                         |
| 定位自愈       | selector 失效按 text→role→视觉 降级，成功后新 selector 回写元素库                        |
| 数据/文件准备    | 预生成上传文件、数据库造数工具                                                         |

#### 4.5 断言与取证

- 结构断言（URL/DOM/接口返回码）→ 规则，0 token；语义断言 → LLM 但输入为结构化摘要。
- 失败自动取证包：截图+DOM 快照+接口日志+操作轨迹，agent 不自行取证。
- 截图基线 diff：视觉回归自动化。

#### 4.6 可靠性机制

- **失败自愈器**：定位失败→换策略；流程失败→按策略重试；超限→人工接管。
- **人工接管通道**：卡住时暂停、推送通知（客户端/Web），用户操作后（如手动过验证码）agent 续跑。
- **执行遥测**：逐步记录耗时/token/结果，支撑报告与优化闭环。

### 阶段 5：缺陷分析

| 工具     | 职责                       | 要点                               |
| ------ | ------------------------ | -------------------------------- |
| 失败归因器  | 分类：产品 bug/脚本问题/环境问题/数据问题 | 输入取证包做结构化分析，LLM 分类+置信度，低置信度转人工   |
| 缺陷去重器  | 向量比对缺陷库                  | 避免重复提单，历史缺陷链接展示                  |
| 缺陷单生成器 | 自动生成并提交                  | 复现步骤+环境+证据附件，对接 Jira/禅道/内置 issue |
| 归因知识回流 | 归因结果入库                   | 同类失败模式入库，下次直接命中规则                |

### 阶段 6：测试报告

| 工具     | 要点                                               |
| ------ | ------------------------------------------------ |
| 报告模板引擎 | 固定结构（结果统计、覆盖率、缺陷分布）由模板渲染，0 token；质量风险分析由 LLM 写一段 |
| 趋势看板   | 多轮回归趋势对比，管理端展示；含 token 成本趋势（向管理层证明优化成效）          |

## 三、横向机制

1. **知识库体系**：测试点 checklist、历史用例、缺陷模式、元素 selector 库四库统一管理，每轮测试沉淀回流，形成数据飞轮。
2. **人工接管/确认通道**：全流程统一交互组件（需求澄清、用例确认、验证码、归因存疑）。
3. **模型分级策略**：页面定位/结构化抽取用低成本模型；语义判断/生成用主力模型；全程可配置预算上限，超限告警。

## 四、实施路线图

| 阶段      | 周期      | 交付物                                | 对应解决的痛点                |
| ------- | ------- | ---------------------------------- | ---------------------- |
| M1 执行底座 | 2~3 周   | 登录器+验证码处理器+环境检查+登录态复用+执行计划编译器（最小版） | 冷启动十几分钟→1 分钟内；token 爆炸 |
| M2 演示体验 | 与 M1 并行 | 客户端可见浏览器通道+操作高亮+录屏+人工接管面板          | 演示观感                   |
| M3 执行增强 | +2 周    | 结构化 DOM 工具集、断言体系、自愈器、执行遥测          | 稳定性、成本可量化              |
| M4 分析层  | +2~3 周  | 测试点知识库、覆盖率校验、测试数据工厂、用例评审器          | 覆盖率与用例质量               |
| M5 闭环层  | +2 周    | 失败归因、去重、缺陷单生成、知识回流、报告引擎            | 全流程闭环与差异化              |

## 五、成效度量（对管理层汇报口径）

**核心叙事**：我们把测试工程做成了可积累、可复现的资产体系——这是通用 agent 永远不具备的，是"为什么不直接用 codex"的完整答案。

- 执行可复现性：执行路径可回放、可审计，失败可归因（先归因到系统，再谈产品缺陷）
- 冷启动时间：十几分钟 → ≤1 分钟（登录态复用后秒级）
- 用例执行成功率（含自愈）：目标 > 90%
- 人工介入率：跟踪下降趋势
- 需求→用例覆盖率：100%（含覆盖率校验器保证）
- token 消耗：百万级 → 下降 80%+（结构化的自然结果，作为副产品呈现）
- 资产积累：登录配置、selector 库、执行计划、知识库条目数逐轮增长

## 六、关键风险与对策

| 风险             | 对策                           |
| -------------- | ---------------------------- |
| 验证码形式复杂（强人机校验） | 推动研发提供测试后门/万能码，作为流程规范输出给被测团队 |
| 内网环境服务端浏览器不可达  | 客户端探针方案（本地驱动）兜底              |
| 确定性/决策步骤划分不准   | 遥测数据持续调优，规则库可配置              |
| 知识库初期内容少       | 先手工灌注通用 checklist 起步，随使用增长   |
