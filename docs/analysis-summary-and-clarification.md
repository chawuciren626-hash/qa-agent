## 台账摘要

结构化只读动作：

```json
{"action":"analysis_summary","run_id":"run-example"}
```

使用已有project-action execute入口及请求文件调用。读取当前run的台账、来源快照和生成Markdown，沿用来源引用校验，并核验正文与台账一致。返回groups（requirements、assumptions、observations）、每组数量、unresolved_ids、out_of_scope_ids、来源和文件哈希；条目的statement/status/scope保持原值，不额外推导主题或批准。

每个文件在一次调用内只读取一次，供验证和哈希共同使用；这是文件快照，不宣称跨文件事务或语义充分性。动作不改清单、不写业务产物、不批准阶段、不占用变更令牌。错误使用独立只读纠错预算，不消耗变更输入预算；照常保留动作审计。缺台账、伪造引文或正文不一致时不返回猜测摘要，交专业角色按既有修订流程处理。

总控展示业务总结时只引用实际存在的条目及其状态。“未排除”不能改写成“已全部登记”；空列表只表示没有记录，并不证明没有问题。requirements数量包含不同状态，不能直接称全部已确认；confirmed规则也不是阶段审批。流程状态另读run_status。observations默认称观察/材料局限，不能仅因kind为observation就声称检查过实现。

摘要是只读辅助，不新增完成必需产物或审批节点。它不能阻止模型口头偏离，所以最终回复一致性仍需真实复验，不能把结构化接口通过当作自由文本生成已受强制约束。

## 澄清排序

不固定问题数量，不使用业务关键词硬编码优先级。专业角色先检查原文已经要求的行为，识别不同解释是否会改变测试预期：输入分类与单位、边界、状态转移、成功和失败结果。优先列这类问题，其次是影响授权或数据安全的执行条件，最后才是表现细节或额外建议。紧急安全风险可优先提出，不为了排序压低风险。

复用现有reason字段，说明关联规则ID、不同解释如何改变预期及优先级理由。不存在的业务行为不为凑题添加；原文已明确的不重复询问。不自创priority等台账字段，不默认替用户确认答案。原型、接口文档、历史缺陷不是分析文字需求的通用必交材料。

本轮没有自动语义排序器或完整性评分：排序由专业Agent判断，用户在原有业务确认节点裁决。通过提示和Skill改善问题选择，不以新增技术关卡代替判断。
